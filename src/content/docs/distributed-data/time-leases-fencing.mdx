## The failure: two servers number one chat

In the [chat case study](../../case-studies/chat/), the server gives each message in a conversation the next sequence
number, and phones sort by it. Exactly one server may hand out numbers for a conversation, or two messages share a
number. A common way to pick that server is a **lease**: a lock that expires on its own. Server A asks a lock service
such as etcd or ZooKeeper for the conversation, gets it for 10 seconds, and renews every 3 seconds. If A dies, the
lease runs out and server B takes over.

A checks its lease before every write, so this looks safe. Here is the story that breaks it.

The [payment recovery story](../../reliability/idempotency/) had the same failure: a paused server woke and saved its
receipt after recovery took over. A lease tells you when to start recovery. It cannot stop an old owner that does not
know it is old.

## Clocks you cannot trust

A lease is a promise about time, so it is only as good as the clocks involved. Machine clocks disagree in three ways:

- **Drift.** A quartz clock runs a little fast or slow. At 200 parts per million, that is 17 seconds a day.
- **Steps.** NTP corrects drift and can jump the clock forward or back. A timeout measured as the difference of two
  wall clock readings can come out negative.
- **Skew.** Even with NTP, two servers often differ by a millisecond or more, and far more when one loses its time
  source.

Two rules follow. Measure durations with a **monotonic clock** (`CLOCK_MONOTONIC`, `System.nanoTime()`,
`performance.now()`), which never jumps. And count the lease from when the holder **sent** the renewal request, since
the grant happened later, so the holder errs toward stopping early. When you only need the order of events, logical
clocks skip physical time altogether.

<details>
<summary>Go deeper: logical clocks</summary>

A **Lamport clock** is a counter: each server bumps it on every event, stamps it on every message, and on receipt sets
its own counter past the one it received. If one event caused another, the cause gets the smaller number. **Vector
clocks**, one counter per server, also detect writes that happened concurrently, which is how the
[quorum cart](../quorums/) kept both versions of a conflicting cart. Hybrid logical clocks in CockroachDB pair wall time
with a counter, and Google Spanner's TrueTime returns an interval of a few milliseconds and waits it out before a commit
becomes visible. None of these make a paused server notice that it paused.

</details>

## The idea: a lease plus a token the storage checks

The fix moves the final decision to the one place every write passes through: storage. Each time the lock service
grants the lease, it also hands out a **fencing token**, a number that grows with every grant. The writer sends its
token with every write. Storage remembers the highest token it has seen and refuses any write with a lower one.

<Analogy>

A hotel issues a key card to each guest. When a new guest checks into the room, the front desk encodes a newer card,
and the door lock remembers the newest card it has seen. The previous guest's card stops working at the first swipe of
the new one, no matter what time the old guest thinks it is. The lock decides, at the door.

</Analogy>

For the chat, the conversation row holds the owner's token, and each append locks and checks it:

```sql
UPDATE conversations SET owner_token = $2 WHERE id = $1 AND owner_token < $2;

INSERT INTO messages (conversation_id, seq, body, token)
SELECT $1, $3, $4, $2 FROM conversations WHERE id = $1 AND owner_token = $2 FOR SHARE;
```

The first statement runs once at takeover and registers the new token. The second runs on every append and inserts
nothing when the token is stale. `FOR SHARE` makes the takeover wait for appends already in flight. ZooKeeper's
transaction id and etcd's revision both grow with every change, so either can serve as the token. Raft does the same
with its [term numbers](../raft/): every follower refuses a leader with an old term.

What to look for:

- **Long pause.** A wakes at 17.5 s with a stale seq 3. The left log stores it next to B's seq 3. The right log
  rejects it, and A steps down.
- **Slow clock.** A's clock runs at 60% speed and A loses the lock service at 4 s. B takes over at 13.5 s, but A's slow
  timer still shows time left, so A keeps writing until 21 s. The left log accepts seq 8, 9, and 10 from A, each a
  duplicate of B's. The right log rejects the first one and A stops.
- **Slow network.** Watch the counter of stale writes.
- **No faults.** Both lanes hold 15 messages. Fencing costs one comparison per write.

## Safety margins and what they cannot fix

Teams often add a margin: the holder treats a 10 second lease as 8 seconds. A margin covers slow clocks, because drift
has a known bound. Pauses and slow networks have no bound, so a 12.5 second pause beats an 8 second margin just as it
beats a 10 second one.

Lease length then trades two failures. A long lease means a long outage when the owner crashes: nobody numbers the
conversation until it runs out. A short lease means a takeover after every hiccup longer than the lease, which moves the
conversation and makes phones reconnect. Fencing lets you pick the length for failover speed alone, because correctness
no longer depends on it.

<details>
<summary>Go deeper: typical lease settings</summary>

Values from 5 to 30 seconds are common, with renewals every third of the lease so that one lost renewal does not cost
it. Holders that run garbage collected languages often pick the upper end, because a collector pause of a few seconds
is routine under memory pressure. Lock services usually also expose a session timeout separate from each lease. Keep
the two consistent, or a session can expire while the lease still looks valid.

</details>

## Trade-offs

<TradeoffTable title="Ways to keep one owner">

| Choice                          | What it buys                                    | What it costs                                         |
| ------------------------------- | ----------------------------------------------- | ----------------------------------------------------- |
| Lease alone                     | Automatic failover, simple to add               | A paused or slow owner can still write                |
| Lease plus fencing token        | Stale writes refused by storage                 | Storage must store and check the token on every write |
| Longer lease                    | Fewer false takeovers                           | Longer outage when the owner crashes                  |
| Shorter lease                   | Faster failover                                 | More takeovers and renewal traffic                    |
| Safety margin on the holder     | Covers drift and skew                           | Shorter usable lease, no help against pauses          |
| Consensus log for every write   | One agreed order with no separate lock          | A majority round trip on every write                  |

</TradeoffTable>

## Common mistakes

- Treating "I checked my lease" as "my write is safe". The write can land any time after the check.
- Measuring timeouts with the wall clock, which NTP can move in either direction.
- Fencing with a number the writer makes up, such as its own timestamp. The token must come from the grant.
- Relying on a unique key on sequence numbers alone. It rejects whichever copy arrives second, which can be the new
  owner's message.
- Guarding a data change with a lock that has no token, such as a Redis lock with a timeout. Such locks suit only work
  where a rare double run wastes time and nothing else.

<KeyTakeaways>

- A lease decides when someone else may take over. It cannot stop the old owner, who may not know it paused.
- Clocks drift, jump, and disagree. Use monotonic clocks for durations, and logical clocks when you only need order.
- A fencing token grows with every grant, and storage refuses writes with an older token.
- Pick the lease length for failover speed. Fencing keeps it safe whatever the length.

</KeyTakeaways>

<div slot="answer">

- **One token per shard.** Use the etcd revision of the lease key. Store it in a shard row, and have each append lock
  and check that row, as in the SQL above.
- **Register first, then read.** The new owner writes its token to the shard row, which waits for appends in flight,
  then reads the highest sequence number per conversation. Reading first lets the old owner append after the read.
- **A short stall, then a retry.** Sends to server 12 time out. Each phone retries with the same client message id and
  reaches the new owner. When server 12 wakes, its leftover appends fail the token check, and it drops the shard.

</div>
