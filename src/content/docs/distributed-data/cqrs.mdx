## The failure: one table for every job

The shop keeps carts in one table, updated in place, which checkout writes, the cart page reads, and a dashboard
scans. A sale exposes three problems:

- **Reads and writes fight.** Dashboard scans slow checkout, and every index added for them slows every write.
- **One shape suits nobody.** Each screen rebuilds its own shape with joins and sums.
- **The history is gone.** Marketing asks which items shoppers remove, but removing an item deleted its row.

Splitting off the reads fixes the first two, and keeping every change as an event fixes the third. The cost: reads
run behind writes.

## The idea: write events, read projections

- The **write model** checks each **command** (AddItem, RemoveItem, Checkout) against the cart's state, then rejects it
  or appends past-tense **events** (ItemAdded, ItemRemoved, CheckedOut) to an **append-only event log**.
- **Projections**, or read models, follow the log. Each keeps its own position, applies events in order, and stores a
  table shaped for one screen. How far it trails the end of the log is its **lag**.

Separating the write model from the read models is **CQRS** (command query responsibility segregation). Keeping the
events as the source of truth, with a cart's state a fold of its events, is **event sourcing**. Each works alone: CQRS
can feed read models through an outbox, as in [Event-driven design](../../async/event-driven-design/), and event
sourcing can fold a cart's events on every read.

<Analogy>

Clerks only add lines to a shop's ledger, and whiteboards summarize it. A runner copies new lines onto each board, so
a board can trail by a few lines. A wrong board gets wiped and recounted from page one. The invoice clerk keeps a
bookmark, so the recount never sends an invoice twice.

Where it breaks: a real runner copies thousands of lines per second, and the ledger's format changes over years.

</Analogy>

## Read your own writes

The shopper who just added a mug expects to see it, while everyone else can live with a slightly old view. Let the
writer wait:

1. The write model returns the position of the event it appended, say event 42.
2. The client sends that position with its next read.
3. The read waits until the projection reaches event 42, capped at about a second, then falls back to the change in
   the client's memory.

In the toy run, this turns 19 stale loads into 0 for 24 ms of wait per load on average and 200 ms at worst. It mirrors
sending a user's reads to the primary in [Read replicas](../../scaling/read-replicas/), and
[Consistency models](../consistency-models/) calls it read-your-writes consistency.

<details>
<summary>Go deeper: when one projection falls behind</summary>

The projection that does the most work per event, or writes to the slowest store, falls behind first, and a burst of
commands exposes it. In the flash sale, the log grows faster than top items applies events, so its lag climbs until the
sale ends. Checkout never notices.

- **Measure lag two ways.** Events behind shows how much work is queued, and time behind shows how old the answers
  are. Alert on age, because age is what people feel.
- **Give each projection its own worker,** so a slow dashboard never delays the cart page.
- **Split a busy projection by cart id,** so several workers each apply one slice of the log. Events for one cart must
  stay in order, which is the same partitioning question as [Sharding](../../scaling/sharding/).

</details>

## Replay without repeating side effects

Replay turns a projection bug into a redeploy:

1. Deploy v2 next to v1, writing a new table from position 0.
2. Let v2 catch up while v1 keeps serving reads.
3. Switch reads to v2 once its lag is near zero, then drop v1's table.

The same move builds new views from old events, such as marketing's report on removed items. Readers that act on the
world stay out of it: the email sender keeps its own position, so receipts stay at 14. Key each side effect anyway,
say by event position, so a retry cannot mail twice, as in [Idempotency](../../reliability/idempotency/).

<details>
<summary>Go deeper: long replays, events that live forever, and snapshots</summary>

**Long replays.** A log of several years can take hours to replay even at thousands of events per second. Teams split
the replay across partitions, or start a projection from a saved copy of its table at a known position when the bug
arrived after that copy.

**Events live forever.** Every future version of every projection must read every old event. Rename a field, and
years of old events still carry the old name. Teams add fields with defaults and keep every old field, put a version
number on each event type, and write **upcasters**, small functions that turn an old event shape into the current one
as it is read. Fix a wrong event with a new correcting event, because the log stays append only. Plan for deletion laws
up front: keep personal data outside the log, or encrypt it with a key per shopper and delete the key when asked.

**Snapshots.** The write model folds a cart's events before each command. A cart has a handful, so that costs little.
A bank account with ten years of transactions has thousands. A **snapshot** stores the folded state at a known
position, so the write model loads the latest one and folds only the events after it. Snapshots work like a cache:
delete one and you can rebuild it from the log.

**More projections.** Each new question becomes a new projection that replays the history on its first day, with no
change to the write side. Each one is another reader to deploy, monitor, and rebuild.

</details>

## Trade-offs

<TradeoffTable title="CQRS and event sourcing choices">

| Choice                           | What it buys                                                       | What it costs                                                     |
| -------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------- |
| Separate read models             | A table shaped for each screen, and reads that stop slowing writes | Reads trail the writes, and more stores to run and watch          |
| Event log as the source of truth | Full history, new views from old events, and bug fixes by replay   | Event schemas live forever, replays take time, deletion is harder |
| Wait for my event                | The writer always sees their own change                            | Slower reads right after a write, and a timeout for stuck readers |

</TradeoffTable>

Skip both when one database, a cache, and a read replica keep up. Reach for CQRS when reads and writes want different shapes or scale, and for event sourcing
when the history has value: audits, money, or questions nobody has asked yet.

## Common mistakes

- **Checking commands against a projection.** It trails, so two buyers can both see the last seat free. Check in the
  write model.
- **Replaying through side effects.** Resetting the email sender mails every receipt again. Rebuild one table, and key
  every side effect.
- **Editing old events.** The log stays append only. Record a correcting event or fix the projection.
- **Alerting on lag in events alone.** People feel age, so alert on how old the answers are.

<KeyTakeaways>

- The write model checks commands and appends events. Projections follow the log at their own pace.
- Projections trail the writes. Return the event's position so the writer can wait for it.
- Fix a broken view by replaying the log into a new table, and keep side effects on their own positions.
- CQRS and event sourcing each work alone. Adopt each only when its cost buys something.

</KeyTakeaways>

billion events and grows by 2,000 per second at peak. One worker applies 50,000 events per second, and a bug forces a

<div slot="answer">

- One worker: 5,000,000,000 ÷ 50,000 = 100,000 s, about **28 hours**, and closer to 29 since it gains only 48,000 per
  second on new events.
- 20 partitions: about 250 million events each in 5,000 s, about **83 minutes**, against about 100 new events per
  second per partition.
- The badge: the projection has not applied ConversationRead yet. Have the inbox wait for that event's position, with
  a cap, or clear the badge in the client.
- Leave alone: push notifications and emails, which keep their own positions and idempotency keys.

</div>
