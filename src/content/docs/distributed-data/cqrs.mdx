## The failure: one table for every job

The shop keeps carts in one table, one row per cart line, updated in place. Checkout writes to it, the cart page reads
it, and so does a new "popular right now" dashboard that scans every cart from the last hour and counts items. Three
problems show up during a sale:

- **Reads and writes fight.** The dashboard's big scans compete with checkout for the same CPU, disk, and cache, and
  every index added to speed up the dashboard slows every write.
- **One shape suits nobody.** Checkout wants a row per line. The cart page wants a cart with its total, and the
  dashboard wants a count per item. Every read rebuilds its shape with joins and sums.
- **The history is gone.** Marketing asks which items shoppers add and then remove. The table cannot answer, because
  removing an item deleted its row.

Splitting the reads off solves the first two problems, and keeping every change as an event solves the third. Both
bring a new cost: the read side runs behind the writes.

## The idea: write events, read projections

Split the system in two.

- The **write model** takes **commands** (AddItem, RemoveItem, Checkout), checks each one against the cart's current
  state, and either rejects it or records what happened as **events** (ItemAdded, ItemRemoved, CheckedOut). Events are
  facts in the past tense. Each one gets the next position in an **append-only event log**, and nobody edits or deletes
  them.
- **Projections**, also called read models, follow the log. Each keeps its own position, applies events in order, and
  stores a table shaped for one screen: the cart page wants lines and a total per cart, and the dashboard wants a count
  per item. The distance between the end of the log and a projection's position is its **lag**.

Separating the write model from the read models is **CQRS**, short for command query responsibility segregation.
Keeping the events themselves as the source of truth, and treating every other table as something you can recompute,
is **event sourcing**. A cart's state is a fold of its events: start empty and apply each one in order.

The two ideas often travel together, and each works alone. CQRS works with ordinary tables: the write side updates
rows, and an outbox table or change data capture feeds the read models. Event sourcing works without separate read
models: a small system can fold a cart's few events on every read. The [Event-driven design](../../async/event-driven-design/) lesson covers events that
travel between services; here the events live inside one service's storage.

<Analogy>

A shop keeps a ledger at the counter. Clerks only add lines to it, such as "sold one mug" or "returned the socks", and

What to look for:

- **The write model filters commands.** In the normal run, 98 commands arrive and 3 get rejected (two checkouts of a
  cart already checked out, and one removal of tea that was never in the cart), so the log holds 95 events. Rejected
  commands never reach a reader.
- **Each reader has its own gap.** A reader's bar marks its position in the log, and the hatched gap after it is its
  lag. In the strip of recent page loads, a ring marks a stale load.
- **19 of 95 page loads are stale** when the page reads right away. The table compares the same run with every page
  load first waiting for the shopper's own event: no stale pages, 24 ms of extra wait per page load on average, and
  200 ms at worst.
- **A flash sale swamps one reader.** Commands jump to 15 per second, and top items applies at most 10 events per
  second. It falls 42 events behind at 11.4 s and drains the backlog by 18.5 s. The cart page never trails by more than
  9 events, and the write model appends all 156 events without waiting for anyone.
- **The replay sweeps from position 0.** When v2 ships at 12 s, 6 carts show a wrong total. v1 keeps serving while v2
  rebuilds, so the count reaches 7. v2 replays 57 events in 2.8 s, catches up, and takes over with every total right.
  Receipts stay at 14.

## Read your own writes

The shopper who just added a mug expects to see it. Everyone else can live with a view that trails by a few hundred
milliseconds. So give the person who wrote a way to wait:

1. The write model returns the position of the event it appended, for example event 42.
2. The client sends that position with its next read.
3. The read waits until the projection reaches event 42, then answers. Cap the wait at a second or so, and fall back to
   showing the change from the client's own memory.

In the toy run, this turns 19 stale page loads into 0 at a cost of 24 ms per page load on average. It is the same idea
as sending a user's reads to the primary in [Read replicas](../../scaling/read-replicas/), and
[Consistency models](../consistency-models/) gives it a precise name: read-your-writes consistency.

## When one projection falls behind

Each projection runs at its own speed. The one that does the most work per event, or writes to the slowest store,
falls behind first, and a burst of commands exposes it. In the flash sale, the log grows faster than top items can
apply events, so its lag climbs until the sale ends. The dashboard only gets older; checkout never notices.

- **Measure lag two ways:** in events, which shows how much work is queued, and in time, which shows how old the
  answers are. Alert on age, because age is what people feel.
- **Give each projection its own worker,** so a slow dashboard never delays the cart page.
- **Split a busy projection by cart id,** so several workers each apply one slice of the log. Events for one cart must
  stay in order, which is the same partitioning question as [Sharding](../../scaling/sharding/).

## Fixing a bug by replaying

Replay turns a projection bug into a redeploy:

1. Deploy v2 next to v1, writing to a new table and starting at position 0.
2. Let v2 catch up while v1 keeps serving reads.
3. Switch reads to v2 once its lag is near zero, then drop v1's table.

The same move builds a brand new view from old events. Marketing's question about items added and then removed becomes
a new projection that replays the whole history on its first day.

A log of several years can take hours to replay even at thousands of events per second. Teams split the replay across
partitions, or start a projection from a saved copy of its table at a known position when the bug arrived after that
copy.

## Replays must not repeat side effects

Some readers act on the world. The email sender mails a receipt for every CheckedOut event, and a rebuild must leave it
alone: it keeps its own position, and the replay rebuilds one table. In the widget, receipts stay at 14 through the
replay. Make every side effect safe to repeat anyway, with an idempotency key such as the event's position, so a retry
after a crash cannot mail twice. The [Idempotency](../../reliability/idempotency/) lesson covers those keys.

## Events live forever

Once an event is in the log, every future version of every projection must read it. Rename a field, and years of old
events still carry the old name. Teams cope by:

- adding fields with defaults and keeping every old field,
- putting a version number on each event type, and
- writing **upcasters**, small functions that turn an old event shape into the current one as it is read.

Fix a wrong event with a new one, such as a correction, because the log stays append only. Plan for deletion laws up
front: keep personal data outside the log, or encrypt it with a key per shopper and delete the key when asked.

## Snapshots

The write model rebuilds a cart's state by folding its events before each command. A cart has a handful of events, so
that costs little. A bank account with ten years of transactions has thousands. A **snapshot** stores the folded state
at a known position. The write model loads the latest snapshot and folds only the events after it. Snapshots work like
a cache: delete one and you can rebuild it from the log.

## When to skip it

Both patterns add moving parts: a log to run, projections to deploy and watch, lag to explain to users, and event
schemas to keep forever. A shop with modest traffic does well with one database, a cache, and a read replica. Reach for
CQRS when reads and writes want different shapes or different scale, and for event sourcing when the history itself is
valuable: audits, money, or questions nobody has asked yet.

## Trade-offs

<TradeoffTable title="CQRS and event sourcing choices">

| Choice                           | What it buys                                                      | What it costs                                                     |
| -------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------- |
| Separate read models             | A table shaped for each screen, and reads that stop slowing writes | Reads trail the writes, and more stores to run and watch           |
| Event log as the source of truth | Full history, new views from old events, and bug fixes by replay  | Event schemas live forever, replays take time, deletion is harder |
| Wait for my event                | The writer always sees their own change                           | Slower reads right after a write, and a timeout for stuck readers |
| More projections                 | New questions answered without touching the write side            | Another reader to deploy, monitor, and rebuild                    |
| Snapshots                        | Fast loads for long event streams                                 | Another format to version, and a rebuild when it changes          |

</TradeoffTable>

A chat app stores every message as a MessagePosted event and every "opened the conversation" as a ConversationRead

projection and must rebuild it, and one worker applies 50,000 events per second.

1. How long does the rebuild take with one worker? With the log split into 20 partitions by conversation id, one worker

2. A user opens a conversation, goes back to the inbox, and still sees the unread badge. Why, and how do you fix it?
3. What must the rebuild leave alone?

<div slot="answer">

- One worker: 5,000,000,000 ÷ 50,000 = 100,000 s, about **28 hours**. New events keep arriving at 2,000 per second, so
  it catches up at 48,000 per second, which makes it closer to 29 hours.
- 20 partitions: each worker replays about 250 million events, and 250,000,000 ÷ 50,000 = 5,000 s, about
  **83 minutes**. Each partition gains only about 100 new events per second meanwhile. The old table keeps serving until
  every partition catches up, then reads switch.
- The badge: the inbox reads the projection, which has not applied the ConversationRead event yet. Return that event's
  position from the "open conversation" command and have the inbox wait for the projection to reach it, with a cap, or
  clear the badge in the client right away.
- Leave alone: push notifications and emails for new messages. They keep their own positions, and the rebuild writes
  only the new unread-counts table. Give each push an idempotency key from the event anyway.

</div>
