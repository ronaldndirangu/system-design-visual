## The failure: a cart that forgets the book

A store keeps three copies of every cart, so a dead disk never empties one. To stay fast, the cart service confirms an
add once **one** copy applies it and answers a view from **one** copy. Each add writes Sam’s whole cart as a new
version: v1 holds the mug, v2 the mug and the book. Sam adds the book, replica D applies it first, and the service
confirms at 0.52 s. At 0.70 s Sam opens the cart.

## The idea: make every read meet every write

The cart service places copies with the consistent hashing ring from [sharding](../../scaling/sharding/). It hashes
`cart:sam` onto the ring and walks clockwise. The first **N** replicas it meets hold copies, and that ordered list is
the key’s **preference list**. Two more numbers decide each request:

- **W** is how many copies must apply an add before the service confirms it.
- **R** is how many copies a view asks. The service returns the newest version it hears.

If **R + W > N**, every view asks at least one copy that applied the latest confirmed add. With N = 3, any two copies
share one with any other two.

<StepDiagram client:visible title="How W and R decide what a view sees" nodes={nodes} edges={edges} steps={steps} height={300} />

<Analogy>

A club keeps its member list in three binders in three rooms. The secretary updates two binders before saying “done”.
A member check reads two binders and trusts the newer entry. Any two rooms out of three share one, so every check finds
the new member.

Where it breaks: a binder sits still, while a replica can go down, return behind, and miss entries until something
copies them over.

</Analogy>

## What real systems do

The widget is a toy. Real Dynamo-style stores differ from it in six ways:

- **Settings are per request.** Cassandra lets each read and write choose ONE, QUORUM, or ALL, which slides one store
  between the lanes of [CAP and PACELC](../cap-and-pacelc/).
- **Replicas catch up.** Hinted handoff, read repair, and background anti-entropy copy missed adds to a replica that
  returns behind.
- **Sloppy quorums trade overlap for availability.** Stand-ins outside the preference list keep writes flowing, so
  R + W > N no longer guarantees that a read meets them.
- **Overlap is weaker than linearizable.** Racing views can disagree while an add is in flight.
  [Linearizable](../consistency-models/) reads need extra work, such as [Raft](../raft/).
- **A failed write can still land.** A timed-out add stays on every copy that applied it, so retries must be safe.
- **Concurrent writers need a merge rule.** Two devices writing one cart need timestamps or vector clocks.

<details>
<summary>Go deeper: how real stores close the gaps</summary>

**Per-request settings.** QUORUM means a majority of N, so with N = 3, QUORUM for both reads and writes means R = 2 and
W = 2. A team can read product reviews at ONE and checkout totals at QUORUM from the same store.

**Three repairs.** In the widget, D stays behind until the next add reaches it. With **hinted handoff**, a neighbor
holds the adds D missed and delivers them when D returns. With **read repair**, a view that hears v2 and v6 writes v6
back to the stale copy. **Anti-entropy** jobs compare replicas in the background, often with Merkle trees, and copy
over what differs.

**Sloppy quorums.** Dynamo keeps accepting writes when preferred replicas are down by counting acks from the next
healthy nodes on the ring. Writes stay available, but those stand-ins sit outside the preference list, so R + W > N no
longer guarantees that a read meets them.

**Weaker than linearizable.** In N3 R2 W2, the view at 1.50 s returns v3 at 1.52 s, 60 ms before Sam’s add of the
scarf is confirmed at 1.58 s. B and D both hold v2 until 1.57 s, so a view that asked them just after 1.52 s would
return an older cart than one already shown. Stores close this gap by making each read write the newest version it saw
back to W copies before answering, or by ordering every write through a consensus log such as Raft.

**Failed writes.** A write that times out stays on every copy that applied it, so a later view can return an add that
Sam was told failed. Retries must be safe to repeat.

**Merge rules.** One shopper writes this cart, so its versions form a simple sequence. When two devices write at once,
stores tag versions with timestamps or vector clocks and must merge siblings, with the same risks the
[CAP lesson](../../distributed-data/cap-and-pacelc/) shows.

</details>

## Trade-offs

<TradeoffTable title="Choosing N, R, and W for one cart">

| Setting  | What it buys                                                   | What it costs                                              |
| -------- | -------------------------------------------------------------- | ---------------------------------------------------------- |
| N3 R1 W1 | The fastest answers (25 ms adds, 16 ms views), no refusals     | 6 stale views of 17 with all up, 7 with D down             |
| N3 R2 W2 | 0 stale views, and adds and views survive one lost copy        | 68 ms adds; 11 of 29 refused with two copies lost          |
| N3 R1 W3 | 0 stale views, and 16 ms views                                 | 222 ms adds, and every add refused while any copy is down  |
| N5 R3 W3 | 0 stale and 0 failed with any two replicas down                | Five copies to store; 70 ms adds, 114 ms with two down     |

</TradeoffTable>

Skip leaderless quorums when every write must land in one agreed order, such as a bank balance or a lock: use one
leader with [Raft](../raft/). A quorum store pays off when replicas must stay writable through failures and a read
needs only the latest confirmed write.

## Common mistakes

- **Treating R + W > N as linearizable.** Overlap covers adds confirmed before a view starts. Racing views can
  disagree while an add is in flight.
- **Counting stand-ins toward the quorum.** Sloppy quorum stand-ins sit outside the preference list, so a read can
  miss them.
- **Setting W = N for safety.** Reads stay fresh, and every write fails while any one copy is down.
- **Expecting a returning replica to catch up on its own.** Without hinted handoff, read repair, or anti-entropy, it
  keeps old data for any R = 1 view to return.

<KeyTakeaways>

- A hash ring picks a key’s N replicas. A write waits for W copies, and a read asks R and returns the newest
  version.
- R + W > N makes every read meet every confirmed write. R + W ≤ N answers faster and can return stale data.
- A read needs R live copies and a write needs W, so overlap alone says nothing about availability. N5 R3 W3 survives
  two lost replicas.
- Quorums alone neither catch up a replica that returns behind nor make reads linearizable. Add repairs, and use a
  leader where order matters.

</KeyTakeaways>
