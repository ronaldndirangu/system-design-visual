## The failure: a cart that forgets the book

An online store keeps three copies of every shopping cart, so a dead disk never empties a cart. To stay fast, the cart
service confirms an add as soon as **one** copy has applied it, and answers a view by asking **one** copy. Every add
carries Sam’s whole cart as a new version: v1 holds the mug, v2 the mug and the book, and so on.

Sam adds a book. Replica D applies it first, and the service confirms the add to Sam at 0.52 s. At 0.70 s Sam opens
the cart, and the service asks replica A.

## The idea: make every read meet every write

The cart service places copies with the same consistent hashing ring you met in [sharding](../../scaling/sharding/).
It hashes the key `cart:sam` onto the ring and walks clockwise. The first **N** replicas it meets hold copies, and that
ordered list is the key’s **preference list**. Then two more numbers decide each request:

- **W** is how many copies must apply an add before the service confirms it.
- **R** is how many copies a view asks before the service answers with the newest version it hears.

If **R + W > N**, the copies a view asks always include at least one copy that applied the latest confirmed add. With
N = 3, a write set of 2 and a read set of 2 cannot avoid each other: there are only three replicas to choose from. That
shared replica carries the newest version, so the view returns it.

<StepDiagram client:visible title="How W and R decide what a view sees" nodes={nodes} edges={edges} steps={steps} height={300} />

<Analogy>

A club keeps its member list in three binders in three rooms. When the secretary adds a member, she updates two
binders before saying “done”. When someone checks membership, they read two binders and trust the newer entry. Two
rooms out of three always share one, so every check finds the new member. If the secretary updated one binder and the
reader checked a different one, the check would miss. If she insisted on updating all three, a locked room would stop
every new membership until someone found the key.

</Analogy>

- With D and B down, **N3 R2 W2** refuses 11 of 29 requests, 4 adds and 7 views, because only A is left: “only 1 of the
  3 replicas for this cart is up and R = 2”.

- With D and B down, **N5 R3 W3** returns 0 stale carts and 0 failures. Three of its five copies are still up, enough

Because each add carries the whole cart, Sam’s app keeps a refused item and sends it again inside the next add that gets
through. A refusal delays an item, and a stale view hides one.

## What real systems do

The widget is a toy, and real systems differ from it in a few important ways:

- **Settings are per request.** Dynamo-style stores such as Cassandra let each read and write choose how many copies to
  wait for: ONE, QUORUM (a majority of N), or ALL. With N = 3, QUORUM for both means R = 2 and W = 2. A team can read
  product reviews at ONE and checkout totals at QUORUM from the same store, which slides one store between the two
  lanes of [CAP and PACELC](../cap-and-pacelc/).
- **Replicas catch up on their own.** Here D stays behind until the next add reaches it. Real stores add three repairs.
  With **hinted handoff**, a neighbor holds the adds D missed and delivers them when D returns. With **read repair**, a
  view that hears v2 and v6 writes v6 back to the stale copy. **Anti-entropy** jobs compare replicas in the background,
  often with Merkle trees, and copy over what differs.
- **Sloppy quorums trade overlap for availability.** Dynamo keeps accepting writes when preferred replicas are down by
  counting acks from the next healthy nodes on the ring. Writes stay available, but those stand-ins sit outside the
  preference list, so R + W > N no longer guarantees that a read meets them.
- **Overlap is weaker than linearizable.** In N3 R2 W2, the view at 1.50 s returns v3 at 1.52 s, 60 ms before Sam’s add
  of the scarf is confirmed at 1.58 s. B and D both hold v2 until 1.57 s, so a view that asked them just after 1.52 s
  would return an older cart than one already shown. For the stronger promises from
  [consistency models](../consistency-models/), stores make each read write the newest version it saw back to W copies
  before answering, or order every write through a consensus log such as [Raft](../raft/).
- **A failed write can still land.** A write that times out stays on every copy that applied it, so a later view can
  return an add that Sam was told failed. Retries must be safe to repeat.
- **Concurrent writers need a merge rule.** One shopper writes this cart, so its versions form a simple sequence. When
  two devices write at once, stores tag versions with timestamps or vector clocks and must merge siblings, with the
  same risks the [CAP lesson](../../distributed-data/cap-and-pacelc/) shows.

<Challenge>

A chat service stores each conversation on a ring with N = 3. The product needs three things: a sender must always see
their own message on the next refresh, the service must keep accepting messages while any one replica is down, and
reading a conversation should stay fast. Choose R and W, and say what you would add so a replica that returns behind
catches up. What changes if the service must survive two lost replicas?

<div slot="answer">

- **Choose W = 2 and R = 2.** 2 + 2 > 3, so a refresh always reaches a replica that stored the sender’s confirmed
  message. Both sets need only two of three copies, so one lost replica refuses nothing. A view waits for two replies
  instead of one, which costs little: 17 ms against 16 ms per view in the run.
- **Rule out the others.** R = 1 and W = 1 is faster but lets a sender miss their own message, like the stale carts in
  the run. R = 1 and W = 3 overlaps, but it refuses every message while any copy is down.
- **Add repair.** Use hinted handoff so a neighbor holds the messages a down replica missed, read repair so a view
  that sees an old copy fixes it, and a background anti-entropy job for conversations nobody reads.
- **Two lost replicas.** Three copies cannot keep two-copy sets alive with two of them gone. Move to N = 5 with R = 3
  and W = 3, as in the last column of the table, and pay for two more copies of every conversation.
- **Know the limit.** Overlap shows every confirmed message. Two members refreshing while a message is still in flight
  can briefly disagree, so a chat that needs strict order should send each conversation through one leader, as in
  [Raft](../raft/).

</div>

</Challenge>
