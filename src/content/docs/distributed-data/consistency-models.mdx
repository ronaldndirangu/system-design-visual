## The failure: a reply with no question

Ana, Ben, and Carla share a group chat. The chat service keeps three copies of every conversation on three replicas,
R1, R2, and R3, so it can answer each phone from a nearby server and survive the loss of one. A router sends each request
to one of the replicas, and the replicas copy new messages to each other in the background. A copy takes a few ticks to
travel.

Ana sends “Lunch at noon?” and it lands on R2. Ben reads from R2, sees the question, and replies “Yes, see you there”.
His reply lands on R3, which has not received Ana’s question yet. Then Carla opens the chat.

## The idea: a consistency model is a promise to readers

A consistency model says which answers a read may return, given what has been written and what this reader has already
seen or written. A weak promise lets any nearby replica answer at once. A strong promise makes some reads wait, or sends
them to a particular replica, so certain anomalies can never reach a screen. This lesson tracks four anomalies:

- **Stale read:** the read misses a message the system already accepted.
- **Own message missing:** you sent a message, and your next read does not show it.
- **Went backwards:** you saw a message, and a later read no longer shows it.
- **Reply before question:** you see an answer without the message it answers.

<StepDiagram client:visible title="How a reply gets ahead of its question" nodes={nodes} edges={edges} steps={steps} height={300} />

<Analogy>

Picture an office with a notice board on each of three floors, and a clerk who walks new notices from board to board.
Under **eventual** consistency, you read the board on your floor, whatever it shows. Under **monotonic reads**, you
remember the newest notice you have read, and you wait if your board is behind it. Under **read your writes**, you wait
until your own notice is pinned up. Under **causal** consistency, the clerk refuses to pin a reply until the notice it
answers is up. Under **linearizable** consistency, everyone walks to one main board, and a notice counts only once a
second floor has a copy.

</Analogy>

## The promises form a ladder with two rails

The five promises do not sit in one straight line. Monotonic reads and read your writes protect different things, so
neither includes the other. The run shows both gaps: under monotonic reads Ana still loses her own message, and under
read your writes Ben still goes backwards. Causal consistency includes both session promises and adds one more rule: a
reply never shows before the message it answers. Linearizable sits at the top: the system behaves as if one copy of the
chat existed, and every read sees the latest confirmed write.

| Promise          | Rules out                                                   | Still allows                                                           |
| ---------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------- |
| Eventual         | nothing                                                     | stale reads, own message missing, going backwards, reply before question |
| Monotonic reads  | going backwards                                             | stale reads, own message missing, reply before question                |
| Read your writes | own message missing                                         | stale reads, going backwards, reply before question                    |
| Causal           | own message missing, going backwards, reply before question | stale reads                                                            |
| Linearizable     | all four anomalies                                          | none of the four                                                       |

## Sequential consistency and the four session guarantees

The widget runs five promises, and design reviews use a few more names on the same ladder.

**Sequential consistency** sits between causal and linearizable. Every replica shows all messages in one agreed order,
and that order keeps each person’s messages in the order they sent them. It sets no deadline: a phone may show the
agreed order a few seconds late, even after Ana’s send was confirmed. Linearizable adds that deadline: once a write is
confirmed, every later read on any phone shows it. ZooKeeper works this way. One leader orders every write, and a
follower answers reads from its own copy, which can lag. A client that needs the newest value calls `sync` first, which
makes its follower catch up with the leader.

Monotonic reads and read your writes belong to a set of four **session guarantees**. Each one protects what a single
person’s session sees, and causal consistency gives all four at once. The widget’s reply-before-question rule is the
fourth one, writes follow reads.

| Session guarantee   | Promise to one session                                                | In the chat                                                          |
| ------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Read your writes    | A read shows every write this session made earlier.                   | Ana sees “Lunch at noon?” right after she sends it.                  |
| Monotonic reads     | A read never shows less than an earlier read in this session.         | A message Ben saw never disappears from his phone.                   |
| Monotonic writes    | Every replica applies this session’s writes in the order it made them. | Ana’s “Booked a table for two” never lands before her “Lunch at noon?”. |
| Writes follow reads | A write lands after every write this session read before making it.   | No replica shows Ben’s reply until it holds Ana’s question.          |

Causal is the strongest promise on this ladder that still answers on both sides of a network partition, as long as each
phone keeps talking to the same replica. Sequential and linearizable both need one agreed order of writes, so a replica
cut off from the rest cannot accept new ones. The [CAP and PACELC](../cap-and-pacelc/) lesson picks up that choice.

## What real systems do

The widget is a toy, and real systems pay for these promises with a few standard tools:

- **Session promises** (monotonic reads and read your writes) usually come from sticky sessions, which pin a person to
  one replica, or from version tokens: the client remembers the newest version it has seen or written, and a replica
  that is behind waits or forwards the request. The [read replicas](../../scaling/read-replicas/) lesson routes fresh
  reads to the primary for the same reason.
- **Causal consistency** needs dependency tracking. Each write carries the versions it depends on, and a replica holds
  the write back from readers until those dependencies arrive, just as R1 holds Ana’s third message in the causal run.
- **Linearizable consistency** needs one agreed order of writes, usually from a leader that replicates to a majority.
  The [Raft](../raft/) lesson shows how replicas elect that leader. A real leader must also confirm it still leads before
  it answers a read, an extra round trip this toy skips, so real linearizable reads cost more than the widget shows.
- When a network partition splits the replicas, a linearizable system must refuse requests on the minority side. The
  [CAP and PACELC](../cap-and-pacelc/) lesson covers that choice.

Many databases let you pick the promise per request. Use that: pay for a strong read only where a feature needs it.

## Trade-offs

<TradeoffTable title="Consistency promises">

| Choice           | What it buys                                                                 | What it costs                                                                                                        |
| ---------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Eventual         | Any replica answers at once; reads stay local and survive a replica loss.     | Readers can see stale data, lose their own writes, go backwards, or see a reply before its question.                 |
| Monotonic reads  | Nobody loses a message they already saw.                                      | Reads wait for a lagging replica or stick to one; own writes and message order stay unprotected.                     |
| Read your writes | People always see what they just sent.                                        | Reads wait after a write or go to the replica that took it; other readers still see anomalies.                      |
| Causal           | Replies never appear before questions, plus both session promises.            | Every write carries dependency metadata, replicas hold messages back, and stale reads remain.                        |
| Sequential       | Every phone shows the same order, and each person’s messages keep the order they were sent in. | One leader orders every write, so a cut-off minority cannot take writes, and follower reads can still trail a confirmed write. |
| Linearizable     | The system acts like a single copy; every read sees the latest confirmed write. | Every request travels to the leader, and every write waits for a majority; a read of an unconfirmed write returns the last confirmed state. One replica carries the load, a real leader confirms it still leads before each read, and a cut-off minority cannot answer. |

</TradeoffTable>
