## The idea: a consistency model is a promise to readers

A consistency model says which answers a read may return, given what has been written and what this reader has already
seen or written. A weak promise lets any nearby replica answer at once. A strong one makes some reads wait or go to a
particular replica. This lesson tracks four anomalies:

- **Stale read:** the read misses a message the system already accepted.
- **Own message missing:** your next read misses a message you sent.
- **Went backwards:** a later read no longer shows a message you saw.
- **Reply before question:** you see an answer without the message it answers.

<StepDiagram client:visible title="How a reply gets ahead of its question" nodes={nodes} edges={edges} steps={steps} height={300} />

<Analogy>

Picture three floors, each with a notice board, and a clerk who carries new notices between them. **Eventual**: you
read your floor’s board as it is. **Monotonic reads**: you wait if your board is older than the newest notice you read.
**Read your writes**: you wait until your own notice is up. **Causal**: the clerk never pins a reply before its notice.
**Linearizable**: everyone uses one main board.

Where it breaks: a building never splits in two, while a network partition can cut replicas apart.

</Analogy>

## The promises form a ladder with two rails

Monotonic reads and read your writes protect different things, so neither includes the other. Causal includes both and
keeps every reply after its question. Linearizable sits at the top: the system acts as if one copy of the chat existed.

| Promise          | Rules out                                                   | Still allows    |
| ---------------- | ----------------------------------------------------------- | --------------- |
| Eventual         | nothing                                                     | all four        |
| Monotonic reads  | going backwards                                             | the other three |
| Read your writes | own message missing                                         | the other three |
| Causal           | own message missing, going backwards, reply before question | stale reads     |
| Linearizable     | all four anomalies                                          | none            |

## Sequential consistency and the four session guarantees

**Sequential consistency** sits between causal and linearizable. Every replica shows all messages in one agreed order
that keeps each person’s messages in the order they sent them. It sets no deadline: a phone may show that order a few
seconds late, even after Ana’s send was confirmed. Linearizable adds the deadline: once a write is confirmed, every
later read on any phone shows it.

<details>
<summary>Go deeper: ZooKeeper and sync</summary>

ZooKeeper works this way. One leader orders every write, and a follower answers reads from its own copy, which can lag.
A client that needs the newest value calls `sync` first, which makes its follower catch up with the leader.

</details>

Monotonic reads and read your writes are two of four **session guarantees**, and causal consistency gives all four. The
widget’s reply-before-question rule is the fourth one, writes follow reads.

| Session guarantee   | Promise to one session                                 | In the chat                                          |
| ------------------- | ------------------------------------------------------ | ---------------------------------------------------- |
| Read your writes    | A read shows this session’s earlier writes.            | Ana sees her question as soon as she sends it.       |
| Monotonic reads     | A read never shows less than an earlier read.          | A message Ben saw never disappears.                  |
| Monotonic writes    | Replicas apply this session’s writes in order.         | Ana’s two messages land in the order she sent them.  |
| Writes follow reads | A write lands after the writes its session read first. | Ben’s reply never lands before Ana’s question.       |

Causal is the strongest promise on this ladder that still answers on both sides of a network partition, as long as each
phone keeps talking to the same replica. Sequential and linearizable both need one agreed order of writes, so a replica
cut off from the rest cannot accept new ones. The [CAP and PACELC](../cap-and-pacelc/) lesson picks up that choice.

## What real systems do

- **Session promises** use sticky sessions or a version token: the client carries the newest version it has seen, and
  a lagging replica waits or forwards the request, as in the [read replicas](../../scaling/read-replicas/) lesson.
- **Causal consistency** attaches to each write the versions it depends on, and a replica hides the write until those
  arrive.
- **Linearizable consistency** needs a leader that replicates each write to a majority, elected as in the
  [Raft](../raft/) lesson. A read also costs a round trip to a quorum, or a lease, before the leader answers.

Many databases let you pick the promise per request.

<details>
<summary>Go deeper: how a leader serves a linearizable read</summary>

An old leader may not know it was replaced: a partition can elect a new leader while the old one still answers
clients from its own copy. Raft offers two safe ways to read.

With a **read index**, the leader notes its commit index, exchanges one round of heartbeats with a majority to confirm
it still leads, waits until its state machine has applied up to that index, and then answers. A follower can serve the
read too: it asks the leader for the read index and waits until it has applied that far.

With a **lease**, the leader skips the heartbeat round. After a majority acknowledges a heartbeat, no other leader can
win an election until an election timeout passes, so the leader answers reads alone until then. This trusts that server
clocks drift by a bounded amount.

</details>

## Trade-offs

<TradeoffTable title="Consistency promises">

| Choice           | What it buys                                                 | What it costs                                                                                                     |
| ---------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| Eventual         | Any replica answers at once.                                 | All four anomalies.                                                                                               |
| Monotonic reads  | Nobody loses a message they saw.                             | Reads wait for a lagging replica or stick to one.                                                                 |
| Read your writes | People see what they just sent.                              | Reads wait after a write or go to the replica that took it.                                                       |
| Causal           | Replies after questions, plus both session promises.         | Dependency metadata on every write, and stale reads remain.                                                       |
| Sequential       | One order that keeps each person’s messages in send order.   | A cut-off minority cannot take writes, and reads can trail a confirmed write.                                     |
| Linearizable     | Every read sees the latest confirmed write.                  | Every request goes to the leader, a write waits for a majority, and a read needs a quorum round trip or a lease. |

</TradeoffTable>

Skip linearizable when data a few seconds old is fine, such as a like counter. Pay for it where two people must agree
on one value now, such as claiming a unique username.

## Common mistakes

- **Treating read your writes as fresh for everyone.** It protects only the writer. Other readers can still see stale
  data.
- **Assuming causal means up to date.** Causal orders what a request depends on, and a reader can still see stale data.
- **Calling sequential linearizable.** Sequential agrees on one order but sets no deadline, so a follower read can miss
  a confirmed write.
- **Treating linearizable reads as free.** A leader must confirm with a quorum, or hold a lease, before it answers.

<KeyTakeaways>

- A consistency model promises which answers a read may return. Stronger promises make reads wait or use fewer
  replicas.
- Monotonic reads and read your writes protect a session in different ways. Causal gives both, keeps replies after
  questions, and still allows stale reads.
- Sequential consistency agrees on one order. Linearizable adds a deadline: every read sees the latest confirmed write.
- A linearizable write waits for a majority, and a linearizable read needs a quorum round trip or a lease.

</KeyTakeaways>
