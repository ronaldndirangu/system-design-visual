## The failure: two people, one word

Ada and Ben share a document that reads "cast". At the same moment, Ada deletes the s (she wants "cat") and Ben types an
o after the c (he wants "coast"). Each editor applies its own edit instantly and then sends it to the other. The naive
design describes each edit by position: Ada sends "delete the character at index 2", and Ben sends "insert o at index
1". Each copy applies the incoming op exactly as written.

## The constraint: every copy applies edits in a different order

Waiting a network round trip on every keystroke would make typing feel broken, so each editor applies its own edits
first and everyone else's later, in whatever order the network delivers them. The design must still bring every copy to
the same text once the edits stop, without losing anyone's edit. A **CRDT** (conflict-free replicated data type) is a
data structure built for exactly this: copies that apply the same ops, in any order that respects their dependencies,
end in the same state.

The rest of this lesson walks the [design checklist](../../thinking/design-checklist/).

## Requirements

**Functional**

- Several people type in one document at the same time.
- Each person sees their own keystroke immediately.
- Every copy ends with the same text, and nobody's edit disappears.
- An editor that drops offline catches up when it reconnects.
- A newcomer opens a long-lived document quickly.

**Non-functional** (illustrative targets)

- Local echo inside one screen frame, with no network wait.
- Remote edits visible on other screens within about 200 ms.
- An acknowledged edit survives a server crash.
- 2 to 100 people editing one document at once.

## Estimates

These numbers are illustrative. In this toy, a person typing produces about 5 ops per second, one per keystroke. The
relay receives every op once and forwards it to every other editor of the document.

| Quantity                               | Illustrative value                                                       |
| -------------------------------------- | ------------------------------------------------------------------------ |
| Ops per typist                         | 5 per second                                                             |
| 2 editors                              | 10 ops per second in, 10 out                                             |
| 10 editors                             | 50 in, 450 out (50 × 9)                                                  |
| 100 editors                            | 500 in, 49,500 out (500 × 99, about 49.5K)                               |
| Bytes per character in the CRDT        | 18: 1 for the character, 8 for its id, 8 for its origin, 1 for a flag   |
| 50 KB of visible text                  | 900 KB of CRDT state                                                     |
| The same text plus 50 KB of tombstones | 1.8 MB of CRDT state                                                     |

Two things stand out. First, forwarding grows with the square of the editor count: 10 times the editors means more than
100 times the forwarded ops (450 to 49,500). Most documents have a handful of editors, so one relay can host many
documents. Shard documents across relays by doc id, as in [Sharding](../../scaling/sharding/), so every editor of one
document meets on the same relay. Second, metadata dominates: each character costs 18× its own size. Real libraries
store a run of typed characters as one item with one starting id, which shrinks that overhead sharply.

## API

```text
GET  /docs/{docId}
     returns { snapshot, uptoSeq, opsAfter: [...] }

WS   /docs/{docId}/live?after={seq}&site={site}
  server to client
     { type: "hello", site: "b" }
  client to server
     { opId: "b:3", type: "insert",
       id: "b3", origin: "a2", char: "y" }
     { opId: "b:4", type: "delete", target: "a3" }
  server to client, to every other editor
     { type: "op", seq: 1042, op: {...} }
  server to client, to the sender
     { type: "ack", opId: "b:3", seq: 1042 }
```

The server hands each editor a site letter on its first join. The editor presents the same letter on every reconnect,
so its ids keep counting from where they stopped. An insert names its own id and its origin, the character to its left
(an origin of `null` means the start of the document). A delete names its target. Neither op mentions an index.

Every op also carries an `opId`: the site letter plus the editor's own op counter, so `b:4` is the fourth op Ben's
editor sent. The `opId` exists for dedup and stays separate from the character ids. An insert's `id` could serve as a
dedup key, but a delete has no id of its own. Its `target` names someone else's character, and Ada and Ben can both
delete a3. The relay acks each op by its `opId`, so the sender knows exactly which ops landed.

The live channel is a WebSocket; the [Real-time transport](../../foundations/real-time/) lesson compares it with
polling and server-sent events.

## Data model

| Table     | Key                  | Holds                                                                              |
| --------- | -------------------- | ---------------------------------------------------------------------------------- |
| documents | `doc_id`             | Title, owner, latest sequence number                                               |
| ops       | `(doc_id, seq)`      | Each op as sent, with a unique `(doc_id, op_id)` so a resent op lands once         |
| snapshots | `(doc_id, upto_seq)` | The full character list, with ids, origins, and tombstones                         |
| sites     | `(doc_id, site)`     | Which session owns each site letter, and the last id and op counter it used        |

Every op carries an `opId`, deletes included, so a client that reconnects can resend anything the relay never acked.
The unique `(doc_id, op_id)` key turns a duplicate into a re-ack instead of a second log entry. The
[Idempotency](../../reliability/idempotency/) lesson covers this pattern in depth, and the failure walkthrough below
traces one lost ack.

## High-level design

Each editor keeps a full local copy and applies its own edits instantly. A relay server forwards every op to the other
editors of the same document and appends it to an op log, which makes the edit durable. The relay never needs to
understand text: it orders, stores, and forwards. Now and then, a background job folds the log into a snapshot, so a
new editor loads one snapshot plus a short tail of ops instead of the document's whole history.

## Deep dive: name the neighbor, never the index

### Every character gets a name

Index 2 means a different letter on each copy as soon as edits cross. So every character gets a permanent **id**: the
site that typed it plus a counter, written here as a3 (site a, counter 3). A copy sets the counter one higher than the
largest counter it has seen from anyone, so a character always gets a larger counter than the characters already beside
it. Two ids compare by counter first, then by site letter, so every copy agrees on which of two ids is larger.

### An insert names its left neighbor

An insert op carries its new id, its character, and its **origin**: the id of the character to its left when it was
typed. Ben's o in "cast" (a1 to a4) becomes "insert o, id b5, after a1". On every copy, a1 is the c, wherever the c has
moved.

### Two inserts at the same spot

Origins leave one question open: two characters typed right after the same neighbor. Every copy runs the same rule to
place a remote insert:

```text
1. Find the origin (or the start of the document).
2. Look at the character just right of it.
3. If that character's id is larger than the new id, step over it and repeat step 2.
4. Otherwise, place the new character here.
```

Step 3 also steps over the characters typed after that larger neighbor, since they carry even larger counters. Here is
the rule on the Same-spot inserts scenario, where both copies start with Hi (a1, a2):

```text
Start, both copies            H a1   i a2
Ada types !                   H a1   i a2   ! a3
Ben types y, then a           H a1   i a2   y b3   a b4

Ben's copy receives ! (a3, after a2)
  right of a2 sits y b3. b3 is larger than a3 (same counter, and b beats a), so step over it.
  next sits a b4. b4 is larger, so step over it.
  end of the text, so ! goes here.
  now: H a1   i a2   y b3   a b4   ! a3

Ada's copy receives y (b3, after a2)
  right of a2 sits ! a3. a3 is smaller than b3, so y goes here.
  now: H a1   i a2   y b3   ! a3
Ada's copy receives a (b4, after b3)
  right of b3 sits ! a3. a3 is smaller than b4, so a goes here.
  now: H a1   i a2   y b3   a b4   ! a3
```

Both copies read "Hiya!". The index design ends with "Hiya!" on Ada's copy and "Hi!ya" on Ben's, because Ben's copy put
the ! at index 2, between his i and his y.

### Deletes leave tombstones

A delete names its target: Ada's delete of the s in "cast" becomes "delete a3". If a copy removed a3 outright, any op
that says "after a3" would have nowhere to go. So a deleted character stays in the list as a **tombstone**: hidden from
the text, still in place as an anchor. In the Insert beside a delete scenario, both copies end with "coat", and each
keeps one tombstone (2 across both copies).

### Ops that arrive early wait

Ids fix where an op goes, but an op can only go somewhere its anchor already exists. Ada types an s and then a ! at the
end of "cat" while Ben types an h after the c, and the network hands Ben's copy the ! first. Its origin, a4, is the s,
which Ben's copy has not seen yet.

**Hold the ! until the s arrives.** The op says "after a4", and Ben's copy has no a4 yet. A guess can put the ! ahead of

reloading the document also recovers, at the cost of a round trip for every reordered op.

</Predict>

One honest note: with a single relay that forwards ops over ordered WebSocket connections, ops already arrive in an order
that respects these dependencies, because the relay acts as a sequencer. Buffering earns its keep when copies sync peer
to peer, through several relays, or by replaying a backlog after a reconnect. The toy lets the network reorder ops so
you can watch the buffer work.

## Failure walkthrough: the ack for a delete gets lost

Back to "cast", now under the CRDT design. The relay has logged Ada's four inserts, a1 to a4, as seq 1 to 4 with opIds
a:1 to a:4. At 10:00:00.000 Ada deletes the s, and her editor sends `{ opId: "a:5", type: "delete", target: "a3" }`.
The relay logs it as seq 5, forwards it to Ben, and sends the ack at about 10:00:00.040. Her laptop switched from Wi-Fi
to cellular at 10:00:00.030, so the socket is already gone and the ack never arrives. Her editor cannot tell whether
the relay logged the delete, so it keeps a:5 in its unacked buffer. At 10:00:01, while she is offline, Ben types his o
after the c, and the relay logs it as seq 6.

Without an `opId`, the resent delete becomes seq 7 and reaches Ben a second time. His copy absorbs it, because a3 is
already a tombstone, yet the log now holds a phantom op that every catch-up and every snapshot build replays. An op
without that built-in protection, such as a future "toggle bold", would apply twice and undo itself.

With the `opId`, the resend lands once:

1. **Ada's editor reconnects** at about 10:00:02 with `after=4&site=a`: the last sequence number it saw and its old
   site letter. It resends everything in its unacked buffer, which is a:5.
2. **The relay finds the duplicate.** Its lookup on `(doc_id, op_id)` finds a:5, already logged as seq 5. The relay
   replies `{ type: "ack", opId: "a:5", seq: 5 }` and neither logs nor forwards the op again.
3. **Ada's editor clears a:5.** The ack carries the original sequence number, so her editor records seq 5 as its own
   op, already applied.
4. **The relay replays what she missed.** The ops after seq 4 are seq 5 and seq 6. Her editor skips seq 5, its own
   delete, and places Ben's o after the c. Both copies read "coat", and the log holds the delete once.

If the relay crashed before logging a:5, the lookup in step 2 finds nothing, and the resend logs as a fresh op. Either
way, the delete lands once. Resending until acked gives [at-least-once delivery](../../async/delivery-semantics/), and
the unique key on the log makes the effect happen once, the same pairing the
[Idempotency](../../reliability/idempotency/) lesson builds with request keys.

## Trade-offs

**Operational transformation (OT)** is the other main approach, and the one Google Docs uses. Ops keep plain indexes,
and a central server transforms each incoming op against the concurrent ops it has already applied. If Ben inserted a
character before index 2, Ada's "delete at index 2" becomes "delete at index 3" on Ben's copy. That shift is exactly
what the index lane was missing. OT keeps the document free of per-character ids, and it needs a central server to pick
one order plus a transform for every pair of op types, which is notoriously hard to get right.

<TradeoffTable title="Ways to merge concurrent edits">

| Design                           | What it buys                                                     | What it costs                                                                    |
| -------------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Index positions, applied as sent | Tiny ops and trivial code                                        | Copies diverge as soon as two edits cross                                        |
| Locks or turn taking             | One writer at a time, so nothing conflicts                       | Typing waits on the lock, and one slow editor blocks everyone                    |
| OT with a central server         | Compact ops, no per-character metadata, mature in production     | Transform functions are hard to get right, and every op must pass the server     |
| CRDT, RGA style (this lesson)    | Any copy merges ops in any causal order, offline or peer to peer | An id and an origin on every character, and tombstones that grow until collected |

</TradeoffTable>

## Honest simplifications

This lesson's model is a toy. Here is what it leaves out:

- **Tombstones never go away.** Real systems collect a tombstone only once it is causally stable: every copy has seen
  the delete, and every op that could still name the character has reached every copy. That requires knowing every copy
  and what each has seen, plus a rule for a copy that stays offline past the cut, such as reloading from a fresh
  snapshot instead of replaying its old ops. The toy keeps every tombstone.
- **Plain characters only.** No bold, links, or comments. Rich text needs ids for formatting ranges too.
- **One op per character.** Real editors send a run of typed characters as one op and store it as one item, which cuts
  the 18 bytes per character sharply.
- **Interleaving.** In this toy, two runs typed forward at the same spot stay together: abc and xyz merge to "xyzabc" on
  both copies. If each person types backward (c, then b to its left, then a), the runs interleave as "xaybzc". The
  copies still agree, and the text reads oddly. Some newer sequence CRDTs add rules to avoid even this.
- **The server still matters.** The CRDT removes the need for a server to decide the order, yet this design still uses
  one to relay ops, persist the log, hand out site letters, and serve snapshots.
- **No presence.** Cursors, selections, and who is here indicators travel on a separate, lossy channel and are out of
  scope.
- **Two copies and short words.** The widget runs two copies so you can read every tile. The unit tests also check 300
  seeded random sessions across two and three copies, and every one converges.

<details>
<summary>Go deeper: a class of 20 editing one outline</summary>

A class of 20 students edits one shared outline during a lecture, each typing about 5 ops per second at peak. By the end
of term the outline shows 20,000 characters, and students have deleted 60,000 more along the way. Use this lesson's
illustrative numbers.

- **Relay load.** Relay in: 20 × 5 = **100 ops per second**. Relay out: each op goes to the 19 other students, so
  100 × 19 = **1,900 ops per second**.
- **CRDT state.** (20,000 + 60,000) characters × 18 bytes = **1,440,000 bytes, about 1.44 MB**, against **20 KB** of
  visible text. That is **72×** the text.
- **First changes.** Store each run of typed characters as one item, and batch outgoing ops into one message per short
  window. Collect a tombstone once it is causally stable: every student has seen the delete, and every op that could
  still name the character has reached everyone. The relay already numbers every op, so it can track the last number
  each student has acknowledged. A student who stays offline past the cut reloads from a snapshot before sending again.
  If many classes edit at once, shard relays by doc id.

</details>

## Check yourself

<KeyTakeaways>

- Ops that name an index diverge as soon as two edits cross. Give every character an id and every insert its left
  neighbor, and an op lands in the same place on every copy.
- A delete leaves a tombstone, so later ops still find their anchor. An op whose anchor has not arrived waits in a
  buffer until it does.
- Every op carries an `opId`, deletes included. Editors resend until the relay acks, and the unique `(doc_id, op_id)`
  key turns a resend into a re-ack, so each op lands once.
- A CRDT merges ops in any causal order and pays with an id and an origin on every character, plus tombstones that
  grow. OT keeps ops compact and needs a central server plus transform functions that are hard to get right.

</KeyTakeaways>

**Closing rubric: grow one dimension tenfold.** Keep the estimates from this lesson (5 ops per second per typist, 18
bytes per character, and 50 KB of visible text held in 900 KB of CRDT state, or 1.8 MB with 50 KB of tombstones), and
raise one document's editors from 10 to 100.

<div slot="answer">

**The relay's fan-out breaks first.**

- **The new numbers.** Ops in grow tenfold, from 50 to 500 per second. Ops out grow 110×, from 450 to 49,500 per
  second, because each op now goes to 99 editors instead of 9. The CRDT state stays at 900 KB to 1.8 MB, since more
  editors do not lengthen the text. Yet 100 newcomers joining at the start of a meeting pull up to 180 MB of snapshots
  at once.
- **The change.** Batch on the relay: send each editor one message per 50 ms window with every op from that window.
  That is 100 × 20 = 2,000 messages per second instead of 49,500, carrying the same ops. Give the hot document its own
  relay, because every editor of one document must meet on one relay and sharding cannot split it. Serve snapshots
  from a cache or CDN in front of the relay. The cost: up to 50 ms of extra delay, still inside the 200 ms target, and
  a relay sized for one document that sits mostly idle once the meeting ends.
- **The crash.** The relay acks an op only after the op log holds it, so every acked op survives. Each editor keeps
  its own copy, its typing, and its unacked buffer. Each one reconnects, with a random delay so 100 sockets do not
  arrive in the same instant, and sends `after=` its last seen sequence number and `site=` its letter. It resends every
  unacked op; the relay re-acks any opId it logged before the crash and logs the rest fresh. Then the relay replays
  the ops each editor missed. Every copy converges, and nobody's edit disappears. Remote edits pause only for the
  restart.
