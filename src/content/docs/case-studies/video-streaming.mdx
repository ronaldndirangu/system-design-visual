## The failure: a train, three tunnels, one fixed file

A commuter starts a video on the train, served as one fixed 1080p encode at 5 Mbps. In the open the phone gets 5 to 8
Mbps, and in each of three tunnels in the first 90 s it gets about 1 Mbps. The player keeps a **buffer** of downloaded
video. When the buffer empties, the picture freezes: that is a **stall**, and the frozen time is **rebuffering**.

## Requirements

Video counts bytes more than requests. The rest of this lesson walks the
[design checklist](../../thinking/design-checklist/).

**Functional**

- Creators upload videos of a few gigabytes, and an upload survives a dropped connection without starting over.
- Each upload becomes a ladder of rungs, and the video goes live once a minimum playable set (360p and 720p) is ready.
- The player adapts quality to the network on its own.

**Non-functional** (illustrative): first frame within about 2 s, rebuffering under 1% of watch time, no completed
upload lost, and a video ready within minutes.

## Estimates

Suppose creators upload 50,000 videos a day, 8 minutes each at 10 Mbps. The ladder has five rungs, from 240p at 0.4
Mbps to 1080p at 5 Mbps. At peak, 1 million people watch at 3 Mbps on average.

| Quantity (illustrative)                           | Value                        |
| ------------------------------------------------- | ---------------------------- |
| Source per upload (8 min × 60 s × 10 Mbps ÷ 8)    | 600 MB                       |
| Sources per day (50,000 × 600 MB)                 | 30 TB, about 2.78 Gbps       |
| Ladder bitrates summed (0.4 + 0.8 + 1.4 + 2.8 + 5) | 10.4 Mbps, 78 MB per minute |
| Ladder per day (400,000 minutes × 78 MB)          | 31.2 TB                      |
| New storage per day, per year                     | 61.2 TB, about 22.3 PB       |
| Peak egress (1 million × 3 Mbps)                  | 3,000 Gbps                   |

Storage grows forever, so cheap gigabytes matter. Peak egress is about 1,080 times the upload rate, so bandwidth
dominates the bill.

## API

```text
POST /videos  {title, sizeBytes}
     returns { videoId, uploadId, partSize, parts }
POST /videos/{videoId}/parts/{n}/url  {sha256}
     returns { url, expiresAt }
PUT  {url}  (one part's bytes and its SHA-256, sent straight to object storage)
     returns { etag }
GET  /videos/{videoId}/parts
     returns [ { n, etag, sha256 } ] for every part that arrived
POST /videos/{videoId}/complete  {parts: [ { n, etag, sha256 } ]}
     returns 202 Accepted
GET  /videos/{videoId}
     returns { status, masterUrl }

GET  {cdn}/videos/{videoId}/master.m3u8
     returns the master (multivariant) playlist: one entry per ready rung
GET  {cdn}/videos/{videoId}/720p/playlist.m3u8
     returns the 720p media playlist: every segment URL with its duration
GET  {cdn}/videos/{videoId}/720p/seg_00012.ts
     returns 4 s of video at 720p
```

The API server never touches video bytes. Storage's ETag is an opaque name for a stored part, and for a multipart
object it is no MD5 of the bytes. Integrity needs an explicit checksum: the server signs each part's SHA-256 into its
URL, and storage rejects bytes that do not match. Complete moves the video to processing and writes an outbox row for
the transcode job in one transaction. A retried complete gets the same 202 and no second job, as in
[Idempotency](../../reliability/idempotency/).

## Data model

| Table        | Key                | Holds                                                                  |
| ------------ | ------------------ | ---------------------------------------------------------------------- |
| `videos`     | `video_id`         | Owner, title, status, duration, source key, master playlist key        |
| `uploads`    | `upload_id`        | Video id, part size, parts received with their ETags and SHA-256s      |
| `renditions` | `(video_id, rung)` | Resolution, bitrate, media playlist key, status: pending, encoding, ready |
| `outbox`     | `id`               | Video id, the owed transcode job, and whether the relay sent it        |

The video bytes live in object storage, which is cheap per gigabyte and answers no queries, so "which videos belong to
this creator?" goes to the database. [Data modeling](../../foundations/data-modeling/) compares these stores.

<details>
<summary>Go deeper: object storage keys, and how object storage differs from a database</summary>

The video lives in object storage under keys like these:

```text
sources/{videoId}/original.mp4
videos/{videoId}/master.m3u8
videos/{videoId}/720p/playlist.m3u8
videos/{videoId}/720p/seg_00012.ts
```

- **Buckets and keys.** A bucket is a named container, and a key is a path-like string inside it. You `PUT` an object
  under a key and `GET` it back by that key. The slashes are only part of the name; there are no folders, rows, or
  indexes.
- **Whole, immutable objects.** You write an object in one go and replace it whole. You cannot edit a few bytes in the
  middle. Reads can ask for a byte range, which players use for some formats.
- **Cheap and durable per gigabyte.** The service either copies each object to several disks or splits it with erasure
  coding into fragments plus parity, spread across machines, so a dead disk or a dead machine loses nothing. A terabyte
  here costs far less than a terabyte on database disks.
- **Slow per request, with no queries.** Each request carries far more latency than a lookup in a well-indexed
  database, and listing keys by prefix is the closest thing to a query.
- **One key that changes.** Segments and media playlists never change once written. The master playlist is the
  exception: it is rewritten whole as rungs join, so it gets a short cache lifetime.

</details>

## Deep dive: adaptive bitrate playback

### Segments and the ladder

The transcoder cuts each video into 4 s **segments** and encodes each one at every rung of a **bitrate ladder**:

| Rung  | Bitrate (illustrative) | Bits per 4 s segment |
| ----- | ---------------------- | -------------------- |
| 240p  | 0.4 Mbps               | 1.6 Mb               |
| 360p  | 0.8 Mbps               | 3.2 Mb               |
| 480p  | 1.4 Mbps               | 5.6 Mb               |
| 720p  | 2.8 Mbps               | 11.2 Mb              |
| 1080p | 5 Mbps                 | 20 Mb                |

HLS uses two kinds of playlist (`.m3u8`). The **master playlist** (RFC 8216 calls it multivariant) lists the rungs,
each with a bitrate and the URL of its media playlist. Each **media playlist** lists one rung's segments and their
durations. The player fetches the master playlist, then one media playlist, then segments over plain HTTP, so any CDN
can cache them.

Every segment starts with a **keyframe**, a full picture, at the same timestamps in every rung, so the player can switch
rungs between any two segments.

<details>
<summary>Go deeper: the buffer race, the adaptive rule, DASH, and what the duel shows</summary>

DASH describes the same two levels in one MPD file.

**The buffer race.** Playback drains the buffer at one second of video per second. Downloads refill it at a rate set by
the network and the rung. Take the tunnel's 1 Mbps:

- A 1080p segment is 4 s × 5 Mbps = 20 Mb. It takes 20 s to arrive, so the buffer gains 0.2 s of video per second of
  wall time while playback spends 1 s. The buffer shrinks every second.
- A 360p segment is 4 s × 0.8 Mbps = 3.2 Mb. It takes 3.2 s to arrive, so the buffer gains 1.25 s per second. The
  buffer grows, slowly, even in the tunnel.

When the buffer reaches zero, playback stalls until enough video arrives to resume. In the toy model, playback starts or
resumes once 4 s (one segment) is buffered, and the player stops fetching once 20 s is buffered.

**A simple adaptive rule.** Lane B follows a deliberately simple rule:

```text
for each segment:
  if nothing is measured yet, or less than 4 s is buffered:
      fetch the lowest rung (240p)
  else:
      estimate = average throughput of the last 3 downloads
      fetch the highest rung at or below 0.8 × estimate

while a segment downloads:
  speed = this download's average speed so far
  if it will not finish before the buffer runs dry,
  and the highest lower rung within 0.8 × speed would arrive sooner:
      drop it and fetch the same segment at that rung
```

The 0.8 is a safety margin. It leaves room for the network to dip a little without draining the buffer. Throughput is
measured per download, as the segment's size divided by the time it took, so a slow download counts only once it
finishes. That makes the estimate lag: the rule notices a tunnel late, and it notices open air late too. The buffer is
what carries the player through the lag, and the drop rule is its emergency brake.

Real players are more refined. Buffer-based algorithms such as BOLA choose rungs mainly from how full the buffer is,
and hybrid algorithms blend measured throughput with buffer level and look ahead. Real players also avoid switching too
often, because a picture that keeps changing sharpness annoys viewers. The toy rule is enough to show the core idea.

**What to look for in the widget:**

- **Fixed 1080p stalls in every tunnel.** It stalls at 27, 57, and 80 s: three stalls and 9 s of rebuffering. In 90 s
  it shows only 78 s of video.
- **The adaptive player starts fast, then reaches for quality.** It fetches segment 1 at 240p and starts playing at
  0.5 s, against 3 s for fixed 1080p. Its first throughput sample then sends it straight up to 1080p.
- **It stalls once, in the first tunnel.** Segment 8 is still downloading at 1080p when the first tunnel hits. That
  download's average speed still counts its fast start in the open, so the drop rule never fires, and the adaptive
  player stalls at 28.5 s for 2 s. It never stalls in the second or third tunnel, and it shows 87.5 s of video.
- **It steps down late.** Because a slow download counts only when it finishes, each step down lands within 1 s after a
  tunnel ends. The buffer built up in the open does the real work.
- **At 47 s it drops a download.** Early in the second tunnel, the player sees that a 1080p segment cannot finish before
  its 16 s of buffer runs out. It drops the segment and fetches it again at 360p, wasting 0.55 Mb, a small price for
  avoiding a stall.
- **Now pick Steady home Wi-Fi.** Both lanes play smoothly, and fixed 1080p wins on quality: it averages 5 Mbps against
  4.8 Mbps for the adaptive player, which spent its first segment on 240p. The adaptive player starts sooner, at 0.5 s
  against 2 s. On a steady, fast network, a ladder buys little.
- **Then pick Crowded evening.** The link never carries 5 Mbps. Fixed 1080p takes 7 s to start, stalls 11 times for
  38.5 s of rebuffering, and shows only 44.5 s of video. The adaptive player starts at 1 s, fetches every segment after
  the first at 480p, and never stalls.

</details>

## Deep dive: uploads that survive a dropped connection

A creator uploads a 2 GB video from a phone on a shaky connection. With one long `PUT`, a drop throws away everything
sent so far.

### Multipart upload

1. **Initiate.** The API server opens a multipart upload and returns the upload id with a part plan.
2. **Upload parts.** The client sends each part and its SHA-256 to a **pre-signed URL**, a storage URL the server signs
   for one action until it expires. Storage rejects a mismatch.
3. **Complete.** The client sends the part list. Storage joins the parts, and the server records the transcode job.

After a drop, the client asks which parts arrived and retries only the missing ones, with
[backoff and jitter](../../reliability/retries/).

<details>
<summary>Go deeper: pre-signed URLs, cleanup, whole-object checksums, and what the widget shows</summary>

**Cleanup.** A lifecycle rule in object storage deletes the parts of uploads nobody completed, or abandoned parts pile
up and cost money forever.

**Pre-signed URLs.** The API server creates each URL with its own credentials, so the video bytes travel from the phone
to object storage without passing through the API servers. Those servers stay small and cheap: they answer tiny JSON
requests while object storage, built for bulk bytes, takes the heavy traffic. When the server signs the part's SHA-256
into the URL, the client must send that exact checksum with the bytes.

**Whole-object checksums.** After complete, S3 also stores a checksum for the assembled object: a checksum of the part
checksums, or for CRC algorithms a full-object checksum. The server can compare it with the part list the client hashed
before it records the transcode job.

**What to look for in the widget:**

- **One drop costs a single request half the file.** With 3 drops, one request sends 5,000 MB to deliver 2,000 MB:
  3,000 MB wasted across 4 attempts. With 5 drops it sends 7,000 MB.
- **Multipart loses only the parts in flight.** With 3 drops and 100 MB parts, it sends 2,600 MB: 12 retried parts and
  600 MB wasted, across 34 requests.
- **Smaller parts waste less and cost more requests.** At 25 MB parts the waste falls to 150 MB, and the upload takes
  94 requests. Every request has overhead, and storage services usually charge per request.
- **Huge parts lose the benefit.** At 500 MB, 4 parts cover the whole file, so all of them are in flight at once and
  each drop wastes as much as it does for one request.
- **With no drops, both send exactly 2,000 MB.** Multipart only adds requests: 22 against 1.

</details>

## Deep dive: transcoding into a ladder

Encoding is slow and CPU heavy, so it runs on its own worker fleet. An 8 minute upload has 120 segments of 4 s, and
five rungs make 600 segment encodes.

### Split at keyframes, encode in parallel

Most frames store only changes since earlier frames and cannot be decoded alone, so the split follows keyframes:

- **Chunk at random-access points.** A planner reads the source's keyframe index and cuts chunks on segment boundaries.
- **Decode pre-roll, then trim.** Each worker starts decoding at the last keyframe before its chunk and drops the
  frames before its start.
- **Align keyframes.** Every output segment is one closed GOP (a group of pictures that references nothing outside
  itself) opening with a keyframe at 0, 4, 8 s, in every rung.
- **Minimum playable set first.** 360p and 720p tasks go on a high-priority lane.

### Publish each rung on its own

1. When a rung's last segment lands, the worker writes its media playlist and marks its `renditions` row ready.
2. It rebuilds the master playlist from the ready rows, under the same key.
3. Once 360p and 720p are ready, the video goes live. Other rungs join the master playlist as they finish.

Segments and media playlists never change, so the CDN caches them for a long time. The master playlist gets a short
cache lifetime, a minute or less.

### Retries without duplicates

The queue redelivers tasks after crashes. Segment 12 at 720p always goes to `videos/{videoId}/720p/seg_00012.ts`, so a
rerun writes identical bytes, and publishing skips rungs already ready.
[Queues and backpressure](../../reliability/queues-and-backpressure/) covers adding workers when uploads spike.

<details>
<summary>Go deeper: mezzanine files, lazy top rungs, racing publishers, and audio</summary>

- **Wall time.** Split across workers, a long upload finishes in about the time of its slowest chunk plus planning and
  publishing.
- **Mezzanine files.** Some pipelines first rewrite the source as a mezzanine file of closed GOPs with a keyframe every
  4 s, so every chunk starts cleanly with no pre-roll.
- **Late rungs and open players.** A player reads the master playlist when playback starts, so a viewer who pressed
  play before 1080p arrived stays on the lower rungs until the next play.
- **Encode the top rungs lazily.** Most uploads get few views. Encoding every upload at 1080p spends compute and storage
  on video almost nobody watches at 1080p. Some platforms encode the lower rungs up front and encode 1080p only once a
  video starts drawing views. The cost is a short window when a fresh hit plays without 1080p.
- **Two rungs can finish at once.** Two workers each read the ready rows and write the master playlist, and the write
  that lands last can drop the rung the other just added. Serialize the rebuilds, for example by holding a lock on the
  video row while reading the ready rungs and writing the master playlist, so the last write lists every ready rung.
- **Audio goes in one pass.** Audio encoders such as AAC add a short run of priming samples at the start of every
  encode, so stitching audio chunks leaves small gaps or clicks at the seams. Pipelines usually encode the audio track
  once, end to end, and serve it alongside every video rung.

</details>

## Failure walkthrough: the API server crashes between commit and publish

A creator's complete call commits at 14:00:00, and the API server crashes at 14:00:00.1. Had the server committed and
then enqueued as a second step, video 4417 would sit in processing forever with no job. With the outbox, the job row
committed in the same transaction as the status change.

1. **The relay restarts.** It reads unsent outbox rows and finds video 4417.
2. **It publishes again.** The queue may now hold two copies. The relay marks the row sent only after the queue
   confirms, so delivery is [at least once](../../async/delivery-semantics/).
3. **The workers absorb the duplicate.** Reruns write the same keys, and the publish step checks each rung's status.
4. **The creator sees the video late.** The delay equals the relay's downtime. No upload is lost.

Change data capture (CDC), which tails the database's commit log, gives the same guarantee with no outbox table.

## Deep dive: paying for egress

Every byte sent toward a viewer is **egress**, billed per gigabyte. With a [CDN](../../scaling/cdn/), an edge pulls a
segment from the origin once and serves it to everyone nearby. Immutable segments suit
[caching](../../scaling/caching/) perfectly.

### Try it

The calculator uses round illustrative prices: $0.05 per GB from the origin and $0.02 per GB from the CDN.

With the defaults, 10M views of 6 minutes at 720p, a 90% hit ratio cuts the monthly bill from $63,000 to $31,500.

<details>
<summary>Go deeper: what the calculator shows, and the long tail</summary>

- **The defaults: 10M views × 6 minutes at 720p.** At 2.8 Mbps that delivers 1.26 PB a month. With a 90% hit ratio, the
  origin serves only 126 TB. The bill falls from $63,000 without a CDN to $31,500 with one: 1,260,000 GB × $0.02 =
  $25,200 for CDN delivery, plus 126,000 GB × $0.05 = $6,300 to fill the edge caches.
- **The ladder choice is a bill choice.** Switch the average bitrate to 1080p, and the same views deliver 2.25 PB. The
  bill scales with the average delivered bitrate, so a higher top rung raises it and a more efficient encoder lowers it.
- **The hit ratio decides whether the CDN pays.** Drag it down. At 40% the CDN breaks even. At 20% it costs more than
  serving from the origin alone, because you pay the CDN for every byte and the origin for every miss.
- **At 0%, the origin sends every byte the viewers get,** and the CDN only adds its own charge on top.
- **Real prices** vary by provider, region, and volume, and large platforms negotiate their own.

**The long tail.** Views on a video platform follow a long tail. A small set of popular videos draws most of the views,
while millions of old or niche videos get a few views each. Popular segments stay hot in every edge. A rarely watched
video misses at the edge almost every time, so its bytes come from the origin. The hit ratio is a property of the
catalog and the audience, and platforms push it up in three ways. They keep long cache lifetimes on immutable segments.
They pre-warm edges with a video they expect to spread. And they add a regional cache tier between the edges and the
origin, so a miss at many edges becomes a single origin fetch.

The player controls the other half of the bill. The top rung, the encoder's efficiency (newer codecs reach similar
quality in fewer bits), and the safety margin in the adaptive rule all set the average delivered bitrate.

</details>

## Trade-offs

<TradeoffTable title="Choices for storing and delivering video">

| Design                                | What it buys                                   | What it costs                                         |
| ------------------------------------- | ---------------------------------------------- | ----------------------------------------------------- |
| One fixed 1080p file                  | One encode, top quality on fast networks       | Stalls whenever bandwidth dips below 5 Mbps           |
| Adaptive bitrate ladder (this lesson) | Few stalls, fast startup                       | Five encodes per video, about twice the stored bytes  |
| Go live at 360p and 720p              | Live after two of five rungs                   | A changing master playlist with a short cache lifetime |
| Outbox for the transcode job          | No video stuck in processing after a crash     | A relay, and duplicate jobs to absorb                 |

</TradeoffTable>

<details>
<summary>Go deeper: more trade-offs, and what this lesson's model leaves out</summary>

| Design             | What it buys                                       | What it costs                                            |
| ------------------ | -------------------------------------------------- | -------------------------------------------------------- |
| Origin plus CDN    | Cheaper bytes near viewers at high hit ratios      | Costs more than origin only at low hit ratios            |
| Multipart upload   | Retries only failed parts                          | Part bookkeeping, more requests, cleanup                 |
| Lazy top rungs     | Less compute and storage for rarely watched videos | New hits play without 1080p until it finishes            |
| Origin only        | No CDN contract to manage                          | Origin prices on every byte; distant viewers wait longer |
| One upload request | Simplest client and server                         | Every drop restarts the upload from zero                 |

- **Scripted bandwidth.** Real networks change in bursts, and throughput also depends on latency, TCP behavior, and
  other apps sharing the phone.
- **Exact segment sizes.** Real encoders vary the bitrate with the content. An action scene takes more bits than a
  static shot, so segments on the same rung differ in size.
- **A basic adaptive rule.** Real players use buffer-based or hybrid algorithms, smooth their estimates, and limit how
  often they switch.
- **A 90 s window.** The duel follows the first 90 s of a longer video, so a player may end the run with segments still
  in its buffer. Near the real end of a video, players stop fetching once the last segment lands.
- **Instant startup once a segment lands.** Real startup also waits on DNS, TLS, the playlist fetches, and the decoder.
- **No codecs, captions, or DRM.** Real platforms encode several codecs, carry separate caption tracks, and protect paid
  content with DRM.
- **Equal segment encodes.** A 1080p segment takes far more CPU to encode than a 240p one, so real fleets plan
  capacity in compute time per rung.
- **Tidy upload drops.** Each drop lands halfway through every transfer in flight. Real drops land anywhere, and real
  clients also handle expired URLs and uploads that never complete.
- **Round prices.** Real egress pricing has tiers, regions, and negotiated rates.
- **Video on demand only.** Live streaming encodes in real time and keeps segments short to cut delay, which changes
  most of the trade-offs above.

</details>

<KeyTakeaways>

- Put the bytes in object storage behind a CDN and the facts in a database. Upload in parts, each verified by an
  explicit checksum.
- Align keyframes across every rung. The master playlist lists rungs, each media playlist lists segments, and the player
  picks a rung per segment.
- Split transcodes at keyframes with pre-roll, go live at 360p and 720p, and add later rungs as they finish.
- Record the transcode job in the status change's transaction, through an outbox or CDC, and make tasks safe to repeat.
- Egress scales with views × minutes × bitrate, and the CDN hit ratio decides how much the origin pays.

</KeyTakeaways>
