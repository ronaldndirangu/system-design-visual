## The failure: the answer above the question

A group of five plans dinner. Ana asks "Thai or pizza?" and Ben answers "Thai!" a moment later. On Chen's phone,
"Thai!" appears first, and the question lands below it. Two minutes later Chen rides through a tunnel. When the signal
returns, the chat looks complete, yet the message with the restaurant address never arrives. Nothing on screen says
anything is missing.

Both bugs come from the same place. The server pushes messages down a pipe it does not fully control: several workers
deliver in parallel, and a phone's connection can die without telling anyone.

## The idea: the server numbers, the phone sorts, the cursor repairs

This case study has one dominant constraint: **every device shows every message of a conversation, in the same order,
even though connections come and go.** The volume is large, yet each message is small and cheap. Order and completeness
are the hard part.

The chat service gives each message a **sequence number** within its conversation, so the order exists in one place. The
phone shows messages in sequence order and holds back any that arrive early, in a **reorder buffer**. Heartbeats detect
sockets that died silently. When a phone reconnects, it sends a **cursor**, the sequence number of the last message it
showed, and the server replays everything after it from the **message log**. One server owns each conversation and
picks its numbers. The [Time, leases, and fencing](../../distributed-data/time-leases-fencing/) lesson shows how a new
owner takes over without a paused one writing duplicates.

## Walk the design checklist

The seven steps from the [design checklist](../../thinking/design-checklist/), applied to a chat service.

<Steps>

1. **Requirements.** One-to-one and group chats of up to a few hundred members. A message reaches an online reader within
   a second. Every device shows a conversation in the same order. A phone or laptop that was offline catches up with
   everything it missed. Calls, media, search, and end-to-end encryption stay out of scope.

2. **Estimates (illustrative).** Fifty million daily users who send 40 messages each make **2 billion messages a day**,
   about **23,148 per second** on average and **69,444 per second** at a 3× peak. Each message reaches 5 readers on
   average, so the push side handles about **347,222 deliveries per second** at peak. If 40% of users are online at peak,
   that is **20 million open sockets**, and at 100,000 sockets per gateway, **200 gateway servers**. A heartbeat every
   30 s on each socket adds **666,667 heartbeats per second**. At 200 bytes a message, the log grows by about **400 GB a
   day**. (See [requirements and estimates](../../thinking/requirements-and-estimates/) for the method.)

3. **API.** The phone opens a long-lived socket (`wss://chat.example/ws`). It sends
   `send {conversation, clientMessageId, text}` and gets back `ack {sequence}`. The server sends
   `message {conversation, sequence, sender, text}`, and both sides trade `ping` and `pong`. Catch-up uses plain HTTP:
   `GET /conversations/{id}/messages?after=29&limit=100`. Read receipts post `POST /conversations/{id}/read {upTo}`.

4. **Data model.** A `messages` table keyed by `(conversation_id, sequence)`, with the sender, the client message ID
   (unique per sender, to drop resends), the text, and the time. A `members` table holds each member of a conversation
   with the highest sequence they have read. A `conversations` table holds each conversation's last sequence and the
   epoch of the server that owns it. Each device keeps its own cursor per conversation. Shard by conversation ID (see
   [sharding](../../scaling/sharding/)), so one conversation's counter and log live on one shard.

5. **High-level design.** Gateways hold sockets and know nothing about chats. The chat service numbers messages, writes
   them to the log, and publishes them. Push workers read the topic and route each message to the gateways that hold its
   readers' sockets, using a presence map of who is connected where. A load balancer spreads new sockets across gateways
   by connection count (see [load balancing](../../scaling/load-balancing/)). The [Real-time transport](../../foundations/real-time/) lesson compares
   sockets, server-sent events, and long polling, and the [Logs and pub/sub](../../async/logs-and-pubsub/) lesson covers the topic in the middle.

6. **Deep dive: order and gaps.** This is where the design breaks first, and both simulations below live here. Parallel
   push workers reorder messages, and a socket that died silently swallows them. Sequence numbers fix the first, as
   long as the server never hands out a number without storing its message. Cursors fix the second.

7. **Trade-offs.** One push path or many, the heartbeat interval, and server-side queues or a replayable log. The table at
   the end of this page lays them out.

</Steps>

cannot assume that, so it also runs a gap timer; the failure walkthrough below shows why.

## Number messages safely

The reorder buffer trusts one promise from the server: every sequence number it hands out belongs to a message in the
log. Break that promise and every phone in the conversation waits for a message that does not exist.

The obvious shortcut breaks it. Take the next number from a separate counter (an `INCR` in a cache), then write the
message to the log. A crash between the two steps burns sequence 42 with nothing stored under it, and a send retried
after the crash takes a fresh number, so the same text can appear twice. Instead, allocate and append in one
[transaction](../../foundations/transactions/) on the conversation's shard:

```sql
WITH next AS (
  UPDATE conversations
     SET last_sequence = last_sequence + 1
   WHERE id = 'c-981' AND owner_epoch = 7
  RETURNING last_sequence
)
INSERT INTO messages (conversation_id, sequence, sender_id, client_message_id, text)
SELECT 'c-981', last_sequence, 'ana', 'm-5521', 'Thai or pizza?' FROM next;
```

Three rules make this safe:

- **Both writes or neither.** The counter moves only if the message lands. A crash rolls back both, so the log never
  holds a number without its message.
- **A unique key catches resends.** `(conversation_id, sender_id, client_message_id)` is unique. A resend violates it,
  the whole statement rolls back, counter included, and the service answers with the sequence already stored.
- **Ack after commit.** The server sends `ack {sequence}` only once the commit returns, then publishes the message to
  the topic. An earlier ack would let a crash erase a message the sender already saw as delivered.

One chat server owns each conversation at a time, so it numbers and publishes messages in order to one partition. If
the owner stalls, say in a long garbage-collection pause, a coordinator hands the conversation to another server and
raises `owner_epoch` from 7 to 8 (the [Raft](../../distributed-data/raft/) lesson shows how a group agrees on such a
handover). When the old owner resumes, its update still says `owner_epoch = 7`, matches 0 rows, and inserts nothing.
The epoch works as a **fencing token**, the same guard the [idempotency](../../reliability/idempotency/) lesson uses
when a paused server wakes after its lease ran out.

## Heartbeats and silent disconnects

A phone that enters a tunnel does not hang up. Its radio just stops, so the server's socket stays open and accepts writes
that go nowhere. The gateway learns about it only when something it expects stops arriving. That is the job of the
heartbeat: if no ping arrives within a timeout, the gateway closes the socket and marks the phone offline.

A short timeout finds dead sockets sooner, at a price. At the illustrative scale above, cutting the heartbeat interval
from 30 s to 10 s triples the load to **2 million heartbeats per second** and wakes every phone's radio three times as
often. Any timeout leaves a window in which the server pushes into a socket that is already dead.

A cursor needs a log to read from. Keep each conversation's messages, numbered, for as long as a device might stay
offline, and a phone or laptop of any age can resync with one question. A device asleep longer than the log keeps
messages needs a full resync. When a gateway restarts, its 100,000 phones reconnect at once and all ask for catch-up, so
phones wait a random moment before reconnecting. The [Retries with backoff and jitter](../../reliability/retries/) lesson covers that spread.

<summary>Go deeper: one person, two devices</summary>

Mia reads a long conversation on her phone during a week away, while her laptop sleeps. When the laptop wakes, it must
show every message in order with unread badges that match the phone, and the server keeps no per-device queues. Store
each conversation once, and let each device carry its own cursors.

- **One log per conversation:** messages live in `messages`, keyed by `(conversation_id, sequence)`, with no copy per
  device. Keep them as long as a device may stay away, say 30 days, and fall back to a full resync after that.
- **A cursor per device per conversation:** the laptop remembers the last sequence it showed in each conversation. On
  wake it asks for everything after each cursor, newest conversations first, 100 messages a page, and shows them in
  sequence order.
- **Read state as a number:** `members.read_up_to` stores the highest sequence Mia has read. The phone raises it as she
  reads, and the laptop fetches it on wake, so unread counts are the difference between the latest sequence and
  `read_up_to`. A higher value always wins, so two devices can never move it backwards.
- **Wake the laptop gently:** while the laptop sleeps, a notification at most nudges it. Once awake it opens a socket and
  syncs, with a random delay so a fleet of laptops waking at 9:00 does not reconnect at the same instant.

</details>

## Failure walkthrough: the owner crashes before it publishes

Chen's phone has shown Ana's group up to message 41. Ana sends the restaurant address, and the server that owns the
conversation crashes a moment later. Here is what each guard does.

1. **0 s: 42 commits, then the owner dies.** The address commits as 42 in one transaction, and Ana's phone gets
   `ack {42}`. The owner crashes before it publishes 42 to the topic, so the log holds 42 and no push worker ever sees
   it.
2. **5 s: a new owner takes over at epoch 8.** The old owner's lease runs out, and the coordinator hands the
   conversation to another server with `owner_epoch` 8. The new owner cannot tell whether 42 reached the topic, so it
   republishes the newest messages it inherits, here 42. Sends during the handover got no ack, so phones resend them
   with the same client message IDs. Ben's reply commits as 43 and goes out to the topic.
3. **5.3 s: Chen's phone holds 43 and starts a gap timer.** The republished 42 meets a stalled push worker, so 43 lands
   first. The buffer holds it and starts a 2 s timer. Transport keeps moving: 44 and 45 arrive and wait behind the gap
   too.
4. **7.3 s: the timer fires, and the log fills the gap.** The phone calls
   `GET /conversations/{id}/messages?after=41`, and the server replays 42 through 45. The phone keeps one copy of each
   sequence and shows all four in order, address first. When the stalled copy of 42 lands later, the phone drops it.

Each guard covers one gap. The single transaction means the log never holds a number without its message, so the replay
always finds 42. Ack after commit means Ana's phone marks 42 as sent only once the log holds it. If the old owner was
only paused, the epoch stops it when it wakes: its update matches 0 rows. The republish covers a quiet conversation,
where no later message would expose the gap. The gap timer bounds the wait: transport progress stays independent while
ordered display waits for gaps, for 2 s at most before the phone asks the log. Set the timer a little above a normal
race. In the busy-group run no message waited longer than 1.7 s, and a timer that fires on a plain race costs one extra
read, since the phone drops duplicates by sequence. The simulation's buffer has no timer: every late message in it does
arrive, so it simply waits for the late copy.

## Chat versus notifications

[Notifications](../notifications/) is the other half of this pair. Both deliver short messages to people's devices, and
they guard different things.

| Question           | Chat                                                   | Notifications                                             |
| ------------------ | ------------------------------------------------------ | --------------------------------------------------------- |
| Who owns delivery? | Your gateways, over sockets you hold open              | External providers (push services, SMS, email)            |
| What must hold?    | Order within a conversation, and nothing missing       | Arrival before a deadline, within the user's choices      |
| What goes wrong?   | Messages overtake each other or vanish in dead sockets | A provider throttles or fails, and the code expires       |
| The guard          | Sequence numbers and a cursor into a replayable log    | Priority lanes, deadlines, and failover between providers |
| Late is…           | Fine, if the order is right                            | Often worthless: a login code that arrives late is junk   |

Chat systems use notifications too: when the app is closed, the server asks the phone's push service to wake it, and the
phone then opens its socket and catches up with its cursor.

## Trade-offs

<TradeoffTable title="Designing a chat service">

| Choice                                 | What it buys                                             | What it costs                                                        |
| -------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------- |
| One push path per conversation         | Order with no work on the phone                          | One stall delays every message behind it                             |
| Parallel paths and a reorder buffer    | Independent transport progress: a stall slows one worker | Ordered display still waits for gaps, so the phone needs a gap timer |
| Counter and message in one transaction | A sequence number never exists without its message       | Every send locks the conversation row, which caps a hot group        |
| Short heartbeat timeout                | Dead sockets found within seconds                        | Battery, radio wakeups, and heartbeat load on every gateway          |
| Long heartbeat timeout                 | Cheap, quiet connections                                 | A longer window of pushes into dead sockets                          |
| Queue on the server per device         | Simple push on reconnect                                 | Storage per device, and anything pushed into a dead socket is gone   |
| Per-conversation log and cursors       | Any device resyncs, and lost pushes come back            | Each device tracks cursors, and mass reconnects spike reads          |

</TradeoffTable>

<KeyTakeaways>

- The server numbers each conversation, and every phone sorts by that number. Phone clocks and arrival order cannot
  settle who spoke first.
- Parallel push paths keep transport progress independent, while ordered display still waits for gaps. A gap timer
  bounds that wait by asking the log for the missing numbers.
- Allocate the sequence and append the message in one transaction, fence a stale owner with an epoch, and ack only
  after commit, so no number ever exists without its message.
- Heartbeats find a dead socket only after a window of lost pushes. A cursor per device into the conversation log
  recovers every message from that window.

</KeyTakeaways>

**The gateways' push budget breaks first.**

- **The new numbers.** Messages stay at 69,444 per second at peak, and the log still grows about 400 GB a day,
  because a group message is stored once. Sockets and heartbeats stay the same. Deliveries grow tenfold, to about
  3,472,222 per second: about 17,361 per gateway, 3.5 times the 5,000 a gateway can push. Today each gateway pushes
  about 1,736. Presence lookups grow tenfold with the deliveries.
- **The change.** Two options, often combined. Grow the fleet to about 868 gateways, which keeps 20% headroom over the
