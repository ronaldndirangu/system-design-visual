## The brief

You built sho.rt piece by piece in Module 2. This case puts every piece under load at once, and you make the calls.
Work each step on paper first. A reference answer sits under each step, folded away.

**What sho.rt must do**

- Turn a long URL into a short code, and answer each click with a 302 redirect.
- Count clicks per link for the owner's dashboard.
- Let a creator open a new link the moment they make it.
- Keep serving when one app server dies.
- Serve readers in a new region as fast as readers at home.

**The numbers**

| Constraint         | Target                                         |
| ------------------ | ---------------------------------------------- |
| New links          | 100 per second                                 |
| Redirects          | 10,000 per second on average, 50,000 at peak   |
| Link record        | About 500 bytes, kept for 5 years              |
| Redirect latency   | p99 under 100 ms for readers in both regions   |
| Click counts       | Visible on the dashboard within a minute       |
| One server lost    | No server above 85% busy afterward             |

## The failure: one link goes viral

At 7:58 p.m., a sports star posts sho.rt/abc1234 to 40 million followers. Clicks on that one code climb from zero to
20,000 a second in under a minute. The cache holds the link, so the first wave goes fine.

At 8:03 p.m., the cache entry's TTL runs out. Every app server misses at once, and each miss reads the database. The
replica serving those reads stalls, every other code's misses queue behind it, and redirects across the whole site slow
to seconds. Nothing broke. One popular key turned an ordinary expiry into a flood.

## The idea: every layer guards the next

A redirect passes through four layers: CDN edge, app pool, cache, and database. Each layer exists to shield the one
behind it. The design work is sizing each shield and planning what happens when it fails: an entry expires, a server
dies, or a region starts cold.

## Step 1: Size the traffic

Start with the brief's numbers. Work out total storage after five years, how many base62 characters a code needs, how
many reads reach the database at a 90% cache hit rate, and how many replicas serve them. Use
[the caching lesson](../../scaling/caching/) for hit rates.

<details>
<summary>Show one possible answer</summary>

- **Links**: 100 per second × 86,400 × 365 × 5 ≈ 15.8 billion. At 500 bytes each, that is about 7.9 TB.
- **Code length**: 62⁶ ≈ 56.8 billion, so six characters would be 28% full by year five, and random codes would
  collide often. 62⁷ ≈ 3.5 trillion keeps it under 0.5%. Use seven.
- **Database reads**: 50,000 redirects at a 90% hit rate leave 5,000 reads a second.
- **Replicas**: at 2,000 reads a second each, four replicas give 8,000. Losing one leaves 6,000, still above 5,000.

</details>

## Step 2: Spread the redirects

Each app server handles about 4,500 redirects a second before it slows. Pick a pool size for the 50,000 peak, then run
the N+1 check: if one server dies, the survivors each carry u × N ÷ (N − 1). Three servers at 70% leave each survivor at
105%. Ten at 70% leave each at 77.8%.

<details>
<summary>Show one possible answer</summary>

- 50,000 ÷ 4,500 ≈ 11 servers at 100%, which is too hot. At 70% each server takes about 3,150, so 50,000 ÷ 3,150 ≈ 16.
- **N+1**: 70% × 16 ÷ 15 ≈ 74.7%. One loss keeps every survivor under the 85% target.
- Spread the 16 across at least two zones so one zone outage does not take half the pool.

</details>

## Step 3: Absorb the viral link

One code takes 20,000 clicks a second. Plan three things: stop the stampede when its cache entry expires, keep the edges
from all missing at once, and keep its click counter from melting one shard. Review
[when the cache misses at once](../../scaling/caching/#when-the-cache-misses-at-once) and
[hot keys](../../scaling/sharding/#hot-keys-hot-reads-and-hot-writes).

<details>
<summary>Show one possible answer</summary>

- **Stampede**: single flight per app server caps a miss at 16 reads. Add TTL jitter so hot keys never expire
  together, and serve stale while one request refreshes.
- **Edges**: cache the 302 at the edge for 60 seconds. An
  [origin shield](../../scaling/cdn/#origin-shield-one-cache-in-front-of-the-origin) collapses misses from every edge
  into one origin request.
- **Counter**: salt the hot counter into 8 parts, abc1234#0 to #7, and have each app server batch its counts once a
  second. The dashboard trails by a second, well inside the one minute target.
- **Edge clicks**: edges answer most clicks, so count from edge logs. Sending no-store instead makes every click pay
  the origin trip.

</details>

## Step 4: Lose an app server

At peak, one of the 16 servers crashes just after a health check passes. Checks run every 5 s, and three failures mark
it down. Count the failed requests, then shrink that number.

**About 47,000.** The balancer keeps sending the dead server its 1/16 share, 3,125 requests a second, for 15 s.

Review [plan for a crash](../../scaling/load-balancing/#plan-for-a-crash) before you open the answer.

<details>
<summary>Show one possible answer</summary>

- **Outlier detection** ejects a server after a short run of failed responses, often within a second.
- **Retry once on another server.** A redirect is a GET with no side effects, so the balancer can send it again.
- **Least requests with two random choices** caps a broken server at about twice its share while it still looks idle.
- Together these cut 47,000 failures to a few thousand, and the retry hides most of those.

</details>

## Step 5: Serve a new region

sho.rt opens to readers in a region 180 ms from the origin. Decide what the edges cache and for how long, how the origin
copes with every edge warming up alone, and how a creator in that region opens a link they just made. Review
[freshness tokens](../../scaling/read-replicas/#freshness-tokens-read-your-writes-and-monotonic-reads).

<details>
<summary>Show one possible answer</summary>

- **Edges**: regional edges answer cached 302s in a few milliseconds. Misses still cross to the origin once.
- **Shield**: each edge warms alone, so put a shield in front of the origin to merge their misses.
- **Regional replica**: a replica in the region answers edge misses in 10 ms. It trails the primary by a little.
- **Read your writes**: the create call returns a freshness token. The regional replica waits for that position or
  forwards the read to the primary.
- **Short negative TTL**: cache a 404 for a few seconds at most, or an early click pins the miss at the edge.

</details>

## Step 6: Where the data lives

Year one holds about 1.6 TB, and year five 7.9 TB. Decide when to shard, what key to shard on, and whether to place
keys by range or by hash. Review [range or hash placement](../../scaling/sharding/#range-or-hash-placement).

<details>
<summary>Show one possible answer</summary>

- **Year one**: one primary and four replicas hold 1.6 TB and serve 8,000 reads a second.
- **Shard before the primary passes about 2 TB**, around year two, so backups and rebuilds stay quick.
- **Key**: the code. Every redirect reads exactly one code, so every read hits one shard.
- **Placement**: hash. Random codes would spread evenly under range placement too, so either works today. Hash keeps
  load even if sho.rt ever moves to counter or time ordered codes, where range placement would send every new link,
  and most new clicks, to the newest shard.

</details>

## Reading your score

Count your solid answers. Four or more means you can carry Module 2 into an interview. Two or three means the pieces
are there and the numbers need practice: redo Steps 1 and 2 with the [capstone](../../practice/capstone/) brief. Fewer
than two means a lesson needs another pass. Step 3 maps to caching and sharding, Step 4 to load balancing, and Step 5

Common misses: forgetting that edge hits never reach the click counter, sizing a pool that fails the N+1 check, and
caching a 404 long enough to hide a brand new link.

## Trade-offs

<TradeoffTable title="Choices sho.rt made at scale">

| Choice                          | What it buys                                 | What it costs                                    |
| ------------------------------- | -------------------------------------------- | ------------------------------------------------ |
| Cache the 302 at the edge       | Fast clicks worldwide, a quiet origin        | Clicks you must count from edge logs             |
| Single flight per server        | A hot miss costs at most 16 reads            | Waiters share one slow read                      |
| Salted, batched click counters  | Hot writes spread across shards              | Reads gather 8 parts, and counts trail a second  |
| 16 servers for a 50,000 peak    | One loss keeps survivors under 75%           | Idle capacity most of the day                    |
| Freshness tokens                | Creators see their own links at once         | Some reads wait or travel to the primary         |
| Hash placement on the code      | Even load whatever the code scheme           | No cheap range scans by code                     |

</TradeoffTable>

<KeyTakeaways>

- Size first: 15.8 billion links, 7.9 TB, 7 base62 characters, and 5,000 database reads a second at peak.
- One hot key turns a cache expiry into 1,000 database reads. Single flight, jitter, and stale reads stop it.
- Run the N+1 check on every pool: u × N ÷ (N − 1) must stay well under 100%.
- Health checks alone fail about 47,000 requests at peak. Outlier detection and one retry shrink that.
- Edges, a shield, and a regional replica serve a new region. Freshness tokens keep a creator's own link readable.

</KeyTakeaways>
