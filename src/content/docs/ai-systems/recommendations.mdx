## The idea: a funnel

A recommendation system narrows the catalog in stages. **Candidate generation** uses cheap sources to pull a few
hundred plausible items from millions. **Ranking** scores only those with an accurate, expensive model. Eligibility
rules run before ranking, and a live stock check and a re-rank pick the final handful. The stages split because no
model is both cheap enough for millions of items and rich enough to order them well. YouTube's recommender (RecSys
2016) uses the same shape.

<StepDiagram client:visible title="From 3,000,000 items to five" nodes={nodes} edges={edges} steps={steps} height={300} />

<Analogy>

Hiring five people for a busy store. A quick resume screen cuts 3,000 applicants to a few hundred, interviews rank
those carefully, reference checks remove anyone who cannot start, and the manager picks five across teams. If the
screen rejects the best applicant, no interview brings them back.

Where it breaks: a store screens once, while a recommender reruns the screen for every customer in milliseconds, so
the screen must be a precomputed lookup.

</Analogy>

Every row balances: items in equals items out plus items dropped. Lookups remove almost everything in 9 ms.

### Recall caps quality

- **The ranker orders what it receives.** An item missing from the candidates never gets a score, so candidate recall
  caps final quality.
- **Measure recall at the candidate stage.** Here 8 of 9 known good items survive. The RV fresh water hose sits at
  rank 900 among embedding neighbors, past the 300 kept.
- **Filter for eligibility before ranking, and keep spares for live checks.** The ranker never scores an item this
  customer cannot buy, the same rule as tenant scoping in [retrieval](../retrieval/). It keeps 15 for five slots, so
  the stock and diversity checks still leave a full list.

<details>
<summary>Go deeper: fixing misses and precomputing sources</summary>

**Fix missed items at the source.** When candidate recall drops, add a source that sees a different signal, or give
the source that finds the missed items a bigger share of the budget. A heavier ranker cannot help, because it never
sees those items. Each source covers a gap: the hose and reel cart arrives only through bought together, because its
text and vector look nothing like a hose.

**Precompute the sources.** Embeddings, bought together lists, and category best sellers come from background jobs,
and the request only looks them up. This is [caching](../../scaling/caching/) applied to recommendations, with the same
cost: the lists go stale between refreshes, so new items and stock changes lag until the next run. Live checks after
the ranker cover the facts that change by the minute.

</details>

Why 500 candidates, instead of 50 or 5,000? Two curves decide. **Recall**, the share of the 9 known good items that
reach the ranker, climbs fast and then flattens. **Ranker time** grows in a straight line. Drag the slider.

candidates. Measure both curves on real traffic.

## Embeddings, cold start, and feedback loops

### Two towers turn candidate generation into a lookup

An **embedding** is a vector that places similar things close together. A **two-tower model** has a user tower, which
turns the request (customer, history, current item) into a vector, and an item tower, which turns each item into a
vector in the same space. Training pulls clicked pairs together, so a dot product scores a match.

Because the towers never see a user and an item together, a background job can embed the whole catalog into an
approximate nearest neighbor (ANN) index. Each request runs the user tower once and fetches the closest few hundred
items, typically in a few milliseconds. The cost: the towers miss cross features such as "fits this customer's hose
reel," so the ranker adds them.

### Cold start

A new customer has no history, so fall back on the current item, its category, popular items, and onboarding choices.
A new item has no clicks, so an item tower that learns only from item ids gives it a meaningless vector. Feed the item
tower content features (title, description, category, price), and a new item gets a useful vector on day one.

### Feedback loops and exploration

The model learns only from clicks on what it showed. Top items collect clicks and climb, unseen items never earn one,
and the logs cannot reveal what the list missed. **Exploration** breaks the loop: reserve a small share of slots,
typically a few percent, for new or uncertain items, and log which slots explored, so those clicks become fair
training data.

<details>
<summary>Go deeper: training the two towers</summary>

**Negatives.** Training needs items the user did not pick. Scoring every catalog item for each example is too slow, so
a common trick uses the other items in the same training batch as negatives. Popular items show up in many batches and
get pushed down too often. Yi et al. (RecSys 2019) estimate how often each item appears in the training stream and
correct each score for it, and they feed content features into the item tower, which helps fresh items.

**ANN recall.** An approximate index trades a little recall for a lot of speed. Typical settings return 90 to 99% of
the exact nearest neighbors. Measure that loss like any other candidate source.

**YouTube's version.** Covington et al. (RecSys 2016) train candidate generation as a classifier over millions of
videos, then serve it as a nearest neighbor search over the learned video vectors, the same split described above.

</details>

<details>
<summary>Go deeper: bandits, replay, and position bias</summary>

**Contextual bandits.** A fixed random share wastes slots on items that are clearly poor. A contextual bandit picks
each exploratory item from the request context and its own uncertainty: it shows an item when the expected click rate
is high or when it knows little about that item. Li et al. (WWW 2010) ran this as LinUCB on Yahoo front page news.

**Offline replay.** The same paper evaluates a new policy on logged traffic in which articles were shown at random. It
keeps only the events where the new policy would have picked the article that was shown. This works only when some
traffic was random, which is another reason to log exploration.

**Position bias.** People click the first slot more often whatever it holds, so raw click rates overrate top slots. Log
the position with every impression, and train with position as an input that serving fixes to one value, or weight
clicks by how often each position gets looked at.

</details>

## Trade-offs

<TradeoffTable title="Designing a recommendation funnel">

| Choice | What it buys | What it costs |
| --- | --- | --- |
| More candidates | Higher recall | Ranker time grows with every candidate |
| Several sources | Items one signal misses arrive through another | More pipelines to build and merge |
| Heavy ranker | Better order at the top | Fewer candidates fit the budget |
| Two-tower embeddings | One ANN lookup covers the catalog | No cross features, so the ranker adds them |
| Precomputed sources | Fast lookups | Stale lists until the next refresh |
| Exploration slots | Data on new items and a way out of the feedback loop | A few weaker items shown today |

</TradeoffTable>

Skip the funnel when the ranker can score the whole catalog in budget: at an illustrative 10 microseconds per item,
50 ms covers about 5,000 items.

## Common mistakes

- **Tuning the ranker when recall is the bottleneck.** No ranker can show an item it never sees.
- **Filtering eligibility after ranking.** Items the customer cannot buy take ranked slots, and the list comes up short.
- **Training only on logged clicks.** The list narrows to what it already showed. Reserve exploration slots.
- **Giving new items only an id embedding.** Feed content features to the item tower.

<KeyTakeaways>

- A funnel: cheap candidate generation narrows millions to hundreds, an accurate ranker orders them, and filters pick
  the handful.
- Candidate recall caps final quality.
- Size the candidate count where recall flattens and ranker time still fits.
- Run eligibility before ranking, and keep spares for live checks.
- Two towers make candidates a lookup, content features handle cold start, and exploration breaks the feedback loop.

</KeyTakeaways>
