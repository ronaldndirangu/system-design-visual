## The failure: a prototype that works in the demo

A software company hosts support assistants for small shops. Two of them share the system: **Harbor Bikes** and **Pine
Street Books**. The team builds a prototype in a week. It searches every document it has, asks the model, caches the
answer by question text, and lets the model call a refund tool. In the demo, every answer looks great.

Then the first week of real traffic arrives. A Pine Street customer asks about returns and gets Harbor's 30 day bike
policy. Another Pine customer asks about bike frames and gets Harbor's warranty. A Harbor customer asks how refunds get
flagged and reads the staff only review rules.

Nothing in the prototype is broken in the usual sense. Every part does exactly what it was built to do. The design just
never decided who may see what, what counts as evidence, who approves money moving, or who pays for the model.

## Walk the design checklist

The [design checklist](../../thinking/design-checklist/) works for an AI product the same way it works for a URL
shortener. Each step below names the earlier lesson in this module that it draws on.

### 1. Requirements

- Answer customer questions about returns, delivery, warranties, and orders from **that store's** documents only.
- Staff can also read **staff only** documents. Customers never see them.
- Every answer **cites** the documents it used.
- When evidence is weak or a check fails, **hand off** to a person instead of guessing.
- **One action:** request a refund. A person approves it, and it never runs twice.
- A **fixed model budget** per day, shared fairly so one busy store cannot starve another.
- Out of scope: changing orders, editing accounts, and any other tool.

The [evaluation and budgets](../evaluation-and-budgets/) lesson turns these into an eval set before any model is
chosen. The must decline cases here are concrete: another store's policy, a staff only rule, and a refund the policy
forbids.

### 2. Estimates

All numbers are illustrative. Use the [requirements and estimates](../../thinking/requirements-and-estimates/) habit to
make your own.

- 500 stores ask 40,000 questions a day: about 0.5 per second on average, or about 1.4 per second at a 3x peak.
- Each question sends about 2,000 input tokens (instructions, the question, and retrieved chunks) and gets about 200
  output tokens back. That is 80 million input tokens and 8 million output tokens a day.
- 500 stores with 300 documents each, cut into about 20 chunks per document, is 3 million chunks. A 1,024 dimension
  embedding stored as 4 byte floats takes 4 KB, so the vectors need about 12 GB before index overhead.

Requests per second are small. The pressure sits on tokens, which set cost and latency, and on keeping 500 stores'
documents apart in one index.

### 3. API

- `POST /v1/assist` takes `{ question, conversation_id }`. The store and the role come from the sign-in token, never from
  the body and never from the model.
- It returns `{ outcome, answer, citations }`, where `outcome` is `answered` or `handoff`. A handoff tells the customer a
  person will reply and gives them a ticket number.
- The refund tool takes `{ order_id, amount, reason }` with an `Idempotency-Key` header. It refuses any call that a
  person has not approved.

### 4. Data model

- **Documents and chunks** carry `store_id` and `visibility` (`public` or `staff`). Search filters on both inside the
  query, before ranking, as in [retrieval](../retrieval/).
- **Answer cache:** key `store | role | prompt version | question`. Values expire, and a document change clears that
  store's entries.
- **Budget ledger:** units spent per store per day, checked before each model call, as in the
  [AI gateway](../gateway/).
- **Refunds:** keyed by idempotency key, with the order, amount, approver, and result.
- **Traces:** for every request, the stages it visited, the chunks retrieved, the citations, and the outcome. These feed
  the eval set when something goes wrong.

### 5. High-level design

<StepDiagram client:visible title="The guarded support assistant" nodes={nodes} edges={edges} steps={steps} height={300} />

The model sits in the middle, and code surrounds it on both sides. Code decides who is asking and what the model may
read before the call. Code checks what the model wrote and what it may do after the call. The model itself runs behind
a serving layer like the one in [serving models](../llm-serving/), where batching and KV cache memory set throughput.

<Analogy>

A bank branch. The front desk checks your ID before anything else (the gateway). A teller can only open your branch's
files (filtered search), quotes the rule they are reading from (citations), and calls a manager when the rulebook has no
answer (handoff). Paying out money needs a supervisor's signature and a receipt number, so the same slip cannot be
cashed twice (approval and an idempotency key). Each branch has its own daily cash limit, so a rush at one branch cannot
empty the vault for the others (per store budget).

</Analogy>

### 6. Deep dive: four ways it breaks

Each scenario in the widget is one deep dive. Run them in order.

**Tenant leak probe.** The prototype leaks four times: two shared cache hits, one cross-store search hit, and one staff
only document. The guarded design answers 4 and hands off 2. Its two handoffs (the Pine bike question and the Harbor
customer asking about refund flags) find nothing above the evidence gate once search is filtered, so they cost no model
units. Notice the cache: the guarded lane gets 1 hit instead of 2, because Pine can no longer reuse Harbor's answer.

**Weak evidence.** The prototype answers all 5, and 3 of them state things no document supports: a promise about
signed first editions, a price match, and a student discount. The guarded design hands off W2 (best score 0.52) and W3
(0.41) before the model runs. W5 scores 0.62, just above the gate, so the model runs, and its answer cites
pine/student-discount, a document search never returned. The citation check catches it. Result: 2 answered, 3 handed
off, and 9 units spent instead of 15. This is the abstention path from [retrieval](../retrieval/).

**Refund requests.** The model asks for a refund on all 4 requests. The prototype runs all of them and pays out $697 it
should not have: a second $45 for a double submit, a $12 ebook the policy calls final sale, and a $640 bike outside the
return window. The guarded design sends the first three to staff, who approve one and decline two. The fourth carries
the idempotency key `refund:2201`, so the tool returns the first result and moves no money. Staff touch 3 requests
instead of 0. That trade is the point of [agents and tools](../agents/): a model may propose an action, and code plus a
person decide whether it runs.

each store strands 1 unit it cannot use, and Harbor refuses three recall questions while Pine has nothing left to ask.
The usual fix is a guaranteed share per store plus a small shared burst pool, so a spike can borrow without starving
anyone.

### 7. Trade-offs

<TradeoffTable title="Guards in the support assistant">

| Choice | What it buys | What it costs |
| --- | --- | --- |
| Cache key with store, role, and prompt version | No cached answer crosses stores or roles, and a prompt change cannot serve stale answers | Fewer hits: 1 instead of 2 in the leak probe |
| Store and visibility filter inside search | Other stores' chunks and staff only rules never reach the model | Every chunk needs the right tags, and a missing tag hides a document |
| Evidence gate (hand off below 0.6) | Weak questions reach a person instead of a guess | Fewer automatic answers, and the threshold needs tuning on your eval set |
| Citation check after the model | Catches answers that cite something search never returned | The model call is already paid for, and a strict check rejects some good answers |
| Staff approval on every refund | No refund runs against policy | Staff time on every refund, and customers wait for a person |
| Idempotency key on the refund tool | A double submit returns the first result | A table of keys, and a careful choice of what counts as the same refund |
| Budget split per store | One store's spike cannot starve another | Unused share sits idle unless you add a shared burst pool |

</TradeoffTable>

None of the guards makes the model smarter. Each one changes what the model may see, what leaves the system, or who
decides. That is why the same fixture outputs produce zero harms in one lane and many in the other.

## What this design leaves for later

- **Evaluation in production.** Every handoff and every failed check becomes a new eval case, so the
  [evaluation and budgets](../evaluation-and-budgets/) loop keeps running after launch.
- **Routing and fallbacks.** The [AI gateway](../gateway/) can send easy policy questions to a smaller model and fall
  back when a provider is slow.
- **Suggested articles.** Showing "customers also read" help articles is a ranking problem, covered in
  [recommendation systems](../recommendations/).
