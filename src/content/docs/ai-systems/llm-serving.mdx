chat turn at a time. On Monday morning the queue grows faster than it drains, yet the GPU's math units sit mostly idle:

## The idea: fill every step, and budget memory per token

A model answers in two phases. **Prefill** reads the whole prompt in one pass and produces the first token. **Decode**
then adds one token per step, using the keys and values of all earlier tokens, which the server keeps in the
**KV cache**. A **scheduler** picks which requests run in each step, and **continuous batching** (iteration-level
scheduling) lets it add or drop a request at every step.

<StepDiagram client:visible title="One scheduler step at a time" nodes={nodes} edges={edges} steps={steps} height={300} />

<Analogy>

Picture a shuttle with four seats. Static batching runs it as a tour bus that returns only when the longest tour ends,
so riders who leave early leave empty seats. Continuous batching runs it as a tram: each freed seat goes to the next
person on the platform. Each rider's luggage (the KV cache) grows at every stop, and when the rack is
full, the last rider to board steps off and boards again later.

Where it breaks: a rider knows their stop on boarding. A request learns its length only at its last token, so the
scheduler cannot plan ahead.

</Analogy>

## Prefill, decode, and memory per token

Each step moves bytes (all the weights, plus every cached key and value) and does math (a pass through the weights for
each token in the step). The GPU overlaps the two, so the slower one sets the step. This is the **roofline** view:
step time = max(memory time, compute time).

Decode adds one token per request yet reads every weight, so at small batches it is **memory-bandwidth bound**, and
batching shares that read. Prefill pushes a whole prompt through each weight. Up to the **ridge** (256 tokens in the
toy model) the step stays at 10 ms. Past it the step turns **compute bound**: 512 prompt tokens take 18 ms and 1,024
take 34 ms.

Users feel two latencies: **time to first token (TTFT)**, which is queue wait plus prefill, and **time per output token
(TPOT)**, mostly the decode step. A bigger batch raises throughput and lengthens every step.

Memory sets the other limit. Llama 3 8B stores **128 KiB of KV cache per token**, so an 8,192-token conversation takes
1 GiB. KV memory usually runs out before math does, which caps how many requests run at once.

From 1 to 128 requests, the toy model's step time grows 2.9 times while its throughput grows 44 times. Then the gain
flattens: doubling from 128 to 256 adds about a fifth more throughput, and each request now waits 48.4 ms per token
instead of 29.2 ms. Real servers show the same shape. In Databricks' measurements of a 7B parameter model, a batch of
64 gave about 14 times the throughput of a single request for about 4 times the latency. Once a step is compute bound,
a bigger batch only adds latency.

This toy model gives each decoding request a fixed cost. In a real server that cost grows with context length, because
every step reads every cached token of every request, so long conversations make big batches slower than shown here.

</details>

<details>
<summary>Go deeper: KV cache arithmetic</summary>

Each token stores a key and a value for every layer and every KV head. For Llama 3 8B (32 layers, 8 KV heads, 128
values per head, 2 bytes per value):

2 (key and value) × 32 layers × 8 KV heads × 128 values × 2 bytes = 131,072 bytes = **128 KiB per token**

| Amount | KV cache memory |
| --- | --- |
| 1 token | 128 KiB |
| 1 block of 16 tokens | 2 MiB |
| 1 conversation of 8,192 tokens | 1 GiB |
| 20 GiB of KV memory | 163,840 tokens in any mix |
| Same model without grouped-query attention (32 KV heads) | 512 KiB per token, so 40,960 tokens in 20 GiB |

Grouped-query attention lets several query heads share one key and value head, which cuts the KV cache to a quarter
here.

</details>

## Paged blocks, admission, and preemption

Older servers reserved KV memory for each request's maximum length. Most answers end far short of it, and the vLLM
paper found such systems used only 20.4% to 38.2% of KV memory for actual tokens. **Paged** allocation
(PagedAttention) splits the cache into small fixed-size blocks, like operating system pages, and adds a block only when
the last one fills. vLLM reached 96.3%.

**Admission control** starts a request once free blocks can hold its whole prompt. If the pool runs dry mid-answer, the
server **preempts** the most recent arrival, frees all its blocks, and later recomputes them in one prefill.

<ServingKvWidget client:visible />

What to look for:

- **Reserved but empty.** On Chat traffic, 34.3% of the reserve server's token slots hold tokens. Paged blocks reach
  88.9%.
- **Admission waits.** Reserving 128 answer tokens per request caps the reserve server at 4 of its 8 seats. The
  paged server fills all 8, and the median TTFT falls from 269 ms to 19 ms.
- **Memory squeeze preempts.** Ten long answers arrive within 0.1 s. The paged server preempts R8 at step 66 and R7 at
  step 80, recomputes 183 tokens, and still finishes in 2,214 ms against 3,134 ms.

<details>
<summary>Go deeper: recompute or swap, and the toy model</summary>

vLLM evicts the most recent arrival first and frees all of its blocks at once. By default its current engine then
**recomputes** the evicted request: when it is admitted again, its prompt and the tokens it already wrote run through
one prefill. The alternative, swapping blocks out to CPU memory and back, keeps the work but costs copy time over the
link between CPU and GPU, plus CPU memory to hold the blocks.

- **The tail.** On Chat traffic the p95 time to first token falls from 1,016 ms to 277 ms with paged blocks.
- **The squeeze in detail.** The paged server admits eight of the ten long answers, then runs out of blocks as they
  grow. R8 and R7 are the latest arrivals still running when the pool runs dry.
- **The last block is partly empty.** Each request's newest block fills one token at a time, so paged blocks stay
  below 100%. The toy model's requests are short, so that partial block weighs more here than in the paper.

This is a **toy model**: 48 blocks of 16 tokens, eight seats per server, a 128-token reserve for answers, and the same
step cost as before. Recompute is modeled as one prefill of the prompt plus the tokens generated so far. Every number is
illustrative.

</details>

## Long prompts and shared prefixes

A joining request's whole prompt runs in the same step as everyone else's decode, so a long prompt pauses every stream
mid-answer. **Chunked prefill** runs a long prompt in pieces, one per step, within a token budget that serves decode
tokens first. vLLM enables it by default where it can. Sarathi-Serve calls it stall-free batching.

Every support chat also starts with the same instructions. **Prefix caching** reuses the KV blocks of a shared start,
so that part of prefill is skipped: the [caching](../../scaling/caching/) idea inside one server. In front of these
servers, an [AI gateway](../gateway/) picks the model and server for each request. [Agents and tools](../agents/) comes
next.

<details>
<summary>Go deeper: how prefix caching matches blocks</summary>

vLLM caches full blocks only, and each block's hash includes the block before it, so a change early in the prompt means
no later block matches. Put stable text, such as instructions and tool definitions, first. A cache salt keeps one
tenant's cached blocks out of reach of another. The simulations in this lesson do not model prefix caching.

</details>

Production servers also use speculative decoding, lower precision, multi-GPU splits, mixture of experts models, and
separate GPU pools for prefill and decode.

<details>
<summary>Go deeper: more ways to serve faster</summary>

**Speculative decoding.** A small draft model proposes several tokens, and the large model checks them all in one pass,
which costs about one decode step while the step stays under the ridge. With greedy decoding, the large model keeps the
drafted prefix that matches its own top choices. Sampled decoding needs a different rule. Let p and q be the large and
draft models' next token probabilities after the same accepted prefix, both after temperature and other decoding
settings. The large model accepts a drafted token x with probability min(1, p(x) / q(x)). At the first rejection it
samples a replacement from max(0, p minus q), normalized, and discards the rest of the draft. Example: the large model
gives A 0.8 and B 0.2, and the draft gives A 0.6 and B 0.4. Every drafted A is accepted, and half of the drafted Bs. A
rejected B resamples from the leftover mass, which sits entirely on A. A comes out 0.6 + 0.4 × 0.5 = 0.8 of the time
and B 0.4 × 0.5 = 0.2, exactly the large model's distribution.
[Leviathan et al. (2023)](https://arxiv.org/abs/2211.17192) report 2 to 3 times faster decoding on T5-XXL. The gain
depends on how often the draft guesses right, and it shrinks at large batches, where steps are already compute bound.

**FP8 and other low precision formats.** Storing weights in 8 bits instead of 16 halves the bytes each decode step
reads, so memory-bound steps get faster and more memory is left for the KV cache. An FP8 KV cache doubles the tokens
that fit: 64 KiB per token for Llama 3 8B instead of 128 KiB. [FP8 formats](https://arxiv.org/abs/2209.05433) match
16-bit quality on many models, and 4-bit weight formats save more at more risk to quality. Rerun your eval set from
[evaluation and budgets](../evaluation-and-budgets/) before you switch.

**Tensor or pipeline parallelism.** When a model does not fit on one GPU, split it. Tensor parallelism
([Megatron-LM](https://arxiv.org/abs/1909.08053)) splits every layer across GPUs, which shortens each step but exchanges
data at every layer, so it needs fast links inside one machine. Pipeline parallelism
([GPipe](https://arxiv.org/abs/1811.06965)) gives each GPU a run of whole layers and passes activations from stage to
stage. It tolerates slower links between machines, but stages sit idle (pipeline bubbles) unless enough requests keep
every stage busy. A common starting point: tensor parallelism within a machine, pipeline parallelism across machines.

**Mixture of experts.** A mixture of experts model replaces some layers with many expert blocks and a router that picks
a few per token. [Mixtral 8x7B](https://arxiv.org/abs/2401.04088) has 8 experts per layer and uses 2 per token: about
47B parameters in memory and about 13B active per token. Compute per token drops to that of a much smaller model, yet
every expert must stay in GPU memory, and tokens in one batch hit different experts, so large deployments spread the
experts across GPUs.

**Prefill and decode disaggregation.** Prefill is compute bound and decode is memory bound, and on one GPU they get in
each other's way: a long prefill stalls decodes, which is the problem chunked prefill works around.
[DistServe (2024)](https://arxiv.org/abs/2401.09670) runs them on separate GPU pools and moves each request's KV cache
from the prefill pool to the decode pool, so each pool can meet its own TTFT or TPOT target. It reports up to 7.4 times
more requests served within both targets. The cost is the KV transfer and two pools to size, so it pays off at large
scale with strict budgets for both latencies.

</details>

## Trade-offs

<TradeoffTable title="Serving a model on shared GPUs">

| Choice | What it buys | What it costs |
| --- | --- | --- |
| Static batching | A simple scheduler | Finished requests hold slots, and arrivals wait for the whole batch |
| Continuous batching | Slots refill every step, so throughput rises and queues shrink | A decision every step, and long prompts stretch the steps they join |
| Bigger batch | More tokens from each weight read | Longer steps, more KV memory, and gains that flatten |
| Paged blocks | Little empty memory, so more requests fit | The pool can run dry, so you need preemption |
| Small prefill chunk | Even gaps between tokens mid-answer | Long prompts, and requests behind them, wait longer for a first token |
| Preempt by recompute | No CPU memory or copy traffic | The prefill runs again |

</TradeoffTable>

Skip running your own serving stack when you call a hosted model API: the provider already batches and pages. An
offline job whose answers share one length gains little from continuous batching.

## Common mistakes

- **Sizing KV memory for the average answer.** Requests grow while they run, so size for the long tail and let paged
  blocks reclaim the rest.
- **Setting the prefill chunk far past the ridge.** Every token past the ridge stretches the step for every chat
  mid-answer.
- **Ignoring the preemption count.** Each preemption repeats a prefill. A steady stream means the server admits more
  than its memory holds.

<KeyTakeaways>

- Decode waits on memory at small batches, so batching pays until steps turn compute bound.
- Continuous batching refills a slot at the next step, raising tokens per step and cutting TTFT when answer lengths
  vary.
- KV memory per token caps how many requests run at once. Paged blocks waste little, and recompute covers a dry pool.
- Chunked prefill near the ridge keeps streams smooth at a small cost in first-token time.

</KeyTakeaways>
