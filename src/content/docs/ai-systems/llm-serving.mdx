## The failure: one GPU, one request at a time

The support assistant from [evaluation and budgets](../evaluation-and-budgets/) passed its budgets with Medium, and the
team now hosts Medium on one GPU of its own. The first server is simple: it takes the next chat turn, writes the whole
answer token by token, then takes the next one. At night it feels fine.

On Monday morning chats pile up. Every customer waits for every answer ahead of them to finish streaming, and the
queue grows faster than it drains. A profile shows the odd part: while the server writes an answer, the GPU's math
units are mostly idle. Each new token needs a full read of the model's weights from memory, and the math for one token
finishes long before the next read does.

Someone switches to **static batching**: take four waiting chats, run them together until all four finish, then take
the next four. Throughput rises, but now a customer asking "where is my parcel?" waits for the neighbor whose refund
question needs a long answer, and anyone who arrives mid-batch waits for the whole batch to end.

- **A burst narrows the gap.** When all 16 requests arrive at once, both servers start full. Continuous batching still

token. The static server starts its next batch with whoever is waiting when the previous batch ends and never waits to
fill it. Requests come from a seeded generator (seed 42). No model runs in your browser, and every number is
illustrative.

## The idea: fill every step, and budget memory per token

A language model answers in two phases. **Prefill** reads the whole prompt in one pass and produces the first token.
**Decode** then produces one token per step, and every step needs the keys and values of all earlier tokens, which the
server keeps in the **KV cache**. A **scheduler** decides which requests run in each step. **Continuous batching**
(the research name is iteration-level scheduling) lets it add or remove a request at every step, so a slot that frees up
is filled at the next step.

<StepDiagram client:visible title="One scheduler step at a time" nodes={nodes} edges={edges} steps={steps} height={300} />

<Analogy>

Picture a vehicle with four seats. Static batching runs it as a tour bus: it leaves with a full group, comes back only
when the passenger with the longest tour is done, and people who got off early leave empty seats behind them.
Continuous batching runs it as a hop-on hop-off tram that stops after every block: when one rider gets off, the next
person on the platform takes the seat. Every rider also carries luggage that grows at each stop (the KV cache). When the luggage rack
is full, the last rider to board steps off with their bags and boards again later.

</Analogy>

### Prefill and decode cost different things

During prefill the GPU pushes a whole prompt's worth of tokens through each weight it reads, so the math units stay
busy: prefill is **compute bound**, and its time grows with the prompt length. During decode each request adds just one
token per step, yet the step still reads all the weights and the requests' cached keys and values from memory. At
small batches that read dominates, so decode is **memory-bandwidth bound**. Adding requests to the same step shares
the weight read, which is why batching raises throughput.

<ServingCostWidget client:visible />

| Requests decoding together | Step time | Decode tokens per second, whole server |
| --- | --- | --- |
| 1 | 10.15 ms | 99 |
| 8 | 11.2 ms | 714 |
| 32 | 14.8 ms | 2,162 |
| 128 | 29.2 ms | 4,384 |
| 256 | 48.4 ms | 5,289 |

From 1 to 128 requests, the toy model's step time grows 2.9 times while its throughput grows 44 times. Then the gain
flattens: doubling from 128 to 256 adds about a fifth more throughput, and each request now waits 48.4 ms per token
instead of 29.2 ms. Real servers show the same shape. In Databricks' measurements of a 7B parameter model, a batch of
64 gave about 14 times the throughput of a single request for about 4 times the latency. Once a step is compute bound,
a bigger batch only adds latency.

This toy model gives each decoding request a fixed cost. In a real server that cost grows with context length, because
every step reads every cached token of every request, so long conversations make big batches slower than shown here.

Two latencies matter to a chat user:

- **Time to first token (TTFT)** is queue wait plus prefill. A long queue or a long prompt shows up here.
- **Time per output token (TPOT)** is the gap between later tokens, which is mostly decode step time. A bigger batch
  raises throughput and shortens the queue, but it lengthens every step.

### How much memory one token needs

Each token stores a key and a value for every layer and every KV head. For Llama 3 8B (32 layers, 8 KV heads, 128
values per head, 2 bytes per value):

2 (key and value) × 32 layers × 8 KV heads × 128 values × 2 bytes = 131,072 bytes = **128 KiB per token**

| Amount | KV cache memory |
| --- | --- |
| 1 token | 128 KiB |
| 1 block of 16 tokens | 2 MiB |
| 1 conversation of 8,192 tokens | 1 GiB |
| 20 GiB of KV memory | 163,840 tokens in any mix |
| Same model without grouped-query attention (32 KV heads) | 512 KiB per token, so 40,960 tokens in 20 GiB |

Grouped-query attention lets several query heads share one key and value head, which cuts the KV cache to a quarter
here. Even so, KV memory usually runs out before math does, so it caps how many requests can run at once.

### Reserve the maximum, or hand out blocks

Older serving systems reserved KV memory for a request's maximum length up front. Most answers end well short of the
maximum, so most of that memory sat empty: the vLLM paper measured that earlier systems used only 20.4% to 38.2% of
their KV memory for actual token states. **Paged** allocation (PagedAttention in vLLM) splits the cache into small
fixed-size blocks, like pages in an operating system, and gives a request a new block only when its last one fills.
vLLM reached 96.3%. Less empty memory means more requests fit, so the batch grows.

**Admission control** decides when a waiting request may start. A paged server admits a request once free blocks can
hold its whole prompt, then grows it one block at a time as it decodes. That leaves a risk: running requests keep
growing, and the pool can run dry mid-answer. The safety net is **preemption**. vLLM evicts the most recent arrival
first and frees all of its blocks at once. By default its current engine then **recomputes** the evicted request: when
the request is admitted again, its prompt and the tokens it already wrote run through one prefill. The alternative,
swapping blocks out to CPU memory and back, keeps the work but costs copy time over the link between CPU and GPU.

<ServingKvWidget client:visible />

What to look for:

- **Reserved but empty.** Hatched blocks belong to a request but hold no tokens yet. On Chat traffic, averaged over
  the run, only 34.3% of the token slots the reserve server has allocated hold tokens. Paged blocks reach 88.9%.
- **Admission waits.** The reserve server needs room for the prompt plus 128 answer tokens before it admits anyone,
  so it never runs more than 4 of its 8 seats at once. Its transcript shows lines such as "R5 waits: it needs 10 blocks
  and 3 are free." The paged server fills all 8 seats, and the median time to first token falls from 299 ms to 25 ms
  (p95 from 1,073 ms to 313 ms).
- **Memory squeeze preempts.** Ten long answers arrive within 0.1 s. The paged server admits eight, then runs out of blocks
  as the answers grow. At step 65 it preempts R8, the latest arrival still running, and at step 79 it preempts R7.
  Together they recompute 183 tokens. Even with that repeated work, the paged server finishes in 2,262 ms against
  3,164 ms for the reserve server.
- **The last block is partly empty.** Each request's newest block fills one token at a time, so paged blocks stay
  below 100%. The toy model's requests are short, so that partial block weighs more here than in the paper.

This is a **toy model**: 48 blocks of 16 tokens, eight seats per server, a 128-token reserve for answers, and the same
step cost as before. Recompute is modeled as one prefill of the prompt plus the tokens generated so far. Every number is
illustrative.

### Chunked prefill: long prompts without stalls

Continuous batching has a cost that the first widget hinted at. When a request joins, its whole prompt runs in the same
step as everyone else's decode. A long prompt makes that one step long, and every customer who is mid-answer sees the
stream pause. **Chunked prefill** splits a long prompt into pieces and runs one piece per step alongside the decodes,
within a fixed token budget per step. vLLM's current engine turns it on by default when it can and schedules decode
tokens first. The Sarathi-Serve paper calls this stall-free batching.

### Reuse a shared prefix

Every support chat starts with the same assistant instructions. **Prefix caching** keeps the KV blocks for a shared
start and reuses them when a new request begins with the same tokens, so that part of prefill is skipped. vLLM caches
full blocks only, and each block's hash includes the block before it, so a change early in the prompt means no later
block matches. A cache salt keeps one tenant's cached blocks out of reach of another. It is the
[caching](../../scaling/caching/) idea applied inside one server. The widgets in this lesson do not model it.

In the full system, an [AI gateway](../gateway/) sits in front of model servers like this one. It decides which model
and which server each request goes to, and how many requests each caller may send. The next lesson,
[Agents and tools](../agents/), lets the model call tools with authorization, budgets, and cancellation.

## Trade-offs

<TradeoffTable title="Serving a model on shared GPUs">

| Choice | What it buys | What it costs |
| --- | --- | --- |
| Static batching | A simple scheduler and a fixed batch until every request ends | Finished requests hold their slots, and new arrivals wait for the whole batch |
| Continuous batching | Freed slots refill every step, so throughput rises and queues shrink | A scheduling decision every step, and new prompts lengthen the steps they join |
| Bigger batch | More tokens per second from each weight read | Longer steps for everyone, more KV memory, and gains that flatten |
| Smaller batch | Shorter steps, so each request streams faster | Fewer requests share each weight read, so throughput drops and queues grow |
| Reserve maximum length | No growth mid-answer, so no preemption | Most reserved memory sits empty, which caps the batch and the answer length |
| Paged blocks on demand | Far less empty memory, so more requests fit | The pool can run dry mid-answer, so you need preemption |
| Small prefill chunk | Short, even gaps between tokens for chats mid-answer | Long prompts, and the requests behind them, wait longer for a first token |
| Large prefill chunk | Faster first token for long prompts | Longer pauses for chats mid-answer |
| Preempt by recompute | No CPU memory or copy traffic needed | The preempted request's prefill runs again |
| Preempt by swap to CPU memory | Keeps the work already done | Copy time between CPU and GPU, and CPU memory to hold the blocks |

</TradeoffTable>

Size the support assistant for its Monday peak. At peak, 120 chat turns are in flight at once. Each carries up to
1,536 prompt tokens (instructions plus conversation) and gets an answer of up to 512 tokens. After the weights, each
GPU has 20 GiB left for KV cache, and the model stores 128 KiB per token. The product's budgets are a p95 time to

serving settings do you pick?

<div slot="answer">

- **Memory per request:** 1,536 + 512 = 2,048 tokens at most. 2,048 × 128 KiB = 256 MiB, so 20 GiB holds 80 requests
  at full length.
- **GPUs:** 120 requests at full length need one and a half GPUs' worth of KV memory. Start with two replicas behind a
  [load balancer](../../scaling/load-balancing/), about 60 requests each, which leaves headroom for bursts. If one
  replica fails, the other holds only 80 at full length and the rest queue, so decide whether that is acceptable or
  add a third.
- **Paged blocks and continuous batching:** if most answers end well short of 512 tokens, paged blocks fit more
  requests than the worst case. Keep preemption by recompute as the safety net and watch the preemption count. A
  steady stream of preemptions means each replica admits more than its memory holds.
- **Time to first token:** TTFT is queue wait plus prefill, and a 1,536-token prompt is a long prefill. Turn on
  chunked prefill and tune the budget: smaller protects chats mid-answer, larger protects the first token. Cap the
  queue per replica so waits stay inside 1 s.
- **Shared instructions:** prefix caching reuses the KV blocks for the instructions every request shares, which cuts
  prefill time and memory per request.
- **Check it:** these are [estimates](../../thinking/requirements-and-estimates/). Load test at peak arrivals and
  measure p95 time to first token, time per output token, and preemptions before launch.

</div>

</Challenge>
