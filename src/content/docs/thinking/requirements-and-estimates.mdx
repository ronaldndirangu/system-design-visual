## The failure: a disk that fills in months

A small team ships a URL shortener on one server with a 100 GB disk. Nobody does the math. A few months later the disk is
full, writes start failing, and every new short link returns an error.

<Predict

1,000,000 links × 365 days × 5 years = 1.825 billion links. At 500 bytes each, that is about **913 GB** of raw data,
close to 1 TB. A 100 GB disk holds about 200 days of raw links, and indexes cut that to about 150. Ten minutes of
arithmetic would have caught it.

That 913 GB is one copy. Production keeps **3 copies** (2.74 TB), and indexes add about **30%** more, so plan for
about **3.56 TB** of disk.

</Predict>

## Requirements come first

Before drawing a single box, write down two lists.

- **Functional requirements** say what the system does: create a short link, and redirect anyone who opens it.
- **Non-functional requirements** say how well it does it: redirects in under 100 ms, the service stays up 99.9% of the
  time, and a link never changes once created. The [SLOs](../slos/) lesson turns targets like these into numbers you
  can measure.

Then list what you will **not** build yet, such as analytics or custom aliases. Saying no out loud keeps the design small.

## Estimates in a few lines

Aim for the right **order of magnitude** and round freely: a day has about 100,000 seconds (86,400 exactly).

```text
writes/s  = new links per day ÷ 86,400
reads/s   = writes/s × clicks per link
peak/s    = (writes/s + reads/s) × peak factor
servers   = peak/s ÷ (one server's capacity × 0.7)
links     = links per day × 365 × years
raw data  = links × bytes per link
disk      = raw data × 3 copies × 1.3 for indexes
cache     = links read per day × 20% hot × bytes
bandwidth = peak/s × bytes per response
```

The 0.7 keeps each server at most 70% busy, which leaves headroom for bursts. Losing a server is a separate check. Here is
the growing startup: 1 million new links a day, 100 clicks per link, a 3× peak, 5 years, 500 bytes per link, and app
servers that each handle about 2,000 redirects a second.

### Traffic

```text
writes  = 1,000,000 ÷ 86,400 ≈ 11.57/s
reads   = 11.57 × 100 ≈ 1,157/s
both    = 11.57 + 1,157 ≈ 1,169/s
peak    = 1,169 × 3 ≈ 3,507/s
servers = 3,507 ÷ (2,000 × 0.7) ≈ 2.5, so 3
```

Then check **N-1**, the loss of one server: with 3 servers, the 2 survivors each run 88% busy. A fourth server keeps
the 3 survivors at 58%. [Load balancing](../../scaling/load-balancing/) shows why waits climb near 100%.

The peak is a **throughput** target, one of the four words from the [anatomy of a web app](../anatomy-of-a-web-app/).
If each redirect takes 20 ms, about 3,507 × 0.02 ≈ 70 requests are in flight at once, about 23 per server.

### Storage

```text
links  = 1,000,000 × 365 × 5 = 1.825 billion
raw    = 1.825 billion × 500 B = 912.5 GB
copies = 912.5 GB × 3 ≈ 2.74 TB
disk   = 2.74 TB × 1.3 ≈ 3.56 TB
```

The widget rounds the raw figure to 913 GB. Disk ends up near 4 times the raw data.

### Bandwidth

```text
bandwidth = 3,507/s × 500 B ≈ 1.75 MB/s
```

That is about 14 Mbit/s, a sliver of one server's network card. Short links are tiny, so bandwidth is not the bottleneck
here. It would dominate for images or video: the same 3,507 requests per second at 1 MB each need about 3.5 GB/s
(28 Gbit/s), which is why media sites serve files from a [CDN](../../scaling/cdn/).

### What to notice

- **Reads dwarf writes.** At 100 clicks per link, reads are 99% of all traffic, so the read path gets most of the
  design work.
- **Disk grows with time, and the cache does not.** Slide the years from 1 to 20: disk grows 20 times, while the cache
  holds at 700 MB because only the last week of links is hot.
- **Retention has an infrastructure bill.** Planet scale keeps 365 billion links on about 712 TB of disk.
- **The short code barely grows.** Each extra base62 character multiplies capacity by 62: 6 characters at startup scale,
  7 at planet scale.

## Deep dives

### Copies and indexes multiply the disk

Raw data counts each link once. A production database keeps about **3 copies**, usually in different zones, so one lost
disk or zone loses no links and reads can spread across the copies. Each copy also carries
[indexes](../../foundations/indexes/) (the lookup from short code to row), row headers, and free space for new writes,
which together add roughly 30%. The multipliers stack: 3 × 1.3 = 3.9, so an estimate that skips them comes out almost 4
times too small.

### Size the cache by links, not clicks

A link clicked 100 times takes one cache slot, so count **distinct** links. Most clicks on a short link land in its
first week, so on any day readers touch about 7 days of new links.

```text
links read per day = 1,000,000 × 7 = 7 million
cache = 7 million × 20% × 500 B = 700 MB
```

700 MB fits in one cache server's memory with room to spare. Sizing by clicks (100 million a day) would ask for 10 GB,
about 14 times too much. The 20% is a rule of thumb, and real traffic is more skewed: one viral link can swamp a single
cache node, as [access patterns](../access-patterns/) shows. [Caching](../../scaling/caching/) covers eviction once the
cache fills.

<details>
<summary>Go deeper: where the peak factor comes from</summary>

Traffic follows people's days: evenings run hotter than nights, and one viral post can multiply clicks within minutes.
A factor of 2 to 3 over the daily average is a common first guess for consumer apps. Replace it with measured traffic as
soon as you have some. The 70% target absorbs bursts within the peak minute; the N-1 check above covers a lost server.
A fleet sized to run at 70% fails that check: lose 1 of 3 servers and the survivors hit 105%.

</details>

<details>
<summary>Go deeper: numbers worth memorizing</summary>

Estimates go faster with a few anchors:

- 2¹⁰ ≈ 1 thousand, 2²⁰ ≈ 1 million, 2³⁰ ≈ 1 billion, and 2⁴⁰ ≈ 1 trillion.
- A day is about 10⁵ seconds, and a year is about 3 × 10⁷ seconds.
- 1 million a day is about 12 a second, and 1 billion a day is about 12,000 a second.
- 1 billion items × 1 KB = 1 TB.
- Networks are sold in bits and disks in bytes: 1 MB/s is 8 Mbit/s.

</details>

## Trade-offs

<TradeoffTable title="Every requirement has a price">

| Requirement                    | What it buys                       | What it costs                                  |
| ------------------------------ | ---------------------------------- | ---------------------------------------------- |
| Redirects under 100 ms         | Links feel instant                 | Caches and servers close to users              |
| 99.99% uptime instead of 99.9% | 8 hours less downtime a year       | Redundant servers, databases, and failover     |
| Keep links forever             | No broken links in old posts       | Storage that grows without limit               |
| Custom aliases                 | Memorable links such as sho.rt/sale | A uniqueness check on every write              |
| Click analytics                | Insight for link owners            | A write on every click, so writes match reads  |

</TradeoffTable>

**When to skip the math.** An internal tool for 50 people runs on one small server, so spend the time on features. Once
a service is live, measure real traffic and keep estimates for what has not happened yet, such as a launch, a new
region, or click analytics.

## Common mistakes

- **Sizing disk from raw data.** Skipping 3 copies and 30% for indexes leaves the plan almost 4 times short.
- **Sizing the cache by clicks.** A link clicked 100 times fills one slot, so count distinct links.
- **Planning for the average.** Servers fail in the busiest minute, so size for the peak and keep 30% headroom.
- **Chasing precision.** Rounding 86,400 seconds to 100,000 moves the answer by 14%. A wrong guess of clicks per link
  moves it 100 times.
- **Skipping the not yet list.** Click analytics added later turns every read into a write as well.

<KeyTakeaways>

- Write the functional and non-functional requirements first, plus what you will not build yet.
- Traffic: divide daily totals by 86,400, multiply by clicks per link and the peak factor, then keep servers under 70%
  busy.
- Disk is raw data × 3 copies × 1.3 for indexes, near 4 times the raw number.
- Size the cache by distinct hot links, and check bandwidth: tiny for short links, dominant for images and video.
- Get the order of magnitude right. The ratios matter more than the decimals.

</KeyTakeaways>
