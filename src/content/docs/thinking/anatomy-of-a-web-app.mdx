Every design in this course draws the same few boxes. Learn what each one does now, and every later diagram reads like
a sentence. The running example is the URL shortener: people create short links such as `sho.rt/abc123`, and anyone
who opens one gets redirected to the long URL.

Three ideas hold the picture together. **Stateless app servers** keep nothing between requests, so you add servers when
traffic grows. **The cache** answers the common reads from memory, and **the database** keeps the truth on disk. **The
queue** takes work the user does not need to wait for.

## Four words for slow

**Latency** is how long one request takes, in milliseconds. **Throughput** is how many requests finish each second.
They are linked: requests in flight = throughput × latency. A service that finishes 1,000 requests a second at 50 ms
each holds about 50 in flight at any moment.

**Performance** asks whether the system is fast for one user on a quiet day. **Scalability** asks whether it stays fast
as users, data, and traffic grow. A performance problem shows up with one user, so profile that slow request. A
scalability problem shows up only under load, so look for the box that saturates first. The
[reference sheet](../../reference/) keeps these definitions next to the latency numbers.

<KeyTakeaways>

- A web app is a browser, DNS, a load balancer, stateless app servers, a cache, a database, a queue, and a CDN.
- Stateless servers let you scale by adding machines. State lives in the cache and the database.
- Latency is time per request, and throughput is requests per second. In flight = throughput × latency.
- Slow for one user is a performance problem. Slow only at peak is a scalability problem.

</KeyTakeaways>
