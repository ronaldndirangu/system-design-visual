## The failure: plenty of capacity, one node on fire

The shortener's cache tier has four nodes, and each serves 150 redirects a second. On a normal evening clicks arrive at
40 a second, spread over a thousand links. Then a celebrity posts `sho.rt/abc123`. Clicks jump to 400 a second, and 60%
of them want that one link.

On paper the tier has 600 requests a second of room. In practice, people start getting errors.

## The idea: measure the access pattern first

An **access pattern** describes how a system gets used. Before picking a design, answer four questions:

- **What operations happen?** For the shortener: create a link (a write) and follow a link (a read).
- **What is the read to write ratio?** Each link is created once and clicked many times, about 100 reads per write. In
  [Requirements and estimates](../requirements-and-estimates/) that ratio turned 12 writes a second into 1,200 reads.
- **How skewed is it?** Popularity follows a long tail. A handful of links draw most clicks, and most links are rarely
  touched. The [caching lesson](../../scaling/caching/) uses this skew to answer 70% of clicks from 10% of links.
- **How does it change over time?** Evenings, launches, and viral posts shift both the rate and the skew, sometimes in
  seconds.

Skew helps a cache and hurts a partition. A key that draws a large share of traffic is a **hot key**. Hashing gives each
key one home, which spreads many keys evenly. A single key cannot be split by hashing, so its home node carries all of
it. The same thing happens to a database shard: [sharding](../../scaling/sharding/) spreads many keys and leaves one viral
link on one shard.

What to look for:

- **Busy, no hot key.** Traffic grows tenfold, yet both lanes match exactly: every node handles about 90 to 115 clicks a
  second, nothing gets turned away, and the busiest node peaks at 86%. Even growth is a capacity question.
- **Viral link.** The access pattern panel shows abc123's share jump from about 5% to about 60%. In the hash only lane
  Node 2 runs near 200% and turns away about 2,000 clicks. In the copies lane every node settles near 105 clicks a
  second.
- **Detection lag.** Copies arrive one tick late. Node 2 fills up at 3.3 s in both lanes, so the copies lane still turns
  away 6 clicks before it spreads abc123.

This widget is a **toy model**. The node capacity, the 30 request queue, the 50 a second threshold, and the click mix
are illustrative numbers picked so the effect is easy to see. Real caches serve far more, and the shape of the problem
stays the same.

## Hot writes are harder

Copies fix hot **reads**, because any copy can answer. Hot **writes** need something else, since every copy must change.
Suppose the shortener counts clicks per link: abc123 now takes 240 counter increments a second, all on one key.

- **Split the key.** Store the count as eight parts, `abc123#0` to `abc123#7`. Each click adds to a random part, so the
  writes spread across nodes. Reading the total means adding up all eight.
- **Batch the writes.** Each app server counts in memory and adds its total to the shared counter once a second. The
  count trails by a second, and a crash loses the unsent part.

## Trade-offs

<TradeoffTable title="Handling a hot key">

| Choice                               | What it buys                                        | What it costs                                              |
| ------------------------------------ | --------------------------------------------------- | ---------------------------------------------------------- |
| One home per key (hash only)         | Simple routing, one place to update or delete       | A hot key overloads its home node                          |
| Copy hot keys to every node          | Hot reads spread across the whole tier              | Extra memory, and deletes must reach every copy            |
| Near cache in each app server        | Hot reads never leave the server                    | Copies disagree for up to the TTL                          |
| Split a hot key into parts           | Spreads writes as well as reads                     | Every read gathers and adds up all the parts               |
| Add more nodes                       | More room for the long tail of cold keys            | The hot key still lands on one node                        |
| Detect hot keys automatically        | Handles viral links nobody predicted                | Detection lags, so the first burst still hits one node     |

</TradeoffTable>
