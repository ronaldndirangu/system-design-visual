## The failure: plenty of capacity, one node on fire

The shortener keeps its links in a **cache** (a small, fast copy of popular data held in memory; see
[Caching](../../scaling/caching/)). The cache tier has four nodes, and each serves 150 redirects a second. Each link
lives on one node, picked by **hashing** its short code (turning the code into a number that always points at the same
node; see [Sharding](../../scaling/sharding/)).

On a normal evening clicks arrive at 40 a second, spread over a thousand links. Then a celebrity posts
`sho.rt/abc123`. Clicks jump to 400 a second, and 60% of them want that one link. On paper the tier has room for 600 a
second. In practice, people start getting errors.

## The idea: measure the access pattern first

An **access pattern** describes how a system gets used. Before picking a design, answer four questions:

- **What operations happen?** Create a link (a write) and follow a link (a read).
- **What is the read to write ratio?** About 100 reads per write. In
  [Requirements and estimates](../requirements-and-estimates/) that turned 12 writes a second into 1,200 reads.
- **How skewed is it?** A handful of links draw most clicks. The caching lesson uses this skew to reach a 70% **hit
  rate** (the share of reads the cache answers without the database) while holding 10% of links.
- **How does it change over time?** Launches and viral posts shift the rate and the skew within seconds.

Skew helps a cache and hurts a partition. A key that draws a large share of traffic is a **hot key**. Hashing spreads
many keys evenly, yet each key has one home, so one hot key's node carries all of it. A database **shard** (one slice of
the data on its own machine) has the same problem.

Where it breaks: a library sees bestsellers coming for weeks. A link goes viral in seconds and fades by evening, so the

## Reading the pattern

### Read shape: one key, a range, or a scan

Following a link is a **point read**: one short code, one answer. Listing a user's links is a **range read**: every link
with one owner, newest first. A monthly click report is a **scan** over every click. Point reads spread well by hash,
range reads want one owner's rows stored together, and scans belong on a separate copy so a report never slows a
redirect.

### Find the hot key: per node, then per key

- **Load per node.** One node far above the rest means skew: about 294 clicks a second against about 40 on the others.
- **Top keys by share.** Count reads per key on the busy node, or sample 1 request in 100. abc123 jumping from 5% to 60%
  names the culprit.
- **The hot key against one node.** If one key alone needs more than a node serves (240 against 150), moving other keys
  away cannot save that node.

### Hot writes look different

If the shortener also counts clicks per link, abc123 takes 240 counter updates a second on one key. Find hot writes the
same way, with writes per key and per node. They need different fixes from hot reads, collected below.

<details>
<summary>Revisit after caching and sharding: fixing a hot key</summary>

Come back here after [Caching](../../scaling/caching/) and [Sharding](../../scaling/sharding/), which teach the parts
these fixes are built from.

**Hot reads: give more places a copy.** Any copy of a link can answer a read.

- **Copy the hot key.** The widget's right lane does this. Once abc123 passes 50 clicks a second, every node gets a copy
  and its reads take turns, about 60 per node, so each node settles near 105 clicks a second. The cost: deleting a scam
  link must now reach every copy, or the leftover copies keep redirecting.
- **Near cache.** Each app server keeps the hottest links in its own memory for a second or two. Hot reads never leave
  the server, and the copies can disagree for up to that time.

**Hot writes: spread or batch the changes.** Every write changes the value, so copies alone cannot absorb them.

- **Split the key.** Store the count as eight parts, `abc123#0` to `abc123#7`. Each click adds to a random part, so the
  writes spread across nodes. Reading the total means adding up all eight.
- **Batch the writes.** Each app server counts in memory and adds its total to the shared counter once a second. The
  count trails by a second, and a crash loses the unsent part.

<TradeoffTable title="Fixing a hot key">

| Choice                               | What it buys                                        | What it costs                                              |
| ------------------------------------ | --------------------------------------------------- | ---------------------------------------------------------- |
| One home per key (hash only)         | Simple routing, one place to update or delete       | A hot key overloads its home node                          |
| Copy hot keys to every node          | Hot reads spread across the whole tier              | Extra memory, and deletes must reach every copy            |
| Near cache in each app server        | Hot reads never leave the server                    | Copies disagree for up to the TTL                          |
| Split a hot key into parts           | Spreads writes as well as reads                     | Every read gathers and adds up all the parts               |
| Add more nodes                       | More room for the long tail of cold keys            | The hot key still lands on one node                        |
| Detect hot keys automatically        | Handles viral links nobody predicted                | Detection lags, so the first burst still hits one node     |

</TradeoffTable>

</details>

## Trade-offs

<TradeoffTable title="Ways to see the access pattern">

| Measurement               | What it shows                               | What it hides or costs                                  |
| ------------------------- | ------------------------------------------- | ------------------------------------------------------- |
| Total requests per second | Whether the tier has room overall           | One overloaded node: 400 of 600 looked safe             |
| Load per node             | Which node is overloaded, and since when    | Which key caused it                                     |
| Top keys by share         | The hot key by name, and how hot it is      | Memory to count keys; sampling misses short bursts      |
| Read to write ratio       | Whether to make reads or writes cheap first | Skew: a quiet evening and a viral link share one ratio  |
| Full request log          | Any question, after the fact                | Storage, and too slow to raise an alarm live            |

</TradeoffTable>

**When to skip it.** A prototype at 5 requests a second on one machine has no node to overload, so a total and a read to
write ratio are enough. Per-key tracking pays off once data spreads across several nodes or shards and one item can go
viral: links, celebrity posts, flash sales, live scores.

## Common mistakes

- **Sizing from the total alone.** 400 clicks against 600 of room looked safe while one node ran near twice its limit.
- **Treating the ratio as the whole pattern.** The ratio stays 100 to 1 whether traffic is even or viral. Skew is a
  separate measurement.
- **Adding nodes to cool a hot key.** Hashing still sends the key to one node.
- **Measuring once.** Skew changes in seconds. Track top keys continuously and alert when one node runs far above the
  rest.
- **Watching only reads.** A click counter on a viral link is a hot write key, even when every read hits a cache.

<KeyTakeaways>

- An access pattern has four parts: the operations, the read to write ratio, the skew, and how they change over time.
- Hashing gives each key one home. It spreads many keys evenly and sends all of one hot key to one node or shard.
- Totals hide hot keys. Watch load per node and the top keys by share, and compare the hottest key with one node.
- More nodes take cold keys off the hot node and leave the hot key's own load in place.

</KeyTakeaways>
