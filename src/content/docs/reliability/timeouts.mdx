## The failure: one replica hangs

The sho.rt server answers 50 redirects per second with 16 workers. Each redirect looks up the long URL on one of three
database replicas, A, B, or C, and a healthy lookup takes 10 to 30 ms. At 3 s, replica C hangs: it accepts each query
and never replies. A third of all lookups go to C.

## Why one slow dependency takes everything down

A worker waiting on a hung call does nothing else. Workers are a fixed pool, so each hung call removes one from service
while the healthy replicas sit idle.

A **timeout** caps how long a caller waits. When it fires, the caller reports an error (here **504 Gateway Timeout**)
and moves on. The failure stays the size of the broken part: a third of the clicks fail instead of all of them.

Many HTTP clients, such as Python's requests, wait forever by default, so give every outbound call an explicit timeout.
Health checks from [load balancing](../../scaling/load-balancing/)
do not replace timeouts: a balancer removes a server only after several failed checks, and a hung replica that still
accepts connections can pass a shallow check.

## How long should a timeout be?

A timeout that is too short fails healthy requests on ordinary hiccups. One that is too long leaves workers trapped.
Every dependency has a slow tail, so any timeout cuts off a few healthy requests. Choose how many:

1. **Pick the false-timeout rate you accept,** for example 0.1% of healthy lookups.
2. **Take the matching percentile and add a network allowance.** A 0.1% rate matches the p99.9, the time 999 of every
   1,000 healthy lookups beat (see [SLOs](../../thinking/slos/)). If sho.rt's replicas have a p99.9 of 100 ms, add 50 ms
   for network hiccups: the timeout is 150 ms. About 1 healthy lookup in 1,000 still times out, the rate you chose.
   (The simulations' healthy lookups take 10 to 30 ms, so none time out.)
3. **Check that it fits inside the caller's deadline.** The client gives up after 1 s, so 150 ms leaves room for the
   other hops. If it does not fit, the dependency is too slow for that caller.
4. **Check the pool with [Little's law](../queues-and-backpressure/):** things in a system = arrival rate × time each
   one stays. About 17 lookups per second go to C, so a 150 ms timeout keeps 17 × 0.15 ≈ 2.5 workers waiting, well
   under 16. If the product exceeds your pool, shorten the timeout or give the dependency its own small pool.

## Timing out is half the job: cancel the work

When a timeout fires, the request gives up. The query it started keeps its connection and runs until it finishes or
someone cancels it.

Without cancellation, abandoned queries on C pile up until they hold every connection, and lookups
routed to healthy replicas A and B time out too. So pass the cancel all the way down: in Go, each request carries a
`context` that every call checks, and many database drivers cancel a running query when the context ends.

Cancelling a **write** is harder: the write may already have landed, so the caller cannot know whether it happened.
[Idempotency](../idempotency/) makes that uncertainty safe.

## One deadline for the whole trip

A redirect passes through several hops: the client app, an API gateway, the sho.rt server, and the database. If each
hop picks its own timeout, inner ones are often longer than outer ones, and nobody downstream learns the client gave
up.

A **deadline** fixes this. The client sets one moment by which the answer must arrive, and each hop passes the
remaining time to the next. gRPC sends the remaining time, so clock differences between machines do not
matter.

<DeadlineBudgetWidget client:visible />

What to look for:

1. Drag the query time down to 500 ms. Both timeout styles answer the client at 540 ms.
2. At 2,500 ms, switch to **Pass the deadline along**. Every hop stops at 1,000 ms, so the work after the client gave
   up drops from 1,540 ms to none.
3. At 4,000 ms with fixed timeouts, the gateway's timer fires at 3,010 ms, yet the server and database run to 4,040 ms:
   nobody told them to stop.

Either way, the client's own timer raises **client deadline exceeded** at 1 s. That error never crosses the network; a
504 comes only from a gateway that gave up on the server. The shared deadline stops the system spending workers,
connections, and database time on answers nobody reads. [Retries](../retries/) builds on this,
because a retry that ignores the deadline doubles the wasted work.

## Trade-offs

<TradeoffTable title="How long to wait, and what to stop">

| Choice                  | What it buys                                    | What it costs                                                                            |
| ----------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------- |
| No timeout              | Never abandons a slow but valid request         | One hung dependency can hold every worker forever                                        |
| Short timeout           | Frees workers fast, so the failure stays small  | Fails healthy requests on normal hiccups if set near typical latency                     |
| Long timeout            | Rarely cuts off a healthy request               | Workers still pile up: call rate × timeout can exceed the pool                           |
| Cancel on timeout       | Frees connections and stops work for nobody     | Every layer must check for cancellation, and a cancelled write leaves its outcome unknown |
| Pass one deadline along | Every hop stops when the caller gives up        | Every service must read, honor, and forward the remaining time                           |

</TradeoffTable>

## Common mistakes

- Trusting a client library's default timeout, which is often none at all.
- Setting the timeout from the average instead of the percentile matching your accepted false-timeout rate.
- Giving an inner hop a longer timeout than its caller's deadline.
- Timing out without cancelling, so abandoned queries keep their connections.

<KeyTakeaways>

- With no timeout, one hung dependency traps every worker, and requests that never touch it fail too.
- Pick the false-timeout rate you accept, set the timeout at the matching percentile plus a network allowance, and
  check that it fits inside the caller's deadline.
- Call rate × timeout must fit the pool, or workers still pile up during an outage.
- A timeout frees the caller. Cancellation frees the connection and stops the work below it.
- Pass one deadline from hop to hop so every layer stops when the client gives up.

</KeyTakeaways>

<Challenge>

sho.rt serves 1,000 redirects per second with 200 workers. Each redirect also records the click with a call to the
analytics service, which has a 2 s timeout. One afternoon the analytics service hangs. How many calls would need to wait at
once, what happens to redirects, and what would you change so a broken analytics service never breaks redirects?

<div slot="answer">

- By Little's law, 1,000 calls per second × 2 s = **2,000 calls waiting at once**, ten times the 200 workers. Within
  0.2 s every worker is stuck, and the server starts only 100 redirects a second. The rest queue and fail, though a
  redirect never needed analytics.
- **Take analytics off the critical path.** The visitor needs only the long URL, so record the click in a local
  buffer or queue that ships events later.
- If the call must stay in the request, give it a **short timeout**, such as 50 ms (1,000 × 0.05 = 50 calls stuck at
  most), **cancel** it when the timeout fires, and run it in its **own small pool** so it never takes redirect workers.

</div>

</Challenge>
