## The failure: one replica hangs

The sho.rt server answers 50 redirects per second with 16 workers. Each redirect looks up the long URL on one of three
database replicas, A, B, or C, and a healthy lookup takes 10 to 30 ms. At 3 s, replica C hangs: it accepts each query
and never replies. A third of all lookups go to C.

## Why one slow dependency takes everything down

A worker that waits on a hung call does nothing else. Workers are a fixed pool, so every hung call removes one from
service. The healthy replicas sit idle while their requests wait in line behind workers that will never come back.

A **timeout** caps how long a caller waits. When it fires, the caller gives up, reports an error (here **504 Gateway
Timeout**), and moves on to the next request. The failure stays the size of the broken part: a third of the clicks fail
instead of all of them.

Many HTTP client libraries wait forever by default. Python's popular requests library, for example, never times out
unless you pass a timeout. Every call that leaves your process needs an explicit one.

## How long should a timeout be?

A timeout that is too short fails healthy requests on any small hiccup. A timeout that is too long barely helps,
because a worker stays trapped for the whole wait.

<Predict
  client:visible
  question="Replica C hangs again, and the timeout is 2 s instead of 150 ms. Do the 16 workers still fill up?"
  options={['Yes, all 16 fill up', 'No, a 2 s timeout frees them in time', 'Only about half of them fill up']}
  answer={0}
>

**Yes, all 16 fill up.** About 17 requests per second go to C, a third of 50. If each holds a worker for 2 s, about
17 × 2 ≈ 33 workers are stuck at any moment, twice the pool. With 150 ms, the same math gives 17 × 0.15 ≈ 2.5 workers.
In this toy model with seed 42, the 2 s lane fills all 16 workers at 3.8 s and fails 255 requests (192 turned away and
63 timed out), against 154 for the 150 ms lane.

</Predict>

That multiplication is **Little's law**: the number of things in a system equals their arrival rate times how long each
one stays. It returns in the next lesson, [Queues and backpressure](../queues-and-backpressure/). For timeouts it gives a simple check:

1. Start from healthy latency. Set the timeout a few times above the slowest healthy response you expect, such as the
   99.9th percentile, so normal variation never trips it.
2. Multiply the rate of calls that might hang by the timeout. If the result is bigger than your worker or connection
   pool, the pool can still fill during an outage, so shorten the timeout or give that dependency its own small pool.

## Timing out is half the job: cancel the work

When a timeout fires, the request gives up. The work it started keeps going: the database query holds its connection
and runs until it finishes or someone cancels it.

**Yes, abandoned queries hold every database connection.** Each abandoned query on C keeps a connection, and by 3.8 s
all 16 are taken. After that, every lookup waits for a connection and times out, even for links on A and B. In this toy
model with seed 42, the lane without cancellation times out 449 requests, against 154 with cancellation. After C
recovers, the database still runs all 449 abandoned queries for nobody, and real requests succeed again only 0.7 s
later.

</Predict>

Cancellation has to travel the whole way down. In Go, a request carries a `context` that every call checks and passes
along. Java and .NET use interrupts and cancellation tokens for the same job. Many database drivers can cancel a running
query when the context ends. A query that nobody tells to stop keeps running.

Cancelling a **write** is harder: the write may already have reached the database when the cancel arrives, so the
caller cannot know whether it happened. The [Idempotency](../idempotency/) lesson shows how to make that uncertainty safe.

## One deadline for the whole trip

A redirect passes through several hops: the client app, an API gateway, the sho.rt server, and the link database. If
each hop picks its own timeout, the inner ones are often longer than the outer ones, and nobody downstream learns that
the client gave up.

A **deadline** fixes this. The client sets one moment by which the answer must arrive, and each hop passes the time
remaining to the next. gRPC does this for you: it sends the remaining time with each call, so clock differences between
machines do not matter. When the deadline passes, every hop stops together.

**At about 2.5 s, when the query finishes.** None of the inner hops knows the client left. The database has no limit
and finishes at 2,540 ms. The server and gateway are still within their own timeouts, so all three keep working for
1,540 ms after the client gave up. Switch to **Pass the deadline along** and every hop stops at 1,000 ms.

</Predict>

The client still gets an error when the deadline passes. What changes is the cost of that error: with a shared deadline
the system stops spending workers, connections, and database time on answers nobody will read. The lesson
[Retries with backoff and jitter](../retries/) builds on this, because a retry that ignores the deadline doubles the
wasted work.

## Try it: break things on purpose

1. In the first simulation, press Play with **Replica C hangs**, then switch to **All replicas healthy** and play again.
   The two lanes match exactly: a timeout costs nothing while every dependency answers.
2. In the deadline timeline, drag the query time down to 500 ms. Both timeout styles answer the client at 540 ms.
3. Set the query time to 2,500 ms with fixed timeouts, then switch to **Pass the deadline along**. The work after the
   client gave up drops from 1,540 ms to none.
4. Drag the query time to 4,000 ms with fixed timeouts. The gateway's own 3 s timer fires at 3,010 ms, yet the server
   and database still run to 4,040 ms, because the gateway never told them to stop.

## Trade-offs

<TradeoffTable title="How long to wait, and what to stop">

| Choice                  | What it buys                                    | What it costs                                                                            |
| ----------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------- |
| No timeout              | Never abandons a slow but valid request         | One hung dependency can hold every worker forever                                        |
| Short timeout           | Frees workers fast, so the failure stays small  | Fails healthy requests on normal hiccups if set too close to typical latency             |
| Long timeout            | Rarely cuts off a healthy request               | Workers still pile up: call rate × timeout can exceed the pool                           |
| Cancel on timeout       | Frees connections and stops work for nobody     | Every layer must check for cancellation, and a cancelled write leaves its outcome unknown |
| Pass one deadline along | Every hop stops when the caller gives up        | Every service must read, honor, and forward the remaining time                           |

</TradeoffTable>

<Challenge>

sho.rt serves 1,000 redirects per second with 200 workers. Each redirect also calls the click analytics service to
record the click, with a 2 s timeout. One afternoon the analytics service hangs. How many calls would need to wait at
once, what happens to redirects, and what would you change so that a broken analytics service never breaks redirects?

<div slot="answer">

- By Little's law, 1,000 calls per second × 2 s = **2,000 calls waiting at once**, ten times the 200 workers. Only 200
  can actually wait: within 0.2 s every worker sits on a hung analytics call. Each worker then frees up only every 2 s,
  so the server starts just 100 redirects a second. The other 900 a second pile up in the queue until it fills or the
  visitors give up, and then fail. Almost every redirect fails or crawls, even though the redirect itself never needed
  analytics.
- **Take analytics off the critical path.** The visitor only needs the long URL. Record the click in the background, for
  example by writing it to a local buffer or queue that ships events later.
- If the call must stay in the request, give it a **short timeout**, such as 50 ms (1,000 × 0.05 = 50 calls stuck at
  most, well under the 200 workers), **cancel** it when the timeout fires, and run it in its **own small pool** so it can never take the workers
  that serve redirects.

</div>

</Challenge>
