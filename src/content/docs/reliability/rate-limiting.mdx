## The failure: one client starves everyone

The URL shortener sells API access to four partner apps. Each partner, A through D, sends about 50 requests per second.
The Link API can serve 300 requests per second and queues up to 60 more. Then partner A ships a bug: a retry loop that
pushes its traffic from 50 to 400 requests per second.

This is a **toy model**: four clients with random (Poisson) arrivals, one server that drains a fixed number of requests

requests, so every difference comes from the limiter.

A rate limit protects two things. It protects **fairness**, so one client cannot spend capacity that others need. It
protects the **service**, so a bug or an attacker cannot push it past its capacity. A single global limit of 300
requests per second would protect the service and still leave A holding most of those 300 slots. The fix is a limit
**per client**, keyed by API key, user, or IP address.

## The token bucket

The most common limiter is the **token bucket**. Each client gets a bucket that holds up to `burst` tokens and refills
at `rate` tokens per second. Every request spends one token. A request that finds the bucket empty gets **429 Too Many
Requests**. Two numbers describe the policy:

- **Rate**: the long run average a client may send.
- **Burst**: how many requests a client may send at once after a quiet spell.

The bucket never stores more than `burst` tokens, so a client cannot save up for a giant burst. In practice the limiter
stores only two values per client: the token count and the time of the last refill. It computes the refill lazily when
the next request arrives.

## Windows: counting requests per second

Some limiters count requests in a time window instead of tracking tokens.

- A **fixed window** keeps one counter per client per calendar second (or minute). It allows requests until the counter
  reaches the limit, then rejects the rest until the next window starts. One counter per client makes it cheap.
- A **sliding window log** stores the timestamp of every allowed request and counts those in the last full second. It is
  exact, and it stores one entry per request.
- A **sliding window counter** splits the window into small slots and adds them up, or blends the current and previous
  window counts by how much of each overlaps the last second. It stays close to exact with a few counters per client.
  The model below uses ten 100 ms slots.

The fixed window has a famous flaw. Its counter resets on the boundary, so a client can spend a full window just before
the boundary and a full window just after it.

## Telling clients to slow down

A limiter should reject with a clear, cheap answer:

- Status **429 Too Many Requests**, which means "you, specifically, are sending too fast". Keep **503 Service
  Unavailable** for "the service is overloaded for everyone". The [APIs lesson](../../foundations/apis/) covers status
  codes in more depth.
- A **Retry-After** header with the number of seconds to wait.
- Optionally, headers that show the remaining allowance, so clients can slow down before they hit the limit. The IETF
  draft standard names them `RateLimit` and `RateLimit-Policy`; many APIs use older `X-RateLimit-Remaining` style names.

The client decides what happens next. A careless client retries at once. A well-behaved one waits for Retry-After, adds
a little random jitter so many clients do not return in the same instant, and stops after a few tries. The
[retries lesson](../../reliability/retries/) covers backoff and jitter in depth.

## Where to enforce limits

Limits work best in layers, each keyed by what that layer knows.

- **At the edge** (a CDN or web application firewall): limit by IP address. It stops floods before they cost you
  anything. It knows nothing about users, and many users can share one IP behind a corporate network.
- **At the gateway**: limit by API key, user, or plan. One place sets policy for every service behind it. The
  [AI gateway lesson](../../ai-systems/gateway/) applies the same idea to token budgets for model calls.
- **In the service**: limit expensive operations by their real cost, for example 5 bulk exports per hour per account.
  Only the service knows that one request can cost a thousand times another.

Rate limits keep clients fair. When every client stays under its limit and the sum still exceeds capacity, the service
has to shed load on its own; the [queues and backpressure](../../reliability/queues-and-backpressure/) lesson covers that. Set the limits themselves from measured
capacity and your latency goal. The [SLOs lesson](../../thinking/slos/) shows how to define that goal.

## Limits across many gateways

The shortener runs six gateway instances behind a [load balancer](../../scaling/load-balancing/). Requests from one
client land on different instances, so who keeps the count?

- **A central counter store**, such as Redis, holds every bucket. Each gateway updates the bucket with one atomic
  operation (a Lua script or an increment with expiry). Limits stay exact. Every request pays a network round trip of
  about a millisecond, and the store becomes a dependency every request needs.
- **Local limits** give each of the six instances one sixth of the limit and no shared state. They are fast and survive
  any store outage. They also assume the load balancer spreads each client evenly: a client pinned to one instance gets
  a sixth of its limit.
- **A hybrid** keeps local buckets and syncs counts with the store every 100 ms or so. It trades a little accuracy for
  far fewer round trips, and most large APIs use some version of it.

Decide in advance what happens when the store fails. **Fail open** allows requests, perhaps with a local fallback
limit. **Fail closed** rejects them. For most public APIs, a short spell of looser limits hurts far less than an outage.

## Trade-offs

<TradeoffTable title="Which limiter, and where does the count live?">

| Choice                    | What it buys                                      | What it costs                                                    |
| ------------------------- | ------------------------------------------------- | ---------------------------------------------------------------- |
| Token bucket              | Allows short bursts, then holds the average rate  | Two numbers to tune, and a full burst can still spike the server |
| Fixed window              | One counter per client, simple to explain         | Up to twice the limit across a window boundary                   |
| Sliding window log        | Exact count over any one second                   | Stores one timestamp per request                                 |
| Sliding window counter    | Close to exact with a few counters                | A small error near slot edges                                    |
| Central counter store     | Exact limits across every gateway                 | A network hop per request, and the store must stay up            |
| Local per-instance limits | No shared state, no extra latency                 | Inaccurate when traffic spreads unevenly                         |
| Fail open                 | A store outage never blocks good clients          | A short window where abusers get through                         |
| Fail closed               | Limits always hold                                | A store outage becomes a full outage                             |

</TradeoffTable>

## Mini design challenge

<Challenge>

The shortener opens a public API with two plans. Free accounts may create 10 short links per minute; paid accounts may
create 1,000. Redirects (`GET /abc123`) have no per-account limit, but one botnet recently sent 50,000 redirect requests
per second from a few hundred IP addresses. Six gateway instances run behind a load balancer, and a Redis cluster is
available. Sketch where each limit lives, which limiter it uses, how the gateways share counts, and what happens when
Redis is down.

<div slot="answer">

1. **Edge, by IP, for redirects.** A token bucket per IP at the CDN or firewall, for example 50 per second with a burst
   of 100, stops the botnet before it reaches the gateways. Allow higher limits for known shared IPs such as large
   corporate networks.
2. **Gateway, by API key, for link creation.** A token bucket per key with the plan's rate: 10 per minute with a burst
   of about 5 for free accounts, 1,000 per minute with a burst of about 100 for paid ones. The burst size caps the
   spike any one key can send.
3. **Shared counts in Redis.** Link creation is low volume and its limits matter for billing, so the gateways keep exact
   buckets in Redis with one atomic script per request. Redirects stay at the edge with local counters, since they need
   speed more than precision.
4. **Answers.** Rejected requests get 429 with Retry-After and the `RateLimit` headers. The client libraries the
   shortener publishes wait for Retry-After plus jitter and stop after three tries.
5. **Redis down.** Fail open with a local fallback: each gateway allows one sixth of each plan's limit per key until
   Redis returns, and an alert fires so someone looks.

</div>

</Challenge>
