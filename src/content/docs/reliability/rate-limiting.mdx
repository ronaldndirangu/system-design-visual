A rate limit protects **fairness**. A global limit of 300 per second keeps the server up and still lets A take most

many clients under their limits can still outrun the server, which is the job of

## The token bucket

The most common limiter is the **token bucket**. Each client's bucket holds up to `burst` tokens and refills at `rate`
tokens per second. Every request spends one token, and a request that finds the bucket empty gets **429 Too Many
Requests**. `rate` is the long run average, and `burst` is how many requests may arrive at once after a quiet spell.
The limiter stores just a token count and a timestamp per client.

## Windows: averages and hard quotas

A token bucket enforces an **average rate plus a burst**, so a client with a full bucket can send `burst + rate × period`
requests in one period. When a requirement reads "at most 1,000 per hour", count requests in a window instead.

- A **fixed window** keeps one counter per calendar minute or hour. It is cheap, and a client can spend a full window
  just before the boundary and another just after it.
- A **sliding window** counts the requests in the last full period at every moment, so no stretch of that length ever
  holds more than the limit. It fits a hard quota.

Pick by what the requirement says. "10 per second, short bursts are fine" is a token bucket. "At most 1,000 in any
rolling hour" is a sliding window.

<details>
<summary>Go deeper: fixed and sliding windows</summary>

Two designs implement a sliding window.

- A **sliding window log** stores the timestamp of every allowed request and counts those in the last full second. It is
  exact, and it stores one entry per request.
- A **sliding window counter** splits the window into small slots and adds them up, or blends the current and previous
  window counts by how much of each overlaps the last second. It stays close to exact with a few counters per client.
  The model below uses ten 100 ms slots.

## Telling clients to slow down

Reject with a clear, cheap answer. **429 Too Many Requests** means "you are sending too fast", while **503 Service
Unavailable** means the service is overloaded for everyone (see the [APIs lesson](../../foundations/apis/)). Add a
**Retry-After** header with the seconds to wait. A well-behaved client waits that long plus random jitter and stops
after a few tries, as the [retries lesson](../retries/) explains.

<details>
<summary>Go deeper: what clients do with a 429</summary>

Optional headers show the remaining allowance, so clients can slow down before they hit the limit. The IETF draft
names them `RateLimit` and `RateLimit-Policy`, and many APIs use older `X-RateLimit-Remaining` style names. A careless
client ignores all of this and retries at once.

## Where to enforce limits

Layer limits, each keyed by what its layer knows.

- **Edge** (a CDN or firewall): limit by IP address. That stops one loud machine, yet a botnet spreads over hundreds
  of IPs that each stay under the limit.
- **Gateway**: limit by API key, user, or plan, as the [AI gateway lesson](../../ai-systems/gateway/) does for token
  budgets.
- **Service**: limit expensive operations by their real cost, such as 5 bulk exports per hour.

Per-client limits never cap the total, so the service also needs an **aggregate budget** that sheds or queues the
excess. Size every limit from measured capacity and your [latency goal](../../thinking/slos/).

### Counting across many gateways

Six gateways sit behind a [load balancer](../../scaling/load-balancing/), so who keeps each client's count?

- A **central store** such as Redis updates each bucket atomically: exact limits, with a round trip per request to a
  store everything now depends on.
- **Local limits** give each gateway a sixth of the limit: fast and storeless, though a client pinned to one gateway
  gets only a sixth.
- A **hybrid** syncs local buckets with the store every 100 ms or so.

When the store fails, **fail open** (allow, perhaps with a local fallback) or **fail closed** (reject). For most public
APIs, briefly looser limits beat an outage.

## Trade-offs

<TradeoffTable title="Which limiter, and where does the count live?">

| Choice                    | What it buys                             | What it costs                                 |
| ------------------------- | ---------------------------------------- | --------------------------------------------- |
| Token bucket              | Short bursts, then a steady average      | No hard count per period                      |
| Fixed window              | One cheap counter per client             | Up to twice the limit across a boundary       |
| Sliding window            | A hard count over any rolling period     | More memory, or a small error with slots      |
| Central counter store     | Exact limits across gateways             | A hop per request, and the store must stay up |
| Local per-instance limits | No shared state or extra latency         | Inaccurate when traffic spreads unevenly      |
| Fail open                 | A store outage never blocks good clients | Abusers get through for a while               |
| Fail closed               | Limits always hold                       | A store outage becomes a full outage          |

</TradeoffTable>

## Common mistakes

- **One global limit only.** One noisy client still takes most of the capacity.
- **A token bucket for a contract quota.** "1,000 per hour" needs a sliding window.
- **Per-IP limits as a botnet defense.** 300 IPs at 50 per second each still send 15,000 per second. Add bot filtering,
  caching, and an aggregate budget.
- **503 or a bare 429.** Send 429 with Retry-After.
- **Instant or endless retries.** Wait for Retry-After plus jitter, and cap the tries.

<KeyTakeaways>

- Per-client limits stop one noisy client from starving everyone else.
- A token bucket enforces an average rate plus a burst; a sliding window enforces a hard count per rolling period.
- Per-client limits never cap the total, so the service also needs an aggregate budget.
- Answer with 429 and Retry-After, and have clients wait with jitter and a retry cap.
- Layer limits at the edge, gateway, and service, and decide how gateways share counts and fail.

</KeyTakeaways>

<div slot="answer">

1. **Match the limiter to the requirement.** Free keys get a token bucket that refills 10 per minute and holds about 5,
   since the plan states an average with bursts. Paid keys get a sliding window over the last 60 minutes, since a
   token bucket would allow its burst plus a full hour of refill.
2. **Redirects: filter, cache, then budget.** A per-IP limit of 50 per second only caps each source's share: 300 IPs
   × 50 per second still deliver 15,000 per second. So filter bots first with reputation lists and challenges, serve
   hot short codes from the CDN cache, and put an aggregate budget of about 6,000 cache misses per second in front of
   the redirect servers. Beyond it, shed with 503 and Retry-After, or queue briefly.
3. **Counts.** Gateways keep exact link creation counts in Redis. Edge limits use local counters.
4. **Answers.** Send 429 with Retry-After. Client libraries add jitter and stop after three tries.
5. **Redis down.** Fail open with a local fallback of one sixth of each limit per gateway, and fire an alert.

</div>
