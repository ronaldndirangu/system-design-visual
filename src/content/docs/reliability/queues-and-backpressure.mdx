## The failure: a link goes viral

The sho.rt server has 5 workers, and each redirect takes about 100 ms, so it answers about 50 redirects per second. On
a normal day, 40 arrive each second, and visitors give up after 1 s. Then a celebrity shares a sho.rt link, and for 12 s
traffic jumps to 75 requests per second.

Two copies of the server get the same requests. One keeps every request in a line with no limit. The other caps the
line at 40 and turns away anything that arrives while it is full.

## Why a line with no limit fails everyone

When requests arrive faster than workers finish them, the extras wait in a **queue** until a worker is free. Trouble
starts when arrivals stay above the service rate: 75 arrive and 50 leave, so the line grows by 25 each second, to about
300 after 12 s.

That line takes 6 s to clear, and visitors give up after 1 s. The workers stay 100% busy, so CPU graphs look healthy,
while **goodput**, the answers that arrive while someone still wants them, collapses. At 20 s the unbounded server still
holds 266 requests that will all finish late.

<Analogy>

A popular restaurant keeps a waitlist. On a wild night, a host who writes down every name promises tables in three hours
to guests who leave in twenty minutes, and the kitchen cooks for empty tables. A good host says "We are full, come back
at eight." That honest no is **backpressure**.

</Analogy>

The analogy breaks because guests see the crowd and leave on their own. A request cannot see the line, and an abandoned
one still holds its place until a worker reaches it, so the server has to decide for it.

### Little's law: a line is a wait

**Little's law** says the average number of requests in a line, L, equals the rate they enter, λ, times the average
time each spends there, W: **L = λ × W**. It holds for long-run averages of any arrival pattern.

So a line limit is a promise about time. The last request in a full line waits limit ÷ drain rate, then
needs its own work, and that sum must fit the client's deadline. sho.rt drains about 50 per second, its slowest
redirect takes 140 ms, and visitors wait 1 s: 50 × (1 s minus 0.14 s) ≈ 43, so the limit is 40.

## Push back when the line is full

When the bounded line fills, the server answers the next request at once with **503 Service Unavailable** and a
**Retry-After** header. That fast no costs no worker and reaches the visitor in time to act. A calling service can try
another server or show a fallback.

This is **backpressure**: a component that cannot keep up tells its senders to slow down. A 503 only helps if callers
respect it, since clients that retry instantly multiply the load. [Retries with backoff and jitter](../retries/),
[Rate limiting](../rate-limiting/), and [Circuit breakers](../circuit-breakers/) each handle part of that.

## Shed load before the server tips over

A full line is a late signal. A limit counts requests, yet the wait each one adds depends on how fast workers run.
Suppose the link database slows from 4 s to 14 s, and every redirect takes twice as long. Workers drain about 25 per
second, so a full line of 40 means 1.6 s of waiting.

**Load shedding by wait** watches time instead. The server averages recent work times, estimates a new request's wait
(line length × average work ÷ 5 workers), and rejects it if the estimate passes a budget, here 600 ms. It also drops
requests whose visitors gave up.

### A wait budget reduces late work

Seed 42 ends with no late answers, yet the budget is no guarantee: across other seeds of this model, about 1 run in 10
still answers a few requests late. The estimate uses recent work times, so it lags when the backend slows, and a
request admitted on an old, fast average can still finish late. Two checks close most of that gap:

- **Check the budget again at pickup.** When a worker takes a request, compare the time left before the visitor's
  deadline with the expected work, and drop the request if it cannot finish.
- **Cancel cooperatively.** When the visitor gives up, mark the request cancelled. The worker checks the mark between
  steps and stops, as in [Timeouts and cancellation](../timeouts/).

<details>
<summary>Go deeper: CoDel and what to shed</summary>

Network routers use the same idea as **CoDel** (controlled delay, RFC 8289): drop packets that keep sitting in a queue
longer than a target time. TCP flow control, bounded channels in Go, and reactive streams apply backpressure the same
way inside networks and programs.

Real servers also choose **what** to shed. sho.rt drops analytics work and link previews long before a redirect, and
never sheds the health checks its load balancer uses.

</details>

## The click analytics buffer

Every redirect also produces a click event. The [Timeouts and cancellation](../timeouts/) challenge moved analytics off
the critical path, and the rest of this course keeps that design: each redirect writes its click into a small **bounded
buffer** in memory and answers at once. A separate **uploader** drains the buffer in batches to click ingest, so a slow
analytics service never blocks a redirect.

The buffer is a queue too, so it needs a rule for when it fills:

- **Block the producer.** The redirect waits for space. On the redirect path this is a deliberately unsafe design:
  slow analytics stalls every visitor. Keep it for work that must never be lost, such as payments.
- **Drop or sample.** Discard events when full, or keep 1 in 10 and scale the counts. Count every drop.
- **Spill to a durable log.** Write events to disk or Kafka for consumers to catch up, at the cost of another system.

sho.rt drops and counts at each redirect server, and ingest writes to a durable log. The uploader still calls ingest
over the network, and a failing ingest service can tie it up. [Circuit breakers](../circuit-breakers/) puts a breaker
on that call.

## Trade-offs

<TradeoffTable title="How long to let requests wait">

| Choice                    | What it buys                                     | What it costs                                              |
| ------------------------- | ------------------------------------------------ | ---------------------------------------------------------- |
| No queue                  | Nothing waits or answers late                    | Random bunching rejects requests, even below capacity      |
| Unbounded queue           | Never rejects a request                          | In a long overload, memory grows and most answers are late |
| Queue sized from deadline | Absorbs bursts; admitted requests finish in time | Rejects while full; the right size shifts when work slows  |
| Fast 503 with Retry-After | A cheap, early no                                | Callers must handle it; instant retries add load           |
| Shed by expected wait     | Cuts late answers when the server slows          | Rejects more, and its estimate lags a slowdown             |
| Block the producer        | Never loses work                                 | Slowness spreads upstream; unsafe on the redirect path     |

</TradeoffTable>

## Common mistakes

- **An unbounded queue.** It hides overload until memory runs out.
- **Sizing the line by memory.** Size it from the client's deadline.
- **Trusting the admission estimate alone.** Recheck at pickup and cancel when the caller leaves.
- **Blocking requests on a slow consumer.** Bound the buffer, then drop and count or spill to a log.
- **Retrying a 503 instantly.** Honor Retry-After and back off.

<KeyTakeaways>

- A short line absorbs bursts; an unbounded line turns a long overload into late answers for almost everyone.
- Little's law ties line length to wait: limit ÷ drain rate plus the work must fit the deadline.
- A fast 503 with Retry-After is backpressure callers can act on.
- Shedding by expected wait reduces late work; recheck at pickup and cancel when the caller leaves.
- Redirects write clicks to a bounded buffer that an uploader drains, so slow analytics never blocks a redirect.

</KeyTakeaways>

sho.rt click ingest receives 2,000 events per second and writes batches to the analytics database, which absorbs 2,500

- The backlog grows 1,000 per second, to **1.8 million events, about 360 MB** after 30 minutes. A crash loses it all.
- It then drains at 500 per second (2,500 out, 2,000 in), so recovery takes **an hour**.
- **Spill to a durable log** sized for a few hours: 2,000 per second × 200 bytes × 3 hours ≈ 4.3 GB.
- Keep each redirect server's buffer **bounded**, and **drop and count** when it fills.
- Alert on the **age of the oldest unprocessed event**. It shows the backlog before memory does.
