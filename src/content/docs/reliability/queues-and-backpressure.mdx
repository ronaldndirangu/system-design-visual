## The failure: a link goes viral

The sho.rt server has 5 workers, and each redirect takes about 100 ms of work, so it can answer about 50 redirects per
second. On a normal day, 40 arrive each second. Visitors give up after 1 s. Then a celebrity shares a sho.rt link, and
for 12 s traffic jumps to 75 requests per second, half again what the server can handle.

Two copies of the server get the exact same requests. One keeps every request in a line with no limit. The other caps
the line at 40 and turns away anything that arrives while it is full.

## Why a line with no limit fails everyone

When requests arrive faster than workers finish them, the extra ones wait in a **queue**. A queue is useful: it holds a
request for a moment so a worker can take it the instant one is free. Trouble starts when arrivals stay above the
service rate. Then the line grows by the difference every second: 75 arrive and 50 leave, so 25 more requests wait each
second, about 300 after 12 s. This run peaks at 308.

Every new request waits behind the whole line. A line of 300 drained at 50 per second takes 6 s to clear, and the
visitor gave up after 1 s. The workers stay 100% busy, so CPU graphs and throughput look healthy. What collapses is
**goodput**: answers that arrive while someone still wants them. The damage also outlasts the spike. At 20 s, 4 s after
traffic falls back, the unbounded server still holds 266 requests, and each will finish long after its visitor left.

## Little's law: a line is a wait

**Little's law** says that the average number of requests in a line, L, equals the rate at which they enter, λ, times
the average time each one spends there, W:

**L = λ × W**

It holds for averages over any long stretch of time, whatever the arrival pattern or the order of service. Over a
finite run it holds exactly when W counts only the time spent in line during the run, so a request still waiting at
the end counts its wait so far. In the unbounded viral run with seed 42, measured over the whole 20 s run, the line
averages L = 152.4 requests, λ = 61.1 requests enter it per second, and each spends W = 2.495 s in line on average:
61.1 × 2.495 ≈ 152.4. The requests still in line at 20 s keep waiting after the run stops, so their full waits run
longer than this W shows. The last rows of the simulation table recompute all three live.

The law turns a line limit into a promise about time. A request at the back of a full line waits about limit ÷ drain
rate, then needs its own work. Size the limit so that sum stays under the client's deadline:

- sho.rt drains about 50 requests per second, the slowest redirect takes 140 ms, and visitors wait 1 s.
- 50 per second × (1 s minus 0.14 s) ≈ 43, so a limit of 40 keeps nearly every admitted request in time.
- In the viral run, the line of 40 answers just 1 request late, at 12.3 s, when several slow redirects line up.

A limit costs nothing while traffic stays below capacity. Pick **Steady traffic** in the simulation above: both lanes
answer the same 800 requests in time, and neither line ever holds more than 7. Waits still climb steeply as the workers
near 100% busy, long before the line overflows; [load balancing](../../scaling/load-balancing/) puts numbers on that
curve.

## Why have a line at all?

The server could skip the line: when all 5 workers are busy, reject the request at once. Then nobody ever waits, and no
answer is ever late.

A short line smooths out both kinds of bunching: the random kind every second, and a burst that lasts a moment. It
cannot fix traffic that stays above capacity. Only fewer requests or more workers can do that.

## Push back when the line is full

When the bounded line fills, the server answers the next request at once with **503 Service Unavailable** and a
**Retry-After** header. That fast no costs microseconds and no worker. The visitor sees an error while still looking at
the screen, and a calling service can try another server or show a fallback.

This is **backpressure**: a component that cannot keep up tells whoever sends it work to slow down. It shows up at
every layer:

- TCP flow control stops a sender when the receiver's buffer fills.
- A bounded channel in Go blocks the producer until a consumer takes an item.
- Reactive streams let a consumer request a fixed number of items at a time.

A 503 only helps if callers respect it. Clients that retry instantly turn one rejected request into a stream of them.
The lessons [Retries with backoff and jitter](../retries/), [Rate limiting](../rate-limiting/), and [Circuit breakers](../circuit-breakers/) each handle a part of
that problem.

## Shed load before the server tips over

A full line is a late signal. A line limit counts requests, and the wait each request adds depends on how fast the
workers run. Suppose the link database slows down from 4 s to 14 s, and every redirect takes twice as long. The server
now drains about 25 requests per second, so a full line of 40 means 1.6 s of waiting: longer than any visitor waits.

**Load shedding by wait** watches time directly. The server keeps a running average of recent work time, estimates how
long a new request would wait (line length × average work ÷ 5 workers), and rejects the request if that estimate passes
a budget, here 600 ms. It also drops any request from the line whose visitor already gave up, so no worker spends time
on it.

Shedding is a trade. It rejects more requests than the line alone, and it depends on a good estimate of work time. In
return, every request it admits gets a useful answer, and the server never spends its workers on visitors who already
left. Network routers use the same idea under the name **CoDel** (controlled delay): they drop packets when packets keep
sitting in a queue longer than a target time.

Real servers also choose **what** to shed. sho.rt would drop analytics work and link previews long before it drops a
redirect, and it never sheds the health checks its load balancer uses to decide whether it is alive.

## The click analytics buffer

Every redirect also produces a click event for analytics. The [Timeouts and cancellation](../timeouts/) challenge moved
that work off the critical path into a local buffer. That buffer is a queue too, and the same rules apply. When the
analytics service falls behind, the buffer fills, and you must pick one of three behaviors:

- **Block the producer.** The redirect waits for buffer space. Backpressure reaches the visitor, so a slow analytics
  service slows redirects again. Wrong for clicks, right for work that must never be lost, such as payments.
- **Drop or sample.** Discard events once the buffer is full, or keep 1 in 10 and scale the counts. Redirects stay fast,
  and the click counts lose some precision. Count every dropped event in a metric so the loss stays visible.
- **Spill to a durable log.** Write events to disk or to a log such as Kafka that holds days of data, and let consumers
  catch up later. Nothing is lost, at the cost of storage, another system to run, and reports that run late.

For sho.rt, redirects never block on analytics. Each server keeps a small bounded buffer that ships events to a durable
log, and if the buffer still fills, it drops events and counts the drops.

## Trade-offs

<TradeoffTable title="How long to let requests wait">

| Choice                      | What it buys                                                | What it costs                                                                   |
| --------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------- |
| No queue                    | No request ever waits or answers late                       | Random bunching rejects many requests, even below capacity                      |
| Unbounded queue             | Never rejects a request                                     | In a long overload, waits and memory grow without limit and most answers are late |
| Queue sized from deadline   | Absorbs bursts, and admitted requests finish in time        | Rejects requests while full; the right size shifts when work slows down          |
| Fast 503 with Retry-After   | A cheap, early no that callers can act on                   | Callers must handle it, and instant retries add load                            |
| Shed by expected wait       | Keeps waits under budget even when the server slows down    | Rejects more requests, and needs a good estimate of work time                   |
| Block the producer          | Never loses work                                            | Slowness spreads upstream to whoever produces the work                          |

</TradeoffTable>

<Challenge>

The sho.rt click ingest service receives 2,000 click events per second and writes them in batches to the analytics
database, which can absorb 2,500 per second. During a nightly backup, the database absorbs only 1,000 per second for
30 minutes. Each event takes about 200 bytes. What happens to an unbounded in-memory buffer during the backup, how long
does recovery take, and what would you build instead?

<div slot="answer">

- The backlog grows by 1,000 events per second (2,000 arrive, 1,000 leave). After 30 minutes it holds **1.8 million
  events, about 360 MB** in memory. A crash or restart loses all of it, and a longer slowdown runs the process out of
  memory.
- After the backup, the backlog drains at 500 per second (2,500 leave, 2,000 arrive), so clearing 1.8 million events
  takes **an hour**. Every report in that hour runs behind.
- Clicks do not need an answer within 1 s; they need to survive. **Spill to a durable log** sized for a few hours:
  2,000 events per second × 200 bytes × 3 hours ≈ 4.3 GB.
- Keep each redirect server's local buffer **bounded**, never block redirects on it, and **drop and count** events if
  it fills.
- Alert on the **age of the oldest unprocessed event**. That is the analytics version of wait time, and it shows the
  backlog long before memory does.

</div>

</Challenge>
