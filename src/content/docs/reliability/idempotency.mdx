<Objectives>

- Explain why a client that hears no answer cannot know whether its request took effect.
- Use an idempotency key and a dedupe store so a repeated request returns the first result instead of repeating the work.
- Claim the key before doing the work, so a duplicate that arrives mid request cannot run it twice.
- Choose who creates keys, how long to keep them, and what to scope them to, and estimate what the store costs.

</Objectives>

## The failure: a lost receipt charges twice

sho.rt sells custom short links, such as sho.rt/launch-party, for $5. The phone app sends **POST /purchases**, the
server charges the card through a payment provider, and the server answers with a receipt. On a train, the phone loses
signal for a moment and the receipt never arrives. The app waits 1 s, hears nothing, and sends the purchase again. To
the server, the second request looks like a brand new purchase.

**Roughly one for every lost receipt.** The server has no way to tell a retry from a new purchase, so every attempt

charges 64 times and answers the 9 retries with the receipt it already saved.

## Why the client cannot just know

From the phone, three different failures look identical: the request got lost on the way in, the receipt got lost on
the way out, or the payment is still running. Each one is silence. The app has two choices, and both are bad without
help:

- **Give up**, and leave a customer who may have paid with no receipt and no link.
- **Retry**, and charge a customer who already paid a second time.

Idempotency removes the dilemma. An operation is **idempotent** when doing it twice has the same effect as doing it
once. "Set the link's target to example.com" is idempotent: run it ten times and the link points to the same place.
"Charge $5" is not. HTTP marks GET, PUT, and DELETE as idempotent methods; POST makes no such promise, so a purchase
endpoint has to earn it.

The usual tool is an **idempotency key**. The app creates a unique key once per purchase and sends it on every attempt,
for example in an `Idempotency-Key` header. The server keeps a **dedupe store** that maps each key to its result. A new
key means do the work and save the result. A known key means return the saved result and do nothing else. Now retrying
is always the right move.

This toy model loses only receipts. A lost request never reached the server, so retrying it was always safe; lost
receipts are the case that charges twice.

A paper cheque carries a number. Mail the same cheque twice by mistake and the bank pays it once, because it recognizes

vault, so a second teller holding a copy waits instead of paying it out too.

## Duplicates that arrive while the first is still running

A simple version saves the key together with the receipt, after the charge. That handles a lost receipt: by the time
the retry arrives, the receipt is in the store. A retry that arrives sooner is a different story.

**No.** The app gives up at 1 s and pauses 250 ms, so its retry reaches the server 1.25 s after the first payment
started. A payment that takes longer than that is still running, the store has nothing under the key yet, and the retry
starts a second payment. In this toy model with seed 42, the saved-after lane starts 10 payments while an earlier one
for the same order is still running: 10 customers pay twice, and $50 is taken by mistake. The claimed-first lane
answers 16 early retries with **409 Conflict**, charges each order exactly once, and still confirms all 64 purchases.

</Predict>

The fix is to **claim the key before doing the work**. The first request writes the key as "in progress" in one atomic
step. A copy that finds "in progress" gets 409 Conflict and tries again later; a copy that finds a saved receipt gets
that receipt. In PostgreSQL, the claim can be a single insert:

```sql
INSERT INTO idempotency_keys (user_id, key, request_hash, status)
VALUES ($1, $2, $3, 'in_progress')
ON CONFLICT (user_id, key) DO NOTHING;
```

If the insert added a row, this request owns the key and charges the card. If it added nothing, the server reads the
existing row and replays or answers 409. A separate "check, then insert" does not work: two copies can both pass the
check before either one inserts. Redis offers the same atomic claim with `SET key value NX`.

Claiming has costs of its own:

- **Extra round trips.** Each 409 sends the client around again. In the slow scenario, the claimed-first lane sends 91
  attempts against 78 for the saved-after lane. Some servers hold the duplicate until the first request finishes and
  return its result instead.
- **Stuck claims.** If the server crashes after claiming and before saving, the key says "in progress" forever. Give
  each claim a lease that expires, and record how far the work got, so a later retry can finish or safely restart it.
- **The next hop needs a key too.** The server's own call to the payment provider can time out just like the app's
  call to the server. Many payment APIs, Stripe among them, accept an idempotency key, so the server passes one along
  and its own retries stay safe. The toy model leaves this hop out.

## How long to keep keys, and who owns them

**The client makes the key, once per intent.** The app generates a random UUID when the customer taps Buy, stores it
with the pending purchase, and reuses it on every retry, even after an app restart. A key made per attempt protects
nothing.

**Scope keys to a user and an operation.** Store keys per account, so one customer's key can never return another
customer's receipt. Store a hash of the request body next to the key. If the same key arrives with a different body,
the client has a bug, and replaying the old receipt would hide it. An IETF draft for the `Idempotency-Key` header
suggests **422 Unprocessable Content** for that case and **409 Conflict** for a request still in progress.

**Keep keys longer than any retry can arrive.** Once a key expires, a late retry looks new and runs again. Stripe, for
example, removes keys once they are at least 24 hours old. The store's size follows from Little's law, which you met in
[Queues and backpressure](../queues-and-backpressure/): keys stored = purchases per second × lifetime. At 100 purchases
per second for 24 hours, that is 100 × 86,400 ≈ 8.6 million keys. With a saved receipt of about 500 bytes each, the
store holds roughly 4.3 GB (illustrative numbers).

Every purchase now pays for one extra write, and every retry for one extra read. That cost is small next to a refund,
a chargeback fee, and an angry customer.

The same idea protects sho.rt's click analytics. When a redirect server re-sends a batch of click events because an
acknowledgment got lost, an analytics counter that runs `clicks += 1` counts those clicks twice. Give each click an
event ID and skip IDs already seen. The lesson [Delivery semantics and the outbox](../../async/delivery-semantics/) covers this side in depth.

## Trade-offs

<TradeoffTable title="Making a repeat safe">

| Choice                                  | What it buys                                                   | What it costs                                                                                |
| --------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| No key                                  | Nothing to store                                               | Every retry after a lost response repeats the work                                           |
| Key saved after the work                | Retries after a finished request get the saved result          | A duplicate that arrives mid request runs the work twice                                     |
| Key claimed before the work             | At most one run per key, even with overlapping duplicates      | Needs an atomic claim, a lease for crashed requests, and extra round trips for 409 answers  |
| Long key lifetime                       | Late retries stay safe                                         | The store grows with requests per second × lifetime                                          |
| Short key lifetime                      | A small store                                                  | A retry after expiry looks new and runs again                                                |
| Naturally idempotent operation          | No store at all: "set to X" is safe to repeat                  | Many operations, such as charging a card, cannot be phrased that way                         |

</TradeoffTable>

<Challenge>

sho.rt's redirect servers send click events in batches to the analytics service, which runs `clicks[link] += 1` for
each event. When an acknowledgment gets lost, the sender re-sends the whole batch. This week, some links show more
clicks than the redirects the servers logged. About 1,000 clicks arrive per second, and every re-send happens within 10
minutes. What is going wrong, how do you fix it, and how big is your dedupe store?

<div slot="answer">

- **Re-sent batches get counted again.** Adding one is not idempotent, so every re-send inflates the counts.
- **Give each click an event ID** when the redirect server creates it, and keep that ID on every re-send.
- **Skip events already seen.** The analytics service records each event ID and the count change in the same
  transaction, so a crash between the two can neither double count nor lose a click. Storing one row per event ID and
  counting rows works too: a repeat insert changes nothing.
- **Size it with Little's law.** Keep IDs comfortably longer than the 10 minute re-send window, such as 1 hour:
  1,000 × 3,600 = 3.6 million IDs, about 58 MB of raw 16 byte IDs before index overhead.

</div>

</Challenge>
