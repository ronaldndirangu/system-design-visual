Keep this page open while you estimate. Every figure is a rough order of magnitude, rounded so the arithmetic stays easy.
Real hardware varies by a factor of two or more, so measure your own system before you bet a design on one number.

The [requirements and estimates lesson](../thinking/requirements-and-estimates/) shows how to put these numbers to work.

## Latency numbers

| Operation                              | Rough time | Compared with a memory read |
| -------------------------------------- | ---------- | --------------------------- |
| Read from the CPU's L1 cache           | 1 ns       | 0.01×                       |
| Read from memory                       | 100 ns     | 1×                          |
| Send 1 KB over a 1 Gbps network        | 10 µs      | 100×                        |
| Read 4 KB from an SSD                  | 100 µs     | 1,000×                      |
| Round trip inside one data center      | 0.5 ms     | 5,000×                      |
| Read 1 MB in sequence from an SSD      | 0.5 ms     | 5,000×                      |
| Read 1 MB in sequence from a hard disk | 5 ms       | 50,000×                     |
| Seek to a new spot on a hard disk      | 10 ms      | 100,000×                    |
| Round trip within one continent        | 40 ms      | 400,000×                    |
| Round trip across an ocean             | 150 ms     | 1,500,000×                  |

Four patterns explain most performance surprises:

- **Memory beats storage by about a thousand times.** That gap is the whole reason [caching](../scaling/caching/) works.
- **Network hops add up.** One call inside a data center costs as much time as 5,000 memory reads. A page that makes 20
  calls in a row spends 10 ms just waiting on the wire.
- **Distance dominates.** One ocean crossing costs as much as 300 round trips inside a data center. Serve users from a
  region near them.
- **Sequential reads beat random reads.** A hard disk reads a whole megabyte in less time than one seek, so storage
  engines append and read in long runs.

The [click lesson](../foundations/what-happens-when-you-click/) shows where each round trip in a page load comes from.

## Powers of two

| Power          | Exact value       | Roughly               | Unit  |
| -------------- | ----------------- | --------------------- | ----- |
| 2<sup>10</sup> | 1,024             | a thousand (10³)      | 1 KB  |
| 2<sup>20</sup> | 1,048,576         | a million (10⁶)       | 1 MB  |
| 2<sup>30</sup> | 1,073,741,824     | a billion (10⁹)       | 1 GB  |
| 2<sup>40</sup> | 1,099,511,627,776 | a trillion (10¹²)     | 1 TB  |
| 2<sup>50</sup> | about 1.13 × 10¹⁵ | a quadrillion (10¹⁵)  | 1 PB  |

Estimates treat 1 KB as 1,000 bytes. The error grows to about 10% at a terabyte, which is still smaller than the
uncertainty in your traffic guess.

## Common sizes

| Item                                              | Rough size |
| ------------------------------------------------- | ---------- |
| One ASCII character or a boolean                  | 1 B        |
| A 32 bit integer                                  | 4 B        |
| A 64 bit integer or a timestamp                   | 8 B        |
| A UUID                                            | 16 B       |
| One short link row (code, long URL, timestamps)   | 500 B      |
| A short text post with its metadata               | 1 KB       |
| A compressed phone photo                          | 2 MB       |
| One minute of 1080p video at 5 Mbps               | 40 MB      |

A handy storage rule: 1 KB per record times 1 million records a day is 1 GB a day, or about 365 GB a year.

## Availability in nines

Each extra nine cuts the downtime budget tenfold. A month here means 30 days.

| Availability | Downtime per year | Per month | Per week     | Per day |
| ------------ | ----------------- | --------- | ------------ | ------- |
| 99%          | 3.65 days         | 7.2 h     | 1 h 41 min   | 14.4 min |
| 99.9%        | 8.76 h            | 43.2 min  | 10.1 min     | 86.4 s  |
| 99.95%       | 4.38 h            | 21.6 min  | 5.04 min     | 43.2 s  |
| 99.99%       | 52.6 min          | 4.32 min  | 60.5 s       | 8.64 s  |
| 99.999%      | 5.26 min          | 25.9 s    | 6.05 s       | 0.86 s  |

At four nines, one slow deploy can spend a whole month's budget. Teams at that level automate rollbacks because a human
cannot react inside four minutes.

## Combining availability

### Parts in series

When a request needs every part to work, it succeeds only when all of them are up. **Multiply the availabilities.**

A load balancer at 99.99%, an app server at 99.9%, and a database at 99.9% give 0.9999 × 0.999 × 0.999 ≈ 99.79%. That
is about 18 hours of downtime a year, worse than any single part. Every dependency you add lowers the ceiling.

### Parts in parallel

When any one of several copies can serve a request, the system fails only when every copy fails at the same time.
**Multiply the failure chances, then subtract the product from 1.**

Two replicas at 99.9% each fail 0.1% of the time. Both fail together 0.001 × 0.001 = 0.000001 of the time, so the pair
reaches 99.9999% in theory.

That figure assumes the copies fail independently and failover works instantly. Shared power, one bad deploy pushed to
both copies, or a failover that takes two minutes all pull the real number far lower. Treat parallel math as an upper
bound, then test failover for real. The [read replicas lesson](../scaling/read-replicas/) shows what a replica can and
cannot take over.
