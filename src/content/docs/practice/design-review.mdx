<Objectives>

- Read a system design and flag the parts that will fail under load, using the questions from the design checklist.
- Name six common anti-patterns: a single point of failure, a cache with no expiry, a cross-shard join on the hot path,
  retries without backoff or jitter, an unbounded queue, and a dual write without an outbox.
- Tell a real risk from a sound choice that only looks unusual, and count false alarms as a cost.
- Propose the standard fix for each flaw and name the lesson that teaches it.

</Objectives>

## The failure: every box was there

A team reviews the design for a concert ticket sale. The reviewers walk the diagram from left to right and ask one
question per box: is it there? Load balancer, web servers, session store, database. Every box is there, so the design
passes.

At 10:00 the sale opens. At 10:03 the single session store runs out of memory and restarts. Every buyer is logged out
mid checkout, and the retry storm of fresh logins keeps it down for twenty minutes.

Ask what happens when a box stops. The answer here is "every buyer loses their session", and one machine with no
standby makes that outcome certain sooner or later. A useful review asks failure questions about each part: what if it
stops, what if load grows ten times, what if a call to it slows down, what if two writes split. "Is it there" only
checks the drawing.

</Predict>

## How a review works

The questions come from [the design checklist](../../thinking/design-checklist/). A review runs them against someone
else's design, one part at a time.

<Steps>

1. **Read each part and its note.** The notes are the design document's own words. They describe what each part does
   and give nothing away.

2. **Ask the failure questions.** What if this stops? What if load grows ten times? What if a call to it slows down?
   What if it holds stale data? Turn on **Show review questions** to see the checklist step that would catch each
   item, with its question.

3. **Flag what looks wrong and pick a fix.** Press a number key (1 to 9, and 0 for item 10) or use the Flag buttons.
   Each flag opens a list of fixes; pick the one you would ask for.

4. **Replay the first hour of the sale.** Press **Play replay** or step one event at a time with **Next event**. Each
   item either causes an incident or holds, and the transcript records whether you flagged it.

5. **Reveal the answers.** Every card shows its verdict, the anti-pattern or the sound choice behind it, the
   reference fix, and the lesson that teaches it.

</Steps>

<Analogy>

A building inspector walks a new building with a code book. They spend no time on whether the lobby looks nice. They
check specific failure modes: one exit for the whole floor, wiring sized for half the load, a fire door propped open.
Each finding cites the rule that fixes it. A design review works the same way, with the anti-patterns as the code book.

</Analogy>

## Reading your review

- **A missed flaw** shows up as an incident you did not flag. Read its card first: the explanation names the question
  that would have caught it.
- **A false alarm** is a part you flagged that held. Its card explains why the choice is sound, which is worth as much
  as spotting a flaw.
- **A fix that does not match** usually treats the symptom. "Add more servers of the same kind" and "Move it to a
  bigger machine" buy time for most of these flaws without removing them.
- **Where to go next.** [Load balancing](../../scaling/load-balancing/) teaches the fix for the single point of
  failure, [caching](../../scaling/caching/) teaches expiry and invalidation, and
  [sharding](../../scaling/sharding/) teaches how to keep hot queries on one shard. [Retries with backoff and jitter](../../reliability/retries/),
  [queues with backpressure](../../reliability/queues-and-backpressure/), and
  [the outbox](../../async/delivery-semantics/) each get their own lesson in the Reliability and Async modules.

## Trade-offs

<TradeoffTable title="How to run a design review">

| Choice                              | What it buys                                           | What it costs                                                  |
| ----------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------- |
| Walk the request path, part by part | Covers every part, in the order a request touches them | Can miss problems that span parts, such as a dual write        |
| Walk a list of anti-patterns        | Catches the known failure modes fast                   | Misses a flaw that fits no pattern on the list                 |
| Flag broadly                        | Fewer misses                                           | More false alarms, and the real risks get diluted              |
| Flag only what you can explain      | A short list the team trusts                           | You may hold back on a real risk you cannot yet put into words |
| Propose a fix with every flag       | Turns findings into work the team can start            | Slower, and a weak fix can anchor the discussion               |
| List findings first, fix later      | A faster review that stays on risks                    | Findings without fixes tend to sit in the backlog              |

</TradeoffTable>

<KeyTakeaways>

- Look for the boundaries where a design fails, overloads, or serves stale data.
- Flag a choice only when you can explain how it breaks; an unfamiliar choice alone is no finding.
- Pair each finding with a fix, and say why the fix holds at that boundary.

</KeyTakeaways>

<Challenge>

Review this design on paper before you open the answer. **A photo sharing app:** uploads go to one web server, which
saves each photo on its own disk; a nightly job copies the day's photos to object storage. The upload request also
sends a push notification to every follower before it returns. Like counts live in one row per photo, updated by
reading the count, adding one, and writing it back. Photos reach viewers through a CDN under content-hashed names.
Find the flaws, propose a fix for each, and name the part that holds.

<div slot="answer">

1. **Photos on one server's disk, behind one web server.** The server is a single point of failure, and a disk failure
   loses every photo since the last nightly copy. Run two or more stateless web servers behind a load balancer, sized
   so the others carry the peak when one fails, and write each upload straight to replicated object storage.
2. **Notifications inside the upload request.** A user with many followers makes every upload slow, and a slow push
   service fails uploads. Report success once the photo is in object storage and the transaction that saves its row
   commits; if that commit fails, the upload fails and a cleanup job deletes the stored object. In the same
   transaction, insert a notification row into an outbox. A relay publishes outbox rows to a durable queue at least
   once, so a relay crash can send a row twice, and the notification workers skip any upload id they have already
   sent.
3. **Read, add one, write back on the like count.** Two likes at the same moment both read 10 and both write 11, so
   one like vanishes. Use an atomic increment in the database, or split a hot counter across several rows and sum them.
4. **The CDN with content-hashed names holds.** A new photo gets a new name, so a cached copy never goes stale, and
   a long cache lifetime is safe.

</div>

</Challenge>
