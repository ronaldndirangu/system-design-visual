## The failure: page 2 repeats page 1

The dashboard lists a user's links newest first, 10 per page, with `GET /v1/users/7/links?page=2&size=10`. Every test
passes. Then a power user who creates links from a script while browsing writes in: page 2 shows links from page 1, and
a link they know exists never appears on any page. Nothing errored, and the logs look clean.

## The idea: name the last link you saw

An offset says "skip 10 rows". Rows are positions, and positions move whenever the list changes above them. A cursor
says "start after link #41". A link keeps its identity however many links arrive or vanish, so the next page starts in
the right place every time.

<StepDiagram client:visible title="Offset pagination on a changing list" nodes={nodes} edges={edges} steps={steps} height={290} />

<Analogy>

A friend reads your mail aloud from a pile, newest on top, and you say "read me letters 11 to 20". While they read, two
new letters land on the pile. Letters 11 and 12 are now ones you already heard. If you say "read the 10 letters under
the one from the bank" instead, it does not matter how many letters land on top.

</Analogy>

The simulation is a toy model. The client fetches a page every 3 seconds, and the creates and deletes follow a seeded
random schedule, so each scenario plays out the same way every run. The row counts are illustrative.

<PaginationWidget client:visible />

What to look for:

- **Busy creator.** Offset pagination shows 10 repeated rows and needs 6 pages to reach the end of a 50 link list. The
  cursor shows each of the 50 links once, in 5 pages. Both lanes leave out the 13 links created after page 1 loaded; a
  refresh shows them at the top.
- **Deletions.** Each delete slides the links below it up one row. Offset pagination skips 6 links it never showed. The
  cursor skips none.
- **Both.** Offset pagination shows 9 repeats and skips 5 links. Of the 41 links that existed for its whole session, 28
  appear once, 8 appear twice or more, and 5 never appear: 28 + 8 + 5 = 41. The cursor lane finishes sooner, so 46
  links last its whole session, and it shows each of them exactly once.
- **Rows walked.** In the Both run, the database walks 201 rows to serve the offset pages and 48 for the cursor pages.
  At page 500 with 20 links per page, an offset makes the database step over 10,000 rows to return 20. A cursor seeks
  straight to its spot through an index.
- **Quiet list.** With nothing changing, both lanes show all 50 links once. Offset pagination works fine on a list that
  holds still, which is why the bug passes tests.

## Cursors in practice

The two lanes differ by one clause in the query.

```sql
-- Offset: page 3 walks past 20 rows, then returns 10.
SELECT code, url FROM links
WHERE user_id = 7
ORDER BY id DESC
LIMIT 10 OFFSET 20;

-- Cursor: seek to the last link the client saw, then return 10.
SELECT code, url FROM links
WHERE user_id = 7 AND id < 41
ORDER BY id DESC
LIMIT 10;
```

The cursor query needs an index on `(user_id, id)` to seek instead of scan; the [indexes lesson](../indexes/) shows
why. Sort on a key that never repeats. If you sort by `created_at`, add `id` as a tiebreaker and put both in the cursor.

Hand the client an **opaque cursor**, such as `"next": "eyJpZCI6NDF9"`, instead of a raw id. The client sends it back
unread, so you can change the sort order or the encoding later without breaking anyone. Return `"next": null` on the
last page.

Cursors give up two things: jumping straight to page 37, and a cheap total count. Infinite scroll and API clients rarely
need either. Admin tables with page numbers over a list that rarely changes can keep offsets.

## Name resources, let HTTP supply the verbs

A good API reads like a list of nouns. The URL names a resource, the HTTP method says what to do with it, and the status
code says what happened.

```text
POST   /v1/links               create a link           201 Created, Location: /v1/links/x7Kp2
GET    /v1/links/{code}        read one link           200 OK
PATCH  /v1/links/{code}        change fields           200 OK with the updated link
DELETE /v1/links/{code}        delete it               204 No Content
GET    /v1/users/{id}/links    the dashboard list      200 OK with one page and a next cursor
GET    /{code}                 the redirect            302 Found, Location: the long URL, Cache-Control: no-store
```

Use plural nouns and stable identifiers. Avoid verbs in paths such as `/createLink` or `/getLinksForUser`; the method
already carries the verb. `PATCH` sends only the fields that change, so two editors who change different fields do not
erase each other. The `Location` header on a `201` tells the client where the new link lives.

**The redirect: 301 or 302?** The status code says whether the move is permanent, and the `Cache-Control` header says
who may remember it. Browsers may cache a `301 Moved Permanently` with no expiry, and many do. Once a browser holds it,
later clicks from that browser skip your server: fast and cheap, yet those clicks never reach your counter, and the
owner can no longer change where that browser goes. A `302 Found` (or `307 Temporary Redirect`) marks the move as
temporary, so browsers keep it only when headers allow. Send `Cache-Control: no-store` with it, and no browser or proxy
keeps a copy, so every click reaches the server and edits take effect at once. A shortener that sells click analytics
answers `302` with `no-store`.

## Status codes say what happened

A client should know what happened, and what to do next, from the status code alone. The body adds detail.

| Code | Meaning | Shortener example |
| --- | --- | --- |
| `200 OK` | It worked; here is the result | `GET /v1/links/x7Kp2` |
| `201 Created` | A new resource exists at `Location` | `POST /v1/links` |
| `204 No Content` | It worked; nothing to return | `DELETE /v1/links/x7Kp2` |
| `301` / `302` | Go to `Location` instead | The redirect `GET /x7Kp2` |
| `400 Bad Request` | The request is malformed | The body is not JSON, or `url` is missing |
| `401 Unauthorized` | We do not know who you are | Missing or expired token |
| `403 Forbidden` | We know who you are; you may not do this | Deleting another user's link |
| `404 Not Found` | No such resource | `GET /v1/links/nope` |
| `409 Conflict` | Clashes with the current state | The custom alias is taken (see [transactions](../transactions/)) |
| `422 Unprocessable Content` | Well formed, but breaks a rule | `url` points back at the shortener itself |
| `429 Too Many Requests` | Slow down; `Retry-After` says when | A script creating links in a tight loop |
| `500 Internal Server Error` | The server has a bug | An unhandled exception |
| `503 Service Unavailable` | Down for now; try again later | The database is failing over |

A `4xx` code means the client must change the request before it tries again. A `5xx` code means the server failed, and
the same request may work later. Retry `5xx` and `429` with backoff; retrying most `4xx` codes just repeats the
mistake. The [Rate limiting](../../reliability/rate-limiting/) lesson covers how a server decides when to send `429`.

Give every error the same body shape, with a stable machine readable code next to the human message:

```json
{
  "error": {
    "code": "alias_taken",
    "message": "The alias sale is already in use.",
    "request_id": "req_7Hq2LmX9"
  }
}
```

Apps branch on `code`, people read `message`, and support asks for `request_id`.

**Retries need idempotency.** A phone on a train sends `POST /v1/links`, and the connection drops before the `201`
arrives. The app cannot tell whether the link exists, so it retries, and the user may end up with two links. `GET`,
`PUT`, and `DELETE` are idempotent by definition: sending one twice leaves the same result as sending it once. `POST` is
not. The fix is an `Idempotency-Key` header: the client
sends a random key with the request, and the server stores the first response under that key and returns it again for
any repeat. The [Idempotency](../../reliability/idempotency/) lesson builds this in detail.

## Request IDs connect a complaint to a log line

A user writes in: "Creating a link failed this morning." Without more detail, you search millions of log lines by time
and guess. With a request ID, you search for one string.

The server assigns an ID to every request, or adopts the caller's `traceparent` header when one arrives, and does three
things with it:

1. Returns it on **every** response, errors included, as `X-Request-Id`.
2. Writes it on every log line that request produces, and passes it along on every call to another service.
3. Shows it in error messages, so the user can paste it into a support ticket.

```http
HTTP/1.1 409 Conflict
X-Request-Id: req_7Hq2LmX9
Content-Type: application/json
```

One ticket, one search, one request's full story across every service it touched.

## Breaking changes

Once a client ships, the API is a promise. The contract covers more than the URL list: field names, field types, which
fields are required, the status codes, the error codes, and the defaults. A client written against `/v1` relies on all
of it, and you cannot update every client on the day you deploy. Old phones keep old app versions for years, and a
partner's integration changes on the partner's schedule.

Some changes are safe for any client that ignores fields it does not know: adding an optional response field, adding an
optional request parameter, adding a new endpoint. Others break clients the moment they deploy: renaming or removing a
field, changing its type, making a parameter required. The worst ones break nothing loudly. Change the redirect default
from `302` to `301`, and every client still gets a valid response while click counts quietly fall short.

<ContractChangeWidget client:visible />

What to look for:

- **Rename a field, in place.** The old mobile app and the partner both use `url`, so both break on deploy. The web app
  breaks too: its new code ships in the same deploy, yet every tab opened before the deploy still runs the old code until
  the user reloads. Switch to **Expand, then contract**: nobody breaks, and the price is running `/v1` and `/v2` side by
  side until the old clients retire.
- **Change a default, in place.** No client sees an error, yet two of them are now wrong: browsers that cache the `301`
  skip the server, and the dashboards undercount clicks. A silent break is harder to catch than a crash.
- **Add an optional field, with the strict parser on.** The safest change on the list breaks the partner, because its
  parser rejects any field it does not know. Turn the toggle off to see the same change break nobody.

The last point is why clients should be **tolerant readers**: read the fields you need, ignore the rest, and treat a
missing optional field as absent. Then the server can add fields freely. Most JSON libraries behave this way by
default; strict schema validation on responses turns every addition into an outage.

**Expand, then contract** turns one breaking change into three safe steps. Expand: add the new shape next to the old one
and accept both. Migrate: move clients over, and track traffic per version and per client (an app version header makes
this easy) to see who still calls the old shape. Contract: remove the old shape, but only in a new version, so clients
that never migrate keep working on the old one.

## Versioning

A version gives breaking changes somewhere to live. Two common places to put it:

- **In the URL**, as in `/v1/links` and `/v2/links`. Easy to see in logs, easy to route, and easy to try in a browser.
  Caches treat the versions as different resources with no extra setup.
- **In a header**, such as `Accept: application/vnd.shortener.v2+json` or a dated `Api-Version: 2025-06-01`. URLs stay
  stable, and a client can move one request at a time. Logs and caches must read the header too, and a cache must list
  it in `Vary` so it does not serve a `v1` body to a `v2` client.

Either works when you are consistent. Bump the version only for breaking changes; additive changes ship in place. When
you plan to retire a version, announce a date, return a `Sunset` header on its responses, and watch its traffic. Turn
it off when the traffic reaches zero, or when the date arrives and the remaining callers have been told.

## REST, RPC, and GraphQL

Everything above uses REST: resources at URLs, HTTP methods as verbs, status codes as outcomes. Two other styles come up
often, and one shortener can use all three in different places.

**REST** for the public API. A client asks for a resource by URL:

```http
GET /v1/links/x7Kp2
Accept: application/json
```

**RPC with gRPC** for the redirect service telling the analytics service about each click. A client calls a function
whose signature lives in a shared `.proto` file:

```proto
service Analytics {
  rpc RecordClick (Click) returns (Ack);
}

message Click {
  string code = 1;
  int64 clicked_at_ms = 2;
}
```

**GraphQL** for a dashboard screen that shows each link with its owner and its recent clicks. A client sends one query
to one endpoint, `POST /graphql`, and names every field it wants back:

```graphql
query {
  user(id: 7) {
    plan
    links(first: 10) {
      code
      url
      clicksLast7Days
    }
  }
}
```

| | REST | gRPC | GraphQL |
| --- | --- | --- | --- |
| How a client asks | An HTTP method on a resource URL | A call to a generated function, sent as binary over HTTP/2 | A query listing exact fields, posted to a single endpoint |
| The contract | URLs, methods, status codes, and JSON shapes, often written down in OpenAPI | A `.proto` schema; both sides generate typed code from it | One typed schema; the server checks every query against it |
| Caching | Built in: browsers, CDNs, and proxies cache `GET` responses by URL | None at the HTTP layer; the caller caches in its own code | Hard at the HTTP layer, since most queries are POSTs to one URL; clients cache objects by id |
| Fits best | Public APIs over resources, and anything a browser or `curl` calls | High volume calls between your own services | Screens that each need a different slice of related data |

**REST** works with every HTTP tool ever written, and `GET` responses cache for free. A CDN can answer
`GET /v1/links/x7Kp2` from an edge near the user with the right `Cache-Control` header. The cost shows on rich screens:
a page that needs links, owners, and click stats may make several calls, or push you to add endpoints shaped for one
screen.

**gRPC** gives both sides generated code from one schema, so a call with the wrong field or type fails to compile inside
each service. That check ends at the build: the two services deploy separately, so old and new versions talk to each
other during every rollout. Protobuf makes careful evolution possible. It identifies fields by number, so adding a
field with a new number is safe, renaming a field is safe on the binary wire, and reusing a number for a new meaning
breaks old readers. A breaking change check in CI, such as `buf breaking`, compares each `.proto` edit against the last
release, and a rollout test with old and new versions side by side catches the rest. Messages are small and binary, and
one HTTP/2 connection carries many calls at once, plus streams. Browsers cannot call gRPC directly without a gRPC-Web
proxy, and you cannot try it with plain `curl`.

**GraphQL** lets the dashboard fetch exactly the fields one screen needs in one round trip, and the server can see which
fields clients still request before it removes one. One innocent query can fan out into thousands of database reads,
one per link per field, so servers batch lookups and cap query depth and cost. Errors usually arrive as `200 OK` with an
`errors` list in the body, so monitoring must read bodies as well as status codes.

Many systems mix them: REST at the public edge, gRPC between internal services, and sometimes GraphQL as a layer that
gathers data from several services for one rich frontend.

## Trade-offs

<TradeoffTable title="Choices for the links API">

| Choice                                   | What it buys                                                         | What it costs                                                                  |
| ---------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Offset pagination (`?page=3&size=10`)    | Jump to any page; easy totals; simple SQL                            | Repeats and skips on a changing list; deep pages walk every earlier row        |
| Cursor pagination (`?after=<cursor>`)    | Stable pages while the list changes; each page costs one index seek  | No jumping to page 37; no cheap total; needs a unique, indexed sort key        |
| `302` redirect with `no-store`           | Every click reaches the server and counts; owners can edit the target | Every click costs a round trip to your server                                  |
| `301` redirect                           | Browsers may cache it; repeat clicks can skip your servers           | Cached clicks go uncounted; you cannot change or expire a cached destination   |
| Change the contract in place             | One version to run; fast to ship                                     | Old clients break on deploy, or worse, keep running and quietly go wrong       |
| Expand, then contract, with `/v2`        | No client breaks; each one moves on its own schedule                 | Two versions to run, test, and document until the old one retires              |
| REST                                     | Works with every HTTP tool; `GET` responses cache in browsers and CDNs | Rich screens need several calls or custom endpoints                          |
| gRPC                                     | Typed generated stubs; compact binary messages; streaming            | Browsers need a proxy; no HTTP caching; harder to try by hand                  |
| GraphQL                                  | Each client fetches exactly the fields it needs in one round trip    | HTTP caching is hard; one query can cost a lot without depth and cost limits   |

</TradeoffTable>

<Challenge>

Design the API for a new feature: a user uploads a CSV with 500 long URLs, and the shortener creates a link for each.

1. Which endpoint, and what status code does a successful upload return?
2. Row 212 asks for an alias someone else owns, and row 380 holds a URL that does not parse. What happens to the
   other 498 rows, and how does the client find out?
3. How does the client page through 500 results?
4. The phone loses its connection mid upload. What makes the retry safe?
5. How do clients that only know `/v1` keep working?

<div slot="answer">

1. **Treat the import as a resource:** `POST /v1/link-imports`. A small file can finish inside the request and return
   `201 Created` with the import's summary. A large one should return `202 Accepted` with
   `Location: /v1/link-imports/imp_42`, which the client polls until its status reads `done`. A file that is not a CSV
   gets `400`; one over the size limit gets `413 Content Too Large`.
2. **Partial success, reported per row.** Create the 498 good links and record each failure with its row number and the
   same error codes the single create uses: `alias_taken` and `invalid_url`. The import's summary reports
   `created: 498, failed: 2`. If some users need all or nothing, offer `"atomic": true`, which runs every insert in one
   transaction and creates nothing when any row fails.
3. **With a cursor:** `GET /v1/link-imports/imp_42/results?size=100&after=<cursor>`, ordered by row number, with a
   filter such as `?status=failed` so the client can show just the two problems.
4. **An `Idempotency-Key` header on the upload.** A retry with the same key returns the same import instead of creating
   500 more links. Count all 500 creates against the user's rate limit, so an import cannot bypass the limit that single
   creates obey.
5. **The feature is purely additive:** new endpoints and new error codes in the same body shape. Nothing that `/v1`
   clients already call changes, so no version bump is needed, and clients that ignore the feature never notice it.

</div>

</Challenge>
