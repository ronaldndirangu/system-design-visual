## The failure: one tap, two links

A commuter pastes a long URL into the shortener's phone app and taps Shorten as the train enters a tunnel. The server
creates the link `x7Kp2` and answers `201 Created`, and the response dies in the tunnel. After 10 seconds of silence,
the app sends the same `POST /v1/links` again. That afternoon a ticket arrives: "I tapped once and got two links."

You mail a payment form to your bank, hear nothing, and mail a copy. If both carry the same reference number, the

## Name resources, let HTTP supply the verbs

A good API reads like a list of nouns: the URL names a resource, the method says what to do with it, and the status
code says what happened. Here is the shortener's public API:

```text
POST   /v1/links             201, Location: /v1/links/x7Kp2
GET    /v1/links/{code}      200 with the link
PATCH  /v1/links/{code}      200 with the updated link
DELETE /v1/links/{code}      204 No Content
GET    /v1/users/{id}/links  200 with one page of links
GET    /{code}               302, Location: the long URL
```

Use plural nouns and stable ids, and keep verbs such as `/createLink` out of paths; the method already carries the
verb. `PATCH` sends only the fields that change, and a `201` carries a `Location` header that says where the new link
lives.

**The redirect: 301 or 302?** As [What happens when you click](../what-happens-when-you-click/) showed, browsers may
cache a `301 Moved Permanently`. Repeat clicks from that browser skip your server and the click counter, and the owner
can no longer change where they go. A `302 Found` with `Cache-Control: no-store` sends every click to the server, so
each one counts and edits apply at once.

## Methods and idempotency

A request is **idempotent** when sending it twice leaves the server in the same state as sending it once. HTTP defines
`GET`, `PUT`, and `DELETE` as idempotent, so a client may resend them after a timeout. A second `DELETE` may answer
`404`, yet the link is gone either way. `POST` and `PATCH` make no such promise: each `POST` may create something new,
which is the tunnel bug.

The fix gives the retry something to match. The app generates a random key once per tap and sends it with every
attempt:

```http
POST /v1/links
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
Content-Type: application/json

{"url": "https://example.com/a/very/long/path"}
```

The server stores the key with its response. When the key arrives again, it skips the insert and replays the stored
`201` for `x7Kp2`. Write the key in the same [transaction](../transactions/) as the link, so two racing attempts cannot
both insert. The IETF draft for this header adds two rules: a reused key with a different body gets `422`, and a retry
that arrives while the first attempt still runs gets `409`. Stripe prunes keys once they are at least 24 hours old, so
retries must finish inside that window.

[Idempotency](../../reliability/idempotency/) builds the key store in depth, and [Retries](../../reliability/retries/)
covers backoff and when to give up.

## Status codes say what happened

A client should know what happened, and what to do next, from the status code alone.

| Code | Meaning | Shortener example |
| --- | --- | --- |
| `200 OK` | It worked; here is the result | `GET /v1/links/x7Kp2` |
| `201 Created` | A new resource exists at `Location` | `POST /v1/links` |
| `204 No Content` | It worked; nothing to return | `DELETE /v1/links/x7Kp2` |
| `301` / `302` | Go to `Location` instead | The redirect `GET /x7Kp2` |
| `400 Bad Request` | The request is malformed | `url` is missing |
| `401 Unauthorized` | We do not know who you are | Missing or expired token |
| `403 Forbidden` | We know who you are; you may not do this | Deleting another user's link |
| `404 Not Found` | No such resource | `GET /v1/links/nope` |
| `409 Conflict` | Clashes with the current state | The custom alias is taken |
| `422 Unprocessable Content` | Well formed, but breaks a rule | `url` points at the shortener |
| `429 Too Many Requests` | Slow down; `Retry-After` says when | A script in a tight loop |
| `500 Internal Server Error` | The server has a bug | An unhandled exception |
| `503 Service Unavailable` | Down for now; try again later | The database is failing over |

Most `4xx` codes mean the client must change the request before it tries again. A `5xx` code means the server failed,
and the same request may work later. Retry `5xx` and `429` with backoff; [Rate limiting](../../reliability/rate-limiting/)
covers when a server sends `429`. [API design details](../api-design/) adds the error body that names the exact
failure, plus request IDs, pagination, and versioning.

## REST, RPC, and GraphQL

Everything above is REST: resources at URLs, methods as verbs, status codes as outcomes. Two other styles come up
often, and one shortener can use all three.

### REST

The public API. A client asks for a resource by URL:

```http
GET /v1/links/x7Kp2
Accept: application/json
```

REST works with every HTTP tool, and a CDN can cache `GET` responses near the user. Rich screens pay for it: a page
that needs links, owners, and click stats makes several calls.

### gRPC

Calls between your own services, such as the redirect service reporting each click. The function signature lives in a
shared `.proto` file:

```proto
service Analytics {
  rpc RecordClick (Click) returns (Ack);
}

message Click {
  string code = 1;
  int64 clicked_at_ms = 2;
}
```

Both sides generate code from that schema, so a call with the wrong field fails to compile. Messages are small and
binary, and one HTTP/2 connection carries many calls at once. Browsers need a gRPC-Web proxy, and plain `curl` cannot
call it.

<details>
<summary>Go deeper: changing a .proto without breaking callers</summary>

The compile check ends at the build. The two services deploy separately, so old and new versions talk to each other
during every rollout. Protobuf identifies fields by number: adding a field with a new number is safe, renaming a field
is safe on the binary wire, and reusing a number for a new meaning breaks old readers. A breaking change check in CI,
such as `buf breaking`, compares each `.proto` edit against the last release, and a rollout test with old and new
versions side by side catches the rest.

</details>

### GraphQL

A dashboard that shows a user's plan and each link with its recent clicks. The client posts one query to `/graphql`
and names every field it wants:

```graphql
query {
  user(id: 7) {
    plan
    links(first: 10) {
      code
      url
      clicksLast7Days
    }
  }
}
```

One round trip returns exactly the fields one screen needs. One query can also fan out into thousands of database
reads, so servers batch lookups and cap query depth and cost. Errors often arrive as `200 OK` with an `errors` list in
the body, so monitoring must read bodies as well as status codes.

Many systems mix the three: REST at the public edge, gRPC between internal services, and sometimes GraphQL in front of
several services for one rich frontend.

## Trade-offs

<TradeoffTable title="Choices for the links API">

| Choice | What it buys | What it costs |
| --- | --- | --- |
| `302` redirect with `no-store` | Every click counts; owners can edit the target | A round trip to your server per click |
| `301` redirect | Repeat clicks can skip your servers | Cached clicks go uncounted, and you cannot change their target |
| `POST` with `Idempotency-Key` | Safe retries of creates | A store of keys and responses for a window |
| REST | Every HTTP tool works; `GET` responses cache in CDNs | Rich screens need several calls |
| gRPC | Typed generated stubs, binary messages, streams | Browsers need a proxy; no HTTP caching |
| GraphQL | Exact fields for each screen in one round trip | Hard to cache; needs depth and cost limits |

</TradeoffTable>

When not to use them: `GET`, `PUT`, and `DELETE` need no key store, since repeats are already safe. A `301` fits a
target that never changes and clicks nobody counts. Skip gRPC when browsers or partners call the API, and skip GraphQL
when every screen needs the same few resources.

## Common mistakes

- Generating a new `Idempotency-Key` for each attempt, so every retry looks like a new request.
- Putting a write behind `GET`, such as `GET /deleteLink?code=x7Kp2`, so a crawler or prefetching browser deletes it.
- Returning `200 OK` with an error in the body, so dashboards count the failure as a success.
- Retrying `400` and `403`, which repeats the mistake and adds load.
- Answering the redirect with `301`, then wondering why click counts stall.

<KeyTakeaways>

- URLs name resources with nouns, HTTP methods carry the verbs, and status codes say what happened.
- `GET`, `PUT`, and `DELETE` are idempotent. `POST` is not, so a retried create needs one `Idempotency-Key` sent with
  every attempt.
- Most `4xx` codes mean fix the request. A `5xx` or `429` means retry later with backoff.
- REST suits public APIs and caching, gRPC suits high volume calls between your own services, and GraphQL suits screens
  that each need a different slice of data.

</KeyTakeaways>
