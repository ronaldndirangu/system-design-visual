The shortener has a live dashboard: open a link's stats page and its click count should tick up as people click.
Plain HTTP only lets the browser ask and the server answer, so the server has no way to speak first. Four transports
work around that. They differ in how quickly a click reaches the screen, how many requests they send, and what they
hold open on the server.

## The four transports

1. **Polling.** The browser asks "anything new?" every few seconds. It is the simplest option and works through every
   proxy and cache. Each click waits for the next poll, and quiet periods produce empty answers.
2. **Long polling.** The browser asks, and the server holds the request open until a click happens or a timeout
   passes (25 s here). The answer ends the request, so the browser asks again straight away. Clicks arrive quickly,
   at the cost of one held request per viewer and one new request per message.
3. **Server-sent events (SSE).** The browser opens one HTTP request with `EventSource`, and the server never finishes
   the response. It writes a `data:` line for every click. Messages flow from server to browser only. When the stream
   drops, the browser reconnects on its own. Resuming takes server work too: tag each event with an `id:` line, and the
   browser sends the last id it saw in a `Last-Event-ID` header. The server can then replay the events after it, as
   long as it still keeps them.
4. **WebSocket.** The browser sends an HTTP request with `Upgrade: websocket`, the server answers
   `101 Switching Protocols`, and the connection becomes a two-way channel of text or binary frames. Either side can
   send at any moment. Your code handles reconnects and resuming.

- **Viral burst.** 16 clicks pile up between two polls and arrive in one answer, up to 4.5 s late. Long polling stays

- **The server's side.** Both streams hold a connection for 59.9 s of the minute, per viewer. Polling holds nothing
  between requests.

## Side by side

| | Polling | Long polling | Server-sent events | WebSocket |
| --- | --- | --- | --- | --- |
| Who sends | Browser asks, server answers | Browser asks, server answers when there is news | Server pushes; the browser sends with ordinary requests | Both sides, any time |
| Delay to show a click | Up to one poll interval | About one network trip | About one network trip | About one network trip |
| Requests in the quiet minute (toy) | 12 | 7 | 1 | 1 |
| Held on the server | Nothing between polls | One request per viewer, until news or timeout | One response per viewer, for the session | One connection per viewer, for the session |
| Reconnect | The next poll | The next request | Built in; resuming needs event ids and server replay | Your code |
| Payload | Any HTTP body | Any HTTP body | UTF-8 text events | Text or binary frames |

## What the table leaves out

- **Idle timeouts.** Proxies and load balancers close connections that stay silent too long, often after 60
  seconds. Keep the long poll timeout under that limit, and send a heartbeat on streams every 15 to 30 seconds.
- **Buffering.** A proxy that buffers responses holds SSE events back until its buffer fills. Turn buffering off for
  the stream's route.
- **Connection limits.** Over HTTP/1.1, a browser opens about six connections per host, and every SSE tab uses one.
  HTTP/2 carries many streams over one connection and removes the problem.
- **Fan-out.** A click lands on whichever app server the [load balancer](../../scaling/load-balancing/) picks, and the
  viewer's stream lives on one particular server. A shared pub/sub channel carries the click to the server that holds
  the stream. The Logs and pub/sub lesson in Module 4 covers that channel.
- **Deploys.** Restarting a server drops every stream it holds, and all those browsers reconnect at once. Add a random
  delay before each reconnect so the new servers do not take the whole crowd in the same second.
- **TCP and UDP.** All four run over TCP in most setups. TCP delivers bytes in order and resends lost packets, so
  nothing goes missing while the connection lives. The cost: one lost packet holds up every byte behind it until the
  resend arrives. UDP sends separate datagrams with no ordering and no resend. Voice calls, video, and fast games
  choose it, because waiting for a resend stalls playback and a frame that arrives after its moment is useless.
  Browsers reach UDP through WebRTC. HTTP/3 also runs over UDP: its QUIC layer adds ordering and resends per stream,
  so one lost packet stalls only its own stream.

## When to use which

- **Polling** when updates are rare or a few seconds of lag is fine: a report that refreshes each minute, or the
  status of a long job.
- **Long polling** when you need fast updates but the path between browser and server only passes plain
  request and response, or as a fallback for the other two.
- **Server-sent events** for feeds from server to browser: live dashboards, notifications, progress bars, streamed
  text. The shortener's click dashboard fits here.
- **WebSocket** when both sides talk often with little delay: chat, multiplayer games, shared editing, trading screens.

All four still start with the HTTP request from [what happens when you click](../what-happens-when-you-click/).
They change what happens after it.
