## Four ways to hear about a click

- **Polling.** The browser asks every few seconds, and a click waits for the next poll.
- **Long polling.** The server holds each request until a click or a 25 s timeout, then the browser asks again.
- **Server-sent events (SSE).** The server keeps one response open and writes an event per click, one way only.
- **WebSocket.** One upgraded connection carries messages both ways.

<Analogy>

Polling is checking the mailbox every few minutes: most trips find it empty. SSE is a doorbell that rings when a
parcel arrives. A WebSocket is an open phone call: either side talks at any moment.

Where it breaks: a doorbell only announces, while an SSE event carries the message. And every open stream holds
memory and a socket, and a proxy may hang up on a silent line.

</Analogy>

<details>
<summary>Go deeper: how SSE resumes and how a WebSocket starts</summary>

**SSE** runs over a plain HTTP response that the server never finishes, opened in the browser with `EventSource`. The
server writes a `data:` line for every click. Resuming takes server work: tag each event with an `id:` line, and the
reconnecting browser sends the last id it saw in a `Last-Event-ID` header. The server can then replay the events after
it, as long as it still keeps them.

**WebSocket** starts as an HTTP/1.1 request with `Upgrade: websocket`. The server answers `101 Switching Protocols`,
and the connection becomes a two-way channel of text or binary frames. Your code handles reconnects and resuming.

</details>

## Pick one

<TradeoffTable title="Four transports at a glance">

| Transport    | Direction         | Delay to show a click   | Server holds per viewer |
| ------------ | ----------------- | ----------------------- | ----------------------- |
| Polling      | Browser asks      | Up to one poll interval | Nothing between polls   |
| Long polling | Browser asks      | About one trip          | One waiting request     |
| SSE          | Server to browser | About one trip          | One open response       |
| WebSocket    | Both ways         | About one trip          | One open connection     |

</TradeoffTable>

Poll when updates are rare or lag is fine. Use SSE for feeds from server to browser, like this dashboard, and a
WebSocket when both sides talk often, as in chat. Long poll when the path allows only plain request and response. All
four start with the request from [what happens when you click](../what-happens-when-you-click/).

<details>
<summary>Go deeper: the full comparison, and what it leaves out</summary>

| | Polling | Long polling | Server-sent events | WebSocket |
| --- | --- | --- | --- | --- |
| Who sends | Browser asks, server answers | Browser asks, server answers when there is news | Server pushes; the browser sends with ordinary requests | Both sides, any time |
| Delay to show a click | Up to one poll interval | About one network trip | About one network trip | About one network trip |
| Requests in the quiet minute (toy) | 12 | 7 | 1 | 1 |
| Held on the server | Nothing between polls | One request per viewer, until news or timeout | One response per viewer, for the session | One connection per viewer, for the session |
| Reconnect | The next poll | The next request | Built in; resuming needs event ids and server replay | Your code |
| Payload | Any HTTP body | Any HTTP body | UTF-8 text events | Text or binary frames |

- **Server cost.** In the sim, each stream holds its connection for 59.9 s of the minute, per viewer. Polling holds
  nothing between requests.
- **Idle timeouts.** Proxies and load balancers close connections that stay silent too long, often after 60
  seconds. Keep the long poll timeout under that limit, and send a heartbeat on streams every 15 to 30 seconds.
- **Buffering.** A proxy that buffers responses holds SSE events back until its buffer fills. Turn buffering off for
  the stream's route.
- **Connection limits.** Over HTTP/1.1, a browser opens about six connections per host, and every SSE tab uses one.
  HTTP/2 carries many streams over one connection and removes the problem.
- **Fan-out.** A click lands on whichever app server the [load balancer](../../scaling/load-balancing/) picks, and the
  viewer's stream lives on one particular server. A shared pub/sub channel carries the click to the server that holds
  the stream. The [Logs and pub/sub](../../async/logs-and-pubsub/) lesson in Module 4 covers that channel.
- **Deploys.** Restarting a server drops every stream it holds, and all those browsers reconnect at once. Add a random
  delay before each reconnect so the new servers do not take the whole crowd in the same second.
- **TCP and UDP.** All four run over TCP in most setups. TCP delivers bytes in order and resends lost packets, so
  nothing goes missing while the connection lives. The cost: one lost packet holds up every byte behind it until the
  resend arrives. UDP sends separate datagrams with no ordering and no resend. Voice calls, video, and fast games
  choose it, because waiting for a resend stalls playback and a frame that arrives after its moment is useless.
  Browsers reach UDP through WebRTC. HTTP/3 also runs over UDP: its QUIC layer adds ordering and resends per stream,
  so one lost packet stalls only its own stream.

</details>

<KeyTakeaways>

- Plain HTTP lets only the browser speak first. Four transports work around that.
- Polling sends empty answers and adds up to one poll interval of delay.
- Long polling and streams show a click about one network trip after it happens.
- Each stream holds a connection per viewer: plan for idle timeouts, heartbeats, and fan-out.

</KeyTakeaways>

Pick a transport for a live click dashboard watched by 50,000 people at once, and estimate how many connections each

- names the transport and why it fits;

<div slot="answer">

Use SSE, or a WebSocket if the dashboard must send data back. Each viewer holds one open connection, so the fleet holds
50,000. A tuned server holds tens of thousands of mostly idle connections, so 2 to 5 servers carry the load with room
to lose one. Put a pub/sub channel or fan-out layer between the click counter and the connection servers, so each
click reaches every server that holds a viewer of that link.

The cheap option: poll every few seconds against a stats endpoint that the CDN caches for a second or two. The CDN
answers the 10,000 or more requests a second, and the origin sees only a few per cache period.
