## The failure: a viral link loses clicks

The shortener shows each link's click count. The redirect handler does the obvious thing: read `clicks`, add one, write

falls behind the real traffic. Nothing crashes, and no log line mentions it.

## The idea: close the gap between read and write

Between a handler's read and its write, another handler can change the row. Each tool in this lesson closes that gap in
a different way: let the database compute the new value, refuse a write when the row changed, hold a lock, or make the
bad outcome impossible with a constraint.

number, and one visitor disappears from the count. The fix is to let each volunteer add a tick mark to the board
instead of rewriting the total.

## Three tools for one row

**Atomic statement.** When the new value follows from the old one, let the database compute it. The database holds the
row for the instant it reads and writes, so concurrent increments queue up and all count.

```sql
UPDATE links SET clicks = clicks + 1 WHERE alias = 'launch';
```

**Conditional update.** When a person or your code decides the new value, store a version number and write only if it
still matches what you read. This is also called optimistic concurrency control.

```sql
-- Read: the editor opens version 4.
SELECT url, version FROM links WHERE alias = 'launch';

-- Save: succeeds only if nobody saved since.
UPDATE links
SET url = 'https://example.com/new', version = version + 1
WHERE alias = 'launch' AND version = 4;
```

If the update changes 0 rows, someone else saved first. Show the latest version and let the editor decide. A conflict
the user can see beats a change that silently disappears.

**Row lock.** When the code must read, decide, and write with nobody else in between, lock the row as you read it.

```sql
BEGIN;
SELECT clicks FROM links WHERE alias = 'launch' FOR UPDATE;
-- Other writers wait here until COMMIT.
UPDATE links SET clicks = 18 WHERE alias = 'launch';
COMMIT;
```

Locks are correct and simple, but every other writer waits while you hold one. Hold them for milliseconds, never across
a network call or a user's think time.

## Two people claim the same alias

The shortener lets people pick a custom alias. The handler checks whether the alias is free, then inserts it. The
**Same custom alias** scenario above sends 20 people after 5 aliases, three of them on each word within half a second.

<Predict
  client:visible
  question="Three people claim the alias sale within half a second. Each handler checks that sale is free, then inserts it. How many sale rows can end up in the table?"
  options={['Exactly 1', 'Up to 3', 'None, since the checks cancel out']}
  answer={1}
>

**Up to 3.** All three checks run before any insert lands, so all three find the alias free and all three insert. Every
user sees "Your link is ready", but a redirect can follow only one row. A row lock cannot help here either: a new alias
has no row to lock yet.

</Predict>

A **unique constraint** closes the gap. The database checks for a duplicate at the moment of the insert, so the second
insert fails no matter how the requests interleave.

```sql
ALTER TABLE links ADD CONSTRAINT links_alias_key UNIQUE (alias);

INSERT INTO links (alias, url, owner_id)
VALUES ('sale', 'https://example.com/sale', 42)
ON CONFLICT (alias) DO NOTHING
RETURNING id;
```

When the insert returns no row, the API answers **409 Conflict** and suggests another alias. Keep the friendly check in
the form as a hint for the user, and let the constraint enforce the rule.

## Isolation levels: how much the database protects you

`BEGIN` and `COMMIT` make a group of statements all or nothing. The **isolation level** decides what each transaction
sees of the others while they run.

- **Read Committed** (the PostgreSQL default) shows each statement the latest committed data. A read in your code,
  followed by a write of a value you computed, still loses updates.
- **Repeatable Read** shows a transaction one snapshot for its whole life. In PostgreSQL, the second writer to a changed
  row fails with a serialization error instead of overwriting it. In MySQL (where this level is the default), a plain
  `SELECT` reads the snapshot and the later `UPDATE` still overwrites, so you need `FOR UPDATE`.
- **Serializable** aborts any transaction whose result could differ from running them one at a time. It catches the
  most problems, and the application must catch the error and retry the whole transaction.

Stronger isolation trades silent bugs for loud retries. Check which level your database uses by default, and write
code that is correct at that level. Unique keys and atomic statements protect you at every level.

Everything here happens inside one database. When a change spans two databases or services, no single `COMMIT` covers
it. The [Sagas](../../distributed-data/sagas/) lesson in Module 5 picks up that problem.

## Trade-offs

<TradeoffTable title="Keeping one row correct under concurrent writes">

| Choice                                  | What it buys                                                     | What it costs                                                              |
| --------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Atomic statement (`clicks = clicks + 1`) | Correct counts in one round trip, no extra code                  | Works only when SQL can compute the new value; one hot row still queues writers |
| Conditional update (version column)     | No locks while users think; conflicts become visible            | The app must handle "0 rows updated": reload, merge, or ask the user        |
| Row lock (`SELECT ... FOR UPDATE`)      | Read, decide in code, and write with nobody in between          | Other writers wait; long holds and inconsistent lock order cause stalls and deadlocks |
| Serializable isolation                  | The database catches conflict patterns you did not foresee      | Some transactions abort and must be retried; more overhead under contention |
| Unique constraint                       | Duplicates become impossible at any isolation level              | A small cost on every insert; the API must turn the violation into a clear 409 |

</TradeoffTable>
