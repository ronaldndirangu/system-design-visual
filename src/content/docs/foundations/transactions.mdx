## The idea: close the gap between read and write

Between a handler's read and its write, another handler can change the row. Each tool here closes that gap: the
database computes the value, refuses a stale write, holds a lock, or a constraint forbids the bad outcome.

<StepDiagram client:visible title="A lost update, step by step" nodes={nodes} edges={edges} steps={steps} height={290} />

<Analogy>

Two volunteers keep a tally on a whiteboard. Each reads the number, checks a visitor in, then rewrites the total as the
number they remember plus one. When both check someone in at once, one visitor disappears. The fix: each volunteer
adds a tick mark instead of rewriting the total.

</Analogy>

Where the analogy breaks: tick marks work because every visitor adds one. They cannot decide which of two destination
edits wins, or who owns an alias. Those need a version check or a constraint.

## Tools that close the gap

### Three tools for one row

**Atomic statement.** When the new value follows from the old one, let the database compute it. Concurrent increments
queue on the row and all count.

```sql
UPDATE links SET clicks = clicks + 1 WHERE alias = 'launch';
```

**Conditional update.** When a person decides the new value, store a version number and write only if it still matches
what you read. This is optimistic concurrency control.

```sql
-- The editor opened version 4.
UPDATE links
SET url = 'https://example.com/new', version = version + 1
WHERE alias = 'launch' AND version = 4;
```

If it changes 0 rows, someone saved first. Show the latest version and let the editor decide.

**Row lock.** When code must read, decide, and write with nobody in between, lock the row with `SELECT ... FOR UPDATE`.
Other writers wait, so hold it for milliseconds, never across a network call.

<details>
<summary>Go deeper: a row lock in SQL</summary>

```sql
BEGIN;
SELECT clicks FROM links WHERE alias = 'launch' FOR UPDATE;
-- Other writers wait here until COMMIT.
UPDATE links SET clicks = 18 WHERE alias = 'launch';
COMMIT;
```

Two transactions that lock the same two rows in opposite orders wait on each other forever. The database detects
the deadlock and aborts one. Lock rows in a fixed order, such as by id, to avoid it.

</details>

A **unique constraint** closes the gap. The database checks for a duplicate at insert time, using a unique
[index](../indexes/), so the second insert fails however the requests interleave.

```sql
ALTER TABLE links ADD CONSTRAINT links_alias_key UNIQUE (alias);

INSERT INTO links (alias, url, owner_id)
VALUES ('sale', 'https://example.com/sale', 42)
ON CONFLICT (alias) DO NOTHING
RETURNING id;
```

When the insert returns no row, the API answers **409 Conflict** and suggests another alias. The form's "is it free?"
check stays as a hint; the constraint enforces the rule.

### Isolation levels and the anomalies they allow

A transaction gives a group of statements four guarantees, called **ACID**:

- **Atomic:** all statements commit, or none do. That keeps the two click writes from [data modeling](../data-modeling/)
  together.
- **Consistent:** each commit leaves the data obeying its constraints, such as one row per alias.
- **Isolated:** concurrent transactions see each other's work only as far as the isolation level allows.
- **Durable:** once `COMMIT` returns, the change survives a crash.

The isolation level decides which **anomalies** slip through:

- **Dirty read:** the dashboard shows a destination from an edit that later rolls back.
- **Non-repeatable read:** a report reads the `launch` destination twice and gets two URLs.
- **Phantom:** a quota check counts a user's links twice and gets 49, then 50.
- **Lost update:** two handlers read `clicks = 1` and both write 2.
- **Write skew:** two people check that `launch` is free and both insert it. No existing row changed, so only a unique
  key on `alias` or Serializable stops it.

<TradeoffTable title="Which anomalies each isolation level allows">

| Level                         | Dirty read | Non-repeatable read | Phantom   | Lost update       | Write skew |
| ----------------------------- | ---------- | ------------------- | --------- | ----------------- | ---------- |
| Read Committed                | Prevented  | Allowed             | Allowed   | Allowed           | Allowed    |
| Repeatable Read, SQL standard | Prevented  | Prevented           | Allowed   | Varies            | Varies     |
| Repeatable Read, PostgreSQL   | Prevented  | Prevented           | Prevented | Aborts one writer | Allowed    |
| Serializable                  | Prevented  | Prevented           | Prevented | Prevented         | Prevented  |

</TradeoffTable>

Read Committed, the PostgreSQL default, blocks only dirty reads. The SQL standard defines only the first three
anomalies, so engines differ on the last two. Stronger levels block more by aborting one of the conflicting
transactions, so the app must catch the error and rerun the whole transaction. Unique keys and atomic statements work
at every level.

<details>
<summary>Go deeper: how PostgreSQL and MySQL implement the levels</summary>

PostgreSQL implements Repeatable Read as snapshot isolation: each transaction reads one snapshot, so phantoms never
appear in its reads, and the second writer to a row another transaction changed fails with a serialization error.
Write skew still passes, because the two transactions write different rows. Serializable adds tracking of which
transactions read data that others wrote, and aborts one when no serial order fits. The error carries SQLSTATE 40001.
Retry from the first statement with a short random backoff.

MySQL's InnoDB defaults to Repeatable Read. A plain `SELECT` reads the snapshot, yet a later `UPDATE` changes the
latest committed row, so a read in your code followed by a write still loses updates. Use an atomic statement or
`FOR UPDATE`. Locking reads (`FOR UPDATE`, `FOR SHARE`) take next-key locks: they lock the index entries they read and
the gaps between them, so nobody can insert a phantom into that range until you commit.

</details>

When a change spans two databases or services, no single `COMMIT` covers it. The
[Sagas](../../distributed-data/sagas/) lesson picks up that problem.

## Trade-offs

<TradeoffTable title="Keeping one row correct under concurrent writes">

| Choice                                   | What it buys                                        | What it costs                                                      |
| ---------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------ |
| Atomic statement (`clicks = clicks + 1`) | Correct counts in one round trip                    | Works only when SQL can compute the value; a hot row queues writers |
| Conditional update (version column)      | No locks while users think; conflicts become visible | The app must handle "0 rows updated"                               |
| Row lock (`SELECT ... FOR UPDATE`)       | Read, decide, and write with nobody in between      | Other writers wait; long holds stall, and mixed lock order deadlocks |
| Serializable isolation                   | Catches conflict patterns you did not foresee       | Aborted transactions must be retried                               |
| Unique constraint                        | Duplicates are impossible at any isolation level    | A small cost per insert; the API maps the violation to 409         |

</TradeoffTable>

When not to use them: skip row locks and Serializable for counters; an atomic statement needs no waits or retries.
Skip the version column on values your code computes from the old one. Skip Serializable as a default when a unique
key or conditional update already guards the rule.

## Common mistakes

- **Trusting BEGIN and COMMIT alone.** At Read Committed, a read followed by a computed write still loses updates inside
  a transaction.
- **Checking before inserting.** Two requests can both pass the check. Let a unique constraint decide.
- **Retrying a conditional update blindly.** 0 rows updated means someone else saved. Reload and let the person decide.
- **Raising isolation without retry code.** Stronger levels abort transactions. Catch the error and rerun the whole
  transaction.
- **Holding a lock across a network call.** Every other writer queues behind it.

<KeyTakeaways>

- A read in code followed by a computed write lets a concurrent request silently erase a change.
- Let the database compute the value, check a version, or lock the row, depending on who decides the new value.
- A rule about rows that do not exist yet, such as a free alias, needs a unique constraint.
- Stronger isolation levels allow fewer anomalies and turn silent bugs into errors the app retries.

</KeyTakeaways>
