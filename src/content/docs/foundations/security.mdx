## The failure: any signed-in user can delete any link

The shortener lets people delete their own links with `DELETE /links/{code}`. The handler checks that the caller has a
valid session, then deletes the row with that code. It never compares the link's owner with the caller. Every test
passes, because each tester deletes their own links.

In production, any signed-in user who knows a code can delete someone else's link, including one printed on a
thousand posters. The server logs each delete as a normal, authenticated request, so nothing looks wrong until the
owner complains. Security reviewers call this missing object-level authorization, and it tops the OWASP list of API
security risks.

## The idea: four questions, in order

Every request has to answer four questions before the handler touches data. Each question has its own defense, and the
other three cannot stand in for a missing one.

1. **Is the channel private?** TLS (HTTPS) encrypts traffic between the client and the server and proves the server
   owns the domain. Without it, anyone on a shared network can read the request, cookies included. A server that
   refuses plain HTTP acts too late: by the time it says no, the cookie has already crossed the network. Two settings
   keep the cookie off plain HTTP in the first place. An HSTS header (Strict-Transport-Security) tells the browser to
   rewrite every http:// URL for the site to https:// before sending, and the HSTS preload list covers the very first
   visit. The `Secure` flag on the session cookie stops the browser from attaching it to a plain HTTP request at all.
2. **Who is calling?** This is authentication. The server checks a credential: a session cookie that maps to a session
   it stores, or a signed token whose signature and expiry it verifies on every request. Passwords live only as slow,
   salted hashes such as bcrypt or Argon2, and multi-factor authentication (MFA) means a stolen password alone gets
   nobody in.
3. **May this caller do this to this object?** This is authorization. Deny by default, then allow when a rule says yes:
   the caller owns the link, or holds a role such as admin. Check on the server, on every request, for the exact
   object. Give each person and service the least privilege its job needs.
4. **Where do the keys live?** The server's own secrets, such as API keys, database passwords, and token signing keys,
   live in a secret manager and reach the service as environment variables or files injected at deploy. They never
   appear in source code or logs, and they rotate on a schedule and at once after a leak.

## 401 or 403

The two codes answer different questions, and clients act on them differently.

- **401 Unauthorized** means "I cannot tell who you are." The credential is missing, forged, or expired. Despite its
  name, 401 is about authentication. The client should sign in again or refresh its token.
- **403 Forbidden** means "I know who you are, and the answer is no." Signing in again changes nothing. The caller
  needs a different role or a different object.

Some APIs answer 404 Not Found for objects the caller may not see, so a stranger cannot learn which codes exist. Pick
one rule and apply it everywhere. [APIs and contracts](../apis/) covers the rest of the status codes.

## Authorization lives on the server

Hiding the Delete button on other people's links is good design for honest users, and it protects nothing. Any HTTP
client can send the same request without your web app. The rule holds only when the server enforces it.

- **Check every object.** Signing in proves who the caller is. It says nothing about which links they may touch.
- **Check in one place.** Put the rule in one function that every handler calls, or in the query itself, so a new
  endpoint cannot forget it.
- **Deny by default.** A new endpoint starts closed and opens only for the callers a rule names.
- **Grant least privilege.** The cleanup job needs to delete expired links. It does not need an admin key that can
  delete anything.

```ts
async function deleteLink(caller: User, code: string): Promise<Response> {
  const link = await links.find(code);
  if (!link) return status(404);
  const allowed = link.ownerId === caller.id || caller.role === 'admin';
  if (!allowed) return status(403);
  await links.remove(code);
  return status(204);
}
```

Long random link codes do not help here. Every shared URL publishes its code, so codes are public by design.

## Proving who is calling

**Passwords.** Store a slow, salted hash from bcrypt, scrypt, or Argon2, never the password itself. The salt makes
identical passwords hash differently, and the slowness makes each guess against a stolen table expensive. Add MFA so a
leaked password alone gets nobody in, and put rate limiting on the sign-in endpoint to slow guessing.

**Sessions.** After sign-in, the server stores a session and hands the browser a long random ID in a cookie marked
`Secure`, `HttpOnly`, and `SameSite`. Each request costs a lookup, and signing out deletes the session at once.

**Signed tokens.** The server signs a token that names the user and an expiry time, and any service holding the key
can verify it without a lookup. A token keeps working until it expires, so keep lifetimes short (minutes) and pair them
with a refresh step. Always check the signature and the expiry; the second scenario shows what happens when you skip
one.

## Secrets: store, inject, rotate, revoke, audit

A secret is any value that grants access: an API key, a database password, a token signing key. Treat each one as
having a lifecycle.

1. **Store** it in a secret manager, encrypted, with access granted per service.
2. **Inject** it at deploy or startup as an environment variable or mounted file. Code reads it by name and never
   holds the value.
3. **Rotate** it on a schedule and at once after a suspected leak. Accept the old and new keys for a short overlap, so
   nothing breaks mid switch.
4. **Revoke** the old key once nothing uses it. Revocation is what makes a leaked copy worthless.
5. **Audit** every read and use. An admin delete from an unfamiliar service is how the team in the simulation noticed.

A key committed to a repo stays in git history, every clone, and old build logs, even after someone deletes the line.
Rotate first, then clean up. Secret scanning in CI catches most of these before they merge.

## Encryption at rest

Disk, database, and backup encryption protect data when someone walks off with a drive or copies a snapshot. They do
nothing about a request your own app accepts, because the app reads decrypted data. Keep the encryption keys in a key
management service, apart from the data. For a few especially sensitive fields, encrypt the field itself so even a
database administrator sees ciphertext.

## Defense in depth

Each scenario in the simulation removes one defense and keeps the other three, and harm still gets through. Layers
work because each one catches what the others miss: TLS protects the cookie, sign-in rejects the stale token,
authorization stops the wrong user, and the secret manager limits who holds the keys.

Log enough to investigate: who called, which object, what happened, and a request ID. Leave out the secrets. Redact
`Authorization` headers, cookies, tokens, and passwords before a line is written, because logs get copied to many
places and kept for a long time. Rate limiting on expensive and sensitive endpoints adds one more layer. For how TLS
sets up the private channel, see the handshake in [What happens when you click a link](../what-happens-when-you-click/).

## Trade-offs

<TradeoffTable title="Securing a small API">

| Choice                                | What it buys                                           | What it costs                                                         |
| ------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------- |
| Server sessions (random ID in cookie) | Instant sign-out and revocation; a tiny cookie         | A session lookup on every request; a store to run                     |
| Signed tokens with short expiry       | No lookup; any service with the key can verify         | Revocation waits for expiry; a refresh flow and key rotation to build |
| Ownership check on every object       | Stops cross-user access on every endpoint              | One more lookup or condition per request; every endpoint must call it |
| Roles such as admin                   | Simple rules for broad powers                          | Coarse; an admin account or key becomes the prize worth stealing      |
| Secret manager with injection         | One place to store, rotate, revoke, and audit          | A startup dependency and some setup work                              |
| TLS on every hop, internal included   | Privacy and tamper protection everywhere               | Certificates to issue and renew; a small handshake cost               |
| HSTS and `Secure` cookies             | Cookies stay off plain HTTP, even from old links       | An HTTPS mistake locks users out until the HSTS max-age expires       |

</TradeoffTable>
