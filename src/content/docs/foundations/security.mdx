## The failure: any signed-in user can delete any link

The shortener deletes links with `DELETE /links/{code}`. The handler checks that the caller has a valid session, then
deletes the row. It never compares the link's owner with the caller. Every test passes, because each tester deletes
their own links. In production, any signed-in user who knows a code can delete someone else's link, including one
printed on a thousand posters, and the logs show only normal, authenticated deletes.

## The idea: four questions, in order

Every request answers four questions before the handler touches data, and each needs its own defense.

1. **Is the channel private?** TLS encrypts the traffic and proves the server owns the domain: the handshake from
   [What happens when you click a link](../what-happens-when-you-click/). Without it, anyone on the cafe Wi-Fi can read
   the cookie.
2. **Who is calling?** Authentication: the server looks up a session cookie, or verifies a signed token's signature
   and expiry.
3. **May this caller do this to this object?** Authorization: deny by default, then allow the owner or an admin, on
   the server, for the exact object.
4. **Where do the keys live?** Keys and passwords live in a secret manager, never in code or logs.

<details>
<summary>Go deeper: keeping the cookie off plain HTTP</summary>

A server that refuses plain HTTP acts too late: by the time it says no, the cookie has already crossed the network.
Two settings keep the cookie off plain HTTP in the first place. An HSTS header (Strict-Transport-Security) tells the
browser to rewrite every http:// URL for the site to https:// before sending, and the HSTS preload list covers the very
first visit. The `Secure` flag on the session cookie stops the browser from attaching it to a plain HTTP request at all.
In the diagram's first step, the edge sends that HSTS header, so Ben's browser uses https:// for sho.rt from then on,
even when a link or bookmark says http://.

</details>

## Deep dives

### 401 or 403

- **401 Unauthorized:** "I cannot tell who you are." The credential is missing, forged, or expired; sign in again.
- **403 Forbidden:** "I know who you are, and the answer is no." Signing in again changes nothing.

Some APIs answer 404 for objects the caller may not see, so strangers cannot learn which codes exist; pick one rule
everywhere. [API styles](../apis/) covers status codes, and [API design details](../api-design/) covers error bodies a
client can act on.

### Authorization lives on the server

Hiding the Delete button protects nothing, because any HTTP client can send the same request. Check ownership on the
server for every object, in one function that every handler calls, and deny by default. Long random link codes do not
help: every shared URL publishes its code.

<details>
<summary>Go deeper: the authorization rules and the check in code</summary>

- **Check every object.** Signing in proves who the caller is. It says nothing about which links they may touch.
- **Check in one place.** Put the rule in one function that every handler calls, or in the query itself, so a new
  endpoint cannot forget it.
- **Deny by default.** A new endpoint starts closed and opens only for the callers a rule names.
- **Grant least privilege.** The cleanup job needs to delete expired links. An admin key that can delete anything
  gives it far more than that.

```ts
async function deleteLink(
  caller: User,
  code: string,
): Promise<Response> {
  const link = await links.find(code);
  if (!link) return status(404);
  const allowed =
    link.ownerId === caller.id || caller.role === 'admin';
  if (!allowed) return status(403);
  await links.remove(code);
  return status(204);
}
```

</details>

### Proving who is calling

Sign-in checks a password stored as a slow, salted hash, then issues a session ID the server looks up or a signed token
any service with the key can verify. Mark the session cookie `Secure` (never sent over plain HTTP), `HttpOnly` (hidden
from page scripts), and `SameSite=Lax` (left off POSTs that other sites start). SameSite is one of two layers against
cross-site request forgery; see the CSRF row in [Four classic web attacks](#four-classic-web-attacks).
[Sessions, tokens, and OAuth](../auth/) compares sessions with tokens and covers JWT pitfalls and OAuth 2.

<details>
<summary>Go deeper: passwords, sessions, and signed tokens</summary>

**Passwords.** Store a slow, salted hash from bcrypt, scrypt, or Argon2, never the password itself. The salt makes
identical passwords hash differently, and the slowness makes each guess against a stolen table expensive. Add
multi-factor authentication (MFA) so a leaked password alone gets nobody in, and put rate limiting on the sign-in
endpoint to slow guessing.

**Sessions.** After sign-in, the server stores a session and hands the browser a long random ID in a cookie marked
`Secure`, `HttpOnly`, and `SameSite`. Each request costs a lookup, and signing out deletes the session at once.

**Signed tokens.** The server signs a token that names the user and an expiry time, and any service holding the key
can verify it without a lookup. A token keeps working until it expires, so keep lifetimes short (minutes) and pair them
with a refresh step. Always check the signature and the expiry; the second scenario shows what happens when you skip
one.

</details>

### Secrets: store, inject, rotate, revoke, audit

Any value that grants access is a secret. **Store** it in a secret manager, **inject** it at deploy, **rotate** it on a
schedule and after any leak, **revoke** the old copy once nothing uses it, and **audit** every use. Revoking is what
makes a leaked copy worthless.

<details>
<summary>Go deeper: the secret lifecycle, leaked keys, and defense in depth</summary>

1. **Store** it in a secret manager, encrypted, with access granted per service.
2. **Inject** it at deploy or startup as an environment variable or mounted file. Code reads it by name and never
   holds the value.
3. **Rotate** it on a schedule and at once after a suspected leak. Accept the old and new keys for a short overlap, so
   nothing breaks mid switch.
4. **Revoke** the old key once nothing uses it.
5. **Audit** every read and use. An admin delete from an unfamiliar service is how the team in the simulation noticed.

**A key in git history.** A key committed to a repo stays in git history, every clone, and old build logs, even after
someone deletes the line. Rotate first, then clean up. Secret scanning in CI catches most of these before they merge.

**Encryption at rest.** Disk, database, and backup encryption protect data when someone walks off with a drive or
copies a snapshot. They do nothing about a request your own app accepts, because the app reads decrypted data. Keep
the encryption keys in a key management service, apart from the data. For a few especially sensitive fields, encrypt
the field itself so even a database administrator sees ciphertext.

**Defense in depth.** Each scenario in the simulation removes one defense and keeps the other three, and harm still
gets through. Layers work because each one catches what the others miss: TLS protects the cookie, sign-in rejects the
stale token, authorization stops the wrong user, and the secret manager limits who holds the keys.

**Logs without secrets.** Log enough to investigate: who called, which object, what happened, and a request ID. Leave
out the secrets. Redact `Authorization` headers, cookies, tokens, and passwords before a line is written, because logs
get copied to many places and kept for a long time. Rate limiting on expensive and sensitive endpoints adds one more
layer.

</details>

## Four classic web attacks

These attacks abuse what the code does with a request it accepts, and each has a standard fix. JWT mistakes and OAuth
flows live in [Sessions, tokens, and OAuth](../auth/).

| Attack                            | How it hits the shortener                                         | Standard fix                                                                      |
| --------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Broken access control (IDOR)      | `DELETE /links/k7wp` works for any signed-in caller               | Check that the caller owns link `k7wp`, on reads as well as deletes               |
| SQL injection                     | An alias of `x' OR '1'='1` glued into the query matches every row | Parameterized queries: the value travels apart from the SQL                       |
| Cross-site scripting (XSS)        | A link title holding a `<script>` tag runs on the stats page      | Escape output, set a Content-Security-Policy, mark session cookies `HttpOnly`     |
| Cross-site request forgery (CSRF) | Another site makes Ben's browser POST to sho.rt with his cookie   | `SameSite=Lax` cookies plus a per-session CSRF token; never change state with GET |

The SQL injection fix in code:

```js
// Bad: the input becomes part of the SQL text
db.query(
  "SELECT * FROM links WHERE alias = '" + input + "'"
);
// Good: the input travels as a bound value
db.query('SELECT * FROM links WHERE alias = $1', [input]);
```

<details>
<summary>Go deeper: how each attack plays out</summary>

**Broken access control.** This lesson's bug is an insecure direct object reference (IDOR): the request names an
object, and the server acts after checking only that the caller is signed in. `GET /links/k7wp/stats` leaks the same
way a delete does. OWASP ranks broken object level authorization first among API security risks.

**SQL injection.** With the bad query, the alias `x' OR '1'='1` makes the condition true for every row, and the stats
page returns every link in the table. A bound parameter sends the SQL and the value separately, so the database reads
the input as data whatever quotes it holds. Give the service's database account only the rights it needs, so one
missed query cannot drop a table.

**Cross-site scripting.** If the stats page pastes Ana's link title into its HTML as it is, every visitor's browser
runs her script as part of sho.rt: it can read the page and send requests as the signed-in visitor. Escaping on output
shows the title as text. Most template engines escape by default, and the risk returns wherever code inserts raw HTML.
A `Content-Security-Policy` header that allows scripts only from your own origin keeps an injected inline script from
running, and `HttpOnly` keeps a script that does run from reading the session cookie.

**Cross-site request forgery.** Ben, signed in to sho.rt, opens a page on another site that quietly submits a hidden
form to the shortener's settings page and changes his email address. Without defenses, the browser attaches his
cookie, and the server sees a normal request from Ben. `SameSite=Lax` leaves the cookie off POSTs that another site
starts, which stops this attack in current browsers. The CSRF token covers the gaps: the server puts a random
per-session value in each form and rejects a state-changing request without it, and the other site cannot read the
token to forge the form. It still matters for older browsers and for a page on a sibling subdomain, which counts as
the same site. Lax still sends the cookie when another site links to yours, so a GET must never change state. An XSS
bug defeats both layers, because the injected script runs on your own origin and can read the token.

</details>

## Trade-offs

<TradeoffTable title="Securing a small API">

| Choice                                | What it buys                                   | What it costs                                                         |
| ------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------------- |
| Server sessions (random ID in cookie) | Instant sign-out and revocation; a tiny cookie | A session lookup on every request; a store to run                     |
| Signed tokens with short expiry       | No lookup; any service with the key can verify | Revocation waits for expiry; a refresh flow and key rotation to build |
| Ownership check on every object       | Stops cross-user access on every endpoint      | One more lookup or condition per request; every endpoint must call it |
| Secret manager with injection         | One place to store, rotate, revoke, and audit  | A startup dependency and some setup work                              |

</TradeoffTable>

**When not to use them.** A single web app that needs instant sign-out gains little from signed tokens. Owner-only
rules need no role system until a second kind of user appears. Never write your own password hashing, token signing,
or encryption; use a vetted library.

<details>
<summary>Go deeper: roles, internal TLS, and HSTS</summary>

| Choice                              | What it buys                                       | What it costs                                                   |
| ----------------------------------- | -------------------------------------------------- | --------------------------------------------------------------- |
| Roles such as admin                 | Simple rules for broad powers                      | Coarse; an admin account or key becomes the prize worth stealing |
| TLS on every hop, internal included | Privacy and tamper protection everywhere           | Certificates to issue and renew; a small handshake cost         |
| HSTS and `Secure` cookies           | Cookies stay off plain HTTP, even from old links   | An HTTPS mistake locks users out until the HSTS max-age expires |

</details>

## Common mistakes

- Hiding a button and calling it access control.
- Checking a token's signature and skipping its expiry.
- Committing keys to the repo, or writing tokens and cookies into logs.
- Building SQL by gluing strings, or inserting user text into a page as raw HTML.
- Changing state with GET.

<KeyTakeaways>

- Every request answers four questions in order, and no defense covers for a missing one.
- 401 means the server cannot tell who is calling. 403 means it knows and says no.
- Authorization runs on the server, for the exact object, on every request.
- After a secret leaks, rotate and revoke it first, then clean up.
- Bound parameters stop SQL injection, escaping plus a CSP stops XSS, and SameSite plus a CSRF token stops CSRF.

</KeyTakeaways>
