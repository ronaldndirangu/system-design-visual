## Why IDs get hard

Every table in the [data model](../data-modeling/) needs a primary key. One database can number rows with an
auto-increment counter, and [transactions](../transactions/) make sure no two inserts get the same value. Scale breaks
that in three ways. Every insert waits on one machine. Each shard of a [sharded](../../scaling/sharding/) table counts
from 1 on its own. And sequential public IDs let anyone walk your data by adding 1.

## Four schemes

**Counter ranges.** A central counter hands each app server a block of 1,000 numbers. The server spends its block
locally and asks for another when it runs out, so the counter sees one request per 1,000 inserts. A crashed server
wastes the rest of its block. IDs must be unique, and gaps do no harm.

**Snowflake.** Twitter's scheme packs a 64-bit number with no coordination per ID:

| Bits | Field                               | Limit                            |
| ---- | ----------------------------------- | -------------------------------- |
| 1    | Sign, always 0                      |                                  |
| 41   | Milliseconds since a chosen epoch   | About 69 years                   |
| 10   | Machine number                      | 1,024 machines                   |
| 12   | Sequence within one millisecond     | 4,096 IDs per machine per ms     |

IDs sort roughly by time. Each machine needs a unique number, and a clock that steps backward could repeat IDs, so a
generator waits until its clock passes the last timestamp it used.

**UUIDs.** A UUIDv4 holds 122 random bits. Any machine, even a phone offline, can mint one with no realistic chance of
collision. Random order hurts a B-tree [index](../indexes/): every insert lands on a random leaf page. A UUIDv7 puts a
48-bit millisecond timestamp first and random bits after it, so new IDs land at the right edge of the index.

**Random short codes.** sho.rt codes such as `bATJ4g` use 6 base62 characters (a to z, A to Z, 0 to 9): 62 to the 6th,
about 56.8 billion codes. A Snowflake ID needs 11 base62 characters, too long for a short link.

**About 300,000.** This is the birthday paradox: collisions turn likely near the square root of the space, and the
square root of 56.8 billion is about 238,000. So random codes always need a UNIQUE constraint on `code` and a retry
on a duplicate key. With 10 million links stored, a new code collides about once in 5,700 tries, so retries stay rare.

</Predict>

The same ratio helps an attacker: a bot that tries 1 million random codes collects about 175 real links. Short codes
suit public links. Private links such as shared documents need 16 or more random base62 characters (about 95 bits)
plus a rate limit on misses.

## Choosing

| Need                                  | Pick                                                                 |
| ------------------------------------- | -------------------------------------------------------------------- |
| Short public codes                    | Random base62, with a unique constraint and retry                    |
| Private, unguessable links            | 16 or more random base62 characters, plus a rate limit on misses     |
| Short codes with no retries           | Counter ranges, scrambled by a reversible shuffle before base62      |
| Time-sorted IDs from many machines    | Snowflake or UUIDv7                                                  |
| IDs minted offline on devices         | UUIDv4 or UUIDv7                                                     |

<KeyTakeaways>

- Uniqueness is required. Order, size, and resistance to guessing are choices you trade.
- Counter ranges cut coordination to one request per block.
- Snowflake and UUIDv7 sort by time, which keeps B-tree inserts at one edge of the index.
- Random codes collide near the square root of the space, so pair them with a unique constraint and a retry.

</KeyTakeaways>
