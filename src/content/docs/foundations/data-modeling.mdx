## The failure: one document per user

A team building the shortener reasons that each user owns their links, so it stores each user as one document with a
`links` array inside. Sign up, create a link, and load the dashboard all work on day one: each reads or writes one
document by its `_id`. Then the first short link goes out in a newsletter, and the redirect has to find it.

**Every user document.** The redirect knows the code, and the documents are keyed by user. With no index on
`links.code`, the database opens all **300 documents (981 KB)** to return one URL. At 20,000 redirects a second, the toy
model below moves **19.6 GB/s**. Meanwhile user 1, the busiest account, owns 469 links in one **148 KB** document that
every new link rewrites, and MongoDB refuses any document over 16 MB.

</Predict>

The inverse design fails too. A pure key-value store keyed by code makes the redirect a single read, then makes "this
user's newest links" and "every link to this domain" scan every key in the store.

## The idea: list the queries, then pick the shape

Before choosing storage, write down every question the system asks of its data, what it knows when it asks, and how
often. For the shortener, the list is short:

| Query         | What it asks                                | What it knows | Toy rate        |
| ------------- | ------------------------------------------- | ------------- | --------------- |
| Redirect      | The long URL for one code                   | The code      | 20,000 a second |
| Create a link | Store a new code, refusing duplicates       | The code      | 20 a second     |
| Dashboard     | A user's 20 newest links with click counts  | The user      | 50 a second     |
| Analytics     | Clicks per day for one link                 | The code      | 10 a second     |
| Takedown      | Every link that points at one domain        | The domain    | 3 a day         |

The redirect outnumbers everything else by about 250 to 1, and it knows only the code. Whatever else the design does,
the redirect must reach its record by code in one step. The other queries ask by user and by domain, so they need either
an index on those fields or a layout that puts the answer in one place.

<StepDiagram client:visible title="When the layout fights the hot query" nodes={nodes} edges={edges} steps={steps} height={290} />

<Analogy>

A library shelves books by author. "Every book by this author" is one walk to one shelf. "The book called *Dune*"
would mean walking every shelf, so the library also keeps a catalog sorted by title. The catalog is a second copy of
the facts, sorted for a different question, and a librarian has to update it every time a book arrives or leaves.
That is a secondary index, and the upkeep is its price.

</Analogy>

- **Key-value:** one record per code holding the URL, owner, domain, and daily clicks. Nothing else is indexed.

What to look for:

- **Redirect.** Tables and Key-value each read one record in 0.51 toy ms. Documents scan all 300 documents in 11.8 ms,
  which at 20,000 a second would move 19.6 GB/s.
- **Create a link.** All three write by key. Tables write one row plus 2 index entries; Key-value puts the code only if
  it is absent. Documents rewrite user 1's whole document, 149 KB with the new link, to add 0.2 KB.
- **Dashboard.** Tables walk the owner index: 20 index entries and 49 rows (20 links plus their 29 daily rows) in 0.89
  ms. Documents read one 148 KB document to show 20 of its 469 links. Key-value pages through 3,300 keys in 33 round
  trips, 42.8 ms.
- **Analytics.** Key-value wins this one: the record for bATJ4g holds all 21 days of its 3,507 clicks, one read. Tables
  read the same 21 days as a primary key range. Documents scan again.
- **Takedown.** Tables read the 103 matching rows through the domain index. Documents and Key-value scan everything.
  At 3 a day, even a scan is affordable, so this query should not choose your database.
- **The fit table.** Tables win or tie four of five queries here. Key-value wins analytics and ties the redirect and
  create.
  Documents win none, because this dashboard belongs to the busiest account. For the median user with 4 links, the
  document is 1.5 KB and the dashboard costs 0.52 ms, ahead of tables at 0.65 ms (23 rows).

## Tables and the four NoSQL families

The widget runs three shapes, and the full menu is a little longer. Relational tables are one option. "NoSQL" is the
umbrella name for the non-relational rest, which fall into four families. Each family makes one kind of access cheap.

| Family                            | How it stores data                                          | Access pattern it suits                                                  | Where the shortener could use it                                        |
| --------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| Key-value (Redis, DynamoDB)       | One opaque value under each key                             | Read or write by an exact key                                            | The redirect: code to long URL                                          |
| Document (MongoDB, Couchbase)     | Nested records, usually JSON, with fields it can index      | Read or write one self-contained record in a single step                 | A user's profile and settings, shown together on one page               |
| Wide column (Cassandra, Bigtable) | Rows grouped into partitions by a key, sorted inside each   | A heavy stream of appends, read back one partition at a time             | Raw click events, partitioned by code and day, sorted by time           |
| Graph (Neo4j, Neptune)            | Nodes and the edges that connect them                       | Queries that follow relationships several hops out                       | Abuse review: accounts that share domains or payment cards with a banned one |

Relational tables cover the ground between: lookups on several different fields, joins, and constraints that keep
related rows consistent. The widget leaves out wide column and graph stores, since none of the five queries needs a
time series of raw events or a multi-hop walk.

Here is the link `bATJ4g` in the three shapes the widget runs. Each layout answers some questions in one step and
others only with an index or a scan.

```sql
-- Tables: one fact in one place, joined at read time.
CREATE TABLE links (
  code       text PRIMARY KEY,
  owner_id   bigint NOT NULL REFERENCES users (id),
  long_url   text NOT NULL,
  domain     text NOT NULL,
  created_at timestamptz NOT NULL,
  expires_at timestamptz
);
CREATE INDEX links_owner_newest ON links (owner_id, created_at DESC);
CREATE INDEX links_domain ON links (domain);

CREATE TABLE clicks_daily (
  code   text REFERENCES links (code),
  day    date,
  clicks integer NOT NULL,
  PRIMARY KEY (code, day)
);
```

```json
{
  "_id": "user:1",
  "email": "ana@example.com",
  "links": [
    {
      "code": "bATJ4g",
      "url": "https://news-daily.example/launch",
      "domain": "news-daily.example",
      "created": "2024-05-09",
      "daily": [{ "day": "2024-05-31", "clicks": 412 }]
    }
  ]
}
```

```text
key:   link:bATJ4g
value: { url, owner: 1, domain, created, daily: [...] }
```

Each shape can also grow toward the others. PostgreSQL stores JSON in a `jsonb` column and indexes fields inside it.
MongoDB supports secondary indexes, including one on `links.code`, and multi-document transactions. DynamoDB stores
documents under keys and adds global secondary indexes, which are second copies of the data, partitioned by another key
and kept in sync by the database. Judge a product by the access patterns it makes cheap, and expect to design for the
queries in every one of them.

## Denormalization: faster reads, costlier writes

To **denormalize** is to copy data into the shape a read wants, so the read skips a join or a second lookup. The bill
arrives on the write path. Every change must now reach every copy, and a copy that misses an update serves stale data
until something repairs it.

Take the owner's display name. Suppose each link gets a public preview page that says who created it. The normalized
design keeps the name once, in `users`, and the preview joins `links` to `users`. Copy an `owner_name` column onto
every link row, and the preview reads one row. When user 1 renames their account, the app now rewrites 469 link rows,
and any row the update misses keeps the old name. Names change rarely and previews load constantly, so this copy
usually pays for itself. The widget's key-value records make the same bet: each one copies the owner and domain from
its link.

The click counter is the harder case, because the copied value changes on the hottest path. The dashboard shows a click
count for each link. A **normalized** design stores each fact once: clicks live in `clicks_daily`, and the dashboard
sums them.

```sql
-- Each click upserts one daily row.
INSERT INTO clicks_daily (code, day, clicks) VALUES ('bATJ4g', CURRENT_DATE, 1)
ON CONFLICT (code, day) DO UPDATE SET clicks = clicks_daily.clicks + 1;

-- The dashboard sums the days for the 20 newest links.
SELECT l.code, l.long_url, l.created_at, SUM(d.clicks) AS clicks
FROM (SELECT * FROM links WHERE owner_id = 1 ORDER BY created_at DESC LIMIT 20) AS l
LEFT JOIN clicks_daily AS d ON d.code = l.code
GROUP BY l.code, l.long_url, l.created_at
ORDER BY l.created_at DESC;
```

A **denormalized** design also keeps a running total on the link row, so the dashboard skips the join.

```sql
-- Each click now writes twice: the daily row above, and the total.
UPDATE links SET click_count = click_count + 1 WHERE code = 'bATJ4g';

SELECT code, long_url, created_at, click_count
FROM links WHERE owner_id = 1
ORDER BY created_at DESC LIMIT 20;
```

In the toy model, the denormalized dashboard reads **20 rows in 0.74 ms** instead of **49 rows in 0.89 ms**. The price
lands on the busiest path: clicks arrive with every redirect, so writes go from **20,000 to 40,000 a second**, and the
two copies can drift if one write lands and the other fails. Keep them together with a transaction (see
[Transactions and constraints](../transactions/)), or batch the totals from a queue once a second and rebuild them from
`clicks_daily` each night.

Here clicks outnumber dashboard loads 400 to 1, so the normalized design, or a batched total, is the better deal. The
rule of thumb: denormalize when reads of the copy vastly outnumber the writes that keep it fresh, as with the display
name, and keep one copy when the value changes on a hot path, as with the click count. Embedding links in a user
document is denormalization too, with the same bill.

## Schema changes, sharding, and mixed shapes

### Schema changes in each shape

Requirements change. Say the shortener adds link expiry, so every link gains an `expires_at`.

- **Tables** change the schema in one statement. In PostgreSQL 11 and later, adding a nullable column, or one with a
  constant default, only updates the catalog and rewrites no rows. Renames and type changes take more care: add the
  new column, write both, backfill in batches, switch reads, then drop the old one.
- **Documents** accept the new field immediately, because the database does not enforce a shape unless you add a
  validator. The schema moves into the code: every reader must handle documents with and without `expires_at`. A
  common pattern stores a `schema_version` in each document, upgrades a document whenever the app next writes it, and
  runs a background job to finish the rest.
- **Key-value** stores treat the value as opaque bytes. The version lives inside the serialized record, and every
  reader must accept old and new versions until the rewrite finishes.

"Schemaless" means the database skips checking the shape. The application still has a schema, the old data still
exists, and the queries still decide which lookups need an index.

### Mixing shapes, and how sharding changes the choice

Real shorteners rarely pick one shape. A common design keeps **tables as the source of truth** for accounts, links, and
daily clicks, with the indexes the dashboard and takedown need. The redirect path reads a **key-value copy keyed by
code**, in a cache or a key-value store, which the create path fills and every edit updates (see
[Caching](../../scaling/caching/)). That copy is denormalization with a sharp edge: a takedown must delete the
key-value entry as well as the row, or the bad link keeps redirecting.

The shape also decides how the data splits when one machine is not enough. [Sharding](../../scaling/sharding/) divides
rows across machines by a shard key, and only queries that know that key reach a single shard.

- Shard links by **code**, and the redirect, create, and analytics each touch one shard. The dashboard asks by owner,
  so it asks every shard and merges, unless you keep a second copy partitioned by owner.
- Shard by **owner**, as the one-document-per-user design effectively does, and the dashboard touches one shard while
  every redirect has to find out which shard holds its code.

This is the [indexes](../indexes/) trade-off at the scale of machines: each extra access path is another copy to write
and keep in sync. Relational databases shard too (Citus and Vitess, or distributed SQL such as Spanner and
CockroachDB), and document and key-value stores need a good partition key just as much. What scales is a hot query that
one partition can answer.

## Trade-offs

<TradeoffTable title="Choosing a storage shape for the shortener">

| Choice                                 | What it buys                                                                  | What it costs                                                                          |
| -------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Tables with indexes                    | Any query with a matching index takes a few reads; constraints and transactions keep links consistent | Every index adds work to each write; joins, migrations, and sharding need planning |
| Documents, one per user                | One read returns a user with everything shown beside them; a typical dashboard is one 1.5 KB read | Lookups by any other field scan unless indexed; a big account's document grows, and each write rewrites it |
| Key-value by code                      | The cheapest known-key read and write, and easy to spread across machines     | Any question other than "get this key" scans every key or needs a copy you maintain    |
| Denormalized copies (owner name, click total) | Reads skip a join; the dashboard reads 20 rows instead of 49           | Every change writes each copy (a rename rewrites 469 rows, clicks double to 40,000 writes a second); copies can drift |
| Tables plus a key-value redirect copy  | Each query gets a shape that fits it                                          | Two systems to run, and every edit and takedown must reach both copies                 |

</TradeoffTable>
