## The failure: one document per user

A team stores each user as one document with a `links` array inside. Sign up, create, and the dashboard each touch one
document by `_id`. Then a short link goes out in a newsletter, and the redirect has to find it.

<Callout variant="note" title="Index primer">

An **index** is a sorted copy of one or more columns, with a pointer from each entry back to its row, like the index
at the back of a book. A lookup by that column walks the sorted copy and jumps straight to the matching rows instead of
scanning the whole table. Relational databases usually build it as a B-tree. The price lands on writes: every insert,
update, or delete must also update each index on the table, so indexes speed reads and slow writes. Databases index
the primary key for you. A **secondary index** is
any index on another column, such as `owner_id` on a links table keyed by code. This lesson leans on them, and
[Indexes](../indexes/) covers them in full.

</Callout>

## The idea: list the queries, then pick the shape

Before choosing storage, write down the system's [access patterns](../../thinking/access-patterns/): each question it
asks of its data, what it knows when it asks, and how often.

| Query         | What it asks                          | What it knows | Toy rate        |
| ------------- | ------------------------------------- | ------------- | --------------- |
| Redirect      | Long URL for one code                 | Code          | 20,000 a second |
| Create a link | Store a new code, no duplicates       | Code          | 20 a second     |
| Dashboard     | A user's 20 newest links with clicks  | User          | 50 a second     |
| Analytics     | Clicks per day for one link           | Code          | 10 a second     |
| Takedown      | Every link to one domain              | Domain        | 3 a day         |

The redirect outnumbers the rest about 250 to 1 and knows only the code, so it must reach its record in one step. The
dashboard and takedown need an index on user or domain, or a layout that groups the answer.

<StepDiagram client:visible title="When the layout fights the hot query" nodes={nodes} edges={edges} steps={steps} height={290} />

<Analogy>

A library shelves books by author. Finding *Dune* by title would mean walking every shelf, so the library keeps a
catalog sorted by title, updated whenever a book arrives or leaves. That catalog is a secondary index, and its upkeep
is the price. The analogy breaks on timing: a librarian can file cards at the end of the day, while a database updates
every index inside the same write.

</Analogy>

## Tables and the four NoSQL families

Relational tables are one option. "NoSQL" names the non-relational rest, which fall into four families, each making
one kind of access cheap.

| Family                            | How it stores data                        | Access pattern it suits                     | Shortener use                                  |
| --------------------------------- | ----------------------------------------- | ------------------------------------------- | ---------------------------------------------- |
| Key-value (Redis, DynamoDB)       | One opaque value per key                  | Reads and writes by an exact key            | The redirect: code to long URL                 |
| Document (MongoDB, Couchbase)     | Nested JSON records with indexable fields | One self-contained record in a single step  | A user's profile and settings                  |
| Wide column (Cassandra, Bigtable) | Partitions by key, sorted inside          | Heavy appends, read one partition at a time | Raw clicks by code and day, sorted by time     |
| Graph (Neo4j, Neptune)            | Nodes and the edges between them          | Walks that follow edges several hops out    | Accounts sharing domains with a banned one     |

Tables cover the ground between: lookups on several fields, joins, and constraints across rows.

<details>
<summary>Go deeper: link bATJ4g in each shape</summary>

The widget leaves out wide column and graph stores, since no query here needs a raw event stream or a multi-hop walk.
Here is the link `bATJ4g` in the three shapes the widget runs. Each layout answers some questions in one step and
others only with an index or a scan. A graph used for abuse review could also link accounts that share cards with a
banned one.

```sql
-- Tables: one fact in one place, joined at read time.
CREATE TABLE links (
  code       text PRIMARY KEY,
  owner_id   bigint NOT NULL REFERENCES users (id),
  long_url   text NOT NULL,
  domain     text NOT NULL,
  created_at timestamptz NOT NULL,
  expires_at timestamptz
);
CREATE INDEX links_owner_newest ON links (owner_id, created_at DESC);
CREATE INDEX links_domain ON links (domain);

CREATE TABLE clicks_daily (
  code   text REFERENCES links (code),
  day    date,
  clicks integer NOT NULL,
  PRIMARY KEY (code, day)
);
```

```json

  "email": "ana@example.com",
  "links": [
    {
      "code": "bATJ4g",
      "url": "https://news-daily.example/launch",
      "domain": "news-daily.example",
      "created": "2024-05-09",

    }

```

```text
key:   link:bATJ4g
value: { url, owner: 1, domain, created, daily: [...] }
```

Each shape can also grow toward the others. PostgreSQL stores JSON in a `jsonb` column and indexes fields inside it.
MongoDB supports secondary indexes, including one on `links.code`, and multi-document transactions. DynamoDB stores
documents under keys and adds global secondary indexes, which are second copies of the data, partitioned by another key
and kept in sync by the database. Judge a product by the access patterns it makes cheap, and expect to design for the
queries in every one of them.

</details>

## Denormalization: faster reads, costlier writes

To **denormalize** is to copy data where a read wants it, so the read skips a join or a second lookup. Every change
must then reach every copy, and a copy that misses one serves stale data.

Copying the owner's display name onto each link row is the cheap case: a rename rewrites 469 rows, and names change
rarely. A running `click_count` on each link is the costly case. The dashboard reads **20 rows in 0.74 ms** instead of
**49 rows in 0.89 ms**, and every click now writes twice, from **20,000 to 40,000 writes a second**. If one write lands
and the other fails, the copies drift. Keep them together with a transaction (see
[Transactions and constraints](../transactions/)), or batch the totals once a second and rebuild them nightly from
`clicks_daily`.

Clicks outnumber dashboard loads 400 to 1, so the normalized design, or a batched total, is the better deal.
Denormalize when reads of the copy far outnumber the writes that keep it fresh.

<details>
<summary>Go deeper: both dashboards in SQL</summary>

Embedding links in a user document is denormalization too, with the same bill. The display name pays because a public
preview page that says who created the link loads constantly and skips the join to `users`. Any link row the rename
misses keeps the old name. The widget's key-value records make the same bet: each one copies the owner and domain from
its link.

A **normalized** design stores each click once, in `clicks_daily`, and the dashboard sums the days.

```sql
-- Each click upserts one daily row.
INSERT INTO clicks_daily (code, day, clicks) VALUES ('bATJ4g', CURRENT_DATE, 1)
ON CONFLICT (code, day) DO UPDATE SET clicks = clicks_daily.clicks + 1;

-- The dashboard sums the days for the 20 newest links.
SELECT l.code, l.long_url, l.created_at, SUM(d.clicks) AS clicks
FROM (SELECT * FROM links WHERE owner_id = 1 ORDER BY created_at DESC LIMIT 20) AS l
LEFT JOIN clicks_daily AS d ON d.code = l.code
GROUP BY l.code, l.long_url, l.created_at
ORDER BY l.created_at DESC;
```

A **denormalized** design adds a second write to every click and drops the join.

```sql
-- Each click now writes twice: the daily row above, and the total.
UPDATE links SET click_count = click_count + 1 WHERE code = 'bATJ4g';

SELECT code, long_url, created_at, click_count
FROM links WHERE owner_id = 1
ORDER BY created_at DESC LIMIT 20;
```

</details>

## Schema changes, sharding, and mixed shapes

Real shorteners mix shapes. A common design keeps **tables as the source of truth** and serves the redirect from a
**key-value copy keyed by code** (see [Caching](../../scaling/caching/)). A takedown must delete both, or the bad link
keeps redirecting.

[Sharding](../../scaling/sharding/) splits rows across machines by a shard key, and only queries that know that key
reach a single shard.

- Shard by **code**, and the redirect, create, and analytics each touch one shard. The dashboard asks every shard and
  merges, unless you keep a second copy partitioned by owner.
- Shard by **owner**, as one document per user effectively does, and the dashboard touches one shard while every
  redirect must find which shard holds its code.

Each extra access path is another copy to write and keep in sync, the same trade-off [indexes](../indexes/) make on
one machine.

<details>
<summary>Go deeper: schema changes in each shape</summary>

In the mixed design, the create path fills the key-value copy and every edit updates it.

Requirements change. Say the shortener adds link expiry, so every link gains an `expires_at`.

- **Tables** change the schema in one statement. In PostgreSQL 11 and later, adding a nullable column, or one with a
  constant default, only updates the catalog and rewrites no rows. Renames and type changes take more care: add the
  new column, write both, backfill in batches, switch reads, then drop the old one.
- **Documents** accept the new field immediately, because the database does not enforce a shape unless you add a
  validator. The schema moves into the code: every reader must handle documents with and without `expires_at`. A
  common pattern stores a `schema_version` in each document, upgrades a document whenever the app next writes it, and
  runs a background job to finish the rest.
- **Key-value** stores treat the value as opaque bytes. The version lives inside the serialized record, and every
  reader must accept old and new versions until the rewrite finishes.

"Schemaless" means the database skips checking the shape. The application still has a schema, the old data still
exists, and the queries still decide which lookups need an index.

Every shape shards. Relational databases shard with Citus and Vitess, or as distributed SQL such as Spanner and
CockroachDB, and document and key-value stores need a good partition key just as much. What scales is a hot query that
one partition can answer.

</details>

## Trade-offs

<TradeoffTable title="Choosing a storage shape for the shortener">

| Choice                                | What it buys                                      | What it costs                                                  |
| ------------------------------------- | ------------------------------------------------- | -------------------------------------------------------------- |
| Tables with indexes                   | Fast lookups on indexed fields; constraints       | Index work on every write; sharding needs planning             |
| Documents, one per user               | One read returns a user and their page            | Other lookups scan unless indexed; big documents keep growing  |
| Key-value by code                     | The cheapest known-key reads, easy to spread      | Any other question scans or needs a copy you maintain          |
| Denormalized copies                   | Reads skip a join: 20 rows instead of 49          | 469 rows per rename, 40,000 click writes a second; drift       |
| Tables plus a key-value redirect copy | Each query gets a shape that fits it              | Two systems; every edit and takedown must reach both           |

</TradeoffTable>

**When not to leave tables.** If your queries look up by several fields, join, or need constraints across rows, start
with one relational database and add indexes. Move a path to another store when its access pattern is simple and its
load outgrows the database.

## Common mistakes

- **Picking the database before listing the queries.** The hot query should pick the shape.
- **Embedding an unbounded list.** The document grows toward the size cap and draws every write.
- **Trusting "schemaless".** The app still has a schema, and readers must handle old and new records.
- **Denormalizing a hot value with no repair plan.** A copied click count drifts when one write fails.
- **Forgetting a copy on delete.** A takedown that leaves the key-value entry keeps redirecting.

<KeyTakeaways>

- List every query, the key it knows, and its rate before picking storage. The hot query picks the shape.
- A query without the key a shape is organized by needs a secondary index or a full scan.
- Each NoSQL family makes one access pattern cheap, and tables cover lookups by many fields.
- Every extra copy speeds one read, adds work to every write, and can drift.

</KeyTakeaways>
