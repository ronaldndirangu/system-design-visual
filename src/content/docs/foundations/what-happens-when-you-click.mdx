## The failure: fast code, slow links

The team's dashboards say the redirect handler takes 2 ms. Yet people in Sydney complain that `sho.rt` links feel slow.
The server sits on the US West Coast, about 12,000 km away, and a round trip between the two takes about 150 ms.

## The big picture

Before your server sees anything, the browser must find it and open a secure connection to it.

<ArcDiagram stage="dns" caption="The first click: find the server, connect, then ask." />

1. **DNS** turns the name `sho.rt` into an IP address, such as `203.0.113.7`.
2. **TCP** opens a reliable connection with a three-way handshake: one round trip.
3. **TLS** agrees on encryption keys: one round trip with TLS 1.3, two with TLS 1.2.
4. **HTTP** sends the request. The server looks up the code in the database and answers with a redirect.

```http
GET /abc123 HTTP/1.1
Host: sho.rt

HTTP/1.1 302 Found
Location: https://example.com/a/very/long/article-url
```

A round trip time (RTT) is how long a message takes to reach the server and come back. A first click pays for the DNS
lookup plus three round trips, so the formula is DNS + 3 × RTT + server work. A repeat click on an open connection
with a cached address pays one round trip plus the work.

<Analogy>

Think of calling a shop. You look up its number (DNS), dial and wait for someone to pick up (TCP), agree to speak in a
private code (TLS), and finally ask your question (HTTP). The clerk may check the back room (database). If the shop is
abroad, every pause on the line takes longer, no matter how quickly the clerk answers.

The analogy breaks in two places: a phone number lasts for years while a DNS answer expires after its TTL, and a
browser keeps the line open after a call so the next request skips the dialing.

</Analogy>

## Inside the first click

### How DNS finds the server

The DNS lookup in the widget is one fixed cost, 30 ms. Behind it sits a chain of caches and servers, and the lookup
stops at the first one that knows the answer. Step through a lookup that misses every cache.

Each answer carries a time to live (TTL) in seconds, and every cache keeps it until the TTL runs out. That makes most
lookups cheap, and it means a changed record reaches people only as their caches expire.

>

**Within about an hour for most people.** Each cache keeps the old answer until its TTL runs out, and a copy fetched one
second before your change lives the full hour. Some resolvers and clients hold answers longer than the TTL, so a few
stragglers take longer still.

</Predict>

### TTL versus failover time

A long TTL makes first clicks faster, since more lookups end in a cache. It also slows every move: if the server behind
`203.0.113.7` dies and you point `sho.rt` elsewhere, browsers keep sending clicks to the dead address until their caches
expire, up to a day with a one-day TTL.

So most sites keep the DNS answer stable and fail over behind it. A load balancer or
[reverse proxy](../../scaling/load-balancing/#reverse-proxies) holds the public address and forwards each request to a
healthy server. It drops a dead server after a few failed health checks, usually within seconds, and DNS never changes.
For a planned DNS move, lower the TTL to a minute or so at least one old TTL ahead, switch, then raise it again.

### Why distance costs time

Light in fiber covers about 200,000 km per second, two thirds of its speed in a vacuum. A round trip crosses the
distance twice, so every 1,000 km between browser and server adds about 10 ms of RTT. No code change beats that floor.

Sydney to the US West Coast is about 12,000 km: a floor near 120 ms, and real paths of about 140 to 160 ms. Sydney to
Virginia is about 15,700 km, a floor near 157 ms, yet real paths run 200 ms or more because cables do not follow great
circles and every router on the way adds queueing.

## Trade-offs

<TradeoffTable title="Choices that shape a click">

| Choice                | What it buys                                | What it costs                                                                                                                                    |
| --------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Long DNS TTL (hours)  | Fewer lookups, faster first clicks          | Slow to move traffic away from a broken server                                                                                                   |
| 301 Moved Permanently | Browsers cache it and skip your server      | Browsers may keep it a long time (unless Cache-Control sets a max-age), so repeat clicks skip you, counts run low, and a new target reaches only browsers without the cached copy |
| 302 Found             | Every click reaches you to count and update | One round trip on every click                                                                                                                    |
| Keep connections open | Later requests skip TCP and TLS             | Each open connection holds server memory                                                                                                         |
| Servers near users    | Shorter round trips for every step          | More places to deploy, monitor, and keep in sync                                                                                                 |

</TradeoffTable>

When not to use them: skip a second region while most users sit within 40 ms of one server, since little is left to
save. Keep 301 for permanent moves, such as an old domain pointing at a new one. Skip a long TTL on any name you may
need to move in a hurry.

## Common mistakes

- **Tuning code to fix distance.** Halving a 2 ms handler saves 1 ms of a 487 ms first click. Measure where the time
  goes before you optimize.
- **Timing only at the server.** The [SLO lesson](../../thinking/slos/) times redirects at the load balancer, which
  never sees DNS, the handshakes, or the trip. Measure in the browser too before you call a link fast.
- **Changing DNS with a long TTL.** A one-day TTL strands people on the old server for up to a day. Lower it first.
- **Opening a new connection per request.** Each one pays TCP and TLS again, two extra round trips every time.

<KeyTakeaways>

- A first click pays for DNS plus three round trips (TCP, TLS 1.3, and the request), so distance sets the floor.
- Every 1,000 km adds about 10 ms of round trip in fiber; only moving servers closer shortens it.
- DNS answers live in several caches for their TTL, which speeds up lookups and slows down address changes.
- Cached DNS and reused connections skip whole steps: a repeat click costs one round trip plus the work.
- A 302 keeps every click visible to you; a 301 trades counts and control for speed.

</KeyTakeaways>
