## The failure: redirects slow down as the shortener grows

Every redirect runs one query:

```sql
SELECT long_url FROM links WHERE code = 'bATJ4g';
```

The primary key is `id`, and nobody indexed `code`. At 10,000 links the query takes about a millisecond and every test
passes. At 10 million links each redirect takes about a second, and requests queue: the database checks every row, once
per click.

## The idea: sorted pages that narrow the search

An index is a sorted copy of one column, with a pointer from each value to its row. Since `id` is the primary key, an
index on `code` is a **secondary index**, the kind the primer in [Data modeling](../data-modeling/) introduced. Most
databases store it as a **B-tree**: upper pages hold separator keys that split the key range, and leaf pages hold every
key in order. Each level divides the search by the **fanout** (hundreds in practice, 500 here), so lookup cost grows
with the logarithm of the row count.

## Every index costs a write

Each index is its own B-tree, so every `INSERT` walks down each tree and writes a leaf, splitting it when full.

<details>
<summary>Go deeper: what a real insert pays</summary>

Real numbers vary. The upper levels of a busy B-tree usually stay in memory, so an insert mostly pays for the leaf. A
full leaf splits in two, which writes another page or two. Every change also goes to the write-ahead log. The shape
holds: each index adds work to every insert, every delete, and every update of an indexed column.

</details>

### One index, two jobs

`UNIQUE (code)` speeds the redirect and also rejects a duplicate code at insert, the guard from
[Transactions and constraints](../transactions/), by looking the key up in that index.

## Composite indexes and the leftmost prefix

The dashboard shows a user's 20 newest links:

```sql
SELECT code, long_url, created_at
FROM links
WHERE user_id = 42
ORDER BY created_at DESC
LIMIT 20;
```

An index on `(user_id, created_at)` sorts by `user_id`, then by `created_at` within each user, like a phone book sorted
by last name, then first name. The database walks to user 42's newest entry, reads 20 entries in order, and stops, with
no sort.

A composite index serves queries on a **leftmost prefix** of its columns:

- `WHERE user_id = 42` uses it, because `user_id` comes first.
- Adding `ORDER BY created_at DESC` uses all of it.
- `WHERE created_at > '2025-01-01'` cannot seek with it, since dates are sorted only within each user.

So `(created_at, user_id)` has the right columns in the wrong order for the dashboard.

<details>
<summary>Go deeper: covering indexes</summary>

The dashboard query above still reads a table page for each of its 20 rows to fetch `code` and `long_url`. Add those
columns to the index (`INCLUDE (code, long_url)` in PostgreSQL and SQL Server) and the index alone answers the query.
That saves 20 table reads per page view, and it makes the index larger, since long URLs are long, and every insert
writes more bytes.

</details>

## When an index cannot help

An index helps only when its sort order lets the query skip most of the table:

- **A function on the column.** `WHERE lower(code) = 'batj4g'` makes the database compute `lower(code)` for every row.
  Compare the raw column, or index the expression.
- **A leading wildcard.** `LIKE '%sale%'` gives sorted order no starting point. Many databases can use an index for a
  fixed prefix such as `LIKE 'https://shop.%'`, and a full-text index finds words inside text.
- **Low selectivity.** Following an index on `is_active`, true for 95% of rows, costs more random reads than a scan, so
  the planner scans.
- **Tiny tables.** At 100 pages a scan takes about a millisecond, and the planner may correctly skip your index.

### SQL tuning: EXPLAIN, slow query logs, denormalization

Measure before you add an index. `EXPLAIN` prints the plan the database picked (output trimmed):

```sql
EXPLAIN SELECT long_url FROM links
WHERE code = 'bATJ4g';
-- Seq Scan on links
--   Filter: (code = 'bATJ4g'::text)

ALTER TABLE links
  ADD CONSTRAINT links_code_key UNIQUE (code);
-- EXPLAIN again:
-- Index Scan using links_code_key on links
--   Index Cond: (code = 'bATJ4g'::text)
```

`Seq Scan` reads every page, the opening failure, and `Index Scan` walks the tree. PostgreSQL's `EXPLAIN ANALYZE` also
runs the query and reports real times, so wrap a write in `BEGIN` and `ROLLBACK`. To find queries worth explaining, log
the slow ones: MySQL's `slow_query_log` and PostgreSQL's `log_min_duration_statement` record statements past a time
limit, and `pg_stat_statements` totals time per query shape.

Some reads must touch many rows, such as counting a popular link's clicks, and no index fixes them. **Denormalize**:
keep a `click_count` on `links`, or copy a column to skip a join. Each copy adds write work and can drift from its
source, the trade [Data modeling](../data-modeling/) weighs.

<details>
<summary>Go deeper: plans and query statistics</summary>

On a large table the plan may say `Parallel Seq Scan`: the same full read, split across workers. MySQL logs statements
slower than `long_query_time`, and PostgreSQL's `log_min_duration_statement` takes milliseconds. The
`pg_stat_statements` extension counts calls as well as time, so it also surfaces a fast query that runs millions of
times a day.

</details>

When one database cannot keep up with lookups, [Caching](../../scaling/caching/) and
[read replicas](../../scaling/read-replicas/) spread the load.

## Trade-offs

<TradeoffTable title="Choosing indexes for the links table">

| Choice                               | What it buys                                    | What it costs                                         |
| ------------------------------------ | ----------------------------------------------- | ----------------------------------------------------- |
| No index on a queried column         | The cheapest writes and no extra storage        | Every lookup reads the whole table                    |
| B-tree index on `code`               | A few page reads per lookup at any size         | Another tree per insert; about 20% more storage here  |
| Unique index (`UNIQUE (code)`)       | Fast lookups and no duplicate codes             | The API must turn a violation into a clear error      |
| Composite (`(user_id, created_at)`)  | Serves its leftmost prefix, rows already sorted | No help when a query skips the first column           |
| Covering (`INCLUDE (...)`)           | Answers the query from the index alone          | A larger index, and more bytes written per insert     |

</TradeoffTable>

**When not to add one.** Redirects far outnumber creates here, so a few indexes pay off. A write-heavy table with rare
reads, such as a raw click log, wants only the indexes its queries need. Skip low-selectivity columns and tiny tables.

## Common mistakes

- **Indexing every column.** Each index costs every insert, update, and delete, used or not.
- **Putting the sort column first.** `(created_at, user_id)` cannot seek to one user.
- **Keeping a redundant prefix.** Beside `(user_id, created_at)`, a lone `(user_id)` only adds writes.
- **Wrapping the column in a function.** `lower(code)` skips the index on `code`.
- **Trusting test data.** A 10,000-row scan takes a millisecond. Run `EXPLAIN` on production-sized data.

<KeyTakeaways>

- A lookup with no index reads every page, so it slows as the table grows.
- A B-tree reads one page per level: 1,000 times the rows adds about one read.
- Every index is another tree that each write to its columns must update.
- A composite index serves its leftmost prefix: equality first, sort second.
- `EXPLAIN` shows a scan or an index walk. Denormalize reads no index can fix.

</KeyTakeaways>
