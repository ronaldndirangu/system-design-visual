## The failure: redirects slow down as the shortener grows

Every redirect runs one query:

```sql
SELECT long_url FROM links WHERE code = 'bATJ4g';
```

The `links` table uses `id` as its primary key, and nobody added an index on `code`. At launch, with 10,000 links, the
query takes about a millisecond and every test passes. A year later the table holds 10 million links, each redirect
takes about a second, and requests start to queue. Nothing is broken: the database does exactly what the query asks,
reading every page of the table and checking every row, once per click.

## The idea: sorted pages that narrow the search

An index is a second copy of one column, kept sorted, with a pointer from each value to its row. Databases store it as a
**B-tree**: a shallow tree of pages. The root and branch pages hold separator keys that split the key space into
ranges, and the leaf pages hold every key in order. Each level divides the search by the **fanout**, the number of
children per page (hundreds in practice, 500 in this toy model). The number of pages a lookup reads grows with the
logarithm of the row count, base fanout.

## Every index costs a write

Reads got fast because the database keeps a sorted copy of every code. That copy has a price. Each index is its own
B-tree, and every `INSERT` into `links` must add its key to each one: walk from the root to the right leaf, write the
leaf, and split it when it is full.

<IndexWriteCostWidget client:visible />

Turn on `(user_id)` and `(user_id, created_at)` together and the widget flags `(user_id)` as redundant: the composite
index starts with `user_id`, so it answers every query the single-column index can. Turn off the `code` index and the
redirect goes back to scanning the table.

Real numbers vary. The upper levels of a busy B-tree usually stay in memory, so an insert mostly pays for the leaf. A
full leaf splits in two, which writes another page or two. Every change also goes to the write-ahead log. The shape
holds: each index adds work to every insert, every delete, and every update of an indexed column. A shortener serves
far more redirects than it creates links, so a few well-chosen indexes pay off. A write-heavy table, such as a raw click
log, wants as few as its queries need.

One index pays for itself twice. `UNIQUE (code)` makes the redirect fast, and it also rejects a second link with the
same code at the moment of the insert, the guard from [Transactions and constraints](../transactions/). The database
checks uniqueness by looking the key up in that index, so a unique constraint always comes with one.

## Composite indexes and the leftmost prefix

The dashboard shows a user's 20 newest links:

```sql
SELECT code, long_url, created_at
FROM links
WHERE user_id = 42
ORDER BY created_at DESC
LIMIT 20;
```

An index on `(user_id, created_at)` sorts its entries by `user_id` first, then by `created_at` within each user, like a
phone book sorted by last name, then first name. The database walks down to the newest entry for user 42, reads 20
entries in order, and stops. It never sorts, and it never touches the user's older links.

Column order matters. A composite index serves queries that filter on a **leftmost prefix** of its columns:

- `WHERE user_id = 42` uses it, because `user_id` comes first.
- `WHERE user_id = 42 ORDER BY created_at DESC` uses all of it: one user's entries, already in date order.
- `WHERE created_at > '2025-01-01'` cannot seek with it. Dates are sorted only within each user, the way first names
  in a phone book are sorted only within each last name.

An index on `(created_at, user_id)` has the same columns in the wrong order for the dashboard. Once
`(user_id, created_at)` exists, a lone index on `(user_id)` is redundant: it costs a write on every insert and answers
nothing the composite index cannot.

**Covering indexes.** The dashboard query above still reads a table page for each of its 20 rows to fetch `code` and
`long_url`. Add those columns to the index (`INCLUDE (code, long_url)` in PostgreSQL and SQL Server) and the index alone
answers the query. That saves 20 table reads per page view, and it makes the index larger, since long URLs are long,
and every insert writes more bytes.

## When an index cannot help

An index helps only when the query can use its sort order to skip most of the table. Watch for these cases:

- **A function on the column.** `WHERE lower(code) = 'batj4g'` asks about values the index does not store, so the
  database computes `lower(code)` for every row. Compare the raw column, or build an index on the expression.
- **A leading wildcard.** `WHERE long_url LIKE '%sale%'` can match anywhere in the string, so sorted order gives no
  starting point. A fixed prefix such as `LIKE 'https://shop.%'` does, and many databases can use an index for it. For
  words inside text, use a full-text index.
- **Low selectivity.** An index on `is_active`, where 95% of rows are true, points at most of the table. Following it
  costs more random reads than a scan, so the planner scans anyway.
- **Tiny tables.** At 100 pages a scan takes about a millisecond, and the planner may skip your index, correctly.

To see what the database actually does, run `EXPLAIN` (or `EXPLAIN ANALYZE`) on the query. A `Seq Scan on links` under
a lookup by code is the failure from the top of this lesson.

An index makes one lookup cheap. When a single database still cannot keep up with the number of lookups,
[Caching](../../scaling/caching/) and [read replicas](../../scaling/read-replicas/) spread the load.

## Trade-offs

<TradeoffTable title="Choosing indexes for the links table">

| Choice                                   | What it buys                                                    | What it costs                                                                 |
| ---------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| No index on a queried column             | The cheapest writes and no extra storage                        | Every lookup reads the whole table, and its cost grows with the table         |
| B-tree index on one column (`code`)      | Lookups in a few page reads at any table size                   | One more tree to update on every insert; about 20% more storage here          |
| Unique index (`UNIQUE (code)`)           | Fast lookups plus a guarantee of no duplicate codes             | Every insert checks the key; the API must turn a violation into a clear error |
| Composite index (`(user_id, created_at)`) | Serves its leftmost prefix and returns rows already sorted     | No help for queries that skip the first column; order must match the queries  |
| Covering index (`INCLUDE (...)`)         | Answers the query from the index alone, with no table reads     | A larger index, and more bytes written on every insert                        |
| Many indexes "just in case"              | Some query might find a fast path                               | Every insert, update, and delete pays for each one, used or not               |

</TradeoffTable>
