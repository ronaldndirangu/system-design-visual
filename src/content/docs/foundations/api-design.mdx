## The failure: page 2 repeats page 1

The dashboard lists a user's links newest first, 10 per page, with `GET /v1/users/7/links?page=2&size=10`. Every test
passes. Then a power user who creates links from a script while browsing writes in: page 2 shows links from page 1, and
a link they know exists never appears on any page. Nothing errored, and the logs look clean.

## The idea: name the last link you saw

An offset says "skip 10 rows". Rows are positions, and positions move whenever the list changes above them. A cursor
says "start after link #41". A link keeps its identity however many links arrive or vanish, so the next page starts in
the right place every time.

<Analogy>

A friend reads your mail aloud from a pile, newest on top. You ask for letters 11 to 20, and two new letters land on
top while they read, so 11 and 12 are ones you already heard. Ask for "the 10 letters under the bank letter" instead,
and new arrivals do not matter.

The analogy breaks at the pile. Your friend spots the bank letter at a glance; a database needs an index on the cursor
key to find link #41 fast. And if the bank letter is shredded, your friend is stuck, while the query still asks for ids
below 41.

</Analogy>

## Try it

Two clients page through the same 50 links while the same links get created and deleted. The left lane asks for
`?page=N&size=10`. The right lane asks for `?size=10&after=<last id>`. Press Play on the busy creator first. In this toy
model the client fetches a page every 3 seconds, and a seeded schedule makes every run identical.

What to notice:

- **Busy creator.** Offset pagination shows 10 repeated rows and needs 6 pages to reach the end of 50 links. The cursor
  shows each link once, in 5 pages. Neither lane shows the 13 links created after page 1 loaded; a refresh puts them
  on top.
- **Deletions.** Each delete slides the links below it up one row, so offset pagination skips 6 links it never showed.
  The cursor skips none.
- **Quiet list.** With nothing changing, both lanes show all 50 links once, which is why the bug passes tests.

## Cursors in practice

The two lanes differ by one clause in the query.

```sql
-- Offset: page 3 walks past 20 rows, then returns 10.
SELECT code, url FROM links
WHERE user_id = 7
ORDER BY id DESC
LIMIT 10 OFFSET 20;

-- Cursor: seek past the last link seen, return 10.
SELECT code, url FROM links
WHERE user_id = 7 AND id < 41
ORDER BY id DESC
LIMIT 10;
```

The cursor query needs an index on `(user_id, id)` to seek instead of scan; the [indexes lesson](../indexes/) shows
why. Sort on a key that never repeats, or add `id` as a tiebreaker and put both in the cursor.

Hand the client an **opaque cursor**, such as `"next": "eyJpZCI6NDF9"`, and return `"next": null` on the last page.
The client sends it back unread, so you can change the sort or the encoding later without breaking anyone.

## Errors a caller can act on

The status code from [API styles](../apis/) says what kind of failure happened. The body says which one, and the
request ID says where to look.

### One body shape for every error

```json
{
  "error": {
    "code": "alias_taken",
    "message": "The alias sale is already in use.",
    "request_id": "req_7Hq2LmX9"
  }
}
```

Apps branch on `code`, people read `message`, and support asks for `request_id`. Each code joins the contract: an app
that checks for `alias_taken` breaks if you rename it.

<details>
<summary>Go deeper: Problem Details (RFC 9457)</summary>

RFC 9457 standardizes an error body as the `application/problem+json` media type. Its members are `type` (a URI that
names the kind of problem), `title`, `status`, `detail`, and `instance`, and you may add your own, such as
`request_id`. Generic tools can read it without knowing your API. A custom shape works as well when every endpoint
uses it.

</details>

### Request IDs connect a complaint to a log line

A user writes in: "Creating a link failed this morning." Without an ID, you search millions of log lines by time and
guess. So assign an ID to every request (or adopt the caller's `traceparent`), return it as `X-Request-Id` on **every**
response, write it on every log line, and pass it to every service you call. One ticket, one search.

## Breaking changes and versions

Once a client ships, the API is a promise: field names, types, required fields, status codes, error codes, and
defaults. Old phones keep old app versions for years, and partners change on their own schedule. Adding an optional
field or a new endpoint is safe for clients that ignore unknown fields. Renaming or removing a field, changing its
type, or making a parameter required breaks them. Changing a default can break them silently.

<ContractChangeWidget client:visible />

What to notice:

- **Rename a field, in place.** The old mobile app and the partner read `url`, so both break on deploy, and so do web
  tabs opened before it. **Expand, then contract** breaks nobody, at the price of running `/v1` and `/v2` together.
- **Change a default, in place.** No client errors, yet browsers cache the `301`, skip the server, and the dashboards
  undercount clicks. A silent break is harder to catch than a crash.
- **Add an optional field, with the strict parser on.** The partner's parser rejects unknown fields, so even the safest
  change breaks it. Turn the toggle off, and nobody breaks.

So clients should be **tolerant readers**: read the fields you need and ignore the rest.

### Expand, then contract

This turns one breaking change into three safe steps. Expand: add the new shape next to the old one and accept both.
Migrate: move clients over, tracking traffic per version and per client. Contract: remove the old shape, but only in a
new version, so clients that never migrate keep working.

### Versioning

The simplest place for a version is the URL, as in `/v1/links` and `/v2/links`: easy to see in logs, to route, and to
try in a browser. Bump it only for breaking changes. To retire one, announce a date, return a `Sunset` header on its
responses, and turn it off when its traffic reaches zero or the date arrives.

<details>
<summary>Go deeper: versions in a header</summary>

Some APIs put the version in a header, such as `Accept: application/vnd.shortener.v2+json` or a dated
`Api-Version: 2025-06-01`. URLs stay stable, and a client can move one request at a time. Logs and caches must read
the header too, and a cache must list it in `Vary` so it does not serve a `v1` body to a `v2` client. Either place
works when you are consistent.

</details>

## Trade-offs

<TradeoffTable title="Choices for lists and contracts">

| Choice | What it buys | What it costs |
| --- | --- | --- |
| Offset pagination (`?page=3`) | Jump to any page; easy totals | Repeats and skips on a changing list; deep pages walk every earlier row |
| Cursor pagination (`?after=<cursor>`) | Stable pages; one index seek per page | No jumping to page 37; needs a unique, indexed sort key |
| One error body shape with codes | Apps branch on codes; support finds one log line | Every code joins the contract |
| Change the contract in place | One version; fast to ship | Old clients break, some of them silently |
| Expand, then contract, with `/v2` | No client breaks | Two versions to run until the old one retires |

</TradeoffTable>

When not to use them: a list that holds still while someone reads it, such as an admin table, can keep offsets. And
when one team deploys a server and its only client together, such as a batch job, a rename in place is fine. Browser
tabs do not count, since old tabs run old code.

## Common mistakes

- Paging a changing list with `OFFSET` because it passed tests on a list that held still.
- Sorting a cursor on `created_at` alone, so two links with one timestamp straddle a page and one never shows.
- Returning errors as `200 OK` or free text, so apps parse English and monitoring counts failures as success.
- Returning the request ID only on success, which nobody files a ticket about.
- Calling a new field safe while a partner validates responses strictly.

<KeyTakeaways>

- An offset names a position, and positions move when the list changes. A cursor names the last item seen, so pages
  stay stable and each page costs one index seek.
- Give every error one body shape: a stable code for apps, a message for people, and a request ID for support.
- Adding an optional field is safe for tolerant readers. Renames, type changes, new required fields, and changed
  defaults break clients, some of them silently.
- Ship a breaking change as expand, migrate, then contract in a new version, and retire the old version when its
  traffic reaches zero.

</KeyTakeaways>
