## The failure: a link that came back 201 and then vanished

The shortener stores links in one database. [Indexes](../indexes/) showed how a B-tree finds `bATJ4g` among 10 million
rows in 4 page reads. That lesson assumed every row was already safely on disk. Getting it there is the job of the
**storage engine**: the part of the database that lays bytes out on disk and gets them back.

Writing straight to the data pages for every insert is slow, because each insert lands on a random page. Keeping new
rows in memory and writing later is fast, and a power cut erases them. A user who saw 201 Created would then find a
dead link.

## The idea: log first, organize later

Every serious engine starts the same way. Before it changes any data structure, it appends a description of the change
to a **write-ahead log** (WAL) and flushes the log to disk. Appends are fast, since they land at the end of one file.
If the machine crashes, the engine replays the log on restart and rebuilds whatever it had only in memory. This is the
same log that [read replicas](../../scaling/read-replicas/) stream from the primary to stay in sync.

After the log, engines split into two families:

- **B-tree engines** (PostgreSQL, MySQL InnoDB, SQLite) update the sorted tree in place. They change the page in memory,
  mark it dirty, and write it back later.
- **LSM-tree engines** (RocksDB, LevelDB, Cassandra, ScyllaDB) never update a file in place. They collect writes in
  memory, write them out as new sorted files, and merge files in the background. LSM stands for log-structured merge.

## Crash recovery and durable acks

A commit is durable once its log record is on disk. The data pages can lag far behind. A B-tree engine flushes dirty
pages in the background and records a **checkpoint**: a point in the log before which every change has reached the
pages. After a crash, recovery starts at the last checkpoint and replays the log forward. Frequent checkpoints shorten
recovery and cost more page writes.

An `fsync` takes from well under a millisecond to several milliseconds. One fsync per commit would cap a slow drive at a
few hundred commits a second. **Group commit** fixes that: the engine collects every commit that arrives during one
flush, writes them together, and answers all of them when the flush returns.

The log is also why [transactions](../transactions/) can roll back cleanly. Recovery redoes committed changes and
undoes changes from transactions that never committed.

<details>
<summary>Go deeper: torn pages</summary>

A database page is often 8 KB (PostgreSQL) or 16 KB (InnoDB), and a drive may write in 4 KB units. A crash halfway
through a page write leaves a **torn page**: half new, half old. A log record that says "change byte 300" cannot repair
a page whose other half is garbage. PostgreSQL writes a full copy of each page into the log the first time it changes
after a checkpoint. InnoDB writes pages to a doublewrite buffer first. Both pay extra writes to make every page
recoverable.

</details>

## Reads, Bloom filters, and compaction

An LSM read checks the memtable, then every SSTable that might hold the key, newest first. A code that exists stops at
the first match. A code that does not exist, such as a mistyped link, would check every file. A **Bloom filter**
prevents most of that work. It is a small bit array per file, kept in memory, that answers "definitely not here" or
"maybe here". About 10 bits per key give a false positive rate near 1%.

>

**About 0.06.** Each filter wrongly says "maybe" 1% of the time, so 6 files give 6 times 0.01, or 0.06 expected disk
reads. Most of these lookups touch the disk zero times. Without filters, every one of them reads all 6 files. The
filters cost memory: 10 bits per key is about 12 MB for 10 million links.

</Predict>

**Compaction** keeps the file count down. It merges sorted files into larger ones, keeps the newest version of each key,
and drops keys that were deleted. A delete in an LSM engine is itself a write: a **tombstone** that hides older values
until compaction removes both.

<details>
<summary>Go deeper: leveled and tiered compaction</summary>

**Leveled compaction** keeps each level about 10 times the size of the one above, with no overlapping keys inside a
level. Reads check about one file per level, and data gets rewritten many times as it moves down. **Tiered
compaction** waits until several similar-sized files pile up, then merges them. It rewrites data less often, and reads
check more files.

</details>

## Read, write, and space amplification

Every engine pays somewhere. Three ratios name the bill:

- **Write amplification:** bytes written to disk per byte the application writes. A B-tree rewrites a whole 8 KB page
  to change an 80-byte row. An LSM tree writes each record to the log, a flushed file, and again at each compaction.
- **Read amplification:** disk reads per lookup. A B-tree reads one page per level. An LSM tree reads up to one file
  per level, fewer with Bloom filters and caches.
- **Space amplification:** disk used per byte of live data. B-tree pages run partly empty after splits. An LSM tree
  holds old versions and tombstones until compaction catches up.

| | B-tree | LSM tree |
| --- | --- | --- |
| Write path | Log, then rewrite the page in place | Log, memtable, then new sorted files |
| Writes | Random page writes | Sequential appends and file writes |
| Point reads | Steady: one page per level | Memtable plus files, helped by Bloom filters |
| Range scans | One sorted run of leaf pages | Merge the range from several files |
| Background work | Checkpoints and page flushes | Compaction, which competes with live traffic |
| Typical use | Transactional apps with many reads | Heavy writes: events, metrics, messages |

## Trade-offs

<TradeoffTable title="Storage engine choices">

| Choice                        | What it buys                                        | What it costs                                                   |
| ----------------------------- | --------------------------------------------------- | --------------------------------------------------------------- |
| fsync the log on every commit | No acknowledged write lost to a crash               | Commit latency includes a disk flush                            |
| Group commit                  | Hundreds of commits share one flush                 | Each commit waits a little for the batch                        |
| B-tree engine                 | Predictable reads and range scans                   | Random page writes, partly empty pages                          |
| LSM engine                    | High write throughput on ordinary drives            | Compaction load, slower misses, old versions take space         |
| Leveled compaction            | Fewer files per read, less wasted space             | More rewrites per byte                                          |
| More Bloom filter bits        | Fewer wasted disk reads for absent keys             | Memory for every key                                            |

</TradeoffTable>

## Common mistakes

- Answering the client before the log reaches stable storage, or trusting a drive cache that a power cut wipes.
- Turning off `fsync` to win a benchmark and leaving it off in production.
- Expecting an LSM delete to free space at once. It writes a tombstone, and space returns after compaction.
- Running an LSM disk nearly full. Compaction writes its output before it deletes its input and needs the headroom.
- Picking an engine by write speed alone, when the workload is mostly point reads and range scans.

<KeyTakeaways>

- A commit is durable when its log record is on disk. Data pages catch up later, and recovery replays the log.
- B-trees update sorted pages in place. LSM trees append, flush sorted files, and merge them in the background.
- Bloom filters let an LSM read skip most files that cannot hold the key.
- Every engine trades among read, write, and space amplification. Pick the one whose costs your workload can afford.

</KeyTakeaways>

The shortener records every click: code, time, and country. At peak it sees 20,000 clicks a second. The dashboard
asks for clicks per day for one code over the last 30 days, and a privacy rule deletes clicks older than 90 days.

1. Which engine family fits the click store, and why?
2. How would you lay out keys so the dashboard query reads one sorted range?
3. How would you delete 90-day-old clicks without writing billions of tombstones?

<div slot="answer">

- **An LSM engine.** Writes dominate by far, and appends keep up with 20,000 a second. Group commit keeps the number of
  log flushes small.
- **Key by code, then time.** With keys like `bATJ4g#2024-05-01T10:15:02.137#a91f`, one code's clicks sit together in
  time order in every file, so the 30-day query is one range scan per file. The random suffix keeps two clicks in the

  so the dashboard reads 30 small rows.
- **Drop whole files or partitions.** Split the data by day, as separate tables or partitions, and drop each day after

  tombstones. Deleting rows one at a time would write billions of tombstones and slow every read until compaction
  clears them.

</div>
