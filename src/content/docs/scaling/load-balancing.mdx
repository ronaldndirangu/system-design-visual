## The failure: a link goes viral

The URL shortener runs on one server that can redirect 100 requests per second. A celebrity posts a short link, and
traffic jumps from 60 to 150 requests per second.

Trouble starts well before 100%. Requests arrive in random bursts, so even when the average fits, a burst can outrun the
server. At 50% busy, the line clears between bursts. At 95% busy, there is almost no quiet time to catch up. The rule
of thumb from [requirements and estimates](../../thinking/requirements-and-estimates/) is **plan for about 70% busy at
peak**. That 30% is queueing headroom that keeps waits short during bursts.

## Two ways out

**Vertical scaling** buys a bigger machine. It needs no code changes, but machines only come so big, prices rise faster
than power, and one machine is still one point of failure.

**Horizontal scaling** adds more machines of the same size and puts a **load balancer** in front of them. Clients talk to
the load balancer, which picks a server for each request.

<ArcDiagram stage="single" caption="Before: one server does everything." />

<ArcDiagram stage="scale-out" caption="After: a load balancer spreads requests over identical servers." />

For this to work, the servers must be **stateless**: any server can answer any request, because links live in the shared
database and nothing important lives in one server's memory.

<Analogy>

A supermarket with one cashier can hire a faster cashier (vertical) or open more lanes (horizontal). More lanes need
a greeter pointing shoppers to a free lane: the load balancer. When a cashier goes on break, the greeter skips that lane.

</Analogy>

## How a load balancer chooses

- **Round robin** sends requests to each server in turn. Simple and fair when every request costs the same.
- **Random** picks any server. Also simple, and slightly less even.
- **Least connections** picks the server with the fewest requests in progress. It adapts when some requests are slow.
- **Weighted round robin** gives each server a share in proportion to its weight. A server with twice the CPU gets
  weight 2. A new release under test (a canary) gets weight 1 out of 20, so only 5% of traffic reaches it.

The load balancer also runs **health checks**: it probes each server on a fixed interval and removes a server after
several failures in a row. Detection takes up to the interval times that threshold, so checks every 5 seconds with a
threshold of 3 leave a crashed server in the pool for up to about 15 seconds. Requests sent to it in that window fail.
The simulations here remove a crashed server about 2 seconds after it crashes.

Before a deploy or a scale-in, the balancer **drains** a server instead: it stops sending new requests and lets the
ones in progress finish, up to a timeout that AWS calls the deregistration delay. Nothing is cut off mid-request.

Least connections has a blind spot. A crashed server often fails fast: it refuses each request at once, so it never has
a request in progress. To a simple least connections balancer that checks every server, the broken server looks like
the least busy one in the farm.

Production load balancers defend against this in two ways:

- **Outlier detection**, which Envoy offers, ejects a server after a run of failed responses without waiting for the
  next health check.
- **Sampling two servers at random** and sending the request to the one with fewer active requests (the power of two
  choices). Envoy's least request balancer does this by default when all servers have equal weights. A broken server
  wins only when it lands in the sample, so on average it receives at most twice its equal share. In a pool of 50
  servers, that cap is 4% of traffic, though short bursts can run higher. Health checks or outlier detection still have
  to remove it.

</details>

## Plan for a crash

The 70% target buys queueing headroom. It does not cover a crash on its own. When one of N servers dies, the survivors
split its traffic, so each one goes from u busy to u × N ÷ (N − 1).

- Three servers at 70% leave two survivors at 70% × 3 ÷ 2 = **105%**. Queues grow without limit until a replacement
  arrives.
- To keep two survivors under 100%, three servers can run at most 66.7% busy. To keep them at 70%, at most 46.7%.
- Bigger pools need less spare room: 10 servers at 70% leave nine survivors at 77.8%.

Size the pool twice. First pick N so each server stays near 70% at peak. Then check what N − 1 servers would run at,
and add servers until that number is one you can live with. Teams call this N+1 sizing.

## Inside the load balancer

### Layer 4 or layer 7

Load balancers differ in how much of each request they read.

- A **layer 4** (transport layer) balancer forwards connections by IP address and port and never reads the HTTP
  request. It is fast, cheap, and works for any protocol. It sends a whole connection to one server.
- A **layer 7** (application layer) balancer reads every HTTP request. It can route by path, header, or cookie, retry a
  failed request on another server, and terminate TLS (the handshake from
  [what happens when you click](../../foundations/what-happens-when-you-click/)) so the servers skip that work.

The shortener can use layer 7 to split its traffic: redirects such as `GET /abc123` go to a pool tuned for speed, and
`/dashboard` goes to a separate pool, so a slow dashboard query never delays a redirect.

A layer 7 balancer can also pin each user to one server with a cookie, called **sticky sessions**. It lets a server keep
a login in memory, but load turns uneven when a few users are busy, and a crash logs out everyone pinned to that server.
Keep sessions in a shared store instead, and the servers stay stateless.

### Reverse proxies

A **reverse proxy** answers clients on behalf of the servers behind it, so clients see one address. It can terminate
TLS, compress responses, and cache popular answers. A layer 7 load balancer is a reverse proxy with several servers
behind it.

### Who balances the balancer?

Every request passes through the load balancer, so it needs a backup too.

- **Active-passive**: one balancer handles all traffic while a standby watches its heartbeat. When the heartbeat stops,
  the standby takes over the shared IP address, and clients on the failed balancer reconnect.
- **Active-active**: two or more balancers all handle traffic, for example with DNS returning several addresses. Each
  one must keep spare room for a failed partner: two balancers that each run above 50% busy cannot cover for each other.

The server farm runs active-active too, so its survivors need the spare room from [Plan for a crash](#plan-for-a-crash).

## Trade-offs

<TradeoffTable title="Bigger machine or more machines?">

| Approach                     | What it buys                                        | What it costs                                                  |
| ---------------------------- | --------------------------------------------------- | -------------------------------------------------------------- |
| Vertical: a bigger machine   | No code changes, no new components                  | A hard ceiling, rising prices, and one machine that can fail    |
| Horizontal: more machines    | Nearly unlimited growth, survives a crashed server  | A load balancer to run, and servers must stay stateless         |
| Round robin                  | Simple and predictable                              | Uneven queues when request costs vary                           |
| Least connections            | Adapts to slow requests and slow servers            | Favors a server that fails fast                                 |
| Short health check interval  | Faster failover                                     | A brief hiccup can eject a good server                          |
| Layer 4 balancer             | Fast, cheap, works for any protocol                 | Cannot route by path or header, or retry a single request       |
| Layer 7 balancer             | Routes by path, header, or cookie, and terminates TLS | Reads every request, which costs CPU and a little latency     |
| Active-passive balancers     | Simple failover with one shared address             | An idle standby to pay for                                      |
| Active-active balancers      | Uses every machine you pay for                      | Each balancer must keep spare room to cover a failed partner    |

</TradeoffTable>

**When not to add a load balancer.** Skip it while one server runs well under 70% at peak and a few minutes of downtime
is acceptable, as with an internal tool. Skip it too when your platform already balances for you, such as a managed
container or serverless service.

<Callout variant="warning" title="Common mistakes">

- Treating the 70% target as crash cover. Three servers at 70% leave two survivors at 105%.
- Turning on sticky sessions by default. Load turns uneven and a crash logs users out.
- Assuming a health check sees a crash at once. Detection takes the interval times the failure threshold.
- Using plain least connections when a server can fail fast. Add outlier detection.
- Forgetting the load balancer itself. Run two, or use a managed one.

</Callout>

<KeyTakeaways>

- Waits explode as a server nears 100% busy, so plan for about 70% at peak.
- A load balancer lets stateless servers share traffic and routes around a crashed one after its health checks fail.
- Least connections beats round robin when request costs vary; weights handle mixed server sizes and canaries.
- The survivors of a crash run at u × N ÷ (N − 1), so check N − 1 servers against your limit.
- The balancer needs a backup of its own.

</KeyTakeaways>

Every server in the pool still reads the same database, and [caching](../caching/) is the next fix for that.

Peak traffic for the shortener is 1,200 redirects per second. One server handles 400 per second at full load. How many
servers do you need, if you keep each one at most 70% busy **and** keep the survivors at 70% or less after one server

<div slot="answer">

- At 70%, each server takes 400 × 0.7 = 280 per second, so 1,200 ÷ 280 ≈ 4.3, which rounds up to **5 servers** for
  normal traffic.
- With 5 servers, one crash leaves 4 to carry 1,200 per second: 300 each, or 75% busy. That misses the target.
- The survivors need N − 1 ≥ 4.3, so N − 1 = 5 and **N = 6**. Each server runs at 200 per second (50%) normally and
  240 (60%) after a crash.
- The **load balancer itself** is now the single point of failure. Run two in an active and standby pair, or use a
  managed load balancer that runs redundant copies for you.

</div>
