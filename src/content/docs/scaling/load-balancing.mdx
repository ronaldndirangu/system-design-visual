## Why waiting explodes

A server is a line at a counter. Requests arrive in random bursts, so even when the average fits, a burst can arrive
faster than the server works. At 50% busy, the line clears quickly between bursts. At 95% busy, there is almost no
quiet time to catch up, so the line keeps growing. The rule of thumb: **plan for about 70% busy at peak**.

## Two ways out

**Vertical scaling** buys a bigger machine. It needs no code changes, but machines only come so big, prices rise faster
than power, and one machine is still one point of failure.

**Horizontal scaling** adds more machines of the same size and puts a **load balancer** in front of them. Clients talk to
the load balancer, which picks a server for each request.

<ArcDiagram stage="single" caption="Before: one server does everything." />

<ArcDiagram stage="scale-out" caption="After: a load balancer spreads requests over identical servers." />

For this to work, the servers must be **stateless**: any server can answer any request, because links live in the shared
database and nothing important lives in one server's memory.

<Analogy>

A supermarket with one cashier can hire a faster cashier (vertical) or open more lanes (horizontal). More lanes need
someone at the front pointing shoppers to a free lane, and that person is the load balancer. If a cashier goes on break,
the greeter stops sending people to that lane.

</Analogy>

## How a load balancer chooses

- **Round robin** sends requests to each server in turn. Simple and fair when every request costs the same.
- **Random** picks any server. Also simple, and slightly less even.
- **Least connections** picks the server with the fewest requests in progress. It adapts when some requests are slow.

The load balancer also runs **health checks**: it pings each server every few seconds and stops sending traffic to any
server that fails to answer.

## When least connections backfires

Least connections has a blind spot. A crashed server often fails fast: it refuses each request at once, so it never has
a request in progress. To a simple least connections balancer that checks every server, the broken server looks like
the least busy one in the farm.

<Predict
  client:visible
  question="Server 1 crashes at 3 s, and health checks need 2 s to remove it. Which balancer fails more requests in that window?"
  options={['Round robin', 'Least connections', 'They fail the same number, since the window is the same']}
  answer={1}
>

Least connections, by about 1.5 times in this toy model. Round robin keeps sending the broken server its usual third of
the traffic, about 70 requests per second. Least connections sees a server with nothing in progress and sends it about
half of all traffic, about 100 per second. It stops short of all traffic because an idle healthy server also has
nothing in progress and ties with the broken one. With seed 42, 139 requests fail under round robin and 211 under least
connections.

</Predict>

Production load balancers defend against this in two ways:

- **Outlier detection**, which Envoy offers, ejects a server after a run of failed responses without waiting for the
  next health check.
- **Sampling two servers at random** and sending the request to the one with fewer active requests (the power of two
  choices). Envoy's least request balancer does this by default when all servers have equal weights. A broken server
  wins only when it lands in the sample, so on average it receives at most twice its equal share. In a pool of 50
  servers, that cap is 4% of traffic, though short bursts can run higher. Health checks or outlier detection still have
  to remove it.

## Trade-offs

<TradeoffTable title="Bigger machine or more machines?">

| Approach                     | What it buys                                        | What it costs                                                  |
| ---------------------------- | --------------------------------------------------- | -------------------------------------------------------------- |
| Vertical: a bigger machine   | No code changes, no new components                  | A hard ceiling, rising prices, and one machine that can fail    |
| Horizontal: more machines    | Nearly unlimited growth, survives a crashed server  | A load balancer to run, and servers must stay stateless         |
| Round robin                  | Simple and predictable                              | Uneven queues when request costs vary                           |
| Least connections            | Adapts to slow requests and slow servers            | Tracks every server's open requests, and favors a server that fails fast |
| Short health check interval  | Faster failover                                     | More check traffic, and a brief hiccup can eject a good server  |

</TradeoffTable>

<Challenge>

Peak traffic for the shortener is 1,200 redirects per second. One server handles 400 per second at full load. How many
servers do you need, if you keep each one at most 70% busy **and** survive one server crashing at peak? What single
component can still take the whole service down?

<div slot="answer">

- At 70%, each server takes 400 × 0.7 = 280 per second, so 1,200 ÷ 280 ≈ 4.3, which rounds up to **5 servers**.
- To survive one crash at peak, add one more: **6 servers** (often written N+1).
- The **load balancer itself** is now the single point of failure. Run two in an active and standby pair, or use a
  managed load balancer that runs redundant copies for you.

</div>
