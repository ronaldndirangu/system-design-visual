## The failure: mod N moves almost everything

The [sharding lesson](../sharding/) placed each link with `shard = hash(code) mod N`. The spread was even, and the
trouble came when N changed. Going from 4 shards to 5 moved 188 of 240 links (78%), while the new shard needed only its
fair share: 1 link in 5.

Each moved link is a network copy made while the shards serve traffic, so moving four fifths of a large dataset takes
days. A [cache tier](../caching/) routed with mod N fares worse: it loses most of its hits the moment a node joins or
fails.

The goal: when a shard joins, move only the links it needs for an even share, and take them from the shards that hold
too many.

## The ring

Bend the range of hash values into a circle. Hash each shard's name to a point on the circle, and hash each key the same
way. A key belongs to the first shard you meet walking clockwise from the key's point, so each shard owns the arc between
the shard before it and itself.

Add shard E and it lands at one point, splitting one arc in two. Keys in the part of the arc before E now meet E first,
so they move to E. Every other key still meets the same shard and stays put. Remove a shard and only its own keys move,
all to the next shard clockwise.

<Analogy>

Waiters stand around a round table, and each guest is served by the first waiter clockwise from their seat. A new
waiter who steps into a gap takes over only the guests in that gap. Every other guest keeps the same waiter.

</Analogy>

## Virtual nodes even out the load

The fix gives each shard many points, called **virtual nodes** (Cassandra calls them tokens). Shard A hashes `A#0`,
`A#1`, and so on up to `A#63` onto the ring, and owns all 64 small arcs. Many random arcs average out, so every shard's
total lands near an even share.

Raise **Virtual nodes per shard** to 64 in the simulation above, then add and remove a shard.

- **The load evens out.** With 64 points per shard, the busiest of 4 shards holds 1.07× an even share, and 1.10× after
  E joins.
- **The new shard takes from everyone.** E's 64 points land all around the ring, so it takes 17 links from A, 11 from
  B, 8 from C and 11 from D.
- **Movement matches the fair share.** 47 links move (20%), right at the reference share. With one point, only 15
  moved, and E got less than a third of its share.
- **Removal spreads too.** Remove E again and its 47 links scatter back across all four shards.

More points cost a bigger map and more peers per shard.

<details>
<summary>Go deeper: how many virtual nodes, and rings that place copies</summary>

The router keeps 64 entries per shard instead of one. Each shard also shares data with more peers, so a node rebuild or
a failure touches more machines. Cassandra's production guide recommends 16 tokens for clusters that grow and shrink
often, and fewer for very large clusters, because more tokens per node lower availability when nodes fail.

Rings also place copies. Dynamo stores each key on its owner and the next distinct shards clockwise, so three copies
live on three different machines. [Replication](../read-replicas/) covered why copies matter, and
[quorums](../../distributed-data/quorums/) later shows how reads and writes choose among them.

</details>

## Hash slots: a fixed number of buckets

A ring drops shard points at random. Many systems fix the buckets instead. Redis Cluster splits the key space into
**16384 hash slots**. A key's slot is `CRC16(key) mod 16384`, and that number never changes, because 16384 never
changes. A small table maps each slot to a shard, so 4 shards own 4096 slots each.

Adding a shard leaves every key's slot alone and edits only the table: the new shard takes about 3277 slots, a fifth of
the total, and each moved slot carries its keys with it.

Fixed slots buy three things:

- **Balance by choice.** The operator gives every shard an equal count of slots.
- **Small units of work.** One slot holds about 1/16384 of the keys, so a rebalance can pause at any slot boundary.
- **A small map.** Every client holds all 16384 owners and routes a request in one hop.

## Rebalancing step by step

A slot moves while clients keep using its keys. Redis Cluster marks it **MIGRATING** on the old owner and
**IMPORTING** on the new one, then copies keys in batches.

<StepDiagram client:visible title="Moving one slot to a new shard" nodes={ringNodes} edges={ringEdges} steps={ringSteps} height={300} />

Two redirects keep every request correct during the move:

- **ASK** means "this key has moved, try E for this one request." The client keeps its map, since most of the slot
  still lives on A.
- **MOVED** means "this slot belongs to E now." The client updates its map, so later requests skip the redirect.

Any sharded store can follow the same pattern: copy in the background, catch up on writes made during the copy, switch
the owner in one step, and redirect clients that hold the old map. Slots keep each step small.

<details>
<summary>Go deeper: jump hash, rendezvous hashing, and Dynamo's comparison</summary>

**Jump consistent hash** maps a key to one of N numbered buckets with a short loop and no stored ring at all. Growing
from N to N + 1 buckets moves 1 key in N + 1 on average, exactly the new bucket's share. Its limit: buckets are
numbered, so you can add or remove only the last one. That fits storage shards that each keep their own replicas, and it
fits poorly with a cache cluster where any node can die.

**Rendezvous hashing** (highest random weight) scores every shard for each key with `hash(key, shard)` and picks the
highest score. Removing a shard moves only its keys, each to its own second choice, so they spread evenly with no
virtual nodes. The cost is one hash per shard on every lookup, which is fine for tens of shards and slow for thousands.

**Dynamo's comparison.** The Dynamo paper compared three placement strategies and found that fixed, equal size
partitions spread the load most evenly and kept the membership data smallest, the same conclusion hash slots reach.

</details>

## Trade-offs

<TradeoffTable title="Placement and rebalancing choices">

| Choice                    | What it buys                                     | What it costs                                              |
| ------------------------- | ------------------------------------------------ | ---------------------------------------------------------- |
| hash mod N                | One line of code, even spread                    | Changing N moves almost every key                          |
| Ring, one point per shard | Adding a shard moves only one arc                | Uneven arcs, and one neighbor carries every move           |
| Ring with virtual nodes   | Even load, and each move draws from every shard  | A bigger map, and each shard shares data with more peers   |
| Fixed hash slots          | Exact balance, small units to move               | A table to sync, and the slot count caps the shards        |
| Jump hash                 | No stored map, minimal movement                  | You can add or remove only the last bucket                 |
| Rendezvous hashing        | Even spread with no virtual nodes                | One hash per shard on every lookup                         |

</TradeoffTable>

**When not to use consistent hashing.** A database that changes its shard count once a year can keep mod N and pay for
one planned migration. A system with one central router can keep a table of key ranges and rebalance by splitting a
range.

<Callout variant="warning" title="Common mistakes">

- **One point per shard.** The arcs come out uneven, and one shard runs at twice its share.
- **Counting only moved keys.** A change that moves very few keys can leave the new shard nearly empty. Check the
  balance too.
- **Switching the owner before the copy finishes.** Reads for keys not yet copied come back empty. Copy, catch up,
  then cut over.
- **Expecting consistent hashing to fix a hot key.** Every placement sends one key to one owner. Hot keys still need
  copies or salting.

</Callout>

<KeyTakeaways>

- Hash mod N moves about N in N + 1 keys when a shard joins.
- On a ring, a joining shard takes only the arcs it covers, and a leaving shard hands on only its own keys.
- Virtual nodes even out the load and spread each move across every shard, at the cost of a bigger map and more peers.
- Fixed hash slots separate a key's bucket from its owner, so a rebalance edits a small table and copies whole slots.
- Copy first, switch the owner in one step, and redirect clients that still hold the old map.

</KeyTakeaways>
