## The failure: the database does all the work

The shortener now runs on three servers behind a load balancer. Every click still asks the database for the same few
viral links, thousands of times a second. The database's disk and CPU max out, and redirects slow to a crawl.

## The idea: keep hot answers in memory

A **cache** is a small, fast store (usually memory) that keeps copies of popular answers. Reading memory takes about a
millisecond over the network, while a database that reads from disk takes around ten.

<ArcDiagram stage="cache" caption="A cache sits beside the servers. The database sees only the misses." />

The most common pattern is **cache-aside**: the application checks the cache, falls back to the database on a miss, and
then fills the cache.

<StepDiagram client:visible title="Cache-aside, step by step" nodes={nodes} edges={edges} steps={steps} height={290} />

<Analogy>

You keep the ten files you use every day on your desk and the rest in a filing cabinet in the basement. Most days you
never walk downstairs. When the desk fills up, the file you have not touched for the longest time goes back to the
basement.

</Analogy>

What to look for:

- **Small caches go far** when popularity is skewed. With popularity even (slider at 0), the hit ratio only matches the
  share of links that fit.
- **Restarting the cache** sends every request to the database until the popular links come back. This is a cold cache.
- **A short TTL** lowers the hit ratio, since even popular links expire and must be fetched again.

## Stale data and invalidation

A cache holds copies, and copies can go out of date. For the shortener this is mostly easy: links never change after
creation. Deletion is the exception. If you remove a scam link from the database but not from the cache, the cache
keeps redirecting people to the scam until the entry expires.

Two tools keep caches honest:

- **Expiry (TTL)** puts an upper bound on how old a cached answer can get.
- **Invalidation** deletes the cache entry whenever the source data changes.

## Write strategies

So far the cache only handles reads. The dashboard adds writes: people edit their links, and every click adds 1 to a
click count. Each write now has to reach the cache, the database, or both, and the order decides speed, load, and what a
crash destroys.

- **Write-through.** Each write updates the database and the cache before it returns. A read right after the write
  finds the new value in the cache. Every write waits for the database.
- **Write-behind** (also called write-back). Each write updates only the cache and returns in about a millisecond. Every
  2 seconds the cache saves its changed links to the database, and several changes to one link merge into one database
  write. Until that save, the cache holds the only copy.
- **Write-around.** Each write updates the database and deletes the cached copy. The next read misses and loads the
  fresh value, so written data enters the cache only when someone reads it.

<Predict
  client:visible
  id="scaling/caching/predict-2"

  options={['Write-through', 'Write-behind', 'Write-around', 'All three send the same number']}
  answer={1}
>

**Write-behind**. A popular link gets clicked many times in each 2 second window, and the cache saves only its latest
count. With seed 42, 4,015 click writes reach the database as 1,501 under write-behind, while write-through and
write-around send all 4,015, one database write per click. The count lives under its own key, apart from the redirect it
counts, so write-around never touches a cached redirect: its hit ratio holds at 84%, the same as with no counting.
Write-through and write-behind put every counter they update in the cache, the counters push links out, and their hit
ratio falls to 69%.

</Predict>

<WriteStrategyWidget client:visible initial="clicks" />

What to look for:

- **Count every click** rewards write-behind: frequent writes to the same few keys merge before they reach the
  database. Write-around pays one database write per click and keeps the best hit ratio, because the counters never
  enter the cache.
- **Bulk import** punishes write-through and write-behind. Both put each imported link in the cache, and those links push
  the popular ones out. Write-around keeps the popular links, and its hit ratio for the run ends near 84% against 62%.
- **Cache crashes** shows the price of write-behind. With seed 42 it loses 38 writes that callers already saw succeed.
  Write-through and write-around lose none, because the database already had every write.

A fourth strategy works on the read side. **Refresh-ahead** reloads a popular entry from the database shortly before its
TTL runs out, so readers keep getting fresh answers without ever paying for the miss. It costs database reads for
entries nobody asks for again, and it helps only when the cache can guess which entries people will read next.

Teams that use write-behind for data they cannot lose put the buffer in a replicated cache or a durable log. Click
counts can tolerate a few lost seconds. Payments cannot.

## Trade-offs

<TradeoffTable title="Tuning a cache">

| Choice                       | What it buys                                       | What it costs                                              |
| ---------------------------- | -------------------------------------------------- | ---------------------------------------------------------- |
| Bigger cache                 | Higher hit ratio, less database load               | Memory is pricier than disk, and gains shrink as it grows   |
| Long TTL                     | More hits                                          | Changes and deletes take longer to show                    |
| Short TTL                    | Fresher answers                                    | More misses and more database reads                        |
| Invalidate on every write    | Fresh data without a short TTL                     | Extra code on every write path, and easy to forget one     |
| Shared cache (such as Redis) | Every server sees the same hot links               | One more network hop and one more system to run            |
| Cache inside each server     | Fastest reads, nothing extra to run                | Each server warms up alone, and copies can disagree        |
| Write-through                | Fresh reads after a write, database always current | Every write waits for the database, and writes fill the cache |
| Write-behind                 | Fast writes, and repeated writes merge into one    | A cache crash loses confirmed writes                       |
| Write-around                 | Writes never push hot links out of the cache       | The first read after each write misses                     |
| Refresh-ahead                | Popular entries stay fresh with no miss            | Extra database reads for entries nobody reads again        |

</TradeoffTable>
