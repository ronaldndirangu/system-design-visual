## The failure: the database does all the work

The shortener now runs on three servers behind a [load balancer](../load-balancing/). Every click still asks the
database for the same few viral links, thousands of times a second. The database's disk and CPU max out, and redirects
slow to a crawl. The [access pattern](../../thinking/access-patterns/) already told us where to look: reads outnumber
writes 100 to 1, and a few links get most of the reads.

## The idea: keep hot answers in memory

A **cache** is a small, fast store (usually memory) that keeps copies of popular answers. Reading a cache over the
network takes 0.5 to 1 ms. An indexed database read takes 1 to 5 ms, and much longer once the database is busy. The lab
below uses 1 ms for a hit and 4 ms for a miss (the cache check plus a 3 ms database read).

<ArcDiagram stage="cache" caption="A cache sits beside the servers. The database sees only the misses." />

The most common pattern is **cache-aside**: the application checks the cache, falls back to the database on a miss, and
then fills the cache.

<StepDiagram client:visible title="Cache-aside, step by step" nodes={nodes} edges={edges} steps={steps} height={290} />

<Analogy>

You keep the ten files you use every day on your desk and the rest in a filing cabinet in the basement. Most days you
never walk downstairs. When the desk fills up, the file you have not touched for the longest time goes back to the
basement.

</Analogy>

### Where caches live

Copies can sit at every hop. A layer closer to the user saves more work and is harder to clear.

- **Browser.** It reuses a response only when `Cache-Control` or `Expires` allows it. The shortener sends neither on its
  302 redirects, so every click reaches the server and the counts stay honest.
- **CDN.** Edge servers near users, covered in the [next lesson](../cdn/).
- **In-process.** A map in each server's memory: the fastest read, but each server warms alone and copies can disagree.
- **Shared.** Redis or Memcached on their own machines, as in this lesson. Every server sees the same hot links.
- **Database buffer pool.** Recently read pages in the database's own memory.

An **object cache** keeps one record by key. A **query cache** keeps a whole result, such as "my 20 newest links", and
goes stale when any row in it changes.

## When the cache misses at once

The restart you just tried is the extreme case of a common outage: many requests miss together, and the database was
sized for a warm cache. Three things trigger it. A cache restarts empty. A viral link expires while thousands click it,
so they all miss in the same second (a **stampede**, or thundering herd). Or people request links that do not exist,
which never get cached.

<StepDiagram client:visible title="A stampede, and how single-flight stops it" nodes={herdNodes} edges={herdEdges} steps={herdSteps} height={290} />

The defenses each cut a different trigger:

- **Single-flight** (request coalescing). The first miss on a key reads the database, and later misses wait for its
  answer.
- **TTL jitter.** Add a random few seconds to each TTL so entries filled together do not expire together.
- **Stale-while-revalidate.** Serve the expired copy while one request refreshes it in the background.
- **Negative caching.** Cache "no such link" for a short time, so a flood of bad codes reads the database once per code.
- **Warming.** Load the most popular keys before a fresh cache takes traffic, or shift traffic to it gradually.

## Stale data and invalidation

People can edit and delete links. Say you delete `sho.rt/xyz789` as a scam. The database row is gone, but the cache
keeps redirecting people to the scam until its copy expires. An edit fails the same way: clicks keep going to the old
address.

- **Expiry (TTL)** puts an upper bound on how old a cached answer can get.
- **Invalidation** deletes the cache entry whenever the source data changes. Every edit and every delete must clear the
  cached copy, and one forgotten code path brings the stale answer back. Delete the entry instead of setting a new
  value, since two quick sets can land out of order.

<details>
<summary>Go deeper: the race between a delete and a refill</summary>

Deleting has a race of its own. A reader misses, reads the old row, and stalls for a moment. An edit commits and
deletes the entry. The reader wakes and fills the cache with the old row, and nothing is left to clear it. A rule such
as "fill only if the cached copy is older" cannot help, because the delete removed the copy it would compare against.
Two guards work:

- **Generation or tombstone.** The delete leaves a small marker holding the row's version, such as `xyz789: v8`. A
  fill that carries v7 sees the newer marker and drops itself. Keep the marker longer than any read can stall.
- **Fill lease.** On a miss, the cache hands the reader a lease token. The delete atomically invalidates every open
  lease on that key, so the stale fill bounces. Memcache at Facebook works this way.

A TTL only bounds how long a stale fill survives.

</details>

## Write strategies

The dashboard adds writes: people edit their links, and every click adds 1 to a count. Each write must reach the cache,
the database, or both, and the order decides speed, load, and what a crash destroys.

- **Write-through.** Each write updates the database and the cache before it returns, so every write waits for the
  database.
- **Write-behind** (write-back). Each write updates only the cache and returns in about a millisecond. Every 2 seconds
  the cache saves its changes, and several changes to one link merge into one database write. Until then, the cache
  holds the only copy.
- **Write-around.** Each write updates the database and deletes the cached copy, so written data enters the cache only
  when someone reads it.

**Write-behind**. A popular link gets clicked many times in each 2 second window, and the cache saves only its latest
count. With seed 42, write-behind turns 4,015 click writes into 1,501 database writes; the other two send all 4,015.
Each count lives under its own key, so write-around never touches a cached redirect and its hit ratio holds at 84%.

to 69%.

</Predict>

What to look for:

- **Count every click** rewards write-behind: writes to the same few keys merge before they reach the database.
  Write-around pays one database write per click and keeps the best hit ratio.
- **Bulk import** punishes write-through and write-behind. Both cache each imported link, which pushes the popular ones
  out. Write-around ends the run near 84% against 62%.
- **Cache crashes** shows the price of write-behind. With seed 42 it loses 38 writes that callers already saw succeed.
  The other two lose none.

<details>
<summary>Go deeper: refresh-ahead and durable write-behind</summary>

A fourth strategy works on the read side. **Refresh-ahead** reloads a popular entry from the database shortly before
its TTL runs out, so readers keep getting fresh answers without ever paying for the miss. It costs database reads for
entries nobody asks for again, and it helps only when the cache can guess which entries people will read next.

Teams that use write-behind for data they cannot lose put the buffer in a replicated cache or a durable log. Click
counts can tolerate a few lost seconds. Payments cannot.

</details>

## Trade-offs

<TradeoffTable title="Tuning a cache">

| Choice                       | What it buys                                        | What it costs                                                 |
| ---------------------------- | --------------------------------------------------- | ------------------------------------------------------------- |
| Bigger cache                 | Higher hit ratio, less database load                | Memory is pricier than disk, and gains shrink as it grows     |
| Long TTL                     | More hits                                           | Changes and deletes take longer to show                       |
| Short TTL                    | Fresher answers                                     | More misses and more database reads                           |
| Invalidate on every write    | Fresh data without a short TTL                      | Extra code on every write path, and easy to forget one        |
| Shared cache (such as Redis) | Every server sees the same hot links                | One more network hop and one more system to run               |
| Write-through                | Fresh reads after a write, database always current  | Every write waits for the database, and writes fill the cache |
| Write-behind                 | Fast writes, and repeated writes merge into one     | A cache crash loses confirmed writes                          |
| Write-around                 | Writes never push hot links out of the cache        | The first read after each write misses                        |

</TradeoffTable>

**When not to cache.** Skip the cache when reads spread evenly across far more data than memory holds, when every read
must see the latest write (a balance before a payment), or when the database is already fast enough.

<KeyTakeaways>

- Skewed popularity lets a cache that holds 10% of the links answer well over half of the clicks.
- Cache-aside reads the cache first, falls back to the database, and fills the cache on a miss.
- Many misses at once (a restart, a hot key expiring, unknown keys) can flatten a database sized for a warm cache.
- Every edit and delete must invalidate the cached copy, and the TTL bounds how long a missed one lingers.
- Write-behind merges writes and risks losing them; write-through and write-around never lose a confirmed write.

</KeyTakeaways>
