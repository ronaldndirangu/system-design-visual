## The failure: the database does all the work

The shortener now runs on three servers behind a load balancer. Every click still asks the database for the same few
viral links, thousands of times a second. The database's disk and CPU max out, and redirects slow to a crawl.

<Predict

  options={['About 10%', 'About 30%', 'About 70%', 'All of them']}
  answer={2}
>

About **70%**. Click popularity follows a long tail: the top link gets twice the clicks of the second, three times the
clicks of the third, and so on. The 100 most popular links cover about 70% of all clicks, so the database sees fewer than
a third of the reads it saw before.

</Predict>

## The idea: keep hot answers in memory

A **cache** is a small, fast store (usually memory) that keeps copies of popular answers. Reading memory takes about a
millisecond over the network, while a database that reads from disk takes around ten.

<ArcDiagram stage="cache" caption="A cache sits beside the servers. The database sees only the misses." />

The most common pattern is **cache-aside**: the application checks the cache, falls back to the database on a miss, and
then fills the cache.

<StepDiagram client:visible title="Cache-aside, step by step" nodes={nodes} edges={edges} steps={steps} height={290} />

<Analogy>

You keep the ten files you use every day on your desk and the rest in a filing cabinet in the basement. Most days you
never walk downstairs. When the desk fills up, the file you have not touched for the longest time goes back to the
basement.

</Analogy>

## Try it

Start with no cache, then give it room. Change how uneven popularity is, set an expiry time, and restart the cache in
the middle of a run.

<CacheWidget client:visible />

What to look for:

- **Small caches go far** when popularity is skewed. With popularity even (slider at 0), the hit ratio only matches the
  share of links that fit.
- **Restarting the cache** sends every request to the database until the popular links come back. This is a cold cache.
- **A short TTL** lowers the hit ratio, since even popular links expire and must be fetched again.

## Stale data and invalidation

A cache holds copies, and copies can go out of date. For the shortener this is mostly easy: links never change after
creation. Deletion is the exception. If you remove a scam link from the database but not from the cache, the cache
keeps redirecting people to the scam until the entry expires.

Two tools keep caches honest:

- **Expiry (TTL)** puts an upper bound on how old a cached answer can get.
- **Invalidation** deletes the cache entry whenever the source data changes.

## Trade-offs

<TradeoffTable title="Tuning a cache">

| Choice                       | What it buys                                       | What it costs                                              |
| ---------------------------- | -------------------------------------------------- | ---------------------------------------------------------- |
| Bigger cache                 | Higher hit ratio, less database load               | Memory is pricier than disk, and gains shrink as it grows   |
| Long TTL                     | More hits                                          | Changes and deletes take longer to show                    |
| Short TTL                    | Fresher answers                                    | More misses and more database reads                        |
| Invalidate on every write    | Fresh data without a short TTL                     | Extra code on every write path, and easy to forget one     |
| Shared cache (such as Redis) | Every server sees the same hot links               | One more network hop and one more system to run            |
| Cache inside each server     | Fastest reads, nothing extra to run                | Each server warms up alone, and copies can disagree        |

</TradeoffTable>
