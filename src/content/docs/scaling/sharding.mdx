<Objectives>

- Split a database by feature before splitting it by key.
- Pick a shard key by checking cardinality, skew, and query fan-out.
- Compare range and hash placement, and judge a placement on keys moved and load balance.
- Choose between local and global secondary indexes.
- Treat hot reads and hot writes as two different problems.

</Objectives>

## The failure: one primary runs out of room

At 100 million users, the shortener stores hundreds of terabytes and accepts thousands of new links per second.
[Read replicas](../read-replicas/) copied the reads away, but one primary still has to take every write and hold every
link. No single machine is that big.

The fix is to **split the data**: each database (a **shard**) holds a slice of the links, also called a
**partition**. Two questions decide the design: which field picks the slice, and how a value maps to a shard.

## Split by feature first: federation

Before splitting one table, check whether the database holds unrelated jobs. The shortener keeps links, accounts, and
analytics (one row per click). Clicks write far more often than anything else, and no redirect reads them.

**Federation** gives each feature its own database. The links database stops absorbing click writes, and an accounts
outage leaves redirects running. It has limits:

- **A handful of splits.** A product has a few features, so federation multiplies capacity by a few.
- **Joins and transactions move into the app.** "Links with their owner's plan" reads two databases, and creating an
  account with its first link becomes two writes that can half fail.
- **Each feature keeps one primary.** When the links database alone outgrows a machine, it needs sharding.

## Choosing a shard key

The **shard key** is the field that decides where each record lives. Start from the
[access patterns](../../thinking/access-patterns/): list the queries and their rates, then test each candidate key
against three checks.

- **Cardinality.** The key needs many more distinct values than you will ever have shards. Country caps the count near
  200 shards, while a short code has billions.
- **Skew.** Values should carry similar amounts of data and traffic. A created date sends every new write to today's
  shard. A tenant id sends a giant customer's whole load to one shard.
- **Query fan-out.** The busiest queries should name the key, so each one touches a single shard. A query that leaves
  the key out has to ask every shard.

For the shortener, every redirect names exactly one short code, so every redirect touches exactly one shard. "List my
links" names a user instead, and secondary indexes, below, handle it.

Changing the key later means moving every record while the old layout keeps serving, so pick it with care.

## Range or hash placement

- **Range placement** gives each shard a contiguous slice of keys: codes starting `a` to `f` on shard 1, `g` to `m` on
  shard 2. Range scans stay on one or two shards, and a busy range splits in two. Sequential keys break it: timestamps
  or increasing ids all land in the last range, so one shard takes every new write.
- **Hash placement** hashes the key first, then places the hash. Neighboring keys scatter, so sequential keys spread
  evenly. Range scans now ask every shard.

The simplest hash placement takes the remainder: `shard = hash(code) mod N`. It spreads links evenly, until N changes.

<ShardingWidget client:visible placement="modulo" showPlacement={false} />

What to look for:

- **Two numbers judge a change.** The first is the share of links that move, compared with the **balanced reference
  share**: the slice a new shard needs to hold an even share, 1 in 5 when 4 shards become 5. The second is how even
  the load stays afterward.
- **Mod N passes on balance and fails on movement.** Going from 4 to 5 shards moves 188 of the 240 links (78%) against
  a reference share of 20%, while the busiest shard stays within 1.15× an even share.
- **More shards make it worse.** Going from 7 to 8 moves 220 of 240 links (92%), since a link keeps its shard only
  when both remainders match.

<details>
<summary>Go deeper: moving data without downtime</summary>

Any change of shard count or shard key means copying live data. Teams follow the same five steps:

1. **Backfill.** Copy existing rows to their new shards in the background, throttled so live traffic stays fast.
2. **Catch up.** Stream the change log (or write to both layouts) so rows changed during the copy arrive too.
3. **Verify.** Compare row counts and checksums between old and new homes.
4. **Cut over.** Flip the router to the new layout, one slice at a time, with a way back.
5. **Clean up.** Delete the old copies once nothing reads them.

Tools such as Vitess automate these steps. The amount of data to move still sets the time, which is why the placement
rule matters.

</details>

## Secondary indexes: local or global

Sharding by code makes "list Ada's links" hard, since her links hash to every shard. An
[index](../../foundations/indexes/) on user id helps, and there are two places to keep it.

- **Local index.** Each shard indexes its own links by user id. A new link and its index entry live on the same shard,
  so a write stays on one machine. A query by user asks every shard and merges the answers (**scatter and gather**).
  With 16 shards, one page view becomes 16 queries, and the slowest shard sets the page's latency.
- **Global index.** A separate index, sharded by user id, maps each user to their codes. The query reads one index
  shard, then fetches the links it lists. A write now touches two shards, so most systems update the global index a
  moment later, and a brand new link can be missing from the list for that moment.

Use a local index for rare queries and a global index for frequent ones.

## Hot keys: hot reads and hot writes

Sharding spreads many keys, and it gives each key exactly one home. One viral link keeps its shard busy no matter how
many shards you add. The fix depends on the direction of the traffic.

**Hot reads** have many cures, because any copy can answer a read. The [cache](../caching/) answers most clicks from
memory, and replicas of that one shard take what the cache misses.

**Hot writes** are harder, because every write has to reach the key's one owner.

  options={['About 1%', 'About half', 'All of them']}
  answer={2}
>

**All of them.** A cache absorbs reads by answering from a copy. An increment changes the one row that owns the count,
so every click still lands on that shard. Replicas replay every write, so they cannot help either.

</Predict>

Two fixes from [access patterns](../../thinking/access-patterns/) carry over to shards:

- **Salt the key.** Store the counter as eight parts, `abc123#0` to `abc123#7`. Each click adds to a random part, and
  the parts hash to different shards, so the writes spread. Reading the total means gathering all eight parts.
- **Batch the writes.** Each app server counts clicks in memory and adds its total to the shard once a second. The
  count trails by a second, and a crash loses the unsent part.

Salt only the keys that need it. Salting every key turns every read into a gather across shards.

## Trade-offs

<TradeoffTable title="Partitioning choices">

| Choice                        | What it buys                                        | What it costs                                                |
| ----------------------------- | --------------------------------------------------- | ------------------------------------------------------------ |
| Federation (split by feature) | Each feature scales and fails on its own            | Joins and transactions across features move into the app     |
| hash mod N                    | Simple, even spread, one line of code               | Changing N moves almost every key                            |
| Range sharding (A to F...)    | Fast range scans, easy to split a busy range        | Sequential keys pile onto one shard                          |
| Shard by user instead         | One user's links live together                      | Redirects must find the owner first, and big users run hot   |
| Local secondary index         | Writes stay on one shard                            | Queries on the indexed field ask every shard                 |
| Global secondary index        | Queries on the indexed field read one index shard   | Writes touch two shards, and the index trails the data       |
| Salted hot key                | One key's writes spread over many shards            | Every read gathers and adds up all the parts                 |

</TradeoffTable>

**When not to shard.** Shard last. One large primary handles thousands of writes a second and several terabytes, and a
cache, replicas, and federation are each cheaper and easier to undo. Shard when one feature's writes or data outgrow the
biggest machine you can buy.

<Callout variant="warning" title="Common mistakes">

- **A key with few values or heavy skew,** such as country or created date.
- **Sharding before listing the queries,** then finding that the busiest one leaves out the key and asks every shard.
- **Expecting a cache or replicas to fix a hot write.** Both copy data, and every write still reaches one owner.
- **Splitting data that changes together.** Keep records that one transaction updates on the same shard.

</Callout>

<KeyTakeaways>

- Shard when one primary cannot hold the writes or the data, and federate by feature first.
- A good shard key has many values, little skew, and appears in the busiest queries.
- Range placement keeps scans fast and suffers on sequential keys. Hash placement spreads keys and scatters scans.
- Judge a placement on two numbers: keys moved against the balanced reference share, and how even the load stays.
- Local indexes keep writes on one shard and fan out reads. Global indexes read from one place and lag behind writes.
- Hot reads need copies. Hot writes need salted keys or batched writes.

</KeyTakeaways>

Mod N moved 78% of the links when one shard joined. [Consistent hashing](../consistent-hashing/), the next lesson, moves
close to the 20% reference share and keeps the load even.
