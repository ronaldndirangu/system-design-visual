## The failure: one database, too many reads

The cache answers most clicks, and the [CDN](../cdn/) answers many before they reach a server, but at 10 million users
the misses alone keep one database pinned at 100% busy. Reads now queue behind each other, and the occasional write
waits behind them.

## The idea: one writer, many readers

Copy the database to more machines. The **primary** takes every write and streams the changes to **replicas**, which
serve reads. A URL shortener reads about 100 times for every write, so replicas can carry almost all of the load.

## Try it: add replicas

Press Play. One database cannot keep up. Add replicas until the load bars calm down, then raise the writes. Raise the
lag and watch stale reads (squares with a cross) appear, then turn on read your own writes.

<ReplicationWidget client:visible />

What to look for:

- **Every replica replays every write.** With replicas, only the replicas serve reads. Raise the writes and the read
  capacity of every replica falls at once.
- **Stale reads come from fresh links.** A link created long ago is already on every replica. Only reads inside the lag
  window go wrong.
- **Reads can go back in time.** Each replica lags by its own amount. One read finds a new link on a quick replica, and
  the next lands on a slower one that answers Not found.
- **Read your own writes** sends a person's reads of their own fresh links to the primary. Their stale reads vanish,
  and the primary takes a little extra load.
- **Writes lost if the primary crashed now** counts acknowledged writes each replica has not received yet.

## Synchronous, semi-synchronous, or asynchronous

The real choice is when the primary tells the app "saved". Each answer trades write speed against what a failover
loses.

- **Asynchronous** (the default almost everywhere). The primary acknowledges once the write is on its own disk, and
  replicas copy it later. Writes stay fast. A crash loses the lag window: a replica trailing by half a second at 40
  writes per second misses about 40 × 0.5 = **20 links**.
- **Synchronous.** The primary waits until every replica in its sync set confirms. Promote any of them and no
  acknowledged write is lost. Every write waits for the slowest confirmation, and a replica that stops answering stops
  all writes.
- **Semi-synchronous.** The primary waits for **any one** replica to confirm, so writes wait only for the fastest
  replica. Failover must promote the replica that holds every acknowledged write: the one with the highest log
  position. MySQL falls back to asynchronous replication when no replica confirms within a timeout (10 seconds by
  default), so a replica outage quietly removes the guarantee.

<details>
<summary>Go deeper: distance, and what "confirmed" means</summary>

Distance sets the price. A replica in the same data center confirms in about a millisecond, so semi-synchronous
replication costs little there. A replica in another region sits 70 ms or more away, and a synchronous write waits for
that round trip every time. Many teams keep one semi-synchronous replica nearby and replicate to other regions
asynchronously.

"Confirmed" usually means the replica stored the change in its log, which can happen before it applies the change to
its tables. A synchronous replica can still answer a read from before the write. Durability and freshness are separate
guarantees.

</details>

## Failover and split brain

When the primary dies, a **failover** moves its job to a replica:

1. **Detect.** Monitors declare the primary dead after several missed heartbeats, for example three checks one second
   apart. A shorter timeout fails over on a brief pause, such as a long garbage collection; a longer one keeps writes
   down longer.
2. **Promote.** Pick the replica with the highest applied log position, so the fewest writes are lost, and point the
   other replicas at it.
3. **Redirect.** Move the app's writes to it through a proxy, service discovery, or DNS.

The dangerous case is a primary that is alive and unreachable:

<StepDiagram client:visible title="A failover with and without fencing" nodes={failNodes} edges={failEdges} steps={failSteps} height={300} />

Two primaries taking writes at once is **split brain**. Their histories drift apart, and merging them means discarding
one side's writes. **Fencing** prevents it:

- **Quorum.** An odd number of monitors (3 or 5) vote, and only a majority can promote, so a cut-off minority cannot
  elect a second primary.
- **Lease.** The primary renews a lease of a few seconds from a majority of a coordination service such as etcd. A
  primary that cannot renew stops taking writes, and the new primary waits out the old lease, which adds to every
  failover.
- **Epoch number.** Each promotion raises a number that tags every write. Replicas and storage reject writes with an
  older number, so a stale primary's late writes fail.

[Raft](../../distributed-data/raft/) builds terms and majority votes into a leader election protocol.

<details>
<summary>Go deeper: multi-leader and leaderless replication</summary>

Everything above uses one primary. Two other designs let more than one node accept writes.

**Multi-leader** replication runs a primary in each region, and each one streams its writes to the others. Writes stay
local and fast, and a region keeps writing during a network split. Two regions can then change the same row at once,
so the system needs a conflict rule. "Last write wins" picks the later timestamp and silently drops the other change.
Safer rules merge both changes, or avoid conflicts by routing each user's writes to one home region.

**Leaderless** replication, used by Dynamo-style stores such as Cassandra, sends each write to several replicas and
each read to several replicas. With N copies, a write that W nodes confirm and a read that R nodes answer overlap when
W + R > N, so the read sees the latest write. [Quorums](../../distributed-data/quorums/) covers this in depth.

</details>

## Freshness tokens: read your writes and monotonic reads

The primary numbers every change in its log: a **log sequence number** (LSN) in PostgreSQL, a global transaction id in
MySQL. Each replica reports the highest position it has applied, which turns "fresh enough?" into a comparison.

- **Read your own writes.** The create response carries the write's position, say 1,042, and the app sends it with the
  person's next reads. A replica at 1,042 or later answers. One behind it waits a few milliseconds or hands the read to
  the primary.
- **Monotonic reads.** The app tracks the highest position each person has seen. A replica at 1,045 can answer, and one
  at 1,030 is skipped, so a link they already opened never vanishes. Pinning each user to one replica also works, and
  it spreads load less evenly.

A token in a browser cookie covers one device, so a link created on a phone can still look missing on a laptop. Keep
it in a server-side session to cover both. [Consistency models](../../distributed-data/consistency-models/) covers the
full family of guarantees.

## Trade-offs

<TradeoffTable title="Replication choices">

| Choice                     | What it buys                                                    | What it costs                                                   |
| -------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------- |
| More replicas              | More read capacity, more copies of the data                     | Every replica replays every write                               |
| Asynchronous replication   | Fast writes                                                     | Stale reads, and acknowledged writes can vanish in a failover   |
| Synchronous replication    | No lost acknowledged writes                                     | Slower writes, and a slow replica stalls the primary            |
| Read your own writes       | People see their own changes, even when lag runs long           | Extra primary load, and the app carries log positions           |
| Monotonic reads            | Nobody sees data appear and then vanish                         | Uneven load from pinning, or log positions to track             |
| Replicas in other regions  | Fast reads near users, survives a region loss                   | Lag of 100 ms or more across oceans                             |

</TradeoffTable>

**When not to replicate for reads.** A cache node answers far more reads than a database replica, so let the cache
take what it can first. Replicas help little when the workload writes heavily, since each one replays every write, or
when every read must see the latest write, since those reads go to the primary anyway. One standby for failover is
still worth running.

<Callout variant="warning" title="Common mistakes">

- **Reading a fresh write from a replica,** so a person creates a link and then sees Not found.
- **Promoting whichever replica answers first.** The most caught up replica loses the fewest writes, so compare log
  positions first.
- **Failing over without fencing,** so a cut-off primary keeps taking writes and two histories drift apart.
- **Treating replicas as backups.** A bad delete reaches every replica in milliseconds. Keep point-in-time backups too.

</Callout>

<KeyTakeaways>

- Replicas multiply read capacity. Every write still goes to the primary, and every replica replays it.
- Asynchronous replication keeps writes fast and loses the lag window in a failover. Semi-synchronous and synchronous
  replication spend write latency to keep acknowledged writes.
- Fail over to the most caught up replica, and fence the old primary with a quorum, a lease, or an epoch number.
- Log positions turn freshness into a comparison for read your own writes and monotonic reads.
- Replicas copy mistakes as fast as data, so keep backups.

</KeyTakeaways>

Replicas copy every link to every machine, so the primary still takes every write and each replica still stores
everything. [Sharding](../sharding/), the next lesson, splits the links so each machine holds and writes only a slice.

<div slot="answer">

- 50,000 × 10% = **5,000 reads per second**.
- 2,000 × 0.7 = 1,400, and replaying 100 writes leaves 1,300. 5,000 ÷ 1,300 ≈ 3.8, which rounds up to **4 replicas**,

- At 5,000 writes, replicas stop helping. The primary must accept every write and every replica replays all 5,000.
  Split the data: [sharding](../sharding/), the next lesson.

</div>
