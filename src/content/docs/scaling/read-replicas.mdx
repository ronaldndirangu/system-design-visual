## The failure: one database, too many reads

The cache answers most clicks, but at 10 million users the misses alone keep one database pinned at 100% busy. Reads now
queue behind each other, and the occasional write waits behind them.

**Sometimes a Not found error.** The read lands on a replica that has not received the new link yet. Wait half a
second and it works. The data was never lost; the person just looked too early. This is a **stale read**, and the
fix is to send people's reads of their own fresh data to the primary.

</Predict>

## The idea: one writer, many readers

Copy the database to more machines. The **primary** takes every write and streams the changes to **replicas**, which
serve reads. A URL shortener reads about 100 times for every write, so replicas can carry almost all of the load.

<Analogy>

A teacher writes on the whiteboard in the main room, and assistants copy every change onto whiteboards in other rooms.
Students spread across all the rooms, so nobody crowds the main board. A student who walks into a side room right after

</Analogy>

## Try it

Press Play. One database cannot keep up. Add replicas until the load bars calm down, then raise the lag and watch the
stale reads (squares with a cross) appear. Finally, turn on read your own writes.

<ReplicationWidget client:visible />

What to look for:

- **Read capacity grows with each replica,** while the primary still handles every write.
- **Stale reads come from fresh links.** A link created long ago is already on every replica. Only reads inside the lag
  window go wrong.
- **Read your own writes** moves those few reads to the primary. Stale reads vanish, and the primary takes a little
  extra load.

## When the primary dies

If the primary crashes, you **promote** a replica to become the new primary and point writes at it. With
**asynchronous** replication (the default almost everywhere), writes that had not been copied yet are lost.
**Synchronous** replication waits for a replica to confirm each write before answering, so nothing gets lost, and every
write gets slower.

## Trade-offs

<TradeoffTable title="Replication choices">

| Choice                    | What it buys                                  | What it costs                                            |
| ------------------------- | --------------------------------------------- | -------------------------------------------------------- |
| More replicas             | More read capacity, more copies of the data   | Every replica replays every write, and more lag to watch |
| Asynchronous replication  | Fast writes                                   | Stale reads, and recent writes can vanish in a failover   |
| Synchronous replication   | No lost writes on failover                    | Slower writes, and a slow replica stalls the primary      |
| Read your own writes      | People always see their own changes           | Extra primary load, and routing logic in the app          |
| Replicas in other regions | Fast reads near users, survives a region loss | Lag of 100 ms or more across oceans                      |

</TradeoffTable>

<Challenge>

At 10 million users, the shortener sees 100 new links and 50,000 clicks per second. The cache answers 90% of clicks.
One database node handles 2,000 queries per second, and you keep each node under 70% busy. How many replicas do you
need? And what breaks if a new feature pushes writes to 5,000 per second?

<div slot="answer">

- Cache misses reach the database: 50,000 × 10% = **5,000 reads per second**.
- Each replica takes 2,000 × 0.7 = 1,400 per second, so 5,000 ÷ 1,400 ≈ 3.6, which rounds up to **4 replicas**, plus
  one spare to survive a crash: **5**.
- At 5,000 writes per second, replicas stop helping. The single primary must accept every write, and every replica must
  replay all 5,000 of them on top of its reads. To grow past one machine's write limit, you split the data itself across
  machines. That is sharding, the next lesson.

</div>

</Challenge>
