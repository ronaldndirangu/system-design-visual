## Buckets and keys

Each sho.rt link has a 200 KB preview and a QR image, 400 TB in all. As database blobs, they would slow backups.

Object storage, such as Amazon S3, Azure Blob Storage, or Google Cloud Storage, keeps files called objects in buckets.
You address each object by a key such as `previews/bATJ4g.png` and read, write, or delete it whole. That limit lets the
service spread trillions of objects across thousands of disks and serve them through a [CDN](../cdn/).

The links row keeps only the key and metadata, so the database stays small.

## Uploads that skip your servers

A **presigned URL** is a bucket URL signed with your credentials and an expiry, such as 15 minutes. Your API checks the
user, signs a URL for one key, and returns it. The client sends the bytes straight to the bucket.

A **multipart upload** splits a file into parts, for example 100 MB each, sends them in parallel, and commits them as
one object. A failed part retries alone.

### Closing the loop

The API signs a URL and never sees the upload finish. Four steps close the loop:

1. **Pending row first.** The API writes a `pending` row before it signs the URL.
2. **Confirm, then verify.** A confirm call or object-created event marks the row `ready` once a worker
   checks the stored size and file bytes. A signed `Content-Type` only labels the file.
3. **Sweeper.** A nightly job deletes stale pending rows and orphaned objects.
4. **Abort stale multipart uploads.** A lifecycle rule aborts them after 7 days.

Serve user files from a separate domain, such as `usercontent.example.com`, so uploaded HTML cannot script your site.

<details>
<summary>Go deeper: capping upload size, POST versus PUT</summary>

A presigned **POST** carries a policy, and its `content-length-range` condition makes the bucket reject a body outside
the range. A presigned **PUT** has no policy, so that condition does not apply; at most it signs one exact
`Content-Length`. Either way, the size check in step 2 is the guard you rely on. Add
`Content-Disposition: attachment` on the user-content domain so browsers download files instead of rendering them.

</details>

## Tiers and durability

S3 examples (billing varies by provider; all classes add request fees):

| S3 class             | Billing                        | Reads               | Fits              |
| -------------------- | ------------------------------ | ------------------- | ----------------- |
| Standard             | Highest per GB                 | Instant             | Daily reads       |
| Standard-IA          | 30-day minimum, 128 KB minimum | Per-GB fee, instant | Occasional reads  |
| Glacier Deep Archive | Lowest, 180-day minimum        | Fee, up to 48 hours | Compliance copies |

A lifecycle rule moves objects between tiers by age.

S3 Standard is designed for eleven nines of durability, the odds a stored object survives a year. Three full copies
cost 3 times the data. An **erasure code** cuts each object into 10 data pieces plus 4 parity pieces and spreads them
across disks. Any 10 of the 14 pieces rebuild the object, so it survives 4 lost disks for 1.4 times the data size.
Reads gather 10 pieces, costing more CPU and network than one copy.

<details>
<summary>Go deeper: availability, consistency, and replicas</summary>

Availability, the share of requests that succeed, sits far below durability: S3 Standard is designed for 99.99% and
Standard-IA for 99.9%. Within one Region, S3 gives strong read-after-write consistency: once a write or delete returns,
reads and list calls see it. A replica in another Region copies in the background and can lag minutes behind.

</details>

<KeyTakeaways>

- Keep large files in buckets and their keys in the database.
- Presigned URLs keep file bytes off your servers, and multipart uploads retry one part at a time.
- Lifecycle rules move cold objects to cheaper tiers.
- Erasure coding buys the safety of several copies at a fraction of the disk.

</KeyTakeaways>
