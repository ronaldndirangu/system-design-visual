## The failure: distance sets the floor

The shortener now serves 3 million users on five continents. The servers in Virginia answer a redirect in 2 ms, and the
cache keeps the database calm. Yet people in Sydney say every new link they open feels sluggish.

The server is fast. The light is slow. Light in fiber covers about **200 km per millisecond**, one way (about two
thirds of its speed in a vacuum). Sydney sits about 15,700 km from Virginia in a straight line, so one round trip takes
at least 157 ms. As [What happens when you click a link](../../foundations/what-happens-when-you-click/) showed, a
fresh HTTPS click needs three round trips before the redirect arrives: the TCP handshake, the TLS 1.3 handshake, and the
request itself. (DNS usually answers from a resolver nearby, so this lesson leaves it out.)

## The idea: answer from an edge nearby

A **content delivery network (CDN)** runs cache servers, called **edges**, in many cities. DNS or network routing sends
each person to an edge near them. The edge finishes TCP and TLS over a short distance and answers from its cache when it
can. On a miss, it forwards the request to your own server, called the **origin**, over a connection it keeps open.

Edges cache any response the origin marks as cacheable. For the shortener that means two kinds of bytes:

- **Static assets**: the images, scripts, and styles of the shortener's website. They are large and identical for
  everyone.
- **Redirects**: the small `302 Found` answer for each short link. They are tiny, but there are millions of clicks.

## TTL and invalidation

An edge keeps a copy for as long as the origin allows. Two tools decide how stale a copy can get.

**TTL.** The origin sets it with a `Cache-Control` header. For a redirect you usually want browsers to ask every time,
so you can update or delete the link, while edges reuse the answer for a short while:

```http
HTTP/1.1 302 Found
Location: https://example.com/a/very/long/article-url
Cache-Control: max-age=0, s-maxage=60
```

`max-age=0` tells the browser its copy is stale at once. `s-maxage=60` applies only to shared caches such as CDN edges
and lets them reuse the answer for 60 seconds.

**Versioned file names.** Static assets get a name that changes with their content, such as `app.3f9c2b.js`, and a TTL
of a year. A release ships new names, so edges fetch the new files on their first miss and nothing needs deleting.

**Purge.** When a link must disappear now, such as a scam, delete it at the origin and call the CDN's purge API for its
path. Most CDNs clear every edge within seconds. A purge has a cost: the purged edges go cold, and the origin absorbs the
refill, as the Purge at 10 s scenario shows. Purge only the paths that changed, and save a full purge for emergencies.

### What the edge treats as the same request

An edge files each copy under a **cache key**, by default the host, path, and query string. Two requests with the same
key get the same bytes, so the key and the headers decide who can see what:

- **Per-user pages** such as the sho.rt dashboard send `Cache-Control: private` (only the browser may keep a copy) or
  `no-store` (nobody keeps one). `public` lets edges share a copy across users.
- **Credentials.** Many CDNs skip the cache when a request carries `Authorization` or a response sets `Set-Cookie`, yet
  defaults differ by vendor. Check yours, and mark per-user responses `private` anyway.
- **`Vary`** adds request headers to the key. `Vary: Accept-Encoding` keeps gzip and plain copies apart. `Vary: Cookie`
  gives every user a separate copy, so the hit ratio collapses.
- **Noise in the key.** Strip tracking parameters such as `utm_source` from the key, or one link turns into dozens of
  cold copies.

## Hit ratio: every edge warms up alone

The **edge hit ratio** is the share of clicks an edge answers from its own cache, without asking anything upstream. It
behaves like the [cache](../caching/) hit ratio, with one twist: each city's edge learns the popular links on its own. A
link clicked a hundred times in Tokyo is still a miss the first time someone in London clicks it.

More edge locations put an edge closer to more people, but each edge then sees less traffic and warms up more slowly.
Links in the long tail may expire before anyone in that city clicks them again.

## Origin shield: one cache in front of the origin

An **origin shield** is one extra cache tier that all edges share. Edge misses ask the shield first, and only shield
misses reach the origin. When five edges miss on the same viral link, the origin answers once instead of five times.

In the simulation the shield sits beside the origin, so it cuts origin requests from 1,402 to 683 and saves almost no
time: a Sydney miss still crosses the ocean once. A shield protects the origin. Edges near people cut latency.

A shield hit still counts as an edge miss, because the edge had to ask upstream. With the shield on, the edge hit ratio
stays at 65%, while the origin answers only 683 of the 4,000 clicks.

Edges and shields shrink the traffic that reaches the origin, yet every miss still lands on one database. The
[read replicas](../read-replicas/) lesson adds copies of the database itself.

## Push and pull CDNs

The simulation models a **pull CDN**: edges fetch from the origin on their first miss, keep the copy for its TTL, and
fetch again after it expires. Nothing gets uploaded ahead of time, so new content works the moment it exists. The price
is a slow first request in each city, plus copies that can trail the origin until their TTL ends or a purge clears them.

A **push CDN** works the other way around. You upload files to the CDN's storage as part of each release, and the CDN
serves them from there, so content appears the moment you publish it. That suits large files that change rarely and that
you know about in advance, such as video, app installers, or a site's build output. The price is an explicit publish
step, storage fees for every file you push whether anyone downloads it or not, and cleanup you must remember to do.
Removal still runs through caches: deleting a pushed file leaves copies at edges and in browsers until their TTL ends or
a purge clears them.

For the shortener, redirects suit pull: nobody knows which of millions of links people will click next. The website's
assets work either way, and with versioned file names, pull needs no extra deploy step.

## Who counts the clicks?

The shortener counts clicks at the origin, on every redirect it serves. Once edges answer redirects, most clicks never
arrive. In the Worldwide clicks run, the origin's counter sees only the 35% of clicks that missed the edges.

You have two honest fixes:

- **Count from edge logs.** CDNs can write a log line for every request they handle and ship the logs to you. Count each
  click in one place: edge hits from the logs and misses at the origin, or everything from the logs and nothing at the
  origin. Mixing the two counts every miss twice. The simulation ships complete logs every 5 seconds, so the counter
  catches up after each batch. Real log delivery runs minutes behind and is best effort, so expect small gaps.
- **Keep counted redirects out of the edge cache.** Send `Cache-Control: no-store`, and edges pass every click through
  to the origin. Those clicks still connect to the nearby edge, so they skip two long round trips, as the Brand new links
  scenario shows.

This is a toy model. Distances are straight lines, shares are illustrative, and it leaves out DNS, the last mile, queues,
and packet loss. Real fiber detours around coasts and through undersea cables, so real round trips run longer than these
numbers. The ratios still hold: three long round trips for a fresh click from far away, one for an edge miss, and none
for an edge hit.

## Trade-offs

<TradeoffTable title="Choosing what the edge does">

| Choice                       | What it buys                                            | What it costs                                                       |
| ---------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------- |
| Cache redirects at the edge  | Fast clicks everywhere and far less origin load         | The origin counter misses edge hits unless edges ship logs          |
| Cache only static assets     | Every click reaches the origin to count and update      | Distant people still pay one long round trip on every redirect      |
| Long TTL                     | Higher edge hit ratio, less origin load                 | Deletes and changes need a purge to show quickly                    |
| Short TTL                    | Edges pick up changes on their own                      | More misses: a 1 s TTL roughly doubled origin requests in the run   |
| Versioned asset file names   | One-year TTLs, with instant updates on each release     | A build step that renames files and rewrites references to them     |
| Origin shield                | About one origin fetch per link per TTL                 | An extra hop on shield misses, and one more tier to run and watch   |
| Pull CDN                     | No upload step: edges fetch on their first miss         | A slow first request per city, and copies stale until TTL or purge  |
| Push CDN                     | Files wait at the CDN before anyone asks                | A publish step, storage for every file, and cleanup you must own    |
| More edge locations          | Shorter distance for more people                        | Each edge sees less traffic, so it warms up slower and hits less    |

</TradeoffTable>
