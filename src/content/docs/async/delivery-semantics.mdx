## The failure: two writes, no transaction

The shortener now bills paid links per click, so every click must be **saved as a row** in the clicks database. The
[log from the previous lesson](../logs-and-pubsub/) feeds the analytics dashboard, so every click must also be
**published as an event**, and the two must agree.

The obvious code does both in turn:

```ts
await db.insert('clicks', click);        // 1. save the row
await broker.publish('clicks', click);   // 2. announce it
```

This is a **dual write**: two systems, two writes, and no transaction covering both.

<details>
<summary>Go deeper: why not two phase commit?</summary>

A distributed transaction across the database and the broker (two phase commit) would close the gap. Most brokers do
not support it, and it ties the availability of every click to both systems at once: either one being down blocks the
redirect.

</details>

## The idea: write the event into the database

The **transactional outbox** turns two writes into one. The service writes the click row and an **outbox row** (the
event, waiting to be sent) in the **same local transaction**, so both commit or neither does. A separate **relay**
process then publishes unsent outbox rows.

<StepDiagram client:visible title="How the transactional outbox carries a click" nodes={nodes} edges={edges} steps={steps} height={320} />

The relay can still crash after publishing and before marking rows sent, and then it publishes those rows again: the
outbox delivers **at least once**. Each copy is a new append, so one event can sit at offset 100 and again at offset
101. The consumer skips repeats by event id.

<Analogy>

A clerk used to post a letter and then write it in the ledger, and sometimes got called away in between. Now the clerk
writes the ledger line and drops the letter in the outbox tray in one motion. A courier empties the tray, posts each
letter, and ticks it off. A courier interrupted before ticking means the next one posts that letter again. Each letter
carries a reference number, so the recipient bins any number it already filed.

Where it breaks: a real consumer trims its seen ids, so a replay older than the trim slips through.

</Analogy>

What to look for:

- **Dual write, commit first**: the broker outage leaves **62** clicks saved and never counted.
- **Dual write, publish first**: the same outage just fails the requests, and the database outage creates **49**
  phantom events instead.
- **Outbox**: saved clicks wait in the outbox during the broker outage (the backlog peaks at **62**), and the relay
  drains them. The lane ends with **0** out of sync.
- **Database outage**: both designs fail **49** requests. A failed request is honest, since the caller can retry. A
  silent mismatch is the real damage.
- **Relay crash**: the relay published **5** events without marking them sent, so it publishes them again. The next
  section makes such duplicates harmless.

<details>
<summary>Go deeper: change data capture instead of polling</summary>

A polling relay adds latency: an event waits for the next poll, and every poll is a query on the clicks database.
**Change data capture** (CDC) is the common alternative. A tool such as Debezium tails the database's own write ahead
log and publishes outbox rows as they commit, with no polling queries. Debezium ships an outbox event router that turns
each outbox row into a message on a topic chosen from the row. The cost is one more system to run, tied to the
database's log format.

</details>

## Delivery semantics: when does the consumer commit?

The consumer has the same two step problem. It **counts** a batch of clicks and **commits its offset** so a restart
knows where to resume, and a crash can land between the two. Where the commit goes decides what a crash costs:

- **At most once**: commit the offset, then count. A crash loses the clicks in hand and never rereads them, though a
  relay copy at a new offset still counts twice.
- **At least once**: count, then commit. A crash makes the restarted consumer count the clicks since the last commit
  again. No crash loses a click, as long as the log still holds it.
- **Effectively once**: count, then commit, and make a repeat harmless. The consumer records each click id **in the
  same transaction as the count** and skips ids it has seen. The click id comes from the source (the outbox row id), so
  it catches a reread after a crash and a relay copy at a new offset. Delivery is still at least once, and the effect
  happens once, as in [**Idempotency**](../../reliability/idempotency/).

What to look for:

- **The relay copy at offset 101** arrives at 1.6 s. Offset 101 is new to at most once and at least once, so both
  count click 100 again. Effectively once skips the click id it already counted.
- **At most once** stays too low after each crash: the lost cells sit behind the committed offset.
- **At least once** stays too high after each crash, and with the relay copy it ends **17** too high.
- **Effectively once** rereads as much, skips all **17** repeats, and its count error stays at **Exact**.
- **Crash it yourself** early and late in a batch: at most once loses more early, and at least once double counts more
  late.

Effectively once needs a **stable id** from the source and **one transaction** for the effect and the record.

<details>
<summary>Go deeper: the stable id and the single transaction</summary>

- **A stable id.** The id must be assigned once, at the source. The outbox row id works. A timestamp or a hash of the
  payload can collide or change between retries. The log offset does not work: a consumer that only skips offsets at
  or below its last commit absorbs its own rereads, and the relay's second copy at a new offset slips through.
- **One transaction for the effect and the record.** If the consumer adds to the count and records the id in two
  separate writes, a crash between them reopens the gap. Without multi-row transactions, make the click id the key of
  the effect: insert one row per click id, let a unique key reject a repeat, and compute the count from those rows. A
  store that cannot write the effect and the id in one atomic step cannot give effectively once.

</details>

Redelivery and replay work only while the log still holds the event: a consumer broken for longer than the log's
retention loses those events for good.

<details>
<summary>Go deeper: pick a recovery horizon</summary>

The list of seen ids grows forever unless you trim it, and each store deletes on its own clock: the log after its
retention, the [dead-letter queue](../event-driven-design/) after its own, and the seen ids after their trim. Pick one
**recovery horizon**, the age of the oldest event you promise to replay, such as 7 days. Keep the log and the
dead-letter queue that long, and keep seen ids at least as long as either. Alert when consumer lag reaches half of
retention: a consumer a full retention period behind never reads the events the log deleted.

</details>

<details>
<summary>Go deeper: exactly once delivery</summary>

You will often read about **exactly once delivery**. No network protocol delivers a message exactly once in general:
the sender cannot tell a lost message from a lost acknowledgment, so it either retries (at least once) or gives up (at
most once). Products that advertise exactly once, such as Kafka transactions, make reads and writes **inside the
broker** atomic. The moment a consumer touches an outside database, you are back to an idempotent consumer.

</details>

## Trade-offs

<TradeoffTable title="Delivery choices">

| Choice               | What it buys                                    | What it costs                                                   |
| -------------------- | ----------------------------------------------- | --------------------------------------------------------------- |
| Dual write           | Simple code, no extra table or process          | Lost or phantom events whenever a fault lands between the steps |
| Transactional outbox | Every committed row is published, at least once | An extra write per click, a relay to run, and poll latency      |
| At most once         | No crash rereads, the simplest consumer         | Every crash loses the batch in hand; relay copies still repeat  |
| At least once        | No loss                                         | Every crash repeats work since the last commit                  |
| Effectively once     | No loss and no double counts                    | A stable id, a seen id store, and a transaction around both     |

</TradeoffTable>

Skip the outbox when a lost event costs nothing, such as a hint to warm a cache. Skip the seen id store when applying
an event twice changes nothing, such as setting a link's title to a given value.

## Common mistakes

- **Publishing right after the commit.** A fault between the two writes loses the event. Write an outbox row in the
  same transaction.
- **Deduplicating by offset.** A relay copy lands at a new offset and counts again. Skip repeats by the outbox row's
  event id.
- **Recording the seen id in a separate write.** A crash between the count and the record reopens the gap.
- **Trusting broker exactly once for an outside database.** Broker transactions stop at the broker.

<KeyTakeaways>

- A dual write loses or invents events when a fault lands between its two writes.
- The outbox commits the row and the event together, and its relay publishes at least once.
- Where the consumer commits its offset sets the crash cost: commit first loses work, commit last repeats it.
- Effectively once is at least once delivery plus a stable event id stored with the effect in one transaction, within
  the log's retention.

</KeyTakeaways>
