## The failure: two writes, no transaction

The shortener now sells paid links billed per click, so every click must be **saved as a row** in the clicks database.
The [log from the previous lesson](../logs-and-pubsub/) still feeds the analytics dashboard, so every click must also be
**published as an event**. The billing total and the dashboard must agree.

The obvious code does both, one after the other:

```ts
await db.insert('clicks', click);        // 1. save the row
await broker.publish('clicks', click);   // 2. announce it
```

This is a **dual write**: two systems, two separate writes, and no transaction that covers both. In the simulation
below, the broker goes down for 1.5 seconds while clicks keep arriving.

**The rows are saved, and the events are gone.** The commit succeeded before the publish failed, and nothing remembers
that a publish is still owed. In the simulation, **62** clicks end up billed and never counted. Flip the order (publish,

database never saved. Neither order is safe, because a crash or outage can land between any two steps.

</Predict>

Retrying the publish in memory narrows the gap and does not close it: if the process crashes while it retries, the
event is gone. A distributed transaction across the database and the broker (two phase commit) would close it, but most
brokers do not support it, and it ties the availability of every click to both systems at once.

## The idea: write the event into the database

The **transactional outbox** turns two writes into one. The service writes the click row and an **outbox row** (the
event, waiting to be sent) in the **same local transaction**. The database guarantees that both commit or neither does.
A separate **relay** process then reads unsent outbox rows and publishes them.

<StepDiagram client:visible title="How the transactional outbox carries a click" nodes={nodes} edges={edges} steps={steps} height={320} />

The relay can still crash after publishing and before marking rows sent. It then publishes those rows again, so the
outbox delivers **at least once**. That is the price of never losing an event, and the consumer pays it by skipping
repeats.

<Analogy>

A clerk used to post a letter and then write it in the ledger, and sometimes got called away in between. Now the clerk
writes the ledger line and drops the letter in the outbox tray in one motion. A courier empties the tray, posts each
letter, and ticks it off. If the courier is interrupted before ticking, the next courier posts the same letter again.
Every letter carries a reference number, so the recipient bins any letter whose number it already filed.

</Analogy>

What to look for:

- **Dual write, commit first**: the broker outage leaves **62** clicks saved and never counted. They stay out of sync
  for the rest of the run.
- **Dual write, publish first**: the same outage just fails the requests, and the database outage creates **49**
  phantom events instead.
- **Outbox**: during the broker outage, saved clicks wait in the outbox (the backlog peaks at **62**). When the broker
  returns, the relay drains them, and the lane ends with **0** clicks out of sync.
- **Database outage**: both designs fail **49** requests outright. A failed request is honest: the caller sees an
  error and can retry. A silent mismatch is the real damage.
- **Relay crash**: the relay published **5** events without marking them sent, so it publishes them again. The outbox
  trades lost events for duplicates. The next section makes duplicates harmless.

A polling relay adds latency: an event waits for the next poll. **Change data capture** (CDC) is the common
alternative. A tool such as Debezium tails the database's own write ahead log and publishes outbox rows as they commit,
with no polling queries.

## Delivery semantics: when does the consumer commit?

The consumer faces the same two step problem from the other side. It **counts** a batch of clicks, and it **commits its
offset** in the log so a restart knows where to resume. Those are two writes again, and a crash can land between them.
Where the consumer puts the commit decides what a crash costs:

- **At most once**: commit the offset, then count. A crash loses the clicks in hand. Nothing is ever counted twice.
- **At least once**: count, then commit. A crash makes the restarted consumer count the clicks since the last commit
  again. Nothing is ever lost.
- **Effectively once**: count, then commit, and make a repeat harmless. The consumer records each click id it counted
  **in the same transaction as the count**, and skips ids it has seen. Delivery is still at least once, and the effect
  happens once. The [**Idempotency**](../../reliability/idempotency/) lesson covers this pattern in depth.

What to look for:

- **At most once** keeps the count too low after every crash. The lost cells sit behind the committed offset, so no
  restart ever reaches them.
- **At least once** keeps the count too high after every crash, by the clicks counted since the last commit.
- **Effectively once** rereads exactly as much as at least once, and its count error stays at **Exact**.
- **Crash it yourself** right after a batch starts and right before it ends. At most once loses more early in a batch,
  and at least once double counts more late in one.

Two details make effectively once work in a real system:

- **A stable id.** The id must be assigned once, at the source. The outbox row id works. A timestamp or a hash of the
  payload can collide or change between retries.
- **One transaction for the effect and the record.** If the consumer adds to the count and records the id in two
  separate writes, a crash between them reopens the gap. Without transactions, keep the count and the last applied
  offset per partition in one record, and update both in one atomic write, such as a conditional update that applies
  only when the stored offset is below the new one. A store that cannot update both at once cannot give effectively
  once.

The list of seen ids grows forever unless you trim it. Keep ids for longer than the longest redelivery you expect, such
as the log's retention period.

You will often read about **exactly once delivery**. No network protocol delivers a message exactly once in general:
the sender cannot tell a lost message from a lost acknowledgment, so it either retries (at least once) or gives up (at
most once). Products that advertise exactly once, such as Kafka transactions, make reads and writes **inside the broker**
atomic. The moment a consumer touches an outside database, you are back to an idempotent consumer.

## Trade-offs

<TradeoffTable title="Delivery choices">

| Choice                          | What it buys                                         | What it costs                                                   |
| ------------------------------- | ---------------------------------------------------- | --------------------------------------------------------------- |
| Dual write                      | Simple code, no extra table or process               | Lost or phantom events whenever a fault lands between the steps |
| Transactional outbox, polling   | Every committed row is published, at least once      | An extra write per click, a relay to run, and poll latency      |
| Outbox with change data capture | Low latency and no polling load                      | A CDC tool to run, tied to the database's log format            |
| At most once                    | No duplicates, the simplest consumer                 | Every crash loses the batch in hand                             |
| At least once                   | No loss                                              | Every crash repeats work since the last commit                  |
| Effectively once                | No loss and no double counts                         | A stable id, a seen id store, and a transaction around both     |

</TradeoffTable>

A shop's order service saves each order and must publish an `OrderPlaced` event. An email consumer sends one
confirmation email per order, and a stock consumer reserves items. Today the service commits the order, then publishes,
and support reports orders with no confirmation email and, after a deploy, customers who got two. Redesign both ends and
name what can still go wrong.

<div slot="answer">

- **Producer: a transactional outbox.** Insert the order and an `OrderPlaced` outbox row in one transaction, and let a
  relay (or CDC) publish it. No more orders without an event.
- **Every event carries the order id**, assigned once by the order service, so consumers can recognize repeats.
- **Stock consumer: effectively once.** Reserve the items and record the order id in the same database transaction.
  A repeat finds the order id and changes nothing.
- **Email consumer: deduplicate as close to the send as possible.** The email provider sits outside your transaction,
  so record the order id and send in a known order, and pass the order id as the provider's idempotency key if it
  supports one. Without that, a crash between send and record can still send twice, rarely.
- **Commit offsets after processing** in both consumers, so a crash repeats work instead of losing it.

</div>

</Challenge>
