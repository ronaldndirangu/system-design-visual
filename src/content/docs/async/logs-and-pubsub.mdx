## The failure: the dashboard falls behind

Every redirect on the shortener produces a click event: which link, when, and from where. The analytics pipeline turns
those events into per-link counts for the owner's dashboard. Counting inside the redirect would slow every redirect, so
the redirect service writes the event to a **log** and moves on. Analytics workers read the log at their own pace.

At launch, one worker reads everything. In this toy model, clicks arrive at about 80 per second and one worker handles
50 per second.

## The idea: a log that many readers share

A **log** is an append-only list of events. Producers add to the end. Readers keep a bookmark, the **offset**, and move
it forward as they go. Reading deletes nothing: the log keeps events for a retention period, such as 7 days. A classic
work queue deletes each message once a worker acknowledges it. A log keeps it, so a new reader can replay history.

One log on one machine has a speed limit, so a **topic** splits into **partitions**. Each partition is its own log on
its own disk. A **consumer group** is a set of workers that shares the partitions: each partition has exactly one
reader in the group at a time.

<StepDiagram client:visible title="How a partitioned log carries clicks" layout="stack" nodes={nodes} edges={edges} steps={steps} height={330} />

This is **publish/subscribe** (pub/sub): the producer publishes once, and any number of groups subscribe. Each group sees
every event and keeps its own offsets.

<Analogy>

Picture a mail room with four conveyor belts. Letters for the same street always go onto the same belt. Each clerk
takes one or more belts and handles their letters in order, sliding a bookmark along the belt after every batch. If a
clerk walks out, a colleague takes over the belt at the last bookmark and handles a few letters twice. Hiring a fifth
clerk for four belts just adds someone standing around.

Where it breaks: a clerk bins each letter once handled, while a log keeps every event so another team can replay it.

</Analogy>

What to look for:

- **One consumer** reads all four partitions and falls further behind every second, to a lag of 637.
- **Four consumers** each own one partition and handle about 20 clicks per second. Lag stays at 0 or 1.
- **A consumer crashes** at 8 s. The whole group pauses for 2 s to reassign partitions (a **rebalance**), so lag
  peaks at 222. The crashed consumer saved its offset at 5 s, so P2's new owner reads 58 events again.
- **Six consumers** for four partitions: consumers 5 and 6 process nothing. The partition count caps parallel reads.

Repeated reads are normal in a log, so the counter must tolerate them. The next lesson,
[Delivery semantics and the outbox](../delivery-semantics/), shows how to make a repeat harmless.

<details>
<summary>Go deeper: cooperative rebalancing and heavy readers</summary>

This toy model uses an **eager** rebalance: every consumer stops while the group reassigns partitions. Newer clients
offer **cooperative** rebalancing, which pauses only the partitions that move.

Groups advance independently, and they still share the brokers' disks, network, and CPU. A group that replays a week of
history reads old segments from disk and can slow every other reader and the producers on those brokers. Brokers such
as Kafka let you set a byte-rate **quota** per client, and teams move a heavy reader, such as a bulk backfill, onto its
own cluster or a mirrored copy of the topic.

</details>

## Order holds only within a partition

A partition is one log with one reader, so its events come out in the order they were appended. Across partitions there
is no order at all: two consumers run at their own speeds, and a slow one falls behind.

Plain counts do not care. Five clicks counted in any order still add up to five. Per-link state does care: a
"last clicked" time, a "first click" alert, or a running streak breaks when an older click arrives after a newer one.

The fix is a **partition key**. Hash the short code to pick the partition, as the [sharding lesson](../../scaling/sharding/) does with shard keys,
and every click for one link lands in one partition and reaches one reader in append order.

What to look for:

- **Round robin spreads load perfectly** and gives up order for every link.
- **Keyed by short code** keeps each link in order. The cost is balance: one viral link sends all its clicks to one
  partition, the same hot key problem as in [sharding](../../scaling/sharding/).
- **The stall is local when keyed.** Only the links in the stalled partition wait. Every other link stays current.

### Append order is not click order

A partition keeps **append order**: the order in which writes reached the broker. A redirect server whose network blips
can retry and append a 12:00:01 click after a 12:00:03 click, so a reader that copies each event into "last clicked"
moves it backward. The fix: stamp each click with its **event time**, and let an update win only when it is newer than
the stored value. The widget's redirect servers never retry, so keyed partitions show 0 out of order there.

<details>
<summary>Go deeper: last writer by version</summary>

The reader keeps the newest click time:

```ts
function applyClick(link: LinkState, click: Click) {
  if (click.at > link.lastClickedAt) link.lastClickedAt = click.at;
}
```

This is **last writer by version**: an update wins only when its version is newer than the stored one, so a late
append changes nothing. Clocks on different servers drift by a few milliseconds, which a dashboard can live with.
When the order must be exact, use a version that one writer assigns, such as a counter on the order row that goes up
with every change.

</details>

## Trade-offs

<TradeoffTable title="Log design choices">

| Choice                       | What it buys                                          | What it costs                                                 |
| ---------------------------- | ----------------------------------------------------- | ------------------------------------------------------------- |
| More partitions              | More consumers can read in parallel                   | More files and connections, and slower rebalances             |
| Key by short code            | Every link's clicks reach one reader in append order  | A viral link makes one partition hot                          |
| Round robin                  | Even load on every partition                          | No order for any link                                         |
| Version on every event       | A late append cannot roll a link's state back         | Every producer stamps events, and server clocks drift         |
| Save offsets often           | Fewer repeated reads after a crash                    | More writes to the offset store                               |

</TradeoffTable>

Skip the log when the caller needs the result before it answers, or when one worker pool drains one job queue. A log
pays off when several readers need the same events, or when a reader must replay history.

## Common mistakes

- **Adding consumers past the partition count to cure lag.** The extras sit idle. Add partitions ahead of need, or
  make each consumer faster.
- **Expecting the topic to keep one global order.** Order holds within a partition, and only in append order.
- **Treating retention as forever.** A group that trails by more than the retention period loses events it never read.
- **Adding partitions to a keyed topic on a busy day.** Hash mod N sends most keys to a new partition, so a key's old
  and new events can race on two readers during the switch.

<KeyTakeaways>

- A log appends events and keeps them for a retention period. Each consumer group keeps its own offsets and reads at
  its own pace.
- Within a group, each partition has exactly one reader, so the partition count caps parallel reads.
- A crash pauses the group for a rebalance and repeats every event read since the last saved offset.
- A partition keeps append order only. Key related events to one partition, and stamp a version on each event.

</KeyTakeaways>
