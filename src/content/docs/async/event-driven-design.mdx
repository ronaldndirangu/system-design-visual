## The failure: one bad click stalls the partition

The analytics consumer from [logs and pub/sub](../logs-and-pubsub/) reads the clicks topic in order. A buggy release
publishes a few clicks that no parser can read. The consumer handles every failure the same way: wait 0.3 s and try
again.

That works for a timeout. A malformed click is a **poison message**: it fails on every try, on every consumer, so a
rebalance only moves the stall.

## The idea: park what cannot succeed

Give each event a small retry budget. When the budget runs out, or the error is permanent, move the event to a
**dead-letter queue**, commit its offset, and keep reading. [Retries](../../reliability/retries/) covers backoff
between tries.

<Analogy>

A sorting office meets a letter with an unreadable address. The sorter drops it into a separate bin, and the rest of
the mail keeps moving. Staff at the dead letter office open it later. The bin works only because someone empties it.

Where it breaks: a letter is handled once, while a replayed click can arrive twice, so the consumer must be idempotent.

</Analogy>

## Try it: retry forever against a dead-letter queue

Both lanes read the same seeded partition. The left lane retries a failed click until it works. The right lane retries
up to a budget, then parks the click. Two percent of clicks time out once. The numbers are illustrative.

<PoisonDuelWidget client:visible />

What to look for:

- **The retry lane never recovers.** At 10 s it is on try 27, has counted **88** of **423** clicks, and **335** wait.
- **The dead-letter lane parks after 0.6 s.** Two timeouts behind the click push the backlog to **52** at 3.3 s, then
  it drains to 0 by about 4.2 s, with **416** counted and **2** parked.
- **Park after 1 try.** The lane parks **12** clicks, and **10** only hit a timeout one more try would clear.
- **Park after 10 tries.** Each malformed click holds the partition for 2.7 s, leaving **157** waiting.

Parking is two writes: write the click to the dead-letter queue, wait for a durable acknowledgment, then commit the
offset. Commit first, and a crash between the writes loses the click. The safe order can park it twice, which the
click id makes harmless.

<details>
<summary>Go deeper: per-key order, owners, and each crash point</summary>

Three things the widget leaves out matter in production:

- **Parking breaks per-key order.** Once a click for one short code sits in the dead-letter queue, later clicks for the
  same code get counted first. A counter does not care. A consumer that applies state changes in order, such as an
  account balance, has to park every later event for that key too, or handle stale events on replay.
- **A dead-letter queue needs an owner.** Alert on the first parked event and on a growing count, store the error and
  the source offset with each event, and keep a tested replay tool. A queue nobody reads is silent data loss.
- **Retry topics keep the partition moving.** Many teams send a failed event to a retry topic with a delay, such as 10
  s, then 5 minutes, before the dead-letter queue. The main partition never waits, and order breaks the same way.

A crash can land between the two writes of a park, the same gap the outbox in
[delivery semantics](../delivery-semantics/) closes. Order the writes so a crash can only repeat work:

- **Confirm the park, then commit.** Wait until the dead-letter queue acknowledges a durable write, then commit the
  source offset. Commit first, and a crash between the two writes loses the click from both places.
- **Expect a duplicate park.** A crash after the dead-letter write and before the commit makes the restarted consumer
  fail the same click and park it a second time. Each copy carries the click id, so the replay tool and an idempotent
  consumer treat the two copies as one click. Where the dead-letter topic lives in the same broker and the broker
  supports transactions, as Kafka does, the consumer can write the park and commit the offset in one transaction, and
  the duplicate disappears.
- **When the dead-letter queue is down, stop.** If the park write fails or times out, the consumer leaves the offset
  where it is and retries the park with backoff. The partition stalls like the retry lane, so alert on it. A consumer
  that commits the offset without a confirmed park loses the click.
- **Retention bounds every replay.** The source log, the dead-letter queue, and the consumer's record of seen click ids
  each delete old data on their own schedule. A replay that arrives after its click id left the seen record can count
  a click twice. Pick one recovery horizon and keep all three at least that long, as
  [delivery semantics](../delivery-semantics/) explains.

Replay sends events through the consumer a second time, and some of them may have half finished the first time. Make
the consumer idempotent, keyed by click id, and replay is safe. [Idempotency](../../reliability/idempotency/) covers the
technique in depth.

</details>

## Thin events and fat events

A **thin event** carries ids, such as the click id and the short code, and a consumer that needs details calls the
producer back. A **fat event**, also called event-carried state transfer, carries the state consumers need, such as the
referrer and the country.

Fat events let each consumer work alone and replay the click as it was, at the cost of bigger messages and personal
data copied into every topic. Most designs carry the fields consumers decide on, plus ids for anything large or private.

<details>
<summary>Go deeper: the same click, thin and fat</summary>

With thin events, every consumer calls the click service for every click, and a replay an hour later sees today's
data, such as a plan the owner bought after the click. Fat events also grow fields some consumer comes to depend on.

```json
{ "type": "click.recorded", "clickId": "c_81f2", "code": "abc123" }
```

```json
{
  "type": "click.recorded",
  "clickId": "c_81f2",
  "code": "abc123",
  "clickedAt": "2025-03-01T10:15:00Z",
  "referrer": "news.example.com",
  "country": "KE",
  "ownerPlan": "pro"
}
```

With the thin version, analytics, fraud scoring, and billing each call the click service for every click. The click
service serves three times the reads, and when it goes down, every consumer stalls with it.

</details>

## Choreography and orchestration

Fraud scoring checks each click, and billing charges only for clean ones. In **choreography**, each
service reacts to events and publishes its own, and no service knows the whole flow.

Choreography keeps services loose: a new consumer needs no upstream change. The flow lives only in subscriptions.
Orchestration puts order, retries, and compensation in one place, as [Sagas](../../distributed-data/sagas/) shows, and
every new step changes that service. A common split: choreography
between teams, and an orchestrator for a strict flow such as billing.

## Evolve the schema without breaking readers

Producers and consumers deploy on their own schedules, and the topic holds events from old code for days. Version 1 of
the click event:

```json
{ "code": "abc123", "clickedAt": "2025-03-01T10:15:00Z", "referrer": "news.example.com" }
```

The **strict reader** rejects any field outside the v1 contract. The **tolerant reader** checks only code and
clickedAt and ignores the rest. Both park rejected events, since no retry fixes a schema error.

<SchemaEvolutionWidget client:visible />

What to look for:

- **Add an optional field.** The strict reader counts **106** clicks, all before 3 s, then parks **205** with "unknown
  field country". The tolerant reader counts all **311**.
- **Rename a field in place.** Both readers park **205** clicks with "missing field code": a rename is a removal plus
  an addition.
- **Publish the rename as v2.** Both readers count all **311**, the v2 topic holds **205** events, and the producer
  publishes **516** in total.

The rules: add optional fields, read only the fields you use, and publish a breaking change as a new version.

<details>
<summary>Go deeper: the schema rules in practice</summary>

- **Add, never rename or remove.** New fields are optional or have a default. A field a consumer reads keeps its name
  and its type: in the same toy model, sending clickedAt as a number breaks both readers.
- **Read tolerantly.** Read only the fields you use and ignore the rest. Removing referrer breaks only the strict
  reader, because the tolerant one never read it.
- **Version breaking changes.** Keep v1 and publish v2, with shortCode, to a new topic or with a version field. Move
  each reader, then retire v1. The outbox relay from [delivery semantics](../delivery-semantics/) can publish both
  versions from one outbox row.
- **Check before you ship.** A schema registry with compatibility checks in the build rejects a breaking change before
  it reaches the topic. [APIs and contracts](../../foundations/apis/) covers the same versioning rules for request and
  response APIs.

</details>

## Trade-offs

<TradeoffTable title="Event-driven design choices">

| Choice | What it buys | What it costs |
| --- | --- | --- |
| Retry forever | No event skipped, order kept | One poison message stalls the partition |
| Dead-letter queue after a few tries | The partition keeps moving | Per-key order breaks, the park must be durable before the offset commit, and the queue needs an owner and an idempotent replay |
| Choreography | New consumers need no upstream change | The flow lives nowhere |
| Orchestration | Order, retries, and compensation in one place | Every new step changes one central service |
| Versioned events | Breaking changes without broken readers | Two versions to run until the migration ends |

</TradeoffTable>

Skip the dead-letter queue when events must apply in strict order and a stall is safer than a gap, as with ledger
entries: stop and alert instead. Skip versioned topics while one team deploys the producer and every consumer together.

## Common mistakes

- **Retrying permanent errors.** A parse failure fails every try. Park it at once.
- **A dead-letter queue nobody owns.** Parked events sit unread, which is silent data loss.
- **Committing the offset before the park is durable.** A crash between the writes loses the click.
- **A strict reader that rejects unknown fields.** A safe additive change becomes an outage.
- **Renaming a field in place.** Every reader of the old name breaks. Publish a new version.

<KeyTakeaways>

- Retry each event a few times, then park it, so one poison message cannot stall a partition.
- Make the park durable before the offset commit, give the queue an owner and an alert, and replay only into an
  idempotent consumer.
- Fat events let consumers work alone. Choreography keeps services loose, and orchestration keeps a strict flow in one
  place.
- Add optional fields, read only what you use, and version breaking changes.

</KeyTakeaways>

A new geo enrichment consumer calls a third-party IP lookup service that goes down for about 10 minutes once a week.
Marketing also wants a utm_campaign field on every click, and one of the three click consumers is a strict reader.

- **Own the dead-letter queue.** Store the error and source offset, alert on the first park, and name an owner. Commit

  harmless.

  check.
- **Keep the IP out of the shared event.** Only the derived country goes in the click event.

</div>
