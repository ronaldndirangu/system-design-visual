## The failure: one bad click stalls the partition

The analytics consumer from the [log lesson](../logs-and-pubsub/) reads the clicks topic in order and adds each click to
the click counts. A release of the click service ships a bug, and for a few clicks it publishes an event that no
parser can read. The consumer handles failures the obvious way: try again.

```ts
for (;;) {
  const click = await partition.peek();
  try {
    await countClick(parse(click)); // parse throws on a malformed click
    await partition.commit(click.offset);
  } catch {
    await sleep(300); // then try the same click again
  }
}
```

That loop works for a timeout, which succeeds on the next try. A malformed click fails every time. An event like that
is a **poison message**: it fails on every try, on every consumer. A rebalance only hands it to another consumer in the
group, and that consumer stalls in the same place.

## The idea: park what cannot succeed

Give each event a small retry budget. When the budget runs out, or when the error is permanent, move the event to a
separate **dead-letter queue**, commit its offset, and keep reading. The partition pays for a few retries, and the
bad event waits somewhere a person can look at it.

at it: the letter goes into a separate bin, and the rest of the mail keeps moving. Staff at the dead letter office
open it later, look for a return address, and send it on or destroy it. The bin only works because someone empties it.

## Try it: retry forever against a dead-letter queue

Both lanes read the same seeded partition of clicks. The lane on the left retries a failed click until it works. The
lane on the right retries up to a budget and then parks the click. Each strip shows the clicks around the head of the
partition, oldest on the left: solid for read and counted, dotted with a dashed border for parked, outlined for failed
and retrying, striped for waiting, and a cross for a malformed click. Two percent of clicks hit a timeout once and work
on the next try. This is a toy model with one partition, and the numbers are illustrative.

<PoisonDuelWidget client:visible />

What to look for:

- **The retry lane never recovers.** From 2 s it retries the first malformed click every 0.3 s. At 10 s it is on try
  27, has counted **88** of **423** clicks, and **335** clicks wait in the partition.
- **The dead-letter lane parks after 0.6 s.** Three tries 0.3 s apart, then the malformed click moves to the
  dead-letter queue and the partition moves again. The backlog still climbs to a peak of **52** at 3.3 s, because two
  clicks right behind it hit a timeout and each costs a 0.3 s retry. Then the lane drains to 0 by about 4.2 s. It ends
  the run with **416** clicks counted and **2** parked.
- **Park after 1 try.** The lane never backs up, but it parks **12** clicks, and **10** of them only hit a timeout. One
  more try would have counted them, and now someone has to replay them by hand.
- **Park after 10 tries.** Each malformed click holds the partition for 2.7 s. The lane drains part of the backlog
  between the two bad clicks and still ends with **157** waiting. A retry budget has to stay small next to the arrival
  rate.

Three things the widget leaves out matter in production:

- **Parking breaks per-key order.** Once a click for one short code sits in the dead-letter queue, later clicks for the
  same code get counted first. A counter does not care. A consumer that applies state changes in order, such as an
  account balance, has to park every later event for that key too, or handle stale events on replay.
- **A dead-letter queue needs an owner.** Alert on the first parked event and on a growing count, store the error and
  the source offset with each event, and keep a tested replay tool. A queue nobody reads is silent data loss.
- **Retry topics keep the partition moving.** Many teams send a failed event to a retry topic with a delay, such as 10
  s, then 5 minutes, before the dead-letter queue. The main partition never waits, and order breaks the same way.

Parking is two writes: the click goes to the dead-letter queue, and the offset commit goes to the log. A crash can land
between them, the same gap the outbox in the [delivery semantics lesson](../delivery-semantics/) closes. Order the
writes so a crash can only repeat work:

- **Confirm the park, then commit.** Wait until the dead-letter queue acknowledges a durable write, then commit the
  source offset. Commit first, and a crash between the two writes loses the click from both places.
- **Expect a duplicate park.** A crash after the dead-letter write and before the commit makes the restarted consumer
  fail the same click and park it a second time. Each copy carries the click id, so the replay tool and an idempotent
  consumer treat the two copies as one click. Where the dead-letter topic lives in the same broker and the broker
  supports transactions, as Kafka does, the consumer can write the park and commit the offset in one transaction, and
  the duplicate disappears.
- **When the dead-letter queue is down, stop.** If the park write fails or times out, the consumer leaves the offset
  where it is and retries the park with backoff. The partition stalls like the retry lane, so alert on it. A consumer
  that commits the offset without a confirmed park loses the click.
- **Retention bounds every replay.** The source log, the dead-letter queue, and the consumer's record of seen click ids
  each delete old data on their own schedule. A replay that arrives after its click id left the seen record can count
  a click twice. Pick one recovery horizon and keep all three at least that long, as
  [delivery semantics](../delivery-semantics/) explains.

Replay sends events through the consumer a second time, and some of them may have half finished the first time. That
is the same duplicate problem the [delivery semantics lesson](../delivery-semantics/) solved: make the consumer
idempotent, keyed by click id, and replay is safe. Idempotency covers the technique in depth.

## Thin events and fat events

The dead-letter queue keeps bad events from stopping the pipeline. The next decisions are about the events themselves,
starting with how much each one carries.

A **thin event** says that something happened and carries ids. A consumer that needs details calls the producer back.

```json
{ "type": "click.recorded", "clickId": "c_81f2", "code": "abc123" }
```

A **fat event** carries the state a consumer needs, so the consumer never calls back. Teams also call this event
carried state transfer.

```json
{
  "type": "click.recorded",
  "clickId": "c_81f2",
  "code": "abc123",
  "clickedAt": "2025-03-01T10:15:00Z",
  "referrer": "news.example.com",
  "country": "KE",
  "ownerPlan": "pro"
}
```

With thin events, analytics, fraud scoring, and billing each call the click service for every click. The click
service now serves three times the reads, and when it goes down, every consumer stalls with it. A replay an hour later
fetches the link as it is now, so it can count a click under a plan the owner bought after the click happened.

With fat events, each consumer works alone, and a replay sees the click exactly as it was. The costs move elsewhere:
bigger messages, more fields that some consumer starts to depend on, and personal data such as IP addresses copied
into every topic and every consumer. Most designs land in between: carry the fields consumers decide on, plus ids
for anything large or private.

## Choreography and orchestration

Three services react to a click: analytics counts it, fraud scoring checks it, and billing charges the link owner for
it. Billing must charge only for clicks that fraud scoring marks clean. There are two ways to coordinate them.

In **choreography**, each service reacts to events and publishes its own. No service knows the whole flow.

Choreography keeps services loose: a new consumer needs no change upstream, and no central service can go down for
everyone. The price is a flow you reconstruct from subscriptions, and chains of events that turn into cycles as the
system grows. Orchestration puts order, retries, and compensation in one readable place, at the price of a central
service that every new step has to change. A common split: choreography between teams for facts like click.recorded,
and an orchestrator inside one team for a flow with strict steps, such as billing.

## Evolve the schema without breaking readers

Producers and consumers deploy on their own schedules, and the topic holds events written by old code for days. Every
field in an event is a promise to whoever reads it. Here is version 1 of the click event:

```json
{ "code": "abc123", "clickedAt": "2025-03-01T10:15:00Z", "referrer": "news.example.com" }
```

Two consumers read it. The **strict reader** checks every event against the whole v1 contract and rejects any field it
does not know. The **tolerant reader** checks only the two fields it uses, code and clickedAt, and ignores the rest.
Both park an event they reject in a dead-letter queue, since no retry fixes a schema error.

What to look for:

- **Add an optional field.** The strict reader counts **106** clicks, all from before 3 s, then parks the next
  **205** with "unknown field country". The tolerant reader counts all **311**.
- **Rename a field in place.** Both readers park **205** clicks with "missing field code". Tolerance cannot save a
  reader whose field disappeared. A rename is a removal plus an addition.
- **Publish the rename as v2.** v1 stays exactly as it was, and the click service also publishes v2, with shortCode, to
  a new topic. Both readers count all **311**, and the v2 topic holds **205** events for consumers that upgrade. The
  producer pays for it: **516** events published, and two versions to run until the last v1 reader moves.

The rules that follow from it:

- **Add, never rename or remove.** New fields are optional or have a default. A field a consumer reads keeps its name
  and its type: in the same toy model, sending clickedAt as a number breaks both readers.
- **Read tolerantly.** Read only the fields you use and ignore the rest. Removing referrer breaks only the strict
  reader, because the tolerant one never read it.
- **Version breaking changes.** Publish v2 to a new topic, or with a version field, next to v1. Move each reader, then
  retire v1. The outbox relay from the [delivery semantics lesson](../delivery-semantics/) can publish both versions
  from one outbox row.
- **Check before you ship.** A schema registry with compatibility checks in the build rejects a breaking change before
  it reaches the topic. APIs and contracts covers the same versioning rules for request and response APIs.

## Trade-offs

<TradeoffTable title="Event-driven design choices">

| Choice | What it buys | What it costs |
| --- | --- | --- |
| Retry forever | No event skipped, order kept | One poison message stalls the partition, and lag grows without limit |
| Dead-letter queue after a few tries | The partition keeps moving, and bad events wait for a fix | Per-key order breaks, a park must be durable before the offset commit, and it needs an owner, an alert, a replay tool, and an idempotent consumer |
| Thin events | Small messages, fresh data, private data stays home | Every consumer calls the producer back, and replay sees today's data |
| Fat events | Consumers work alone, and replay sees the event as it was | Bigger messages, more fields to keep forever, personal data in every topic |
| Choreography | Loose coupling, and new consumers need no upstream change | The flow lives nowhere, and event chains get hard to trace |
| Orchestration | Order, retries, and compensation in one place | A central service that every new step has to change |
| Additive changes with tolerant readers | Producers ship without waiting for every consumer | No renames, removals, or type changes in place |
| Versioned events | Breaking changes without broken readers | Two versions to publish and run until the migration ends |

</TradeoffTable>

<Challenge>

The click pipeline gains a geo enrichment consumer that calls a third-party IP lookup service. That service goes down
for about 10 minutes once a week. Marketing also wants a utm_campaign field on every click, and three consumers already
read the click topic, one of them a strict reader. Design how the enrichment consumer handles failures and how the
click service ships the new field.

<div slot="answer">

- **Sort the errors.** Lookup timeouts and 5xx responses are transient: retry twice with backoff, then send the click
  to a retry topic with longer delays, such as 1 minute and then 10 minutes, so the main partition never waits out an
  outage. A click that fails to parse goes straight to the dead-letter queue.
- **Or degrade.** If counts matter more than geo data, write the click without a country during the outage and
  backfill it later from a separate topic. Analytics keeps its pace either way.
- **Own the dead-letter queue.** Store the error, try count, partition, and offset with each parked click. Alert on
  the first one and on growth, name an owning team, and keep a replay tool. Commit the source offset only after the
  park is durable, and key the enrichment writes by click id so a duplicate park or a replay changes nothing twice.
  Keep the click topic, the dead-letter queue, and the seen click ids for the same recovery horizon.
- **Ship utm_campaign additively.** Make it optional with an empty default. Fix the strict reader first, or have it
  ignore unknown fields, and add a registry compatibility check to the build so the next breaking change fails there.
- **Keep the event lean.** The enrichment consumer needs the IP, which is personal data. Keep the IP in a topic only
  that consumer reads, and put only the derived country in the shared click event.

</div>

</Challenge>
