## The failure: a deploy pages on-call

The link owners' dashboard shows clicks per 2 s window from the clicks topic in the [log lesson](../logs-and-pubsub/).
A stream job pages on-call when a window holds more than 60 clicks, 1.5 times the normal 40. It
picks each click's window from its own clock:

```ts
for await (const click of clicksTopic) {
  const window = Math.floor(Date.now() / 2000); // when the job reads it
  const count = await counts.increment(window);
  if (count > SPIKE_ALERT) await pageOnCall(window, count);
}
```

That is **processing time**, and it works while the job keeps up. Then a deploy stops the job from 5 s to 9 s. The
topic keeps every click, so nothing is lost.

## The idea: count by when the click happened

Every click has two times. The **event time** is when the redirect server handled it. The **processing time** is when
the job reads it. Restarts, slow networks, and buffering edge regions move the processing time and leave the
event time alone. So stamp the event time into the click, and window by it:

```ts
const window = Math.floor(click.clickedAt / 2000); // when the click happened
```

That raises a question: when is a window done, if a late click can still arrive?

## Window shapes: tumbling, sliding, and session

The windows so far are **tumbling windows**: fixed length and back to back, so each click lands in exactly one.
**Sliding windows** overlap, a new one starting every slide interval, so they catch a burst that straddles a tumbling
boundary and count each click several times. A **session window** groups one visitor's clicks until a quiet gap closes
it.

<details>
<summary>Go deeper: tumbling and sliding windows side by side</summary>

Kafka Streams calls sliding windows hopping windows. A burst no longer than the window minus the slide (8 s for a 10 s
window that slides every 2 s) lands whole in some window. A longer spread can still fall between windows, and a shorter
slide narrows that gap at the cost of more windows.

Session windows answer "how many links does a visitor open in one sitting". A gap with no clicks, such as 30 minutes,
ends a session, so the job only knows a session is over once the gap passes, and a late click can merge two sessions.

The widget counts one set of clicks two ways: 10 s tumbling windows, and 10 s sliding windows that start every 2 s. A
burst of 24 extra clicks lands over 2 s on top of about 2 clicks a second. This is a toy model, and the numbers are
illustrative.

What to look for:

- **Burst across a boundary.** The burst runs from 19 to 21 s, so the tumbling windows count **17**, **32**, and

- **The cost.** Tumbling windows emit **6** results a minute. Sliding windows emit **30**, and each click lands in
  **5** of them, so the job does five times the counting and keeps five times the state per short code.

</details>

## Watermarks and late data

Event-time windows need a rule for when to publish. The job keeps a **watermark**: the newest event time seen, minus a
fixed wait. When the watermark passes a window's end, the job publishes that count. A click for a published window is
**late**, and a late policy decides its fate:

- **Drop it.** The click is gone for good.
- **Allow lateness and update.** The job keeps each window for a while after publishing. A late click within that
  allowed lateness revises the published result, so every sink downstream must accept an update or a retraction.
- **Side table.** The job saves the click, and a batch job adds it back later.

neither loses a window nor counts a click twice.

<details>
<summary>Go deeper: partition watermarks and revision-safe sinks</summary>

**Lateness costs memory.** With updates, the job keeps each window until the watermark passes its end plus 10 s. At the
end of the run the 0.5 s lane holds **6** windows with updates, against **1** when it drops late clicks.

**One watermark per partition.** A real job tracks a watermark for each partition it reads and uses the smallest. One
idle partition holds every window open, so engines add an idle timeout that ignores a quiet partition.

**Updates must replace, and only forward.** Downstream stores each window's count keyed by short code and window, and
an update overwrites it. Overwriting alone is not retry safe: a delayed retry of an old result can land after a newer
one and roll the count back. So the job gives each window result a **revision** that goes up with every update, and the
store replaces a row only when the incoming revision is higher:

```sql
INSERT INTO window_counts (short_code, window_start, clicks, revision)
VALUES ($1, $2, $3, $4)
ON CONFLICT (short_code, window_start) DO UPDATE
SET clicks = EXCLUDED.clicks, revision = EXCLUDED.revision
WHERE window_counts.revision < EXCLUDED.revision;
```

Revision 7 writes 10 clicks, and revision 8 writes 12. Then a retry of revision 7 arrives late with 10. The revision
check fails, the row keeps 12, and the dashboard never moves back. [Idempotency](../../reliability/idempotency/)
covers retry safety in depth.

</details>

## When batch beats stream

A stream job answers in seconds with counts that are almost right. A **batch job** reads a bounded slice of the log
after the stragglers arrive and computes exact answers. Batch wins when:

- **The answer must be exact**, as for invoices on paid links.
- **The logic changes**, and a new bot filter must rerun over last month.
- **Nobody needs it in seconds**, as for a weekly report.

Here the stream feeds the dashboard and alert, and a nightly batch writes the exact counts billing reads.

<details>
<summary>Go deeper: big joins, Lambda, and Kappa</summary>

**Big joins favor batch.** Matching every click against the full table of link owners and plans is cheaper as one bulk
join than as millions of lookups from a running job.

**Lambda and Kappa.** The **Lambda architecture** runs a stream layer for fast, approximate counts and a batch layer
that recomputes exact counts, and serves both. Its cost is the same logic written and tested twice. The **Kappa
architecture** keeps one stream job and reprocesses history by replaying the log through a new version of it, which
needs a log that keeps months of clicks.

</details>

## Trade-offs

<TradeoffTable title="Stream processing choices">

| Choice | What it buys | What it costs |
| --- | --- | --- |
| Processing-time windows | Simple, immediate results | Restarts misplace clicks and fire false alerts |
| Event-time windows | Clicks land where they happened | The job must decide when a window is done |
| Sliding windows | Catch a burst wherever it lands | Each click counted in several windows |
| Long watermark wait | Fewer late clicks | Slower results, more windows in memory |
| Allowed lateness with updates | Counts catch up with the truth | Counts change downstream, and windows stay longer |
| Batch recount | Exact answers and easy reruns | Answers arrive hours later |

</TradeoffTable>

Skip the stream job when nobody acts on the answer within minutes: a nightly batch over the log is simpler and exact.

## Common mistakes

- **Windowing by the job's clock.** Restarts and backlogs misplace clicks. Window by event time.
- **Treating the watermark as a guarantee.** An outage longer than the wait still sends late clicks, so pick a late
  policy.
- **Writing revisions as increments.** A revision replaces the count, and only when its revision number is higher.
- **Holding windows open for day-late clicks.** Send the long tail to a side table or the batch job.

<KeyTakeaways>

- Window by event time stamped at the source. Processing time misplaces clicks when the job restarts or lags.
- Tumbling windows count each click once. Sliding windows catch bursts that straddle a boundary, for more work.
- A watermark trades speed for completeness. A late click within the allowed lateness revises a published result, so
  sinks must accept revisions.
- A batch job over the log gives exact answers. Pair it with the stream for speed.

</KeyTakeaways>
