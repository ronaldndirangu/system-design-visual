## The failure: a deploy pages on-call

The link owners' dashboard shows clicks per 2 s window, read from the clicks topic from the
[log lesson](../logs-and-pubsub/). A stream job keeps the counts, and it pages on-call when a window holds more than
60 clicks, 1.5 times the normal 40. The first version picks each click's window the obvious way: from the clock on the
server that runs the job.

```ts
for await (const click of clicksTopic) {
  const window = Math.floor(Date.now() / 2000); // the moment the job reads the click
  const count = await counts.increment(window);
  if (count > SPIKE_ALERT) await pageOnCall(window, count);
}
```

That time is the **processing time**. It works while the job keeps up. Then a deploy stops the job at 5 s, and it
starts again at 9 s. The topic keeps every click during the stop, so nothing is lost.

## The idea: count by when the click happened

Every click has two times. The **event time** is when the redirect server handled the click. The **processing time**
is when the stream job reads it. A restart, a slow network, or an edge region that buffers clicks moves the processing
time and leaves the event time alone. So stamp the event time into the click, and pick the window from it.

```ts
const window = Math.floor(click.clickedAt / 2000); // the moment the redirect server handled the click
```

That fixes where a click goes. It raises a new question: when is a window done, so the job can publish its count? A
late click can still belong to a window that ended seconds ago.

<Analogy>

An election office counts each mail-in ballot by its postmark. A ballot postmarked on election day counts even when it

The office also has to finish counting, so it sets a deadline for arrivals and certifies the result after it. That
deadline plays the role of a watermark, and a ballot that arrives after it is late data.

## Window shapes: tumbling, sliding, and session

The windows so far are **tumbling windows**: fixed length, back to back, no overlap. Each click lands in exactly one,
and the job emits one result per window. They answer "how many clicks per minute" well.

A **sliding window** has a fixed length too, and a new one starts every slide interval, so windows overlap. Kafka
Streams calls these hopping windows. They catch a burst that tumbling windows split across a boundary. A burst no
longer than the window minus the slide (8 s for a 10 s window that slides every 2 s) lands whole in some window. A
longer spread can still fall between windows, and a shorter slide narrows that gap at the cost of more windows.

A **session window** has no fixed length. It groups one visitor's clicks until a gap with no clicks, such as 30
minutes, closes it. Sessions answer "how many links does a visitor open in one sitting". Since the gap ends a session,
the job only knows a session is over once the gap passes, and a late click can merge two sessions into one.

The widget counts one set of clicks two ways: 10 s tumbling windows, and 10 s sliding windows that start every 2 s. A
burst of 24 extra clicks lands over 2 s on top of about 2 clicks a second. This is a toy model, and the numbers are
illustrative.

What to look for:

- **Burst across a boundary.** The burst runs from 19 to 21 s, so the tumbling windows count **17**, **32**, and
  **29**, and no alert fires. The sliding window from 12 to 22 s holds **44**, and **3** of the 11 sliding windows
  cross 40. A window that holds exactly 40 does not page.
- **Burst inside a window.** Move the burst to 13 to 15 s and the tumbling windows count **17**, **43**, and **18**. The
  alert fires either way with sliding windows.
- **The cost.** Tumbling windows emit **6** results a minute. Sliding windows emit **30**, and each click lands in
  **5** of them, so the job does five times the counting and keeps five times the state per short code.

## Watermarks and late data

Event-time windows need a rule for when to publish. The job cannot wait for every click, since an edge region can
always send something older. So it keeps a **watermark**: the newest event time it has seen, minus a fixed wait. When
the watermark passes the end of a window, the job publishes that window's count. A click whose window already has a
result is **late**, and a late policy decides what happens to it:

- **Drop it.** The published count stays as it is, and the click is gone for good.
- **Allow lateness and update.** The job keeps the window in memory for a while after it publishes, and sends an
  updated count for each late click. Flink and Beam call this allowed lateness.
- **Side table.** The job writes the click to a separate table, and a batch job adds it back later.

What to look for:

- **A short wait answers fast and misses more.** The 0.5 s lane publishes 0 to 2 s at 2.6 s with **56** clicks,
  where 58 happened. The 3 s lane publishes **58** at 5.0 s. Over the run the mean wait for a first result is **0.6
  s** against **3.1 s**.
- **The policy decides what late clicks cost.** All three policies publish the same first results and see the same
  late clicks. Drop loses them. Allow 10 s of lateness sends **18** updated results for the short wait's 36 late
  clicks, and **4** for the long wait's 12, so every reader downstream must accept a count that changes. Side table
  keeps the 36 or the 12 for the nightly batch job.
- **Lateness costs memory.** With updates, the job keeps each window until the watermark passes the window's end plus
  10 s of allowed lateness, so a stalled watermark holds windows longer. At the end of the
  run the 0.5 s lane holds **6** windows in memory with updates, against **1** when it drops late clicks.

Three things the widget leaves out matter in production:

- **One watermark per partition.** A real job tracks a watermark for each partition it reads and uses the smallest. One
  idle partition holds every window open, so engines add an idle timeout that ignores a quiet partition.
- **Updates must replace, never add.** Downstream stores each window's count keyed by short code and window, and an
  update overwrites it. A retried update then changes nothing. Idempotency covers the technique in depth.
- **Window state survives restarts.** The job checkpoints its open windows together with the offsets it has read, as
  in the [delivery semantics lesson](../delivery-semantics/), so a restart neither loses a window nor counts a click
  twice.

## When batch beats stream

A stream job answers in seconds with counts that are almost right. A **batch job** reads a bounded set of clicks, such
as yesterday's slice of the log, after the stragglers have arrived, and computes an exact answer. Batch wins when:

- **The answer must be exact.** Invoices for link owners on a paid plan count every click, including the ones a phone
  sends a day late. A nightly job can wait for them.
- **The logic changes.** A new bot filter has to apply to last month's clicks. A batch job reruns over stored history.
- **The join is big.** Matching every click against the full table of link owners and plans is cheaper as one bulk
  join than as millions of lookups from a running job.
- **Nobody needs it in seconds.** A weekly report does not justify a job that runs and holds state all day.

Many pipelines run both. The **Lambda architecture** runs a stream layer for fast, approximate counts and a batch
layer that recomputes exact counts, and serves both. Its cost is the same logic written and tested twice. The **Kappa
architecture** keeps one stream job and reprocesses history by replaying the log through a new version of it, which
needs a log that keeps months of clicks. In the click pipeline, the stream job feeds the live dashboard and the spike
alert, the side table catches late clicks, and the nightly batch job writes the exact counts that billing reads.

## Trade-offs

<TradeoffTable title="Stream processing choices">

| Choice | What it buys | What it costs |
| --- | --- | --- |
| Processing-time windows | Simple, and results right away | A restart or an outage moves clicks into the wrong window and fires false alerts |
| Event-time windows | Each click lands in the window it happened in, whatever the delay | The job has to decide when a window is done, and hold windows until then |
| Tumbling windows | One result per window, and each click counted once | A burst that straddles a boundary splits in two |
| Sliding windows | Catch a short burst wherever it lands | Each click counted in several windows: five times the work and state here |
| Session windows | Group activity the way visitors behave | No fixed length, and a session ends only after a gap passes |
| Short watermark wait | Fast results and alerts | More late clicks to drop, update, or set aside |
| Long watermark wait | Fewer late clicks and more complete first results | Slower dashboards and alerts, and more windows in memory |
| Allowed lateness with updates | Published counts catch up with the truth | Downstream sees numbers change, and windows stay in memory longer |
| Batch recount | Exact answers, and easy reruns over history | Answers arrive hours later |

</TradeoffTable>

<Challenge>

Link owners want a dashboard of clicks per minute for each short code, and owners on a paid plan get a monthly invoice
per click. The mobile app buffers clicks while a phone is offline and sends them up to 24 hours later. On-call wants a
page within 30 seconds when a code gets more than 10 times its usual traffic. Design the windows, the watermark, the

<div slot="answer">

- **Count by event time.** The redirect server stamps clickedAt. The app stamps its own clicks, and the server also
  records when it received them, since phone clocks drift: treat a clickedAt far ahead of the receive time as wrong.
- **Alert on sliding windows.** Use a 10 s window that slides every 2 s, and compare it with 10 times the code's usual
  10 s count. An 11 times jump crosses that threshold once it fills 9 s of a window. Add up to 2 s for the next window
  to end and a 3 s watermark wait, and the page lands within about 15 s. A 1 minute window would need 54 s, and
  bigger spikes fire sooner. Require a minimum count too, since short windows are noisy for codes with little traffic.
- **Keep the live path short.** A wait of a few seconds covers retried sends. Allow a minute or two of lateness with
  updates for the dashboard, and store each count keyed by code and window so an update replaces the old one.
- **Send the long tail to batch.** Clicks from offline phones arrive hours late, past any wait the dashboard can
  afford. Write them to a side table, or rely on the raw log, and never hold dashboard windows open for them.
- **Invoice from batch.** A nightly job recounts each day by event time from the log once the 24 hour buffer limit has
  passed, and writes exact counts keyed by code and day, so a rerun overwrites instead of adding. Close each month's
  invoices a day after the month ends.

</div>
